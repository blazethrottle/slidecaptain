# 핸드오프: 회사 PC(Windows)에서 재개, D3 관문의 Windows 확인 (2026-10-16)

다음 세션은 회사 PC(Windows)에서 이 문서를 읽고 시작한다. 이 세션의 목적은 이 Mac에서 판정할 수 없는 D3 관문 항목(실제 PowerPoint 표시, 한글 입력기, Windows 배율)을 확인하고 기록하는 것이다. 새 기능 개발은 이 문서의 범위가 아니다. C1 구현과 리뷰의 상세는 앞 핸드오프 [2026-10-15-c1-plan](2026-10-15-c1-plan.md)이 진본이고, 그 문서의 3절(사용자 결정 대기)은 그대로 유효하다. 상시 규칙은 [2026-10-13-d3c-beta](2026-10-13-d3c-beta.md) 5절을 따른다.

## 1. 지금 상태

- 개발선은 브랜치 `feat/d3-wrapup-c1`이다. main `ba5f7ea`에서 분기했고 C1(복구 화면의 후보 비교와 반영, 도식 후보 다시 열기)을 구현해 품질 관문 세 단계를 모두 거쳤다. 이 Mac에서 판정할 수 있는 D3 관문 항목은 모두 통과다([C1 확인 기록](../qa/2026-10-16-c1-check.md), [D3c 확인 기록](../qa/2026-10-13-d3c-check.md) 5절과 그 정정 문단).
- main 머지는 사용자 결정 대기였다. 그래서 2026-10-14 핸드오프 3절 5항의 "회사 PC 클론은 `git pull`로 main을 받는다"가 맞지 않아 아래 2절의 판별을 넣었다. (2026-10-16 정정: 같은 날 사용자 결정 A로 `--no-ff` 머지 `8beeb05`. 2절 판별은 이제 `main`을 고른다. 개발선은 main이다.)
- 이 Mac 기준선(`099190a`): 백엔드 2,871 통과, 프런트 1,276 통과, CI 두 OS(Windows, macOS) 성공. 실제 AI 호출은 개발 전체에서 0회다.
- 회사 PC가 마지막으로 받은 커밋은 이 Mac에서 알 수 없다. 2026-10-02 기준선 문서는 `feat/windows-feedback-revision`(2026-10-14 main에 머지됨)을 썼다.

## 2. 회사 PC에서 시작하는 순서

1. 저장소 폴더에서 `git status --short`로 미커밋 변경을 확인한다. reset, stash, clean을 하지 않는다. 기존 프로젝트, 인증 프로필, `feedback/`의 회사 자료는 옮기거나 덮지 않는다.
2. `git fetch origin`을 실행한다.
3. 쓸 브랜치를 판별한다: `git merge-base --is-ancestor origin/feat/d3-wrapup-c1 origin/main`이 성공(종료 코드 0)하면 사용자가 머지한 것이므로 `main`, 실패하면 `feat/d3-wrapup-c1`을 쓴다.
4. 그 브랜치로 `git switch <브랜치>` 뒤 `git pull --ff-only`를 실행한다. 미커밋 변경 때문에 전환이나 받기가 거부되면 우회하지 말고 원인 파일을 사용자에게 보고하고 멈춘다.
5. 의존성을 설치한다. 마지막으로 받은 커밋을 모르므로 조건 없이 실행한다: `backend\.venv\Scripts\python.exe -m pip install -e "backend[dev,desktop]"`, 그리고 `frontend`와 `desktop`에서 각각 `npm ci`. 가상 환경이 없으면 Python 3.13 이상으로 `backend\.venv`를 만든다. Node는 64비트 22 이상이다.
6. 3절의 기준 시험을 돌린다.
7. 4절의 확인 항목을 순서대로 진행한다.

## 4. 확인 항목

### 지켜야 할 것 (모든 항목 공통)

- **실제 자료 폴더를 열지 않는다.** `SlideCaptain실행.bat`와 `python -m slidecaptain serve`의 기본값은 사용자의 실제 자료 폴더(`%USERPROFILE%\slidecaptain-projects`)다(로드맵 이월표 (15) ST-07: 막는 장치는 이 문서 규칙뿐이다). 확인에는 `Windows검수준비.bat`가 만드는 합성 프로젝트 폴더를 쓰고, 서버를 직접 띄울 때는 반드시 `--data-dir <검수 폴더>\store --port 8870`을 붙인다. 8765는 사용자의 평소 앱 포트라 쓰지 않는다.
- 실제 AI 호출을 하지 않는다. 아래 항목은 모두 AI 없이 확인할 수 있다. AI가 필요해 보이면 멈추고 사용자에게 묻는다.
- 회사 원문, 계약, 내부 인명, 비공개 수치를 커밋하지 않는다. 피드백 JSON과 화면 캡처는 로컬에 두고, 저장소에는 합성 표본에 대한 판정과 수치만 적는다.
- 사용자가 열어 둔 PowerPoint 문서를 에이전트가 강제로 닫거나 프로세스를 일괄 종료하지 않는다.
- 사람의 판정(보기 좋은가, 읽히는가)은 사용자가 한다. 에이전트는 절차를 안내하고 관측 사실을 기록한다.

### 준비: 검수 앱 열기

`Windows검수준비.bat`를 실행한다. 이 배치는 현재 checkout으로 백엔드를 설치하고 화면을 빌드한 뒤, 새 회차 폴더(`projects\windows-review\run-<시각>`)에 합성 프로젝트 5개(templates 10장, diagram 2장, bar, column, emphasis)와 PPTX, 피드백 양식을 만들고 `http://127.0.0.1:8870`에 검수 앱을 연다. 절차의 세부는 [Windows PowerPoint 검수 안내](../qa/2026-10-02-windows-powerpoint-guide.md)를 따르되, 그 문서의 브랜치 이름(`codex/phase-5b`)은 지금 맞지 않으므로 2절의 판별을 따른다.

이 Mac에서 2026-10-16 확인한 사실: 준비 스크립트(`scripts/prepare_windows_review.py`)는 `099190a`에서 오류 없이 돌았고 PPTX 10개를 만들었다. 그 폴더로 띄운 서버는 프로젝트 5개를 목록에 보였고 덱 읽기가 200이었다. 화면에서 편집 단계로 들어가는 것은 이 Mac에서 확인하지 않았다. 표본은 2026-10-02에 만든 것이라 D3의 보고 유형 10종을 담지 않는다. 그래서 아래 A1은 표본의 PPTX를 그대로 보는 것과, 앱에서 직접 편집한 뒤 내보낸 PPTX를 보는 것 두 갈래로 한다.

### 이 PC의 확인 대상이 아닌 것

- C1 흐름(복구 화면에서 비교하고 반영, 도식 후보 다시 열기)은 이 Mac에서 가짜 CLI와 헤드리스 브라우저로 확인했다. 그 재현 도구는 저장소 밖(Mac의 작업 폴더)에 있어 회사 PC에 없으므로, 회사 PC에서 다시 재현하지 않는다.
- 실제 AI 생성 품질, `codex app-server`의 네트워크 접촉 실측은 D4 소관이고 실제 호출 전에 사용자 승인이 필요하다.
