# Q3b 낡은 보고 계획의 복구 안내 인계

작성: 2026-09-27. 최신 상태 확인 뒤 사용자가 승인한 개발 단위는 현재 자료와 맞지 않는 보고 계획의 안내와 입력 보존이다. [직전 인계](2026-09-27-q3b-answer-guidance-handoff.md)의 다음 후보를 [계획](../plans/2026-09-27-q3b-stale-plan-guidance.md)에 따라 구현했다. 전체 재계획, 자동 자료 복원, 도식 AI 생성은 포함하지 않는다.

## 바뀐 동작

기존 오류는 저장된 도식이 있어 전체 구조안 재생성이 막힌 프로젝트에도 다시 생성하라고 안내했다. 이제 `StaleStoryPlan`의 기존 HTTP 409/문자열 detail에 `code: stale_story_plan`을 더하고, 상태와 코드가 모두 맞을 때만 복구 경로를 표시한다. 다른 409와 412 저장 충돌은 기존 처리를 유지한다. Deck/StoryPlan 모델과 fingerprint 판정은 바꾸지 않았으며 현재 앱의 OpenAPI/생성 타입도 기존 파일과 바이트 단위로 일치한다.

- 저장된 도식이 있으면 전체 재생성이 아직 지원되지 않음을 밝히고 원래 자료/보고 정보/장 구성 복원 또는 별도 프로젝트 시작을 안내한다. 도식과 근거가 자동 이전된다고 하지 않는다.
- 저장된 도식이 없는 상태의 새 초안은 작성 내용을 보관한 뒤 기존 구조안 재생성 경로로 갈 수 있다. 새 구조안 승인에 따른 장 교체 가능성도 표시한다.
- 오류 뒤 도식의 제목, 항목, 관계, 역할과 주장 선택을 유지한다. 현재 입력의 연결/배치 확인에 성공해야 적용할 수 있다. 미적용 내용은 창을 닫거나 새로고침하면 사라지므로 보관 텍스트/복사를 제공한다. 복사 실패와 입력 변경 중 늦은 응답을 구분하고 자동 불러오기/근거 복구의 미지원 상태를 명시한다.
- 일반 장 생성/축약도 같은 안내를 사용한다. 순차 생성에서 낡은 계획을 확인하면 남은 장을 보류하고 이미 성공한 결과는 남긴다. 정적 도움말은 조건문으로 표시해 현재 오류 판정과 구분한다.

주요 경로는 `backend/slidecaptain/server/app.py`, `frontend/src/api/client.ts`, `screens/StoryPlanRecoveryGuidance.tsx`, `screens/StructureScreen.tsx`, `editor/DiagramAuthoringDialog.tsx`, `editor/DiagramDraftBackup.tsx`, `editor/GeneratePanel.tsx`, `styles.css`다. 이전 비차단 제안이던 여러 답변 장의 주장 분담 사례도 `DiagramAuthoringDialog.test.tsx`의 상시 회귀에 포함했다.

사용자가 허용한 리뷰 에이전트 1명이 초기 변경을 검토했고 P2 2건을 발견했다. 오류 후 글자를 입력하면 검토 영역으로 초점이 이동하던 문제와 정상 계획의 정적 도움말이 오류를 확정하던 문제다. 정식 테스트에서 2실패/19통과를 재현한 뒤 수정하여 21개 모두 통과했다. 별도 독립 하네스의 재검토도 3개 모두 통과했다.

후속 Chrome 검증에서 긴 안내와 보관 내용을 펼치면 기존 sticky 영역 아래 복사 버튼이 가려지는 P2 1건을 추가 발견했다. 오류 상태에만 `is-recovering` 클래스를 붙여 고정 배치를 해제했고, 같은 화면에서 버튼 클릭과 현재 제목/주장/관계의 클립보드 복사를 확인했다. 정상 상태의 sticky와 좁은 화면의 기존 static 규칙은 유지한다. 같은 리뷰 에이전트가 추가 변경도 재검토했다. 실제 작은 화면은 이번에 별도로 재검증하지 않았다.

리뷰 승인 시점과 파일 해시는 작업본 상위 `review/initial-review.md`, `review/final-review.md` 및 해당 manifest에 있다. 계획을 포함한 첫 독립 검토는 초기 구현 뒤에 이루어졌으므로 구현 전 계획 게이트를 충족했다고 소급하지 않는다. 이번 변경 범위의 재검토이며 기존 누적 브랜치 전체와 실제 보고서 품질을 승인한 것은 아니다.

## 브라우저 확인

제공자/계정 없는 임시 서버와 합성 프로젝트만 사용했다. 기존 도식에서는 제목 `복구 뒤에도 보존할 도식`과 조건 `입력 보존 확인`을 입력하고 낡은 계획 거절, 보관 복사, 정확한 원자료 복원 뒤 같은 초안의 확인/적용/저장을 검증했다. 새 도식에서는 저장된 도식이 없는 복구 경로, 오류 뒤 ` ABC` 연속 입력의 초점/내용 유지, 복사, 원자료 복원 뒤 확인/저장을 검증했다. 최종 저장본 2개의 계획 현재성 검사도 통과했다.

거절 시점의 덱 식별값과 스냅샷은 처음 값 그대로였고, 사용자가 적용한 뒤에만 각 저장본과 스냅샷이 바뀌었다. 계획 거절 409는 의도한 3건이고 기능과 무관한 favicon 404가 1건 있었다. AI 생성 요청과 사용량 파일은 모두 0개다. 임시 서버와 검증 탭은 종료했다.

실제 AI 인증/호출, Windows 실기기/새 CI, PowerPoint 표시와 독자 품질은 미검증이다. 클립보드 실패 분기는 자동 테스트로 확인했으며 실제 Chrome에서는 성공 분기를 확인했다.
