# Q3b 도식 장과 기존 보고 계획 연결

작성: 2026-09-20. 이전 단위는 도식 의미 입력의 작성/수정과 저장 전 배치 확인이다. 이번 단위에서는 새 도식 장이 기존 보고 계획에 들어갈 때 장부와 fingerprint를 안전하게 갱신하는 최소 경로만 구현한다.

## 목적

도식 작성 UI가 기존 `StoryPlan`을 그대로 둔 채 장을 추가하면, 저장은 가능하지만 다음 장 생성에서 구조안 fingerprint가 낡았다고 판단된다. 사용자가 기존 주장 중 어떤 주장을 도식 장에서 다룰지 명시적으로 선택하고 확인한 경우에만 `StoryPlan.chapters`를 갱신하고 fingerprint를 다시 계산한다.

## 범위

- 도식 장의 보고 역할은 기존 `ChapterRole` 중 `answer`, `context`, `evidence`, `risk`, `action`만 사용한다.
- 도식 장은 기존 `StoryPlan.claims`의 주장 ID를 하나 이상 연결한다. 새 주장이나 새 근거를 자동으로 만들지 않는다.
- 연결 정보는 도식 슬롯에 복제하지 않고 `StoryPlan.chapters`의 기존 `StoryChapter` 항목으로 저장한다. 기존 근거 장부와 비교/계산 결과는 그대로 보존한다.
- 서버의 연결 확인 API는 현재 자료를 사용해 후보 `Deck`을 검증하고 `input_fingerprint`를 다시 계산해 반환한다. 저장, 스냅샷, AI 연결과 호출은 수행하지 않는다.
- 연결 확인 API는 현재 저장본의 ETag를 선택적으로 확인하고, 후보에서 대상 도식 장을 제외한 나머지 덱이 저장본과 같은지 검사한다. 도식과 무관한 구조안·보고 정보 변경을 이 API로 함께 승인할 수 없다.
- 연결 전 현재 저장본의 `StoryPlan.input_fingerprint`도 현재 구조안·보고 정보·자료 해시와 일치해야 한다. 이미 낡은 저장 계획을 새 도식 연결로 회복시키지 않는다.
- 작성 창은 보고 계획이 있는 덱에서 역할과 주장을 선택한 뒤 연결 확인과 도식 배치를 함께 통과해야 적용할 수 있다. 계획이 없는 제안 도식은 기존 경로를 유지한다.
- 기존 도식의 연결을 다시 확인할 때는 같은 `chapter_id`의 항목을 교체해 중복 장부를 만들지 않는다.

## 계약과 불변 조건

요청은 `deck`, `chapter_id`, `role`, `claim_ids`를 가진다.

- `chapter_id`는 후보 덱의 도식 장과 도식 슬롯의 ID를 가리켜야 한다.
- `claim_ids`는 중복되지 않고 현재 계획에 존재해야 한다.
- `cover`와 `divider` 역할은 도식 장 연결에 사용할 수 없다.
- 후보 계획의 기존 주장, 근거, 비교, 계산, 미답 질문과 다른 장의 연결은 변경하지 않는다.
- 연결 전 후보 덱은 기존 fingerprint를 자동으로 고치지 않는다. 명시적 연결 확인이 성공한 경우에만 새 계획과 현재 구조안, 보고 정보와 자료 해시를 사용해 fingerprint를 계산한다.
- 연결 확인은 현재 저장된 덱을 덮어쓰지 않는다. 최종 저장은 기존 PUT, ETag, 스냅샷, undo/redo 경로를 거친다.
- 기존 근거의 source revision과 excerpt가 현재 자료와 일치하지 않으면 fingerprint를 새로 계산하지 않고 낡은 계획으로 거절한다.
- 역할과 주장을 선택하고 fingerprint를 갱신한 사실은 원문 의미의 진실성, 주장과 도식의 의미 일치, 시각 품질 또는 제출 승인으로 해석하지 않는다.

## 적대 검토에서 먼저 막을 경우

1. 새 도식이 계획에 연결되지 않은 채 저장되어 생성 시 낡은 계획으로 남는 경우에는 연결 확인을 통과하지 못하게 한다.
2. 같은 도식 장을 여러 번 확인해 `StoryPlan.chapters`에 중복 항목이 생기는 경우에는 기존 항목을 교체한다.
3. 존재하지 않는 주장 ID나 구조 장 ID를 보내 계획을 오염시키는 경우에는 후보를 반환하지 않는다.
4. 연결 확인 API가 저장이나 AI lease를 시작하는 경우에는 저장과 외부 호출을 사용하지 않는 테스트로 고정한다.
5. 현재 자료가 바뀐 뒤 예전 fingerprint를 재사용하는 경우에는 서버가 현재 자료 해시로 다시 계산한다.
6. 사용자가 도식 입력을 바꾼 뒤 이전 확인 결과를 적용하는 경우에는 기존 작성 창의 요청 순번과 원본 덱 동일성 무효화를 유지한다.
7. 역할 선택이 의미 검수 통과로 오해되지 않도록 화면에 근거와 품질 검수의 별도 상태를 표시한다.
8. 저장본의 기존 계획이 이미 낡은 경우 새 도식 연결로 fingerprint를 덮어쓰지 않고 재계획을 요구한다.

## 구현과 검증 순서

1. 백엔드 순수 연결 함수와 실패 테스트를 먼저 추가한다.
2. 프로젝트별 확인 API와 저장하지 않는 왕복 테스트를 추가한다.
3. 프런트 도식 초안에 역할/주장 선택을 추가하고, 연결 확인 후 배치 확인 결과만 적용한다.
4. 프런트의 늦은 응답, 입력 변경, 원본 변경, 계획 없는 제안 도식 회귀를 추가한다.
5. OpenAPI와 생성 TypeScript를 재생성하고 백엔드/프런트 전체 테스트와 빌드를 실행한다.

## 제외 범위

도식 AI 생성, 전체 StoryPlan 재계획, 새 주장/근거 생성, 검수 승인 저장과 만료, 자유 토폴로지와 분기 배치, 실제 AI 호출, 목표 PowerPoint 표시와 독자 품질 평가는 포함하지 않는다.

## 완료 조건

- 기존 계획의 주장/근거 장부와 다른 장을 보존하면서 도식 장 연결과 fingerprint 갱신이 왕복된다.
- 잘못된 ID, 역할, 중복 연결, 자료 변경과 저장 충돌의 실패 경계가 테스트로 고정된다.
- 연결 확인이 저장, 스냅샷, AI provider와 lease를 호출하지 않음이 검사된다.
- 도식 없는 기존 흐름과 계획 없는 제안 도식의 동작이 유지된다.
- 구현 결과, 테스트 수, 실제 화면 검증 범위와 독립 리뷰 및 실제 품질의 미검증 범위를 다음 인계에 분리해 기록한다.
