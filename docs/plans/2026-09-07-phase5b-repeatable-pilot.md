# 단계 5B: 반복 가능한 로컬 파일럿 계획서 (2026-09-07)

> 로드맵 [2026-08-27-mvp-roadmap.md](2026-08-27-mvp-roadmap.md) 단계 5B, 설계서 [2026-08-27-mvp-design.md](../specs/2026-08-27-mvp-design.md) 9.2절의 상세 계획이다. 단계 5A 완료(2026-09-06, `main` d878902)와 최종 QA([2026-09-06-final-qa-report.md](../qa/2026-09-06-final-qa-report.md)) 뒤에 착수한다.
> **5B는 5A와 성격이 다르다.** 5A는 코드를 만드는 단계였고 5B는 **재는 단계**다. 파일럿에서 나온 불편은 원칙적으로 기록만 하고 고치지 않는다. 고치기 시작하면 세 건이 서로 다른 빌드 위에서 돌아 비교가 무의미해진다.
> **사용자 결정 3건 (2026-09-07)**: ① 판정 기준 6개 축을 파일럿 시작 전에 확정한다(설계서 9.2절, `ecd0d5e`) ② 감사기 후속 회차를 파일럿보다 **먼저** 처리한다 ③ git 이력 92개 커밋에 남은 Windows 계정명은 **그대로 둔다**(현재 트리는 익명화 완료. 이력 재작성은 문서와 위키의 SHA 참조를 전부 깨뜨리고 force push가 필요한 데 비해, 남은 것은 회사명이 아닌 계정명 7자다).

## 5B가 답하는 질문과 답하지 않는 질문

**답하는 질문**: 이 앱으로 실제 업무 보고서를 **반복해서** 끝까지 만들 수 있는가. 만들면 기존 방식보다 나은가. 다음에도 쓰고 싶은가.

**답하지 않는 질문**: 외부 고객이 돈을 낼 것인가(단계 6과 상업화 관문의 몫). 다른 사람의 업무에서도 되는가(단계 6). Windows 실기기에서 같은가(5A에서 CI 갈음으로 결정, 미해결로 남음).

## 확정된 판정 기준 (설계서 9.2절, 2026-09-07 확정)

| 축 | 기준 |
|---|---|
| 파일럿 건수 | 실제 보고서 3건 |
| 데이터 유실 | 0건. 유실은 화면이 "저장됨"이라고 표시했는데 실제로 남지 않은 경우, 또는 정상 조작(되돌리기, 새로고침, 브라우저와 앱 재시작)으로 복구되지 않는 손실이다. 자동저장 주기 한계로 인한 손실은 별도 기록하고 건수에서 제외한다 |
| 작업 완주 | 3건 전부 자료 입력부터 PPTX 내보내기까지 완주 |

| 재사용 의사 | 3건 중 2건 이상에서 "다음 보고서도 이 도구로 만들겠다" |

## 태스크 5B-0: 감사기 후속 회차 (선행, 코드 작업)

5B부터 실제 업무 자료를 반복해서 입력하고 커밋하므로 노출 위험이 가장 커지는 시점이다. 이월 항목 4건을 처리한다.

| 항목 | 내용 | 근거 |
|---|---|---|
| 0-1. 변형 비밀 파일명 | `_is_secret_filename`이 `stem in {credential(s), secret(s)}` 정확 일치만 잡아 `google-credentials.json`, `secret_key.py`, `.secrets`를 놓친다. 부분 일치 규칙으로 넓히되 정상 소스(`secretary.py` 같은 오탐)를 만들지 않는 경계를 테스트로 고정한다 | 이월표 184행, D1 재작업 리뷰 발견 3 |
| 0-2. 본문 식별 문자열 규칙 | 마크다운과 텍스트 본문의 회사 식별 문자열(`C:\Users\<계정명>` 형태의 Windows 경로 등)을 검사한다. **이 구멍이 이번 계정명 유출을 8일간 못 잡았다.** 검사 대상은 경로 패턴이며, 사람 이름 일반을 추측으로 잡지 않는다 | 이월표 185행, QA 2부 구조적 사각 2 |
| 0-3. CI 이력 검사 | CI의 감사 단계가 `--history` 없이 현재 트리만 본다. 이력 검사를 CI에 넣되, 과거 커밋 92개에 남은 계정명은 사용자 결정 ③에 따라 **예외 목록으로 명시**해 통과시킨다(새 유입만 막는다) | 이월표, QA 2부. 예외 없이 켜면 CI가 영구히 실패한다 |
| 0-4. 테스트 공백 2건 | 추적 중이지만 작업트리에서 삭제된 파일의 경로 규칙, 미추적 도구 폴더가 있을 때 오탐 없음 | 이월표 184행 |

**검증**: 백엔드 테스트 전체 통과(현재 603건), 감사기 테스트 추가(현재 58건), `python scripts/audit_public_repo.py`와 `--history` 양쪽 0건, CI 양 OS 성공.

**이 태스크에 넣지 않는 것**: git 이력 재작성(사용자 결정 ③), 비밀 탐지 정규식의 전면 재설계, 회사 이름 사전.

## 태스크 5B-1: 관찰지 준비

`docs/pilot/2026-09-07-5b-관찰지.md` 한 파일에 3건을 나란히 기록한다. 2026-08-31 관찰지를 바탕으로 하되 세 가지를 바꾼다.

1. **판정 기준을 관찰지 안에 박는다.** 사용자가 기록하면서 통과와 미달을 바로 표시할 수 있어야 한다. 나중에 기준을 다시 찾아보게 만들면 판정이 미뤄진다
2. **데이터 유실 칸을 두 줄로 나눈다.** 확정한 정의대로 "유실"과 "자동저장 주기 한계"를 따로 적는다. 한 칸이면 섞인다
3. **3건 비교표를 맨 위에 둔다.** 세 건의 결과가 한 화면에 보여야 판정할 수 있다

회사 기밀 보호 규칙은 그대로 유지한다. 자료 내용과 회사 정보는 적지 않고 앱 사용 경험만 적는다. 0-2가 이 규칙을 기계적으로 뒷받침한다.

## 태스크 5B-2: 파일럿 3건 실행 (사용자 본인)

**세션이 대신할 수 없다.** 실제 회사 업무 자료가 필요하고, 문체와 정확성과 재사용 의사는 업무 맥락을 아는 사람만 판단할 수 있다. AI 호출도 사용자가 앱을 조작해 발생시키며 세션이 대신 호출하지 않는다.

서로 다른 유형의 보고서 3건을 권장한다(예: 텍스트 자료 중심 1건, XLSX 자료 포함 1건, 분량이 큰 1건). 유형이 겹치면 세 번 돌려도 같은 사실만 세 번 확인한다.

각 건마다 자료 입력부터 PPTX 내보내기와 실제 열어보기까지 완주하고 관찰지를 채운다.

## 태스크 5B-3: 중간 처분 판단

**파일럿 도중의 수정은 원칙적으로 하지 않는다.** 예외는 하나다.

| 상황 | 처분 |
|---|---|
| **완주를 막는 결함(blocker)**: 그 건을 끝낼 수 없다 | 즉시 멈추고 고친다. 고친 뒤 **3건을 처음부터 다시 센다**(같은 빌드 위의 3건이어야 판정이 유효하다) |
| 완주는 되지만 불편하거나 어색하다 | 기록만 하고 3건을 끝까지 돈다. 5B-4에서 우선순위를 매긴다 |
| 데이터 유실이 1건이라도 발생 | 판정 기준상 이미 미달이다. 원인을 규명하고 고친 뒤 3건을 다시 센다 |

## 태스크 5B-4: 판정과 기록

세션이 관찰지를 집계해 6개 축의 통과와 미달을 표로 만들고, **판정은 사용자가 한다**(자기평가 금지 원칙). 산출은 다음과 같다.

1. 판정표(축별 통과와 미달, 근거는 관찰지 인용)
2. 파일럿에서 나온 불편의 우선순위 목록. **파일럿이 실제로 걸린 것이 위로 온다.** 이월표의 5B 항목 약 20건은 지금 순서가 아니라 파일럿 결과로 다시 매긴다
3. 로드맵 진행 상태와 이월표 갱신, 이 계획서에 결과 절 추가
4. 단계 6으로 갈지, 5B를 다시 돌지, 그 사이에 수정 묶음을 넣을지 결정 제안

## 5B에서 하지 않는 것

차트 템플릿, 벤치마크 기반 템플릿 재설계, 설정 페이지, 프리셋 환류 UI, 폰트 선택, PDF와 Word 입력, 누적 사용량 화면, 회사 PC 전체 리뷰 발견의 이월표 이관(회사 PC 세션 몫), Windows 실기기 검증, git 이력 재작성, 상업화 기능 일체.

## 실행 순서

1. 5B-0 감사기 후속 회차 → 계획서 적대 리뷰는 생략한다(범위가 이월표 4항목으로 이미 특정돼 있고 설계 선택지가 없다). 태스크별 TDD 구현과 독립 리뷰는 유지한다 → 검증 → push → CI
2. 5B-1 관찰지 준비 → 커밋
3. 5B-2 파일럿 3건(사용자) → 각 건 종료 시 관찰지 기록
4. 5B-3은 필요할 때만 발동
5. 5B-4 집계와 판정 → 문서 갱신 → 커밋과 push

## 완료 관문

- 감사기가 변형 비밀 파일명과 본문 식별 문자열을 잡고, CI가 이력까지 검사하며 양 OS 성공
- 실제 보고서 3건이 같은 빌드 위에서 완주
- 6개 축 판정표가 관찰지 근거와 함께 기록됨
- 사용자가 판정을 내리고 다음 단계 방향이 정해짐

## 이 계획이 틀렸을 가능성

1. **3건이 부족할 수 있다.** 세 건이 우연히 비슷한 유형이면 일반화가 안 된다. 서로 다른 유형을 권장하는 것으로 완화하지만, 판정 시 "세 건이 서로 달랐는가" 를 함께 적어야 한다
2. **"고치지 않고 끝까지 돈다" 가 사용자에게 고통스러울 수 있다.** 실제 업무 보고서를 만드는 중이므로 불편을 참는 비용이 실제 업무에 전가된다. blocker 정의를 넉넉히 잡아 완주가 어려우면 멈추는 쪽이 안전하다
3. **감사기 0-2가 오탐을 낼 수 있다.** 경로 패턴 검사가 정상 문서(README의 예시 경로)를 잡으면 커밋이 막힌다. 테스트로 경계를 고정하고, 막히면 규칙을 좁힌다
4. **0-3의 예외 목록이 새 유출을 덮을 수 있다.** 예외를 커밋 SHA 범위가 아니라 문자열로 걸면 앞으로 같은 계정명이 다시 들어와도 통과한다. 예외는 **과거 커밋 범위로 한정**한다
5. **판정 기준이 너무 엄격할 수 있다.** 특히 "PowerPoint 표시 결함 0건" 은 초기 제품에 가혹할 수 있다. 미달이 나오면 기준을 낮추는 게 아니라 미달 사실을 기록하고 무엇을 고칠지 정한다(사후 기준 완화는 판정을 무의미하게 만든다)
