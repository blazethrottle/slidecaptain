# 보고서 디자인 체계 묶음 계획서 (2026-09-07, 적대 리뷰 반영 재작성)

> 근거: [디자인 격차 분석](2026-09-07-design-gap-analysis.md). 단계 5B 파일럿 2건에서 사용자가 보고한 치명적 발견을 처리한다. 산출물에 표와 불릿 외에 도식이 없고, 원인은 프롬프트가 아니라 **덱 스키마에 담을 자리가 없는 것**이다.
> **사용자 결정 (2026-09-07)**: ① 재설계를 진행한다 ② 벤치마크에서 추출한 배치 원형을 **회사 보고 관례로 간주**하고 표본을 더 늘리지 않는다 ③ 파일럿은 이 묶음을 마친 뒤 3건을 새 빌드로 다시 센다.
> **이 문서는 초판의 재작성이다.** 세 관점 적대 리뷰(렌더, 생성 계약, 프런트와 범위)가 재작업 2건과 수정 후 승인 1건을 냈고 **가정 1, 2, 4, 7이 실측으로 반증**됐다.

## 초판에서 무엇이 틀렸나 (전부 실측으로 확정)

| 초판의 주장 | 실측 | 처분 |
|---|---|---|
| 원형 배지를 `OVAL` 로 그린다 | `OVAL` 은 조정 핸들이 **0개**라 폭과 높이가 다르면 눌린 타원이 된다. `ROUNDED_RECTANGLE` 에 조정값 0.5 를 주면 알약과 정원이 정확히 나온다 | 라이터는 사각형과 둥근 사각형 **두 가지만** 쓴다 |

| 강조 카드는 **굵은 테두리** | 두께는 1.0pt 가 78건, 2.0pt 이상은 2건뿐이고 그마저 어두운 카드가 아니다 | 강조는 **채움과 테두리 색**으로 한다 |
| 색 8역할이면 덮인다 | 채움 13종, 테두리 7종이다. 가장 많이 쓰인 테두리색(`DCE3E5`, 42건)이 초판 팔레트에 없었다 | 팔레트를 실측값으로 다시 뽑는다 |
| 타이포 5단계를 새로 만든다 | `FontRoles` 에 `title_pt`, `subtitle_pt`, `body_pt` 가 **이미 있고** 초판은 같은 이름에 다른 기본값을 제안했다. 바꾸면 기존 6종의 제목 크기가 전부 바뀐다 | 기존 필드를 재사용하고 없는 것만 더한다 |
| 표는 머리행 색 + 본문 행 교차 | 표 4개 전수 조사 결과 **열 단위 색상 코딩**이고 머리행도 칸마다 색이 다르다. `header_fill` 은 행 전체 단일 색이라 표현 불가 | 표 칸별 채움을 별도 태스크로 신설 |
| 스키마 버전을 올린다 | 설계서가 *"기본값이 있는 필드 추가는 버전을 유지한다. 불필요한 상향은 기존 덱 전부를 읽지 못하게 만든다"* 고 정하고 로더는 `!=` 등호 비교만 한다 | **버전을 올리지 않는다.** 마이그레이션 태스크 삭제 |
| 새 필드 추가는 기존 렌더 불변이라 안전 | `Frame` 에 필드를 더하면 커밋된 `openapi.json` 과 라이브 앱이 즉시 어긋나 동기화 테스트가 깨진다 | 기반 태스크마다 스키마 재생성을 같은 커밋에 |
| `templateSwitch.ts` 는 계획에 없음 | 템플릿 전환 로직 전체가 이 파일에 있고 템플릿이 늘면 `TS2366` 컴파일 오류가 난다(재현 확인) | 별도 태스크로 승격 |

**반증되지 않은 것**: 프레임 추상화로 배치 원형을 표현한다는 방향, 미리보기가 템플릿 이름을 모르는 범용 렌더러라는 사실(읽기 전용에 한해 확인), 용량 계약을 실측으로 정한다는 원칙.

## 묶음 DA: 렌더 기반

### DA-1. 렌더 계약 확장

`Frame` 에 `radius_pt: float | None = None` 과 `border_width_pt: float | None = None` 을 더한다.

라이터는 `MSO_SHAPE.RECTANGLE` 과 `ROUNDED_RECTANGLE` **두 가지만** 쓴다. `radius_pt` 가 있으면 둥근 사각형을 쓰고 조정값을 `radius_pt / min(w, h)` 로 계산한 뒤 **0 이상 0.5 이하로 자른다**. python-pptx 는 0.5 초과와 음수를 예외 없이 저장하므로 클램프를 코드에 둔다. 알약과 정원은 조정값 0.5 로 나온다.

미리보기는 `border-radius` 로 그린다. CSS 는 반경 합이 변을 넘으면 브라우저가 비례 축소하므로 같은 모양이 나온다.

**폴백 규칙을 한 곳에 둔다**: 전역 테두리 두께로 되돌리는 판단을 라이터와 미리보기에 각각 구현하면 과거 세로 정렬 사고와 같은 계열의 위험이 생긴다. **레이아웃 엔진이 프레임에 항상 명시**하고 소비자는 값을 그대로 쓴다.

**검증**: 기존 골든 테스트 불변. 조정값 경계(0, 0.5, 상한 초과, 음수). **폭과 높이가 다른 프레임에서 반경이 큰 경우 미리보기와 PPTX 를 나란히 비교.** `openapi.json` 과 프런트 타입 재생성을 **같은 커밋에** 포함한다.

### DA-2. 표 칸별 채움

`TablePlan` 에 `header_fills: list[str] = []`(칸별)과 `body_fills: list[str] = []`(열별)을 더한다. 비어 있으면 기존 `header_fill` 동작 그대로다.

**근거**: 벤치마크 표 4개가 전부 열 단위 색상 코딩이고 머리행도 칸마다 다르다.

**검증**: 기존 표 렌더 불변, 칸별 색 지정 시 라이터와 미리보기 일치, 목록 길이가 열 수와 다르면 거절. 스키마 재생성 같은 커밋.

### DA-3. 프리셋의 색 역할

`Colors` 에 역할을 더한다. 기존 필드와 이름이 겹치지 않는 것을 확인했다.

| 역할 | 값 | 벤치마크 사용 |
|---|---|---|
| `ink` | `1B2A3A` | 채움 7 |
| `ink_soft` | `24384A` | 채움 4 |
| `accent1` | `0E8C7F` | 채움 5, 테두리 25 |
| `accent2` | `C8860B` | 채움 2, 테두리 4 |
| `danger` | `C0473B` | 채움 1, 테두리 2 |
| `ok` | `2E9E5B` | 채움 1, 테두리 1 |
| `surface1` | `EAF2F1` | 채움 18 (최다) |
| `surface2` | `F4F6F7` | 채움 15 |
| `surface3` | `FBF3E6` | 채움 2 |
| `surface_danger` | `FBEEEC` | 채움 1 |
| `rule` | `DCE3E5` | **테두리 42 (최다)**. 초판이 빠뜨렸다 |

**타이포는 새로 만들지 않는다.** `FontRoles` 의 기존 필드를 그대로 쓰고 **기본값을 바꾸지 않는다**. 없는 단계 하나만 더한다: `eyebrow_pt: float = 10.5`. `DesignPanel.tsx` 의 글자 크기 조정 화면은 기존 필드를 가리키므로 변경이 없다.

**검증**: 기본 프리셋으로 기존 덱 렌더 불변(골든), 색 형식과 범위 위반 거절, 스키마 재생성 같은 커밋.

### DA-4. 공통 슬롯 2종과 본문 상단 헬퍼

`Slide` 에 `eyebrow: str = ""` 와 `subtitle: str = ""` 를 더한다.

**각주와 푸터는 더하지 않는다.** `footnote` 는 슬롯 레벨에 이미 있고 통합은 *다르게 해석되는 변경*이라 유일하게 버전 상향이 필요해진다. 쪽 번호는 `page_number_pt` 로 이미 처리된다.

**본문 상단 계산을 헬퍼 하나로 모은다.** 지금은 본문 영역 높이를 6개 빌더가 각자 계산하고, 공유 함수는 프리셋만 받아 슬라이드별 슬롯 유무를 알 수 없다. 두 슬롯의 유무에 따라 본문 상단을 내리는 계산을 헬퍼로 만들고 **기존 6개와 신규 4개 전부가 그 헬퍼를 거치는지 테스트로 강제**한다.

**빈 슬롯 편집 진입을 이번에 정한다.** 값이 없으면 프레임을 안 만드는 현재 규칙은 클릭할 대상이 없어 나중에 추가할 수 없게 만든다(이월표 미해결 항목). **결정: 속성 패널에 입력칸을 둔다.** 미리보기에 빈 프레임을 만들지 않고 속성 패널에서 넣고 지운다. DB-6 이 구현한다.

**검증**: 두 슬롯의 유무 조합에서 본문 상단이 정확히 그만큼 내려가는지 **10개 템플릿 전부**, 값이 없을 때 기존 레이아웃과 동일, 스키마 재생성 같은 커밋.

### DA-5. 템플릿 레지스트리 단일 출처 테스트

템플릿 이름이 **네 곳에 따로 하드코딩**돼 있다: 구조안 스키마의 enum, 프롬프트의 슬롯 매핑, 용량 계약 딕셔너리, 글자 수 환산 함수. 한 곳이라도 빠뜨리면 사용자에게 500 오류가 간다.

`typing.get_args(TemplateName)` 를 단일 출처로 놓고 네 레지스트리와 레이아웃 빌더가 **같은 집합인지** 검사하는 테스트를 **지금(6종 상태에서 통과하게)** 넣는다. 이후 템플릿을 더하는 모든 태스크가 이 테스트에 걸린다.

**검증**: 일부러 한 곳을 빠뜨리면 실패하는지 확인.

### DA 묶음 최종 리뷰

세 관점 병렬 + 발견당 반박자.

## 묶음 DB: 템플릿과 생성

템플릿은 **관측 빈도 순**으로 만든다. 시간이 부족하면 뒤쪽을 잘라도 값이 나온다.

### DB-1. `callout` (강조 밴드)

전폭 둥근 사각형, 문장 1~3줄, 바탕은 역할 이름으로 지정. 벤치마크 슬라이드 절반에 있다.

### DB-2. `cards` (카드 2~4개)

각 카드는 배지 라벨(선택), 제목, 본문, 꼬리 라벨(선택). 강조 카드는 **어두운 채움과 강조 테두리 색**으로 구분한다(굵기 아님).

**용량 계약 함수의 시그니처를 바꾼다.** 카드 수에 따라 폭이 달라지고 폭이 달라지면 줄 수 상한이 달라진다. 기존 계약은 프리셋만으로 정해지는 단일 스칼라 전제라 이 구조를 담지 못한다. 계약 함수에 인자를 더하고 **기존 6종 호출부를 함께 고친다**.

**경계값 왕복 테스트**: 카드 2, 3, 4개 각각에서 계약대로 채우면 실측이 통과하는지.

### DB-3. `process` (번호 단계 3~6개)

각 단계는 번호 배지(둥근 사각형, 조정값 0.5), 제목, 부제, 오른쪽 보조 라벨 2개. 전폭 행으로 쌓는다. 사용자가 요구한 "플로우차트" 의 실제 형태다. 용량 계약과 경계값 왕복 테스트는 DB-2 와 같은 형식.

**`timeline` 은 만들지 않는다.** 초판이 원형 5의 변형으로 넣었으나 벤치마크에서 독립 원형으로 관측되지 않았다. 필요가 확인되면 다음 회차에 만든다.

### DB-4. `matrix` (행 3~6개)

왼쪽 분류 셀, 가운데 대표 항목, 오른쪽 나열. **용량 계약과 경계값 왕복 테스트를 DB-2, DB-3 과 같은 형식으로 둔다**(초판은 이 템플릿에만 계약 문단이 없었다).

### DB-5. 생성 계약

1. **템플릿 안내 문구를 10종 전부 같은 형식으로 다시 쓴다.** 지금 `TEMPLATE_GUIDE` 는 `bullet_box` 를 "가장 흔한 본문 장" 이라 불러 사실상 기본값 지위를 준다. 이것이 쏠림의 직접 원인이다. 지위 부여 표현을 빼고 모두 "이런 내용일 때" 라는 내용 조건으로 통일하고 폴백을 마지막 순서로 명시한다.
2. 장별 프롬프트에 새 템플릿의 슬롯과 계약을 넣는다. **이미 그 장의 계약만 실린다**(실측: 계약 블록 136자 / 전체 1,243자).
3. **형식 재시도 프롬프트에 실패 사유 한 줄을 넣는다.** 개수 제약이 있는 새 템플릿 3종에서 이 약점이 자주 발동한다.
4. `_NUMBER_EXEMPT_FIELDS` 를 새 템플릿에 맞게 점검한다.
5. 스키마 재생성과 프런트 타입과 목 갱신을 같은 커밋에.

> **거절 경로 두 갈래**: AI 생성 결과의 위반은 **형식 게이트의 소프트 실패**다(재시도 1회 뒤 `status="format_error"` 를 HTTP 200 으로). 422 는 사용자가 편집기에서 저장할 때의 경로다.

### DB-6. 프런트 편집

`PropertyPanel.tsx` 와 `slotOps.ts` 와 `labels.ts` 와 `StructureScreen.tsx` 가 템플릿 이름을 직접 참조한다. 미리보기는 범용 렌더러라 손댈 것이 적다.

- 새 템플릿 4종의 속성 패널 분기와 슬롯 편집 분기
- **항목 추가와 삭제**: 카드, 단계, 매트릭스 행. 기존 불릿 전용 함수로는 처리되지 않아 템플릿마다 새로 만든다
- **아이브로우와 부제 입력칸**(DA-4 의 결정)

### DB-7. 템플릿 전환

`templateSwitch.ts` 는 전환 시 무엇을 보존하고 무엇을 버릴지 정하는 유일한 자리다. 템플릿이 늘면 컴파일 오류가 나므로 반드시 고쳐야 한다.

**먼저 보존 매트릭스를 표로 정의하고** 구현한다. 새 템플릿의 배지, 꼬리 라벨, 보조 라벨, 분류 셀은 기존 공통 추상화에 대응점이 없어 설계 없이 구현하면 조용히 사라진다.

이월표의 "템플릿 전환 안내 부족"(손실 안내가 없고 스냅샷을 남기지 않음)을 **같이 해소한다.** 손실 표면이 넓어지는 시점이라 미루면 사고가 는다.

### DB-8. 관통 (메인 세션 수동)

비기밀 합성 자료로 **실호출 1회**로 구조안을 생성해 AI 가 새 템플릿을 실제로 고르는지 본다. 고르지 않으면 DB-5 를 고친다. 그 뒤 샘플 덱으로 4종을 렌더해 PPTX 를 열어 본다.

**사용자 승인 사항**: 실호출 횟수. 기본 1회, 선택이 관측되지 않으면 1회 추가 요청.

### DB 묶음 최종 리뷰

세 관점 + 반박자. 그 뒤 문서 정정과 push.

## 파일럿 재개 조건

**DB-8 관통까지 끝나야 재개한다.** 부분 완성으로는 재개하지 않는다. 세 건이 같은 빌드 위에서 돌아야 판정이 유효하기 때문이며 5B 계획서의 blocker 처분과 같은 논리다.

**기존 파일럿 산출물 2건은 폐기한다.** 기존 템플릿의 렌더가 불변이므로 그 덱을 다시 내보내도 새 도식은 나오지 않는다. 새 도식을 보려면 장마다 템플릿을 손으로 바꿔야 하는데 3건을 새로 만드는 것보다 비용이 크고 판정도 오염된다.

## 완료 관문

- 새 템플릿 4종이 스키마에 있고 레이아웃과 라이터와 미리보기가 모두 그린다
- 기존 6종의 렌더 결과가 바뀌지 않는다(골든)
- 색 역할이 프리셋에 있고 슬라이드 안에서 분류를 표현한다
- 새 템플릿마다 용량 계약이 실측으로 정해지고 경계값 왕복 테스트가 있다
- 레지스트리 단일 출처 테스트가 통과한다
- 템플릿 전환에서 무엇이 보존되고 버려지는지 표로 정의되고 안내된다
- 실호출 1회에서 AI 가 새 템플릿을 최소 1종 고른다
- 백엔드와 프런트 테스트 전부 통과, 감사 0건, CI 양 OS 성공

## 이 계획이 틀렸을 가능성

1. **AI 가 새 템플릿을 안 고를 수 있다.** 안내 문구를 고쳐도 불릿으로 수렴할 수 있다. DB-8 의 유일한 판정 항목이다.
2. **AI 가 부적절한 템플릿을 고를 수 있다.** 표로 낼 내용을 카드로 내면 나빠진다. 다음 파일럿의 관측 항목으로 남긴다.
3. **용량 계약 시그니처 변경이 기존 호출부로 번진다.** DB-2 가 커지면 계약 변경과 템플릿 구현으로 쪼갠다.
4. **본문 상단 헬퍼가 기존 빌더 6개를 건드린다.** 슬롯이 비어 있으면 결과가 기존과 완전히 같아야 하고 골든 테스트가 그것을 고정한다.
5. **글자 크기 단계 회귀 테스트와 충돌할 수 있다.** 본문 영역 글자 크기가 슬라이드당 2단계를 넘으면 실패하는 테스트가 있다. 아이브로우와 부제가 함께 쓰이면 3단계가 될 수 있다. DA-4 에서 그 테스트의 의도를 확인하고 범위를 조정하거나 슬롯을 본문 영역 밖에 둔다.
6. **회사 보고 관례로 간주한 것이 틀릴 수 있다.** 파일럿에서 드러나면 프리셋 값만 바꾼다. 색과 크기를 코드에 박지 않는 이유가 이것이다.
7. **DB-6 과 DB-7 이 프런트에서 가장 큰 태스크다.** 백엔드 4종보다 클 수 있다. 커지면 DB-6 을 템플릿별로 쪼갠다.
