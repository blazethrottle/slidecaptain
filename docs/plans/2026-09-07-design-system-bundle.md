# 보고서 디자인 체계 묶음 계획서 (2026-09-07)

> 근거: [디자인 격차 분석](2026-09-07-design-gap-analysis.md). 단계 5B 파일럿 2건에서 사용자가 보고한 치명적 발견을 처리한다. 산출물에 표와 불릿 외에 도식이 없고, 원인은 프롬프트가 아니라 **덱 스키마에 담을 자리가 없는 것**이다.
> **사용자 결정 (2026-09-07)**: ① 재설계를 진행한다 ② 벤치마크에서 추출한 배치 원형 8종을 **회사 보고 관례로 간주**하고 표본 수를 더 늘리지 않는다 ③ 5B 파일럿은 이 묶음을 마친 뒤 3건을 새 빌드로 다시 센다(계획서 5B-3 의 blocker 처분 준용).
> 브랜치 `codex/phase-5b` 에서 태스크마다 커밋하고, 태스크별 독립 리뷰와 묶음 최종 리뷰를 거쳐 push 한다. 5A 묶음들과 같은 절차다.

## 범위와 원인 묶음

| 태스크 | 포함 항목 | 공통 원인 |
|---|---|---|
| D1. 렌더 계약 확장 | `Frame` 에 모서리 반경과 프레임별 테두리 두께를 더하고 라이터와 미리보기가 그린다 | 벤치마크의 둥근 사각형 60개와 원형 배지를 현재 계약으로는 표현할 수 없다. 라이터가 `MSO_SHAPE.RECTANGLE` 하나만 쓴다 |
| D2. 프리셋의 색 역할과 타이포 단계 | 색 8종(잉크, 강조 2종, 위험, 긍정, 바탕 3종)과 글자 크기 5단계를 프리셋으로 승격 | 현재 산출물의 채움색이 **1종**이다. 색이 순서와 분류를 뜻하게 하려면 역할로 이름 붙은 팔레트가 필요하다 |
| D3. 공통 슬롯 4종 | 아이브로우, 부제, 각주, 푸터를 모든 템플릿에 선택 슬롯으로 | 벤치마크 전 슬라이드에 있는 구조인데 현재 스키마에 자리가 없다 |
| D4. 템플릿 `callout` 과 `cards` | 전폭 강조 밴드, 카드 2~4개(배지, 제목, 본문, 꼬리 라벨, 강조 카드 지정) | 원형 2, 3, 4. 벤치마크에서 가장 자주 쓰인 두 형태 |
| D5. 템플릿 `process` 와 `timeline` | 번호 단계 3~6개(원형 배지, 제목, 부제, 보조 라벨 2개)와 시점 항목 4~8개 | 원형 5. 사용자가 요구한 "플로우차트"의 실제 형태다 |
| D6. 템플릿 `matrix` | 왼쪽 분류 + 대표 항목 + 나열, 행 3~6개 | 원형 6 |
| D7. AI 생성 계약 | 템플릿 선택 기준과 새 템플릿의 용량 계약을 프롬프트와 스키마에 반영 | 선택지가 여섯이라 대부분 `bullet_box` 로 수렴했다. 자리를 만들어도 고르지 않으면 소용이 없다 |
| D8. 프런트 편집 | 새 템플릿의 편집 진입과 속성 패널 | 사용자가 화면에서 고칠 수 없으면 산출물이 고정된다 |
| D9. 관통 | 실호출 1회로 새 템플릿이 실제로 선택되고 렌더되는지 확인 | 자동 테스트는 전부 가짜 프로바이더다 |

**이 묶음에 넣지 않는 것**: 네이티브 차트(이월표의 별도 항목), 그림 삽입, 자유 도형 편집과 임의 좌표 이동, 애니메이션, 대각선 연결선, 프리셋 환류 UI, 설정 페이지.

## 가정 (번호를 붙여 적대 리뷰가 겨냥하게 한다)

1. **렌더 계약은 두 필드만 늘리면 원형 8종을 전부 표현할 수 있다.** 둥근 사각형과 원형 배지는 `radius_pt` 로, 강조 카드의 굵은 테두리는 프레임별 `border_width_pt` 로 덮인다. 가로 구분선은 높이가 작은 채움 프레임으로 대신한다.
2. **대각선 연결선은 필요 없다.** 벤치마크의 선 도형은 슬라이드당 3~6개이고 전부 수평 구분이나 단계 사이 보조다. 흐름은 배치의 반복으로 표현된다.
3. **레이아웃 계산의 진본은 백엔드 하나라는 원칙을 유지한다.** 프런트는 렌더 계획을 그대로 그리므로, 새 필드 두 개만 소비하면 새 템플릿 5종이 자동으로 그려진다.
4. **기존 6종 템플릿의 렌더 결과는 바뀌지 않는다.** 새 필드는 선택이고 기존 템플릿은 지정하지 않는다. 골든 테스트가 이를 고정한다.
5. **AI 는 템플릿을 고를 수 있다.** 구조안 생성 단계에서 장별 템플릿을 정하는 자리가 이미 있으므로, 선택지와 판단 기준을 넓히면 된다.
6. **새 템플릿의 용량 계약은 실측으로 정한다.** 기존 계약이 22~35% 과다 약속했던 사고가 있으므로 경계값 왕복 테스트를 태스크마다 둔다.
7. **덱 스키마 버전을 올려야 한다.** 새 템플릿이 추가되면 옛 로더가 읽지 못한다. 설계서의 판정 기준상 "기존 파일이 읽히지 않는 변경"이므로 버전 상향과 마이그레이션이 필요하다.
8. **색 역할 8종과 타이포 5단계는 회사 보고 관례다** (사용자 결정 ②). 다른 조직에 맞추는 일반화는 하지 않는다.

## 태스크 D1: 렌더 계약 확장

`models/render.py` 의 `Frame` 에 두 필드를 더한다.

- `radius_pt: float | None = None`: 없으면 직각. 값이 `min(w, h) / 2` 이상이면 원 또는 알약으로 그린다
- `border_width_pt: float | None = None`: 없으면 `RenderStyle.border_width_pt` 를 쓴다

라이터는 `radius_pt` 에 따라 `MSO_SHAPE.RECTANGLE`, `ROUNDED_RECTANGLE`, `OVAL` 을 고르고, 둥근 사각형의 조정값을 반경에서 계산한다. 미리보기는 `border-radius` 와 테두리 두께를 반영한다.

**검증**: 기존 골든 테스트 전부 불변(가정 4), 새 필드의 세 분기를 각각 그려 도형 종류와 조정값을 단언, 미리보기 재현 테스트.

## 태스크 D2: 프리셋의 색 역할과 타이포 단계

`models/preset.py` 에 두 블록을 더한다.

| 색 역할 | 기본값 | 쓰임 |
|---|---|---|
| `ink` | `1B2A3A` | 제목과 어두운 카드 바탕 |
| `accent1` | `0E8C7F` | 1순위, 긍정 강조, 아이브로우 |
| `accent2` | `C8860B` | 2순위, 일정 강조 |
| `danger` | `C0473B` | 경고 |
| `ok` | `2E9E5B` | 달성 |
| `surface1` | `EAF2F1` | 강조 1 계열 바탕 |
| `surface2` | `F4F6F7` | 중립 바탕 |
| `surface3` | `FBF3E6` | 강조 2 계열 바탕 |

| 타이포 단계 | 기본값 | 쓰임 |
|---|---|---|
| `eyebrow_pt` | 10.5 | 제목 위 분류 라벨 |
| `title_pt` | 21 | 슬라이드 제목 |
| `subtitle_pt` | 13.5 | 제목 아래 한 문장 |
| `body_pt` | 12 | 카드와 표 안 |
| `caption_pt` | 8.5 | 각주, 출처, 푸터 |

기존 프리셋 필드와 충돌하지 않게 기본값을 주고, 유한값과 범위 검증(묶음 A 태스크 A3 과 같은 방식)을 적용한다.

**검증**: 기본 프리셋으로 기존 덱을 렌더해 결과 불변, 색 값 형식과 크기 범위 위반이 422 로 거절되는지.

## 태스크 D3: 공통 슬롯 4종

`Slide` 에 선택 필드를 더한다: `eyebrow`, `subtitle`, `footnote`, `footer`. 레이아웃은 제목 위(아이브로우), 제목 아래(부제), 하단 왼쪽(각주), 하단 오른쪽(푸터)에 배치하고, 값이 없으면 그 자리를 차지하지 않는다.

푸터는 덱 메타의 제목과 쪽 번호를 자동으로 채우되 슬라이드별로 덮어쓸 수 있다.

**검증**: 네 슬롯의 유무 조합에서 본문 영역 높이가 정확히 그만큼 줄어드는지, 값이 없을 때 기존 레이아웃과 동일한지.

## 태스크 D4: 템플릿 `callout` 과 `cards`

`callout`: 전폭 강조 밴드. 문장 1~3줄, 바탕색은 역할 이름으로 지정(`surface1`~`surface3`), 핵심구 굵게.

`cards`: 카드 2~4개. 각 카드는 배지 라벨(선택), 제목, 본문, 꼬리 라벨(선택). 카드 하나를 `emphasis` 로 지정하면 어두운 바탕과 굵은 테두리로 그린다. 카드 수에 따라 열 폭을 계산하고 최소 폭 미만이면 422 로 거절한다.

**용량 계약**: 카드 수별 제목과 본문의 최대 줄 수를 실측으로 정하고, 경계값 왕복 테스트로 고정한다.

## 태스크 D5: 템플릿 `process` 와 `timeline`

`process`: 번호 단계 3~6개. 각 단계는 원형 번호 배지(색은 단계 순서로 팔레트에서 배정), 제목, 부제, 오른쪽 보조 라벨 2개(중립 알약과 강조 알약). 전폭 행으로 쌓는다.

`timeline`: 시점이 붙은 항목 4~8개. 가로 축 또는 세로 축 중 항목 수로 자동 선택한다.

**용량 계약**: 단계 수별 행 높이와 제목 최대 글자 수. 단계가 6개를 넘으면 422.

## 태스크 D6: 템플릿 `matrix`

행 3~6개. 각 행은 왼쪽 분류 셀(파스텔 채움, 행마다 다른 색), 가운데 대표 항목(점 표식 + 굵은 제목), 오른쪽 나열 문자열.

## 태스크 D7: AI 생성 계약

1. 구조안 생성 프롬프트에 **템플릿 선택 기준**을 넣는다. 어떤 내용일 때 어떤 템플릿인지 한 줄씩 적고, "판단이 서지 않으면 `bullet_box`" 를 명시한다.
2. 장별 생성 프롬프트에 새 템플릿의 슬롯 구조와 용량 계약을 넣는다.
3. 구조화 출력 스키마를 재생성하고 프런트 타입과 목을 같은 커밋에서 갱신한다(생성 산출물 동기화 테스트가 커밋의 원자 단위를 정한다).
4. 덱 스키마 버전을 올리고 마이그레이션을 넣는다(가정 7).

## 태스크 D8: 프런트 편집

새 템플릿 5종의 미리보기 렌더와 편집 진입(프레임 클릭 후 내용 수정), 속성 패널의 배지와 색 역할 선택. 기존 편집 흐름과 저장 안전성 장치를 그대로 쓴다.

## 태스크 D9: 관통 (메인 세션이 수동으로 수행)

새 클론이 아니라 현재 작업공간에서 한다. 비기밀 합성 자료로 프로젝트를 만들고 **실호출 1회**로 구조안을 생성해, AI 가 새 템플릿을 실제로 고르는지 확인한다. 고르지 않으면 D7 의 프롬프트를 고친다. 그 뒤 장별 생성 없이 샘플 덱으로 5종을 모두 렌더해 PPTX 를 열어 본다.

**사용자 승인 사항**: 실호출 횟수. 기본은 1회로 잡되 템플릿 선택이 관측되지 않으면 프롬프트 수정 후 1회를 더 요청한다.

## 실행 순서

1. 계획서 적대 리뷰(세 관점 병렬) → 반영
2. D1 → D2 → D3 (기반. 이 셋이 끝나야 새 템플릿을 만들 수 있다)
3. D4 → D5 → D6 (템플릿. 태스크마다 용량 계약 왕복 테스트)
4. D7 (생성 계약. 스키마 재생성과 프런트 타입 갱신을 같은 커밋에)
5. D8 (프런트 편집)
6. 묶음 최종 리뷰(세 관점 + 반박자) → 반영
7. D9 관통 → 문서 정정 → push → CI
8. 5B 파일럿 3건 재개(새 빌드)

## 완료 관문

- 새 템플릿 5종이 덱 스키마에 있고, 레이아웃과 라이터와 미리보기가 모두 그린다
- 기존 6종 템플릿의 렌더 결과가 바뀌지 않는다(골든 테스트)
- 색 역할 8종과 타이포 5단계가 프리셋에 있고 슬라이드 안에서 분류를 표현한다
- 새 템플릿마다 용량 계약이 실측으로 정해지고 경계값 왕복 테스트가 있다
- 실호출 1회에서 AI 가 새 템플릿을 최소 1종 이상 고른다
- 백엔드와 프런트 테스트 전부 통과, 공개 저장소 감사 0건, CI 양 OS 성공

## 이 계획이 틀렸을 가능성

1. **가정 1이 틀리면 범위가 커진다.** 원형 8종 중 하나라도 두 필드로 표현되지 않으면 렌더 계약을 더 늘려야 하고, 그러면 프런트도 함께 커진다. D1 에서 5종 전부의 도형 목록을 손으로 배치해 먼저 확인한다.
2. **AI 가 새 템플릿을 안 고를 수 있다.** 선택지를 늘려도 프롬프트가 약하면 여전히 불릿으로 수렴한다. 이것이 D9 관통의 유일한 판정 항목이고, 실패하면 계약을 고쳐 다시 시험한다.
3. **AI 가 부적절한 템플릿을 고를 수 있다.** 표로 낼 내용을 카드로 내면 오히려 나빠진다. 선택 기준을 프롬프트에 넣되, 다음 파일럿의 관측 항목으로 남긴다.
4. **용량 계약이 늘어 프롬프트가 비대해진다.** 템플릿 5종의 슬롯과 상한을 전부 적으면 프롬프트가 길어지고 생성 품질이 떨어질 수 있다. 장별 생성에서는 **그 장이 쓰는 템플릿의 계약만** 넣는 방식을 검토한다.
5. **덱 스키마 버전 상향이 기존 파일럿 산출물을 못 읽게 만든다.** 파일럿 2건의 덱이 있으므로 마이그레이션을 반드시 넣고 옛 덱 로드 테스트를 둔다.
6. **회사 보고 관례로 간주한 것이 틀릴 수 있다.** 사용자 결정으로 표본을 늘리지 않기로 했으므로, 이 전제가 어긋나면 파일럿에서 드러난다. 그때는 프리셋 값만 바꾸면 되도록 색과 크기를 코드에 박지 않고 프리셋에 둔다(D2 의 설계 의도).
