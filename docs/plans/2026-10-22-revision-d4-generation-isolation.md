# 개정판 D4 생성 격리: Claude 생성 세션의 내장 스킬과 명령 끄기

작성: 2026-10-22(회사 PC, Windows). 상태: 3판(리뷰 반영 8절, 실측 결과 9절). 브랜치 `feat/d4-generation-isolation`(기준 main `eedab2a`).

상위 문서: [D4 실제 생성 확인 계획](2026-10-21-revision-d4-live-check.md) 11절 질문 3, 로드맵 D4a 이월표의 "생성 세션에 사용자 스킬과 플러그인이 실린다" 행.

## 1. 사용자 결정

- 2026-10-22 "1안으로 진행": D4의 다음 단위를 "생성 세션에서 스킬과 플러그인 빼기"로 정했다.
- 2026-10-22 "A. Claude 1회 실행": 4절의 실제 호출을 설치 CLI, `default`, `low`로 1회 승인했다. 호출 직전에 리뷰(8절)를 반영해 판정 기준을 고쳤고, 횟수와 대상은 승인대로다.

## 2. 전제 정정과 지금 사실 (기준 `eedab2a`, 생성 호출 없음)

1. 전제 정정: 2026-10-21 실측 기록(위 계획 11절)은 초기화 메시지의 개수만 보고 "`setting_sources=[]`인데도 사용자 스킬과 플러그인이 실린다"고 적었다. 2026-10-22 같은 옵션으로 초기화 응답의 이름을 읽어 보니, 명령은 모두 Claude Code 내장분(설치 CLI는 항목마다 `builtin: true`)이고 에이전트 5개(`claude`, `Explore`, `general-purpose`, `Plan`, `statusline-setup`)도 내장분이었다. 사용자가 설치한 스킬과 에이전트는 없었다. 초기화 응답에는 스킬 칸이 따로 없어, 초기화 메시지의 스킬 19개가 내장분이라는 판단은 명령 목록에서 추정한 것이다. 플러그인 3개(설치 CLI만)의 정체는 모른다.
2. 명령 개수는 실행마다 바뀐다. 리뷰어가 같은 2.1.306에서 생성 없이 연달아 확인했을 때 51, 53, 55개였다(원격 기능 설정으로 추정).
3. 스킬 목록이 모델 입력에 붙는 경로: 리뷰어가 설치 CLI 2.1.306 실행 파일에서 확인한 바로는, 스킬 목록은 시스템 프롬프트가 아니라 턴마다 붙는 첨부이고, 도구 목록에 `Skill`이 없으면 붙지 않는다. 생성 경로는 `tools=[]`이므로 지금도 붙지 않을 가능성이 크다(정적 확인, 2.1.247은 확인하지 못했다). SDK 0.2.145가 `system_prompt`가 없을 때 `--system-prompt ""`를 넘기는 것은 맞지만, 목록을 막는 이유는 이것이 아니라 `tools=[]`다.
4. CLI 옵션 `--disable-slash-commands`가 두 판에 모두 있다. 도움말은 2.1.306이 "Disable all skills and commands", 2.1.247이 "Disable all skills"다. SDK `extra_args={"disable-slash-commands": None}`로 넘기면 두 판 모두 초기화 응답의 명령이 0개가 된다. 내장 에이전트 5개는 남지만 생성 경로는 도구가 없어 부를 수 없다.
5. `--bare`는 OAuth와 키체인을 읽지 않아 구독 로그인 경로에서 쓸 수 없다.
6. SDK의 `skills` 옵션은 문서상 모델에 보이는 스킬 목록을 거르는 필터이고(`skills=[]`는 모두 숨김), 초기화 응답의 명령 수는 바꾸지 않았다. `plugins` 옵션은 플러그인 폴더를 더하는 용도다.

## 3. 설계

1. `SubscriptionProvider.complete`의 옵션에 `extra_args={"disable-slash-commands": None}`를 넣는다. 지금도 `tools=[]`로 막혀 있을 가능성이 큰 경로를 한 번 더 막는 방어다. 목록 조회는 초기화 응답의 모델 항목만 읽으므로 바꾸지 않는다.
2. 응답 관측: 초기화 메시지 줄에 `claude_code_version` 값과 플러그인 이름 목록(`plugins#names`)을 더한다. 이름 목록은 `name_keys`로 고른 칸에만 담는다. MCP 서버 이름처럼 사용자가 짓는 문자열에는 이메일이 들어갈 수 있기 때문이다. 이름마다 60자, 40개까지 담고 경로 같은 다른 칸은 담지 않는다.
3. 사용량 진단 줄에 모델별 (입력, 출력, 캐시 읽기, 캐시 생성)을 더한다(`model_usage_by_model`). 보조 모델(haiku)의 토큰이 합계에 섞여 주 모델의 요청 크기를 알 수 없었기 때문이다.
4. 기록 정정: 2026-10-21 계획 3.3 2와 11절 질문 3, 로드맵 D4a 이월표 행에 날짜 붙은 정정을 적는다.

## 4. 실제 호출 (사용자 결정 A, 1회)

설치 CLI 2.1.306, `default`, `low`로 합성 장 하나를 생성한다(2026-10-21 L1과 같은 조건, `--max-calls 1 --stop-after chapter`).

호출로 확인하는 것:

1. 회귀 확인: `--disable-slash-commands`를 넣고도 구조화 출력과 `max_turns=2`로 장 생성이 정상으로 끝나는가. 리뷰어는 명령 목록과 도구 묶음을 따로 계산하므로 영향이 없다고 추정했지만 실제 호출로만 확인할 수 있다.
2. 초기화 메시지의 명령, 스킬 개수가 0이 되는가.
3. 플러그인 3개의 이름.
4. 주 모델 요청 크기 비교: 주 모델의 (입력 + 캐시 생성 + 캐시 읽기)를 L1의 약 6,390토큰과 비교한다. L1 값은 그날 로그의 마지막 턴 값(입력 2, 캐시 생성 6,388)에서 리뷰어가 추정한 것이고, L1은 모델별 값을 남기지 않았다. 예상 결과는 "거의 같음"(3절 근거)이다. 같으면 "원래 붙지 않았다"와 "옵션이 효과 없다"를 구별할 수 없으므로 판정에 쓰지 않고 기록만 한다. 100토큰 넘게 줄면 내장 목록이 입력에 있었다는 증거로 본다.
5. 무효 조건: 초기화 메시지의 `claude_code_version`이 2.1.306이 아니거나 응답 모델이 `claude-opus-5-5`가 아니면 4의 비교는 "판정 불가"로 기록하고 추가 호출하지 않는다.

판정과 기록은 2026-10-21 계획 3.5절과 5절을 따른다. 상한 1회, 실패 포함, 자동 재실행 없음.

## 6. 하지 않는 것과 이월

- 방치 확정(로드맵 방치 확정 문단): 내장 에이전트는 끄는 옵션이 없고 생성 경로에 도구가 없어 부를 수 없다. 목록 조회 경로에는 같은 옵션을 넣지 않는다(모델 항목만 읽는다).

- Grok(xAI) 제공자 추가: 2026-10-22 사용자 질문에 대한 검토만 했다. Grok Build CLI는 세 번째 제공자로 붙일 수 있는 형태(비대화 실행, 모델 목록, 강도, 공식 로그인, 격리 옵션이 있음)이고, CLI에는 스키마 강제 출력이 없다. Grok Bot은 호스팅 컴퓨터에서 비동기로 일하고 외부 호출이 웹훅 접수뿐이라 생성 제공자 자리에 맞지 않는다. 출처는 docs.x.ai의 Grok Build CLI, 인증, 구조화 출력 문서다. 로드맵 D4a 이월표에 담당(D4 제공자 확장)과 함께 올렸고, 착수는 사용자 결정 뒤 계획서로 한다.

확인 항목별 답(4절):

1. 회귀: 옵션을 넣고도 구조화 출력과 `max_turns=2`로 장 생성이 정상으로 끝났다.
2. 명령과 스킬은 0개가 되었다. 내장 에이전트 5개는 남았다(6절 방치 확정).
3. 플러그인 3개는 이름이 `cc-plugin-`으로 시작하는 Claude Code 내장 플러그인이다. 생성 세션에 사용자 설치분은 없다는 것이 확정됐다.
4. 주 모델 요청 크기는 6,390토큰으로 L1(추정 6,390)과 같다. 예상대로 같아서 판정에는 쓰지 않는다. 내장 스킬 목록은 원래 모델 입력에 붙지 않았을 가능성이 크고(2절 3), 이번 옵션은 겹쳐 막는 방어로 남는다.
5. 판본과 응답 모델이 L1과 같아 4의 비교는 유효하다.

새로 관측한 것: 보조 모델(haiku)이 주 모델과 거의 같은 크기의 입력(5,605토큰)을 받고 303토큰을 낸다. 생성 1회마다 프롬프트 크기만큼의 입력을 보조 모델에 한 번 더 보내는 셈이다. 무엇에 쓰는지는 확인하지 못했다. 로드맵 D4a 이월표의 보조 모델 행에 더했다. 원장의 `effort`와 사용량 기록의 `requested_effort`는 이번에도 `low`로 남았다.
