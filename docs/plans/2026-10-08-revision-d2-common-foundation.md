# 개정판 D2 공통 기반 계획

작성: 2026-10-08 (서울 기준). 사용자가 D1 macOS 확인 보고 뒤 "D2 계획서 착수"(선택지 A)를 승인했다. 승인 범위는 이 계획서의 작성, 독립 적대 리뷰, 반영과 확정 커밋까지다. 구현 착수는 확정 뒤 별도로 결정한다.

상위 문서는 다음과 같다. [기술 설계 7절](../architecture/2026-10-02-desktop-revision.md#7-개발-순서와-완료-관문)의 D2 행은 디자인 토큰과 컴포넌트, 프로젝트 상태와 저장, 작업 원장, 데이터 이전을 맡기고 관련 요구로 R01, R02, R11을 든다. [제품 설계 4절과 7절](../design/2026-10-02-revision-product-ux.md#4-상태와-시각-규칙)이 상태 표시와 저장 규칙을 정하고, [개정 계획](2026-10-02-windows-feedback-revision.md)이 요구 목록을 관리한다. 이 계획서는 상위 문서를 재정의하지 않는다. 상위 문서와 다르게 정하는 부분은 「상위 문서와 다르게 정하는 것」 절에 이유와 함께 모은다.

> 2026-10-08 개정: 초안(`0be38aa`)에 대한 세 관점 적대 리뷰(발견 94건)를 반영해 다시 썼다. 판정 내역은 「독립 검토 반영」 절에 있다.

## 1. 이번 단위의 목표

개정판의 모든 화면이 공유할 기반을 먼저 만든다. 목표는 셋이다.

- R01: 사용자가 저장 여부, 충돌, 실패, 보존된 변경을 표시만 보고 구별한다.
- R02의 데이터 보존: 새 버전 앱이 기존 프로젝트를 열고 저장해도 이전 버전이 읽을 수 있는 복구 지점이 남는다. 새 버전끼리는 같은 자료 폴더를 동시에 쓰지 않는다.
- R11의 공통 부분: 충돌로 저장하지 못한 편집과 AI 생성 결과를 버리지 않고 보존한다.

배포된 0.2.0은 이 단위의 보호 장치를 모른다. 0.2.0과 새 버전을 함께 켰을 때의 보호는 이 단위의 목표가 아니며, 그 한계는 8절과 릴리스 안내에 적는다.

## 2. 분할 결정: D2a와 D2b

D2를 두 묶음으로 나눈다.

| 묶음 | 내용 | 이 계획서의 상세 수준 |
|---|---|---|
| D2a 상태와 저장 기반 | 형식 기록과 이전, 충돌 시 미저장본과 생성 결과 보존, 자료 폴더 단일 서비스 잠금, 디자인 토큰, 상태 표시 컴포넌트, 단계 준비 모델 API | 태스크와 시험까지 |
| D2b 작업 원장 | 생성 작업의 원장, 비동기 생성 API, 재시작 조정, 기존 생성 라우트 6개의 이전 | 계약 수준(6절). 상세 태스크는 D2a 완료 뒤 실제 인터페이스를 근거로 별도 계획서에 쓴다(로드맵 원칙) |

분할 이유는 둘이다. 첫째, D2a의 형식 기록과 단일 서비스 잠금은 D2b의 전제다. 원장의 재시작 조정("실행 중으로 남은 작업을 중단으로 바꾼다")은 한 자료 폴더를 서비스 하나만 쓸 때만 맞다. 둘째, 원장은 생성 임대를 쓰는 라우트 6개(구조안, 장 생성, 축약, 도식, 재작성, 수리), AI 동의 관문 6곳, 화면 호출자와 사용량 기록을 모두 바꾼다. 저장 보강과 한 리뷰 단위에 섞으면 독립 검증이 어렵다.

반론과 판정: 실패와 중단 복구(R11)는 사용자가 Windows 첫 사용에서 가장 크게 겪은 문제이므로 원장을 먼저 해야 한다는 주장이 가능하다. 그러나 원장이 없어서 할 수 없는 것은 화면을 떠나거나 재시작한 뒤에도 남는 실패 표시와 후보 보존이다. 세션 안의 장별 진행 표시는 구성 화면이 이미 갖고 있다. 이 계획은 D2a를 먼저 하되, 설계 7절의 D2 완료 관문("변경, 저장, 충돌, 중단 복구 상태를 모의 서버와 실제 저장으로 검증")은 **D2b가 끝나야 통과**로 기록한다. D2a만 끝난 상태를 D2 완료로 표시하지 않는다.

D2a 안의 순서는 데이터 보존 위험이 큰 것부터 둔다: D2a-1 형식 → D2a-2 보존 → D2a-3 잠금 → D2a-4 토큰 → D2a-5 상태 표시 → D2a-6 진행 모델. 새 보고 유형은 이미 이 브랜치(`2ad06ea`)에 있어 지금도 0.2.0이 읽지 못하는 덱이 생길 수 있기 때문이다.

D2b가 바꿀 인터페이스에는 지금 확장 지점을 둔다. 진행 모델 응답의 `jobs` 자리(D2a-6), 상태 표시의 "생성 중"을 호출자가 주는 속성으로 받기(D2a-5), 미저장본 보존 봉투의 `reason`과 `source` 필드(D2a-2)다.

## 4. 현재 코드에서 확인한 사실

코드 기준은 `3bb22f3`이다(초안 커밋 `0be38aa`와 코드가 같다). 2026-10-08 리뷰에서 재확인했다.

1. `frontend/src/styles.css`(177줄)에는 CSS 변수가 0개다. 대소문자를 정규화하면 서로 다른 hex가 30종이고, 이름 색 `white`, `rgba(...)` 2곳, 알파 hex 2곳이 더 있다. 경계색만 11종, 보조 글자색만 4종이다. 제품 설계 4절의 색 토큰 9개로는 모두를 같은 의미로 옮길 수 없다. 화면 코드(`screens`, `editor`)의 hex 2개는 `editor/Preview.tsx`의 슬라이드 미리보기 색이다. `:root { color: #202020 }`은 미리보기 표 칸이 물려받는 글자색이고, 프리셋 기본 글자색 `202020`과 우연히 같다.
2. 자동 저장과 저장 상태 표시는 편집 화면에만 있다. `SaveState = "저장됨" | "저장 대기" | "저장 중" | "저장 실패"`이고, 충돌(412)과 일반 실패가 모두 "저장 실패"다. 화면 표시는 `EditorScreen.tsx`의 `<p>저장 상태: {editor.saveState}</p>` 한 줄이며 오른쪽 패널에 있다. 자료 화면은 버튼 저장이고 미저장 표시가 없다. 성공 안내도 `role="alert"` 문단에 뜨므로 전역 규칙 `[role="alert"] { color: #b00020 }` 때문에 빨갛게 보인다. 구조안 화면의 장 구성 초안은 부모에 미저장 신호를 보내지 않아 창을 닫으면 경고 없이 사라진다.
3. 412 충돌의 회복 경로는 두 개다. 편집 화면은 `useDeckEditor.reloadFromServer`가 서버 덱으로 교체해 미저장 편집을 버린다. 자료, 구조안, 복구 화면은 `ProjectView.reloadDeck`의 "서버 내용 다시 읽기"가 `setDeck(null)`로 화면을 다시 만들어 미저장 입력을 버린다. 구조안 승인 루프는 장 생성 결과를 메모리에 둔 채 저장하므로, 그 저장이 412나 다른 오류로 끝나면 **이미 AI 비용을 쓴 생성 결과가 사라진다**(`StructureScreen.tsx`의 승인 반영과 장 결과 저장).
4. `backend/slidecaptain/storage/file_store.py`는 `deck.json`을 원자적으로 쓰고 SHA-256을 ETag로 쓴다. 프로세스 사이의 보호는 없다. ETag 검사도 프로세스 안 잠금(`threading.RLock`) 안에서 읽기, 비교, 쓰기를 하므로 두 프로세스가 같은 ETag로 동시에 저장하면 뒤의 쓰기가 앞의 쓰기를 덮는다. `If-Match`가 없는 `PUT /deck`은 검사하지 않는다. 내보내기 게시는 이미 OS 파일 잠금(`backend/slidecaptain/export/locking.py`, 잠금 파일 `.slidecaptain-export.lock`, 재시도 5초, 잠금 파일을 지우지 않음)으로 프로세스 사이를 직렬화한다. 스냅샷 복사(`_snapshot_current`)는 `shutil.copy2`라 원자적이지 않다.
5. `Deck.schema_version`은 `SCHEMA_VERSION = 1`과 엄격히 같아야 읽힌다. 프로젝트 폴더에는 형식 기록이 없다. `Deck`과 `DeckMeta`는 모르는 필드를 읽을 때 버리고 저장할 때 지운다. 0.2.0(`v0.2.0` = `4f6a03a`) 대비 덱 계약의 차이는 `ReportType`의 값 6개 추가 하나뿐이다. 0.2.0 코드로 합성 덱을 열어 실측한 결과는 다음과 같다. `schema_version = 2`이고 유형이 기존 값이면 버전 안내 문구가 원인으로 붙는다. 유형이 새 값이면 `schema_version`과 관계없이 `report_type` 검증 오류만 나온다. 버전 검사가 필드 검증 뒤에 실행되기 때문이다. 세 경우 모두 0.2.0의 프로젝트 목록은 "deck.json 읽기 실패: 스냅샷 복구가 필요합니다"로 표시한다. 같은 실측에서 프로젝트 폴더의 `manifest.json`, `drafts/`와 자료 루트의 점으로 시작하는 파일은 0.2.0의 목록을 깨지 않았다.
6. 독립 앱과 웹 모드의 자료 폴더 기본값은 둘 다 `~/slidecaptain-projects`다. 독립 앱에는 단일 실행 잠금(`app.requestSingleInstanceLock`)이 없어 두 번 실행하면 두 번째 서비스가 뜬다. 웹 모드는 한 서비스에 브라우저 탭 여러 개가 붙을 수 있다. 서비스가 시작에 실패하면 `desktop_service.main()`은 영어 일반 문구를 stderr에 쓰고, `runtime.cjs`는 stderr를 버리며 `main.cjs`는 "앱을 시작하지 못했습니다"만 보인다.
7. 생성은 HTTP 요청 하나가 끝날 때까지 기다리는 동기 방식이다. 결과는 응답으로만 화면에 전달되고 서버에 남지 않는다. 생성 임대 `ai_connections.generation()`은 프로세스 메모리의 카운터라 요청 범위에서 잡고 놓으며, 바쁘면 대기 없이 거절한다. AI 동의 관문 `_require_ai_consent`는 생성 라우트 6곳에서 호출한다.
8. 독립 앱 브리지는 OpenAPI와 같은 경로 목록(`desktop/api-routes.json`)만 허용하고, CI가 `scripts/check_desktop_routes.py`로 일치를 검사한다. 요청 본문 상한은 20MB(`desktop/runtime.cjs`의 `MAX_FILE`)다.
9. 화면 테스트 환경에서는 `styles.css`를 읽을 수 없다. vitest의 `?raw` CSS import는 빈 문자열이고, `?raw`와 `node:fs`는 `tsc --noEmit`(화면 빌드)에서 TS2307로 실패하며, jsdom은 `var()`를 풀지 않는다. 컴포넌트 테스트는 `styles.css`를 불러오지 않는다.

## 5. D2a 태스크

### 모든 태스크의 공통 규칙

- TDD로 진행한다. 계획서의 시험은 **RED**(지금 코드에서 틀린 동작을 겨냥해 실패부터 확인하는 시험)와 **고정**(지금도 맞는 동작이 깨지지 않게 묶는 회귀 시험)으로 나눠 적는다.
- 새 라우트나 응답 모델 필드를 더하는 커밋은 같은 커밋에서 OpenAPI, 프런트 타입, 브리지 경로 목록(`check_desktop_routes.py --write`)을 재생성하고 desktop 테스트를 돌린다. 공용 모의 API(`frontend/src/test/fixtures.ts`)에 새 함수의 기본 성공 모의를 더한다.
- 상태 변경 라우트는 `X-Requested-With: SlideCaptain` 헤더 규약을 따른다.
- Windows 전용 분기의 RED는 macOS에서 실패부터 볼 수 없다. 그런 시험은 CI의 Windows 작업에서 처음 실패를 확인한다고 커밋에 적는다.
- 생성 텍스트와 문서에 엠대시와 중점을 쓰지 않는다.

### D2a-1 프로젝트 형식 기록과 이전

판정 기준은 manifest가 아니라 **덱 내용**이다. 0.2.0이 manifest를 고치지 않고 `deck.json`만 다시 쓰므로, manifest만 믿으면 두 파일이 어긋난다.

- 형식 정의: 형식 1은 0.2.0이 읽을 수 있는 덱이고, 형식 2는 그렇지 않은 덱이다. 판정 함수 `deck_format(deck)`는 지금 "`meta.report_type`이 `research`, `approval`, `strategy` 밖이면 2"다(사실 5). 이 앱이 읽을 수 있는 최대 형식은 2다. `SCHEMA_VERSION`은 1로 둔다. 실측대로 올려도 0.2.0의 표시가 나아지지 않기 때문이다. `models/deck.py`의 기존 주석("의미가 바뀌는 변경에는 스키마 버전 상향이 필요하다")은 "형식 판정은 `deck_format`과 manifest가 맡는다"로 고친다.
- 앱 버전은 판정에 쓰지 않는다. 이 브랜치의 `__version__`은 배포본과 같은 `0.2.0`이고 비교 규칙도 없다. manifest에는 진단용으로만 남긴다.
- manifest(`manifest.json`): 형식 이름, 현재 덱의 형식, 마지막으로 쓴 앱 버전(진단용), 이전 기록(시각, 이전 전 형식, 이후 형식, 이전 전 스냅샷 ID, 상태 `pending` 또는 `done`, 되돌림 항목)을 담는다. manifest의 형식은 항상 **현재 `deck.json`이 요구하는 형식**이다. 쓰기 때마다 덱 내용으로 다시 계산해 어긋나면 고친다. 읽기만 할 때는 만들거나 고치지 않는다.
- 강제 스냅샷: 디스크의 `deck.json`이 형식 1이고 새로 쓸 덱이 형식 2이면, 몇 번째 저장이든 화면의 스냅샷 요청과 관계없이 먼저 스냅샷을 남긴다. 0.2.0에서 되돌린 뒤 다시 새 유형으로 저장하는 경우도 여기에 걸린다.
- 쓰기 순서와 복구: ① 스냅샷을 임시 파일에 쓰고 교체한다(`_snapshot_current`를 원자적 쓰기로 바꾸고 스냅샷 ID를 돌려주게 한다) ② manifest에 `pending` 이전 기록을 쓴다 ③ `deck.json`을 교체한다 ④ manifest를 `done`으로 쓴다. 다음 쓰기에서 `pending`을 만나면 덱 내용으로 완료 여부를 판정해 manifest를 고친다. `create_project`는 덱을 쓴 뒤 manifest를 쓴다. 중단으로 manifest가 없으면 덱 내용으로 판정한다.
- 더 새 형식: manifest의 형식이 2보다 크면 이 앱은 그 프로젝트를 열지 않는다. 판정은 덱 검증보다 먼저 하고, 프로젝트 목록 상태를 `newer_format`으로 둔다(`ProjectInfo.status`에 값 추가). 모든 프로젝트 접근의 공통 진입(`_project_dir`, `_project_dir_any`)이 새 예외 `ProjectFormatTooNew`를 내므로 읽기, 쓰기, 복원, 내보내기가 모두 막힌다. 예외 매핑은 `StorageError`보다 앞에 두고 409와 `code: "project_format_too_new"`를 돌려준다. 이렇게 하면 이 앱이 모르는 필드를 버린 화면과 PPTX가 나오지 않는다.
- 이후 형식 변경의 강제 장치: 덱 JSON 스키마의 해시를 형식 번호와 함께 고정하는 시험을 둔다. 스키마가 바뀌었는데 `deck_format`과 최대 형식을 갱신하지 않으면 CI가 실패한다(`test_openapi.py`와 같은 방식).
- 스냅샷 목록 표시: `SnapshotInfo`에 `kind`(`snapshot` 또는 `pre_migration`)를 더해 이전 전 복사본을 구별한다. 복구 화면은 이전 전 복사본에 "새 형식으로 바꾸기 전" 표시를 붙인다.
- 0.2.0 왕복 자동 시험: CI는 이미 `fetch-depth: 0`이라 `v0.2.0` 태그를 쓸 수 있다. `git archive v0.2.0 backend/slidecaptain`을 임시 폴더에 풀고 별도 `PYTHONPATH`의 하위 프로세스로 0.2.0 코드를 실행하는 시험(`backend/tests/test_legacy_compat.py`)을 둔다. 태그가 없으면 건너뛰지 않고 실패한다.
- RED: 형식 1 덱을 형식 2로 바꾸는 저장의 강제 스냅샷과 `done` 이전 기록. 형식 2 저장 뒤 0.2.0 방식으로 형식 1 덱을 직접 써 넣고 다시 형식 2로 저장하면 다시 강제 스냅샷이 남는다. manifest 없는 폴더에 `weekly` 덱이 있으면 첫 쓰기의 manifest 형식이 2다. ②와 ③, ③과 ④ 사이에 예외를 주입한 뒤 다음 쓰기가 manifest를 바로잡는다. `newer_format` 프로젝트의 목록 상태, 열기 거절과 덱 불변. 스키마 해시 시험. 0.2.0 왕복(새 값 없이 저장한 덱을 0.2.0이 연다, 형식 2 덱은 0.2.0에서 `needs_recovery`, 0.2.0의 `restore_snapshot`으로 이전 전 스냅샷을 복원하면 열린다).
- 고정: manifest 없는 폴더를 읽어도 manifest가 생기지 않는다. 0.2.0 형식 덱을 그대로 읽는다. 새 값 없이 저장하면 형식 1로 남는다.

### D2a-2 충돌 시 미저장본과 생성 결과 보존

보존 대상은 **412 충돌로 저장하지 못한 내용**과 **저장하지 못한 AI 생성 결과**다. 412가 아닌 저장 실패(서비스 무응답, 디스크 오류, 덱 검증 오류)는 지금처럼 화면에 변경을 남기고 "다시 저장"으로 다룬다. 이 경우에는 같은 서버로 보내는 보존도 대개 함께 실패하기 때문이다.

- 저장 형식: `drafts/draft-<시각>.json`에 봉투 `{base_etag, saved_at, reason, source, deck}`를 원자적으로 쓴다. `reason`은 `conflict` 또는 `generation_unsaved`, `source`는 `editor`, `structure_approval` 등이다. 덱은 검증하지 않은 원문 JSON으로 보존하고 복원할 때 검증한다. 검증에 실패한 덱도 사용자 내용이라 버리지 않기 위해서다. 본문 상한은 브리지와 같은 20MB이고(사실 8), 넘으면 413이다. 파일 이름은 서버가 만들고 같은 시각 충돌은 번호를 붙인다. 같은 내용 해시의 재요청은 새 파일을 만들지 않는다.
- 개수 상한은 두지 않는다. 상한이 차면 보존을 거절해 사용자가 충돌 상태에서 빠져나올 수 없게 되기 때문이다. 대신 사용자가 고른 미저장본을 지우는 라우트를 둔다. 자동 삭제는 하지 않는다.
- 라우트: `POST /api/projects/{name}/drafts`, `GET .../drafts`, `POST .../drafts/{id}/restore`(ETag 검사, 복원 직전 현재 덱을 스냅샷으로 남김), `DELETE .../drafts/{id}`. 더 새 형식 프로젝트에서는 D2a-1의 공통 진입이 거절한다.
- 편집 화면: 412를 받으면 충돌을 표시하고 자동 저장을 멈춘다(현재 동작). 보존은 사용자가 "서버 내용으로 되돌리기"를 누른 시점, 교체 직전에 한 번 한다. 그 순간의 화면 덱이 마지막 저장본과 다를 때만 보낸다. 따라서 충돌 뒤에 계속한 편집도 보존되고, 보존할 것이 없는 충돌(도식 연결 확인의 412 등)은 요청하지 않는다. 되돌리기가 진행되는 동안 편집 영역과 버튼을 잠근다.
- 보존이 실패하면 교체하지 않고 두 가지를 제시한다. 하나는 "변경 내용 복사"(기존 도식 초안 백업과 같은 방식)이고, 다른 하나는 "보존하지 못했습니다. 그래도 서버 내용으로 되돌리면 이 변경은 사라집니다" 확인 뒤 교체다. 사용자가 충돌 상태에 갇히지 않는다.
- 구조안 승인 루프: 장 생성 결과의 저장이 412나 다른 오류로 끝나면, 그 결과를 붙인 덱을 `reason: generation_unsaved`로 보존한다. 보존도 실패하면 결과를 복사할 수 있게 화면에 남긴다. 승인 반영 저장의 412도 같은 규칙을 따른다.
- 프로젝트 배너의 "서버 내용 다시 읽기"(`ProjectView.reloadDeck`): 자료 화면과 구조안 화면에 미저장 입력이 있으면 "저장하지 않은 입력이 사라집니다" 확인을 먼저 받는다. 이 입력은 덱 전체가 아니라 화면 폼이라 이번 단위에서는 미저장본으로 보존하지 않는다(이월). 구조안 초안의 미저장 신호를 부모에 올려 창 닫기 경고에 포함한다.
- 안내: 보존한 뒤에는 제품 설계 5절 D의 세 요소로 알린다. 무슨 일이 생겼는지(다른 곳에서 먼저 저장), 무엇이 보존됐는지(보존한 변경의 위치), 지금 할 수 있는 일(복구 화면에서 보기, 복원, 삭제)이다.
- 복구 화면: 미저장본은 스냅샷과 섞지 않고 별도 목록 "충돌로 보존한 변경"에 둔다. 항목마다 보존 시각, 사유, 출처 화면을 보인다. 복원 버튼에는 "복원하면 지금 저장본(다른 곳의 변경 포함)은 복원 직전 시점의 스냅샷으로 남습니다"를 함께 보인다.
- RED: 412 뒤 되돌리기를 하면 그때까지의 편집(충돌 뒤 편집 포함)이 미저장본으로 남는다. 미저장 변경이 없는 충돌에서는 보존 요청을 보내지 않는다. 보존 실패 시 교체하지 않고 복사와 확인 뒤 교체를 제시한다. 확인 뒤에는 교체된다. 되돌리기 연속 클릭이 미저장본을 하나만 만든다. 구조안 승인 루프에서 장 결과 저장이 412로 끝나면 생성 결과가 미저장본으로 남는다. 배너 다시 읽기가 미저장 폼 입력이 있을 때 확인을 받는다. 구조안 초안 편집이 창 닫기 경고를 켠다. 검증에 실패하는 덱도 보존되고 복원 때 거절된다. 복원이 ETag 충돌을 존중하고 직전 스냅샷을 남긴다.
- 갱신할 기존 시험: `state/useDeckEditor.save.test.tsx`(되돌리기), `screens/EditorScreen.test.tsx`(충돌 두 건), `editor/diagramAuthoringIntegration.test.tsx`(보존할 것이 없는 충돌, 요청 없음으로 유지), `screens/StructureScreen*.test.tsx`(승인 루프 저장 실패). 기존 단언을 지우지 않고 새 흐름 기준으로 바꾼다.

### D2a-3 자료 폴더 단일 서비스 잠금과 자료 폴더 표시

목표는 **새 버전끼리** 같은 자료 폴더를 동시에 쓰지 않게 하는 것이다. 0.2.0은 잠금을 모르므로 보호하지 못한다(8절).

- 잠금: 서비스 시작 진입(`desktop_service.serve`와 웹 모드 `serve`, 자료 폴더를 만든 직후, 다른 어떤 쓰기보다 먼저)에서 자료 루트의 `.slidecaptain-service.lock`에 OS 파일 잠금을 건다. `export/locking.py`의 OS별 잠금 함수(POSIX `flock`, Windows `msvcrt.locking`의 오프셋 0 고정과 비대기 방식)를 공용 모듈로 옮겨 재사용한다. 잠금 파일은 지우지 않는다. 잠금 fd는 자식에게 상속되지 않음을 단언한다. `FileProjectStore`와 `create_app`에는 잠금을 두지 않는다. 백엔드 시험 다수가 같은 폴더에 저장소를 여러 번 만들기 때문이다. 제출 관문 CLI와 `export` CLI는 잠금 밖의 예외로 두고, 내보내기는 기존 내보내기 잠금으로 직렬화한다.
- 재시도: 잠금을 얻지 못하면 5초 동안 재시도한다. 근거는 D1 macOS 실측(앱 본체 강제 종료 뒤 서비스가 약 2초 안에 스스로 종료)과 기존 내보내기 잠금의 재시도 시간 5초다. Windows는 종료한 프로세스의 잠금 해제 시점을 보장하지 않는다(Microsoft `LockFile` 문서)는 점도 이 재시도가 흡수한다.
- 진단 정보: 잠금 바이트 범위 밖의 별도 파일 `.slidecaptain-service.json`에 PID, 시작 시각, 제품, 버전을 쓴다. Windows 잠금은 잠근 범위를 다른 프로세스가 읽지 못하게 하기 때문이다. 오류 문구는 이 정보를 근거로 "다른 SlideCaptain(시작 시각)이 이 자료 폴더를 사용 중입니다"라고 보인다.
- 잠금 미지원: 잠금 호출이 미지원 오류(`ENOTSUP`, `ENOLCK`, `EOPNOTSUPP` 등)를 내면 시작을 거절하지 않고 잠금 없이 실행하며 화면에 경고를 보인다. 거절하면 그 폴더를 쓰던 사용자가 업데이트 뒤 앱을 켜지 못하기 때문이다. iCloud 같은 동기화 폴더는 잠금이 성공해도 다른 기기와 공유되지 않으며, 이 앱은 그 경우를 감지하지 못한다.
- 오류 전달 통로: 서비스는 준비 신호와 같은 형식의 오류 신호 `{"event":"error","product":"slidecaptain","instance":...,"code":"data_dir_in_use"}` 한 줄을 쓰고 정해진 종료 코드로 끝난다. `runtime.cjs`는 준비 신호처럼 제품과 실행 식별자를 검사한 뒤 코드별 문구로 바꾸고, 60초 시간 초과를 기다리지 않고 즉시 실패를 알린다. `main.cjs`는 그 문구를 대화상자에 보인다. 웹 실행 스크립트(`SlideCaptain실행.command`, `.bat`, 배포본 실행기)도 같은 문구를 보인다.
- 독립 앱 단일 실행: `app.requestSingleInstanceLock()`을 쓰고, 두 번째 실행은 기존 창을 앞으로 가져온 뒤 끝난다. 서비스 잠금은 그 아래의 방어선이다.
- 웹 모드의 여러 탭: 같은 서비스 안의 탭 여러 개는 막지 않는다. 412 충돌 감지와 D2a-2의 보존으로 다룬다.
- 자료 폴더 표시(기술 설계 3절의 "최초 실행에서 발견한 경로 제시"): `/api/status`에 자료 폴더 경로와 프로젝트 수를 더하고, 프로젝트 목록 화면 아래에 "자료 폴더: 경로(프로젝트 N개)"를 보인다. 폴더를 바꾸는 화면은 D6이다.
- RED: 같은 폴더로 두 번째 서비스를 시작하면 오류 신호와 종료 코드로 끝나고 첫 서비스는 계속 응답한다. 다른 폴더는 동시 실행 가능하다. 첫 서비스 종료와 강제 종료 뒤 재시도 시간 안에 두 번째 시작이 성공한다. 자식 프로세스를 남긴 채 서비스를 강제 종료해도 재시작이 성공한다. 잠금 함수 주입으로 미지원 오류를 흉내 내면 경고와 함께 시작한다(실제 네트워크 폴더는 미확인). `runtime.cjs`가 오류 신호를 즉시 사용자 문구로 바꾼다. 독립 앱 두 번째 실행이 기존 창으로 간다. `/api/status`가 자료 폴더 경로와 프로젝트 수를 준다. desktop smoke(`smoke-service.cjs`)에 같은 폴더 두 번째 서비스 거절과 첫 서비스 생존 검사를 더한다.

### D2a-4 디자인 토큰

- 토큰: 제품 설계 4절의 색 9개에 더해 사실 1의 기존 색을 옮길 토큰을 정의한다. 옅은 강조 배경, 컴포넌트 경계(3:1 이상), 장식 구분선, 링크, 초점선, 반투명 덮개, 그림자다. 크기 토큰(글자, 입력과 버튼 높이)은 이번에 정의하지 않고 D3에서 적용과 함께 정의한다. 여백과 모서리는 이번에 쓰는 것(상태 표시 컴포넌트)만 정의한다.
- 매핑표: 첫 커밋에서 기존 30종과 이름 색, rgba를 토큰으로 옮기는 표를 태스크 기록에 남긴다. 합쳐서 시각 구분이 사라지는 곳(녹색 계열 표 머리와 청색 계열 배경 등)은 표에 적고 수용 확인 대상으로 둔다. 미리보기의 선택과 경고 테두리는 화면 토큰(주 행동, 오류)으로 바꾼다.
- 미리보기 격리: `.preview-canvas`는 화면 토큰을 물려받지 않는다. 캔버스 루트에 프리셋 글자색을 명시한다(사실 1의 표 칸 상속).
- 초점: `:focus-visible` 규칙을 새로 둔다(기존 규칙 없음). 초점선은 2px 이상이고 배경과 패널 대비 3:1 이상이다. `prefers-reduced-motion`에서는 회전 표시를 멈춘다.
- 자료 화면의 성공 안내를 `role="alert"` 문단에서 분리해 `role="status"`로 옮긴다. 전역 alert 색 규칙은 오류 토큰으로 바꾼다.
- 검사 수단: 화면 테스트 안에서는 CSS를 읽을 수 없으므로(사실 9) Node 스크립트 `frontend/scripts/check-design-tokens.mjs`로 검사하고 `npm run check:tokens`와 CI 단계에 넣는다. 의존성은 더하지 않는다. 스크립트는 (1) 대비 계산 함수의 자기 검사(흑백 21:1, 같은 색 1:1), (2) 본문, 보조, 상태 색의 배경과 패널 양쪽 대비 4.5:1 이상, (3) 초점선과 컴포넌트 경계의 3:1 이상, (4) `:root` 토큰 블록 밖의 hex, `rgb()`, `rgba()`, 이름 색 금지를 검사한다.
- RED: 미리보기 표 칸의 계산 글자색이 프리셋 글자색과 같다(jsdom은 인라인 색을 계산값으로 읽는다). 자료 화면의 저장 성공 안내가 `alert`가 아니다. 토큰 검사 스크립트가 현재 `styles.css`에서 실패한다.

### D2a-5 상태 표시 컴포넌트

- 상태 종류와 문구: 아래 표로 확정한다. 화면 문구는 제품 설계 4절의 표시 열을 따른다. 아이콘마다 접근 가능한 이름을 둔다.

| 내부 이름 | 화면 문구 | 쓰임 |
|---|---|---|
| `not_started` | 시작 전 | 단계 |
| `unsaved` | 변경사항 있음 | 저장 |
| `saving` | 저장 중 | 저장 |
| `saved` | 저장됨 | 저장 |
| `save_failed` | 저장하지 못했습니다. 변경은 이 화면에 남아 있습니다 | 저장 |
| `conflict` | 다른 곳에서 먼저 저장했습니다 | 저장 |
| `ready` | 준비됨 | 단계 |
| `needs_review` | 확인 필요 | 단계 |
| `failed` | 실행 실패 | 작업 |
| `running` | 생성 중 | 작업 |

- 매핑: `useDeckEditor`의 `SaveState` 유니온은 유지한다. 저장 흐름 시험 다수가 그 문자열을 단언하기 때문이다. 표시 매핑의 입력은 `(saveState, conflict)`이고, "저장 실패"는 `conflict`에 따라 `save_failed`와 `conflict`로 나뉜다. `conflict`는 "서버 내용으로 되돌리기"만 보이고 재시도를 보이지 않는다. `running`은 호출자가 주는 속성으로 받는다(D2b에서 원천이 원장으로 바뀐다).
- 보조 표시: 보존한 미저장본이 있으면 저장 상태 옆에 "보존한 변경 N건"을 보이고 복구 화면으로 이어진다.
- 보조기기: 안정된 전이(저장됨, 저장하지 못함, 충돌)만 시각적으로 숨긴 알림 문단으로 알린다. 변경사항 있음과 저장 중은 시각 표시만 바꾼다. 실패는 기존 `alert` 하나로만 알린다.
- 위치: 편집 화면의 저장 상태를 오른쪽 패널에서 가운데 영역 위로 옮긴다. 좁은 창(1000px 이하)에서 세 영역이 세로로 쌓여도 첫 화면에 보이게 하기 위해서다. 프로젝트 상단 머리로 옮기는 일은 D3다.
- 시험: 상태 10종의 문구와 아이콘 접근 이름이 모두 다르다(RED). 매핑 5가지(저장됨, 저장 대기, 저장 중, 저장 실패, 저장 실패와 충돌)(RED). 충돌 표시는 재시도를 보이지 않는다(RED). 저장 대기와 저장 중은 알림 문단을 바꾸지 않는다(RED). "저장됨"이 서버 응답 전에는 표시되지 않는다(고정). 색 없이 구별되는지는 jsdom으로 검사할 수 없으므로 7절의 화면 확인에서 본다.
- 갱신할 기존 시험: `screens/EditorScreen.stale.test.tsx`, `editor/projectDiagrams.test.tsx`의 "저장 상태: 저장됨" 문구 단언을 컴포넌트 기준 단언으로 바꾼다.

### D2a-6 단계 준비 모델 API

이번 단위는 API, 타입, 단위 시험까지 만든다. 화면 연결은 D3다. 기존 탭 4개와 다섯 단계가 대응하지 않아(보고 목적과 자료가 한 탭, 검토의 세 하위 상태가 세 곳에 흩어짐) 지금 붙이면 의미가 통하지 않고 D3에서 버려지기 때문이다.

- 라우트: `GET /api/projects/{name}/progress`는 항상 200으로 `{project_status: "ok" | "needs_recovery" | "newer_format", stages: [...] | null, jobs: null}`을 돌려준다. `jobs`는 D2b가 채운다.
- 단계별 규칙(현재 저장 계약으로 판정할 수 있는 것만 판정하고, 나머지는 사유 코드로 남긴다):
  - 보고 목적: 기본값을 사용자 확정으로 표시하지 않는다. 유형의 명시 선택 기록이 없으므로(D3) 항상 `needs_review`와 사유 `report_type_unconfirmed`다. 제목이 비면 `not_started`다.
  - 자료: 자료 0개면 `not_started`, 1개 이상이고 모두 읽히며 합계 상한 이내면 `ready`, 읽기 실패나 상한 초과면 `needs_review`다. 부분 추출 경고와 포함 범위는 저장되지 않으므로 사유 `extraction_review_unavailable`로 남긴다(D5).
  - 구성: 장 0개면 `not_started`, 구성 계획이 현재 입력과 맞으면 `ready`, 낡았으면 `needs_review`(`stale_story_plan`), 계획 없이 장만 있으면 `needs_review`(`plan_missing`)다. 낡음 판정의 fingerprint는 제목, 피보고자, 보고 유형, 장 제목과 결론도 포함하므로 그 편집도 구성을 확인 필요로 만든다. 이 계약은 생성 관문이 쓰므로 바꾸지 않고, 사용자에게 혼란인지는 D3에서 판단한다.
  - 편집: 작성된 장 수와 전체 장 수를 돌려준다. "변경이 저장됨"은 화면의 저장 상태가 보완한다. 장별 생성 실패는 D2b다.
  - 검토와 내보내기: 자동 검사, 사람 검토, 파일 저장을 따로 돌려준다. 최신 내보내기 기록 1건만 읽고 전체 이력의 PPTX 해시를 다시 계산하지 않는다.
- 시험(RED): 단계마다 경계 사례. 자료 변경과 보고 유형 변경이 구성과 검토만 확인 필요로 바꾼다. 제목 변경과 장 제목 편집이 구성을 확인 필요로 만든다(현재 fingerprint 규칙의 고정). 계획 없는 장. 복구 필요와 더 새 형식 프로젝트의 응답. 최신 기록만 읽는지(이력 여러 건에서 해시 함수 호출 횟수).

## 6. D2b 계약 (상세 계획은 D2a 뒤)

D2b 계획서는 아래 계약을 출발점으로 쓰고 D2a에서 확정된 인터페이스를 반영한다. 계약의 출처는 기술 설계 6절과 제품 설계 7절이다.

- 저장소: 원장은 기술 설계 6절대로 트랜잭션 가능한 앱 저장소(SQLite)에 둔다. 문서의 정본은 기존 프로젝트 파일이다.
- 상태 전이: 대기, 실행, 검증, 성공 / 취소 요청, 취소 또는 중단 / 실패, 재시작 시 중단 또는 원격 완료 불명.
- 임대와 관문: 생성 임대는 요청이 아니라 작업 수명에 묶는다. 대기 작업은 실행 직전에 임대, 선택, 동의를 다시 검사한다. 재시작 시 실행 중이던 작업은 임대 없이 중단으로 바꾼다. 재시작 조정은 D2a-3의 잠금을 쥔 서비스만 한다. 기존 관문(`X-AI-Consent` 428, `_record_success`, `_append_usage`, 도식 장 생성 거절, 형식 재시도 1회 상한)을 우회하지 않는다.
- 고정할 입력: D2b는 선택 식별자(제공자와 모델), 덱 ETag, 자료 fingerprint를 시작 시점에 고정한다. 계정 프로필, Effort, 동의 리비전 필드는 비워 둔 채 미리 두고 D4가 원장 형식을 올려 채운다.
- 행동 규칙: (1) 같은 프로젝트의 충돌 작업은 직렬화한다. (2) 요청 ID로 중복 클릭을 병합한다. (3) 대기 작업을 계정 변경으로 조용히 재바인딩하지 않는다. (4) 원격 완료가 불명확하면 표시만 하고, 사용자가 다시 생성할 때만 새로 호출한다(자동 재호출 금지). (5) 원격 호출이 끝났고 후보가 저장됐으면 재호출 없이 검증과 적용을 재개한다. (6) 성공한 장 결과와 실패한 장 결과를 구분한다. (7) 취소 요청은 완료와 다르며 이미 보낸 요청이 취소됐다고 추정하지 않는다. (8) 적용은 서버가 현재 ETag와 입력 fingerprint를 다시 비교하고, 다르면 "이전 입력 기준 후보"로 남기며 "후보 보기 / 현재 입력으로 다시 생성"을 제공한다.
- 필수 RED 시험(기술 설계 6절의 다섯 가지와 하나): 저장 중 종료, 강제 종료 직전 완료(재시작 뒤 재호출 0회, 후보 보존 또는 완료 불명 표시), 취소 응답 지연, 계정 만료, 자료 수정과 결과 도착의 경합, 늦게 도착한 성공 응답이 새 편집을 덮지 않음.
- 브리지: 독립 앱 브리지의 동시 요청 상한(128)과 요청 취소는 작업 취소와 분리한다. 조회는 상한 안에서 동작해야 한다.
- 보존과의 관계: D2a-2의 미저장본과 D2b의 이전 입력 기준 후보는 같은 복구 화면 목록에 보인다. 후보는 원장에, 미저장본은 프로젝트 `drafts/`에 둔다.
- 화면: 구성 화면의 장별 진행, D2a-5의 `running`, D2a-6의 `jobs`를 원장에 연결한다. 세션을 넘어 남는 "6장 중 1장 실패" 표시가 여기서 생긴다.

## 7. 수용 기준 (D2a)

- 자동 검사: 백엔드 전체, 프런트 전체, desktop 테스트, 토큰 검사 스크립트, 화면 빌드, OpenAPI와 타입과 브리지 경로 재생성 무변경, 0.2.0 왕복 시험, 공개 저장소 감사, diff 공백 검사를 통과한다. CI의 macOS와 Windows 작업이 모두 성공한다.
- 화면 확인(웹 모드 Chrome, 합성 프로젝트): 상태 표시(변경사항 있음, 저장 중, 저장됨, 저장하지 못함, 충돌, 보존한 변경), 충돌 뒤 되돌리기와 보존 안내, 보존 실패 시 복사와 확인 뒤 교체, 복구 화면의 미저장본 목록과 복원, 구조안 승인 루프의 생성 결과 보존(모의 제공자). 폭은 1440px, 1024px, 512px이고, 200% 확대에서 저장 상태가 첫 화면에 보이는지, 키보드 Tab으로 되돌리기와 다시 저장 버튼에 도달하고 초점선이 보이는지, 움직임 감소 설정에서 회전 표시가 멈추는지, 회색조 캡처에서 상태가 구별되는지 확인한다. 증거는 화면 캡처와 확인 목록으로 남긴다.
- 이 Mac의 패키지 독립 앱 확인: 합성 자료만 담은 별도 `SLIDECAPTAIN_DATA_DIR`로만 한다. 사용자의 `~/slidecaptain-projects`에서는 새 앱을 실행하지 않고 항목 수를 전후로 대조한다. 확인 항목은 두 번째 실행이 기존 창으로 가는지, 같은 폴더의 두 번째 서비스(웹 모드)가 오류 문구로 끝나는지, manifest 첫 쓰기와 강제 스냅샷이다. 증거는 로그, 프로세스 목록, 파일 목록이다. 이 셸에는 화면 기록 권한이 없으므로 창 내용은 사람이 확인했는지를 따로 적는다.
- Windows: 잠금과 재실행 경합은 CI 시험으로 확인한다. Windows 실기기 확인을 CI로 갈음할지는 사용자 결정이며, 결정 전까지 D2a-3은 조건부다.
- 실제 사용자 자료의 첫 형식 이전은 이 단위에서 하지 않는다. 별도 사용자 결정 항목이다.

- 태스크마다 독립 리뷰를 받고, D2a 묶음 끝에 묶음 최종 리뷰를 받는다.

3. 로컬 디스크에서 POSIX `flock`은 프로세스 종료 시 즉시 풀린다(2026-10-08 실험). Windows는 해제 시점을 보장하지 않으므로 5초 재시도로 흡수한다. 그 시간 안에 풀리는지는 Windows CI와 실기기에서 확인한다. 동기화 폴더와 네트워크 드라이브에서는 다른 기기와의 배제를 보장하지 않는다. 독립 서비스는 `--onedir`로 빌드되어 잠금을 쥐는 프로세스가 Electron이 띄운 서비스 자신이다. 빌드 방식을 바꾸면 다시 확인한다.
4. 서비스가 먼저 죽은 상태의 렌더러 편집과, 창을 닫는 순간 진행 중이던 저장의 보존은 다루지 않는다(「상위 문서와 다르게 정하는 것」).
5. 단계 준비 규칙은 제품 설계 4절을 현재 저장 계약에 맞춘 것이다. 사용자가 실제로 현재 상태를 더 잘 구별하는지는 D6의 사용성 검증 전까지 미확인이다.
6. 0.2.0 사용자가 새 앱에서 처음부터 새 유형으로 만든 프로젝트를 열면, 되돌릴 이전 전 스냅샷이 없거나 빈 기본 덱이다. 릴리스 안내에 "새 앱에서 만든 새 유형 프로젝트는 0.2.0에서 열 수 없습니다"와 "옮겨 온 프로젝트는 '새 형식으로 바꾸기 전' 스냅샷(시각은 새 앱의 복구 화면에 표시)을 고르세요"를 나눠 적는다.

## 상위 문서와 다르게 정하는 것

1. 기술 설계 7절의 D2 한 단계를 D2a와 D2b로 나누고, D2 관문 통과는 D2b 완료 뒤로 둔다(2절).
2. 제품 설계 7절의 "동일 프로젝트 편집창 한 개 제한"은 독립 앱의 단일 실행 잠금과 새 버전끼리의 자료 폴더 잠금으로 구현한다. 웹 모드의 여러 탭은 제한하지 않고 412 충돌과 미저장본 보존으로 다룬다. 0.2.0과의 동시 실행은 막지 못한다(8절 가정 2).
3. 제품 설계 7절의 "저장 중 이탈과 종료 시 완료를 기다리거나 복구 가능한 로컬 임시본을 남긴다"는 이번 단위에서 구현하지 않는다. 렌더러는 파일 시스템 접근이 없고 preload IPC를 넓혀야 하기 때문이다. 서버가 살아 있는 412 충돌의 보존만 한다. D2b 계획에서 다시 판단한다.
4. 제품 설계 7절의 "충돌을 표시하고 양쪽 내용을 보존한다"는 편집 화면과 구조안 생성 결과에 적용한다. 자료 화면과 구조안 화면의 폼 입력은 덱이 아니어서 이번에는 확인 뒤 버리는 방식으로 두고 이월한다.
5. 제품 설계 4절의 디자인 토큰 가운데 크기 토큰과 버튼 계층은 D3에서 정의하고 적용한다.
6. 제품 설계 4절의 보고 목적 준비 조건("최소 입력이 저장된 상태")은 명시 선택 기록이 없는 동안 항상 확인 필요로 표시한다.
