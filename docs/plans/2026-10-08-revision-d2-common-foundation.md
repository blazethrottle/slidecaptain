# 개정판 D2 공통 기반 계획

작성: 2026-10-08 (서울 기준). 사용자가 D1 macOS 확인 보고 뒤 "D2 계획서 착수"(선택지 A)를 승인했다. 승인 범위는 이 계획서의 작성과 독립 적대 리뷰, 반영과 확정 커밋까지다. 구현 착수는 확정 뒤 별도로 결정한다. 상위 문서는 [기술 설계 7절](../architecture/2026-10-02-desktop-revision.md#7-개발-순서와-완료-관문)의 D2 행(디자인 토큰과 컴포넌트, 프로젝트 상태와 저장, 작업 원장, 데이터 이전. 관련 요구 R01, R02, R11), [제품 설계 4절과 7절](../design/2026-10-02-revision-product-ux.md#4-상태와-시각-규칙), [개정 계획](2026-10-02-windows-feedback-revision.md)이다. 이 계획서는 상위 문서를 재정의하지 않는다. 상위 문서와 다르게 정하는 부분은 아래 「상위 문서와 다르게 정하는 것」에 이유와 함께 모은다.

## 1. 이번 단위의 목표

개정판의 모든 화면이 공유할 기반을 먼저 만든다. 사용자가 저장 여부, 단계별 준비 상태, 실패와 보존된 내용을 한눈에 구별하게 하고(R01), 앱 교체와 다른 버전이 같은 자료를 만나도 사용자 프로젝트를 잃지 않게 하며(R02의 데이터 보존 부분), 생성이 끊기거나 실패해도 입력과 결과 후보를 잃지 않게 한다(R11의 공통 부분).

## 2. 분할 결정: D2a와 D2b

D2를 두 묶음으로 나눈다. 단계 5B의 디자인 체계 묶음을 DA와 DB로 나눈 선례와 같다.

| 묶음 | 내용 | 이 계획서의 상세 수준 |
|---|---|---|
| D2a 상태와 저장 기반 | 디자인 토큰, 상태 표시 컴포넌트, 단계 준비 모델, 프로젝트 형식 기록과 이전, 충돌과 실패 시 미저장본 보존, 자료 폴더 단일 서비스 잠금 | 태스크와 RED 테스트까지 |
| D2b 작업 원장 | 생성 작업의 원장, 비동기 생성 API, 재시작 조정, 기존 생성 라우트 6개의 이전 | 계약 수준. 상세 태스크는 D2a 완료 뒤 실제 인터페이스를 근거로 별도 계획서에 쓴다(로드맵 원칙) |

분할 이유: 작업 원장은 생성 API를 동기 요청에서 작업 시작과 조회로 바꾸는 일이다. 생성 임대를 쓰는 라우트 6개(구조안, 장 생성, 축약, 도식, 재작성, 수리)와 그 화면 호출자, AI 동의 관문 7곳, 사용량 기록이 모두 바뀐다. D2a의 상태 표시와 저장 보강은 이 변경 없이 독립적으로 검증할 수 있고, D2b가 쓸 상태 표시 컴포넌트와 형식 기록을 먼저 제공한다.

반론(리뷰에서 판정할 것): 실패와 중단 복구는 사용자가 Windows 첫 사용에서 가장 크게 겪은 문제(R11)이고, 단계 준비 모델의 "6장 중 1장 실패" 표시는 원장 없이 만들 수 없다. 그래서 D2b를 먼저 하거나 D2a와 함께 해야 한다는 주장이 가능하다. 이 계획은 D2a를 먼저 하되, 설계 7절의 D2 완료 관문("변경, 저장, 충돌, 중단 복구 상태를 모의 서버와 실제 저장으로 검증")은 **D2b가 끝나야 통과**로 기록한다. D2a만 끝난 상태를 D2 완료로 표시하지 않는다.

## 3. 범위 밖

- 다섯 작업 단계의 왼쪽 내비게이션과 화면 재배치, 새 보고 유형 화면, IR 저장 enum, 원하는 결과 네 가지(D3)
- 상세 AI 사용량 문구 제거(R12, D3). 이번 단위는 사용량 기록 파일을 바꾸지 않는다
- 계정별 영속 동의(R14), 계정 프로필, 모델과 Effort(D4). 기존 `X-AI-Consent` 관문과 탭 단위 동의는 그대로 둔다
- 캔버스 직접 수정의 저장(R16, D3)
- 문서 추출 확장, 폴더 가져오기, 긴 텍스트 입력(D5)
- 설치본, 서명과 공증, 업데이트(D6)
- 실제 AI 호출. 이번 단위의 AI 호출은 0회이고 생성 경로는 기존 모의 제공자로 검증한다
- main 머지와 릴리스

D1의 남은 관문(Windows 실기기 독립 앱 실행, 두 OS의 실제 로그인과 두 계정 전환)은 D2를 막지 않는다. D2a는 OS 전용 기능 가운데 파일 잠금 하나만 쓰며(D2a-6), 그 동작은 양 OS CI에서 검사한다.

## 4. 현재 코드에서 확인한 사실 (2026-10-08, `3bb22f3`)

1. `frontend/src/styles.css`(177줄)에는 CSS 변수가 0개다. 색은 hex를 직접 쓴다(`#1F4E79`, `#B00020`, `#4A5560`, `#d5dde5` 등). 제품 설계 4절의 토큰 초안(`#244C83`, `#B42318`, `#526174`, `#D9E0E7` 등)과 값이 다르다. 화면 코드(`screens`, `editor`)의 hex 2개는 `editor/Preview.tsx`의 슬라이드 미리보기 색이라 화면 토큰 대상이 아니다.
2. 저장 상태는 `frontend/src/state/useDeckEditor.ts`의 `SaveState = "저장됨" | "저장 대기" | "저장 중" | "저장 실패"`이고, 테스트가 이 문자열을 직접 단언한다. 화면 표시는 `EditorScreen.tsx`의 `<p>저장 상태: {editor.saveState}</p>` 한 줄이다. 자료 화면은 별도의 미저장 표시를 쓴다.
3. 충돌(412)이 나면 자동 저장을 멈추고 `reloadFromServer`가 서버 덱으로 교체한다. 이때 화면의 미저장 편집은 사라진다. 제품 설계 7절의 "충돌을 표시하고 양쪽 내용을 보존한다"는 아직 충족하지 않는다.
4. `backend/slidecaptain/storage/file_store.py`는 `deck.json` 한 파일을 원자적으로 쓰고 SHA-256을 ETag로 쓴다. 덱 저장만 ETag로 보호하고, 자료 쓰기, 업로드, 사용량 기록, 스냅샷은 같은 프로세스 안의 잠금(`threading.RLock`)만 쓴다. 주석이 이 범위를 명시한다.
5. `Deck.schema_version`은 `SCHEMA_VERSION = 1`과 엄격히 같아야 읽힌다. 프로젝트 폴더에는 형식 버전이나 이전 기록을 담은 파일이 없다. 2026-10-08 0.2.0 코드(`4f6a03a`)로 합성 덱을 열어 실측한 결과는 다음과 같다. `schema_version = 2`이고 유형이 기존 값이면 버전 안내 문구가 원인으로 붙는다. 유형이 새 값(`weekly`)이면 `schema_version`이 1이든 2이든 `report_type` 검증 오류만 나온다. 버전 검사는 필드 검증이 통과한 뒤에 실행되기 때문이다. 세 경우 모두 0.2.0의 프로젝트 목록은 그 프로젝트를 "deck.json 읽기 실패: 스냅샷 복구가 필요합니다"로 표시한다. 즉 0.2.0 사용자는 새 형식 프로젝트를 손상된 프로젝트로 보고 옛 스냅샷 복원을 권유받는다. 배포된 0.2.0의 이 동작은 새 버전에서 바꿀 수 없다.
6. 독립 앱(`desktop/main.cjs`)의 자료 폴더 기본값은 웹 모드와 같은 `~/slidecaptain-projects`다. 독립 앱과 `SlideCaptain실행.command`의 웹 서버를 동시에 띄우면 두 서비스가 같은 폴더를 쓴다. 이때 덱 외의 쓰기는 프로세스 사이에서 보호되지 않는다.
7. 생성은 HTTP 요청 하나가 끝날 때까지 기다리는 동기 방식이다. 결과는 응답으로만 화면에 전달되고 서버에 남지 않는다. 화면이 결과를 덱에 반영한 뒤 ETag와 함께 저장한다. 요청이 끊기면 결과도 사라진다. 생성 임대 `ai_connections.generation()`은 프로세스 메모리의 카운터로 동시 생성을 막는다.

## 5. D2a 태스크

모든 태스크는 TDD로 진행하고 태스크 하나를 커밋 하나 이상으로 남긴다. 새 라우트나 응답 모델 필드를 더하는 태스크는 같은 커밋에서 OpenAPI와 프런트 타입을 재생성하고 프런트 테스트 목을 갱신한다(관례, `backend/tests/test_openapi.py`가 강제).

### D2a-1 디자인 토큰

- 내용: `styles.css` 첫머리에 제품 설계 4절의 토큰을 CSS 변수로 정의한다(배경, 패널, 본문, 보조, 경계, 주 행동, 완료, 주의, 오류, 여백 4종, 모서리, 초점선 두께). 기존 hex 사용처를 의미가 같은 토큰으로 바꾼다. 색 외의 배치와 크기는 바꾸지 않는다. 초점 표시는 2px 이상 선으로 통일하고 `prefers-reduced-motion`을 따른다.
- RED 테스트: (1) 토큰 쌍(본문/배경, 본문/패널, 보조/패널, 주 행동 위 흰 글자, 완료, 주의, 오류)의 대비율을 WCAG 2 공식으로 계산해 4.5:1 이상인지 검사한다. 토큰 값은 CSS 파일에서 파싱한다. (2) `styles.css`에 토큰 정의 블록 밖의 hex가 남지 않았는지 검사한다(슬라이드 미리보기 색은 화면 코드 밖이라 대상이 아니다).
- 결정: 토큰을 TypeScript 상수로도 내보내지 않는다. 화면 코드의 인라인 스타일은 이미 슬라이드 미리보기에만 있고, 상수를 이중으로 두면 값이 갈라진다.

### D2a-2 상태 표시 컴포넌트

- 내용: 제품 설계 4절의 상태(시작 전, 작성 중/미저장, 저장 중, 저장됨, 준비됨, 확인 필요, 실행 실패, 생성 중)를 그리는 `StatusIndicator`를 만든다. 각 상태는 아이콘과 문구를 함께 표시하고 색만으로 구별하지 않는다. "현재 보고 있는 단계"는 내비게이션의 선택 표시라 D3로 넘긴다. 저장 상태 표시는 `role="status"`로 보조기기에 알린다. 편집 화면의 저장 상태 한 줄을 이 컴포넌트로 바꾼다.
- 결정: `useDeckEditor`의 `SaveState` 문자열 유니온은 유지하고 표시 단계에서만 상태 종류로 매핑한다(저장됨 → 저장됨, 저장 대기 → 작성 중, 저장 중 → 저장 중, 저장 실패 → 실행 실패). 유니온을 바꾸면 저장 흐름 테스트 전체를 다시 써야 하고 이번 단위의 목적과 관계가 없다.
- RED 테스트: (1) 모든 상태가 고유한 문구와 아이콘을 갖는다(색을 제거한 렌더에서도 구별된다). (2) 저장 상태 매핑 4개. (3) 편집 화면에서 저장 실패와 충돌이 "실행 실패" 표시와 기존 재시도 경로를 함께 보인다. (4) "저장됨"이 서버 응답 전에는 표시되지 않는다(기존 저장 흐름 테스트의 단언을 표시 컴포넌트 기준으로 하나 추가).

### D2a-3 단계 준비 모델

- 내용: 백엔드에 순수 함수 `project_progress(deck, sources, export_summary)`를 두고 `GET /api/projects/{name}/progress`로 제공한다. 다섯 단계(보고 목적, 자료, 구성, 편집, 검토와 내보내기)마다 상태와 사유 코드 목록을 돌려준다. 검토와 내보내기는 한 상태로 합치지 않고 자동 검사, 사람 검토, 파일 저장을 따로 돌려준다(제품 설계 4절).
- 백엔드에 두는 이유: 자료 현재성과 구성 계획의 낡음 판정(`stale_story_plan`), 내보내기 이력은 이미 서버가 계산한다. 화면에서 다시 계산하면 두 판정이 갈라진다.
- 현재 저장 계약으로 판정할 수 없는 것: (1) 사용자가 보고 유형을 명시적으로 골랐는지(기본값 `research`와 구별되지 않는다). 그래서 보고 목적의 준비 조건은 "제목이 비어 있지 않고 유형이 저장됨"으로 하고, 명시 선택 여부는 D3의 입력 화면에서 다룬다. (2) 장별 생성 실패. 실패는 저장되지 않으므로 D2a의 편집 단계는 "작성된 장 수 / 전체 장 수"까지만 보이고, 실패 표시는 D2b 원장이 생긴 뒤에 더한다.
- RED 테스트: 단계마다 시작 전, 준비됨, 확인 필요의 경계 사례를 합성 덱으로 검사한다. 자료를 바꾸면 구성만 확인 필요가 되고 보고 목적은 유지된다. 덱 읽기 실패(복구 필요) 프로젝트는 진행 상태 대신 복구 필요를 돌려준다. 이 라우트는 GET이라 상태 변경 헤더가 필요 없다.
- 화면 연결: 이번 단위는 진행 모델의 API와 타입까지 만들고, 기존 탭 머리에 단계별 `StatusIndicator`를 한 줄로 보인다. 단계 내비게이션 자체는 D3다.

### D2a-4 프로젝트 형식 기록과 이전

- 내용: 프로젝트 폴더에 `manifest.json`을 둔다. 필드는 형식 이름, 형식 버전, 이 형식을 읽을 수 있는 최소 앱 버전, 마지막으로 쓴 앱 버전, 이전 기록(시각, 이전 전 형식, 이후 형식, 이전 전 복사본 위치)이다. manifest가 없는 기존 프로젝트는 형식 1로 간주하고, 처음 쓸 때 manifest를 만든다. 읽기만 할 때는 만들지 않는다.
- 덱의 `schema_version` 결정(리뷰에서 판정할 것): `SCHEMA_VERSION`은 1로 유지하고, 형식 판정은 manifest가 맡는다. 사실 5의 실측대로 `schema_version`을 올려도 0.2.0의 표시는 나아지지 않기 때문이다. 이 앱 이후 버전 사이의 판정만 manifest의 최소 앱 버전으로 한다. 검토한 대안은 둘이다. (a) 새 보고 유형을 별도 필드에 두고 `report_type`에는 기존 세 값 중 하나를 대체값으로 남기면 0.2.0이 덱을 연다. 그러나 0.2.0이 그 덱을 저장하면 모르는 필드를 버리므로 새 유형이 경고 없이 사라진다. (b) 0.2.0 호환을 포기하고 그 사실을 알린다. 이 계획은 (b)를 택하고, 기술 설계 3절의 "옛 버전에서도 모든 새 문서를 열 수 있다고 약속하지 않는다"와 "이전 앱은 이전 복사본을 사용한다"를 따른다. 0.2.0 사용자가 볼 "복구 필요" 표시와 그때 스냅샷 복원이 새 내용을 지우지 않고 현재 덱을 먼저 스냅샷으로 남긴다는 사실(0.2.0의 `restore_snapshot`)을 릴리스 안내에 적는다.
- 이전 전 복사본: 0.2.0이 읽을 수 없는 값(첫 단위의 새 보고 유형 6개)을 처음 쓰는 저장이나 manifest 형식 버전이 올라가는 첫 쓰기 직전에는 화면의 스냅샷 요청 여부와 관계없이 현재 `deck.json`을 스냅샷으로 남기고 manifest의 이전 기록에 그 스냅샷 ID를 적는다. 사용자는 기존 스냅샷 복구 화면으로 되돌릴 수 있다.
- 더 새 형식을 만났을 때: manifest의 최소 앱 버전이 현재 앱보다 높으면 프로젝트 목록에 "더 새 버전의 앱이 만든 프로젝트"로 표시하고 쓰기를 거절한다(409 대신 새 오류 코드). 덱을 덮어쓰지 않는다.
- RED 테스트: manifest 없는 폴더 읽기와 첫 쓰기, 새 유형으로 바꾸는 첫 저장의 강제 스냅샷과 이전 기록(두 번째 저장에서는 강제하지 않음), 더 새 형식의 쓰기 거절과 덱 불변, 0.2.0 형식 덱의 그대로 읽기, 이전 기록의 원자적 쓰기, 스냅샷 복구 뒤 manifest 일관성.

### D2a-5 충돌과 실패 시 미저장본 보존

- 내용: 저장이 412 충돌이나 저장 실패로 끝났을 때 화면의 미저장 덱을 서버의 `drafts/`에 별도 파일로 보존한다(`POST /api/projects/{name}/drafts`, ETag 검사 없음, 덱 검증 통과 필요, 개수 상한). `reloadFromServer`는 보존이 확인된 뒤에만 서버 덱으로 교체한다. 보존한 미저장본은 기존 스냅샷 복구 화면에서 "충돌로 보존한 변경"으로 보이고, 복원은 기존 스냅샷 복원과 같은 ETag 검사를 거친다.
- 서버에 두는 이유: 렌더러는 파일 시스템 접근이 없고, 독립 앱의 preload는 정해진 IPC만 노출한다. 충돌과 저장 실패 시점에는 서비스가 살아 있다. 서비스 자체가 죽은 상태의 보존은 다루지 않는다(가정 3).
- RED 테스트: 412 뒤 다시 불러오기를 해도 미저장 편집이 `drafts/`에 남는다. 보존 실패 시 서버 덱으로 교체하지 않고 오류를 보인다. 상한 초과 시 가장 오래된 미저장본부터 정리하지 않고 저장을 거절한다(사용자 자료 자동 삭제 금지). 복원이 ETag 충돌을 존중한다.

### D2a-6 자료 폴더 단일 서비스 잠금

- 내용: 서비스가 시작할 때 자료 폴더의 잠금 파일에 OS 파일 잠금(POSIX `fcntl.flock`, Windows `msvcrt.locking`)을 건다. 이미 다른 SlideCaptain 서비스가 잠금을 쥐고 있으면 시작하지 않고, 준비 신호 대신 "같은 자료 폴더를 다른 SlideCaptain이 사용 중" 오류를 낸다. 독립 앱은 이 오류를 사용자 문구로 보이고 다른 서비스를 종료하지 않는다(D1의 "무관한 서비스 보존" 유지). 프로세스가 끝나면 OS가 잠금을 푼다.
- 결정(리뷰에서 판정할 것): 제품 설계 7절의 "동일 프로젝트 편집창 한 개"를 프로젝트 단위 임대 대신 자료 폴더 단위 잠금으로 구현한다. 독립 앱은 창이 하나라 같은 서비스 안의 중복 편집은 이미 없고, 위험은 서로 다른 서비스가 같은 폴더를 쓰는 경우이기 때문이다. 대안은 미루고 로드맵 이월표에 위험을 적는 것이다.
- RED 테스트: 같은 폴더로 두 번째 서비스 시작 거절, 다른 폴더는 동시 실행 가능, 첫 서비스 종료 뒤 두 번째 시작 성공, 강제 종료 뒤 잠금 해제, 네트워크 드라이브처럼 잠금을 지원하지 않는 폴더의 오류 안내. 기존 웹 모드(`serve`)도 같은 잠금을 쓴다. desktop smoke의 "무관한 서비스 보존" 검사는 서로 다른 자료 폴더를 쓰도록 맞춘다.

## 6. D2b 계약 (상세 계획은 D2a 뒤)

D2b 계획서는 아래 계약을 출발점으로 쓰고 D2a에서 확정된 인터페이스를 반영한다.

- 원장 저장 위치와 형식(SQLite 또는 프로젝트별 원자적 JSON)은 D2b 계획에서 정한다. 기술 설계 6절의 상태 전이(대기, 실행, 검증, 성공 / 취소 요청, 취소 또는 중단 / 실패, 재시작 시 중단 또는 원격 완료 불명)를 따른다.
- 작업 시작은 요청 ID로 중복 클릭을 병합한다. 계정 선택과 입력 리비전(덱 ETag와 자료 fingerprint)을 시작 시점에 고정한다.
- 결과 후보는 서버에 먼저 보존한다. 적용은 서버가 현재 ETag와 입력 fingerprint를 다시 비교해 다르면 적용하지 않고 "이전 입력 기준 후보"로 남긴다. **늦게 도착한 성공 응답이 새 편집을 덮지 않는 회귀를 필수 RED 테스트로 둔다**(기술 설계 6절의 필수 수용 시험).
- 기존 관문을 우회하지 않는다: 생성 임대, `X-AI-Consent` 428, `_record_success`, `_append_usage`, 도식 장 생성 거절, 형식 재시도 1회 상한.
- 생성 라우트 6개를 한 번에 옮길지, 구조안과 장 생성부터 옮기고 나머지는 동기 경로로 남길지를 D2b 계획에서 정한다.
- D2a-3의 편집 단계 실패 표시와 제품 설계 4절의 "6장 중 1장 실패"를 이 원장에 연결한다.

## 7. 수용 기준 (D2a)

- 백엔드 전체, 프런트 전체, desktop 테스트, 화면 빌드, OpenAPI와 타입 재생성 무변경, 공개 저장소 감사, diff 공백 검사를 통과한다.
- 웹 모드의 Chrome에서 상태 표시(저장 대기, 저장 중, 저장됨, 저장 실패, 충돌 뒤 미저장본 보존)와 단계 준비 표시를 합성 프로젝트로 확인한다. 1440px과 1024px에서 가로 넘침이 없다.
- 이 Mac에서 패키지 독립 앱으로 같은 자료 폴더 잠금(두 번째 서비스 거절)과 manifest 첫 쓰기를 확인한다. Windows는 CI로 확인하고 실기기 확인은 회사 PC 몫으로 남긴다.
- 0.2.0 형식의 합성 프로젝트를 새 코드로 열고 새 값 없이 저장한 뒤 0.2.0 코드로 다시 열 수 있는지 확인한다. 새 유형으로 저장한 프로젝트는 0.2.0에서 "복구 필요"로 보이고, 이전 전 스냅샷으로 복원하면 열리는지 확인한다.
- AI 호출 0회.
- 태스크마다 독립 리뷰를 받고, D2a 묶음 끝에 묶음 최종 리뷰를 받는다.

## 8. 가정과 미확인

1. 0.2.0의 표시 동작은 저장소의 0.2.0 코드로 실측했다(사실 5). 배포 ZIP으로 설치한 0.2.0 앱의 화면에서 같은 표시가 나오는지는 D2a-4 구현 때 확인한다.
2. `fcntl.flock`과 `msvcrt.locking`은 로컬 디스크에서 프로세스 종료 시 잠금이 풀린다. 네트워크 드라이브, iCloud 같은 동기화 폴더에서의 동작은 보장하지 않는다(기존 로드맵의 Q1b 이월과 같은 전제).
3. 미저장본 보존은 서비스가 살아 있을 때만 된다. 서비스가 먼저 죽은 상태의 렌더러 편집 보존은 D2b 또는 이후 단계에서 다시 판단한다.
4. 단계 준비 모델의 판정 규칙은 제품 설계 4절을 현재 저장 계약에 맞춘 것이다. 사용자가 그 표시를 보고 실제로 현재 상태를 더 잘 구별하는지는 D6의 사용성 검증 전까지 미확인이다.

## 상위 문서와 다르게 정하는 것

- 제품 설계 7절의 "동일 프로젝트 편집창 한 개 제한"을 자료 폴더 단위 잠금으로 구현한다(D2a-6의 결정과 이유).
- 기술 설계 7절의 D2 한 단계를 D2a와 D2b로 나누고, D2 관문 통과는 D2b 완료 뒤로 둔다(2절).
