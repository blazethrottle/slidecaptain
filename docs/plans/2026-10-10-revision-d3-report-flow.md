## 1. D3의 범위와 분할

구현 설계 7절은 D3를 "목적별 입력/패턴, 구성/편집/검토 5단계, 사용량 문구 정리"로 정의하고 R01, R09, R11, R12, R15, R16을 건다. 다음 단계로 넘어가는 기준은 네 가지다. ① IR 포함 10유형의 저장, 생성, 편집 보존 ② 드롭다운과 시각 구조가 다른 대표 페이지 ③ 직접 요소 편집, 저장, PPTX 일치 ④ 긴 작업 중 이동과 취소, 실패 재개다.

이 범위는 성격이 다른 세 덩어리라 셋으로 나눈다(사용자 결정 2026-10-10).

| 묶음 | 내용 | 저장 형식 | 끝나면 관측되는 것 |
|---|---|---|---|
| D3a 화면 골격 | 다섯 작업 단계 화면과 상단 머리, 단계 상태 표시, 크기 토큰과 버튼 계층, 원인별 실패 안내와 진단 상세(R11 화면, R12), 생성 중 이동과 편집, 여러 탭 처리 | 바꾸지 않는다(원장 열의 허용값 추가는 아래 원칙 참고) | 관문 기준 ④와 R01의 현재/완료 분리 |
| D3b 보고 목적 | 보고 유형의 명시 선택 기록, IR Pitch Deck 저장값, 10종 드롭다운과 유형별로 시각 구조가 다른 예시 화면, 유형별 추가 입력과 "전달할 핵심 내용", 원하는 결과 네 가지, 보고 목적 자동 저장, 구성 화면의 카드 목록과 실행 단계 표시 | 바꾼다(한 번) | 관문 기준 ①②, R09 |
| D3c 직접 수정 | 구현 설계 10절의 직접 수정 데이터 계약(안정적인 요소 ID, 논리 좌표, 명령 단위 되돌리기, 출력 fingerprint 무효화), PPTX가 같은 값을 소비, AI 재생성 때 사용자 수정 보존, 장 후보를 서버가 현재 덱에 적용하는 경로, 장 단위 저장과 묶음 사슬 완화의 재판단, 동기 생성 래퍼 6개의 제거와 시험 이전 | 바꾼다 | 관문 기준 ③, R16 |

분할 원칙은 둘이다.

- D3a는 저장 형식(덱 구조, manifest, 원장의 열과 형식 번호)을 바꾸지 않는다. 0.2.0과 같은 자료 폴더를 쓰는 공존 판정(D2a-1)을 다시 열지 않기 위해서다. 다만 D3a-4는 원장의 기존 TEXT 열에 새 원인 분류 값을 쓴다. 지금의 읽기 경로는 모르는 값 하나에 작업 목록 전체가 500으로 실패하므로(사실 17), D3a-4가 읽기 경로를 먼저 관대하게 바꾸고, 같은 자료 폴더를 쓰는 다른 빌드가 있는지를 가정 1로 확인한다.
- D3a가 먼저다. 다섯 단계 화면의 틀이 있어야 D3b의 보고 목적 화면과 D3c의 편집 화면이 그 안에 들어간다. D3c의 상세는 D3a와 D3b에서 확정된 실제 구조를 보고 쓴다(로드맵 원칙: 단계별 상세 계획은 착수 시점에 작성한다).

D3 관문은 D3c까지 끝나야 통과한다. D3a나 D3b만 끝난 상태를 D3 관문 통과로 기록하지 않는다. 묶음마다 끝나면 랩업 보고 뒤 사용자와 상의하고 다음 묶음으로 넘어간다(단계 경계 규칙).

> 2026-10-10 기록: 단계표의 R15는 개정 요구 목록에서 2026-10-02에 "구현/검증 완료"다(구조안 입력란 명칭). 구현 설계 8절의 R15 수용 기준에는 "저장/오류 후 복구"도 있다. D3a는 단계 이동을 허용하므로 주안점 입력이 이동 사이에 사라지지 않게 하는 일을 D3a-5가 맡는다(4.4). 이 문서에서 "β R15"와 "D2b-5c R15"는 앞 단계 리뷰의 발견 번호이고 요구 R15와 다르다.

## 3. 현재 코드에서 확인한 사실 (기준 `28ab86d`)

1. 앱은 프로젝트 목록과 프로젝트 화면 둘이다(`App.tsx`). 프로젝트 화면(`ProjectView.tsx`)은 탭 4개(자료, 구조안, 편집, 검수 이력)와 버튼 2개(초안 PPTX 내보내기, 스냅샷 복구)를 한 줄 `nav`에 둔다. 처음 여는 탭은 자료이고, 이 프로젝트의 장 생성 묶음이 돌고 있으면 구조안이다. 탭은 조건부 렌더라 전환 때 언마운트된다(`:366-382`). 저장 상태 표시는 편집 화면에만 있다(D2a-5).
2. 자료 탭(`SourcesScreen.tsx`)에 "보고 정보"(제목, 보고 유형, 보고자, 피보고자)와 "입력 자료"가 함께 있다. 보고 정보는 덱의 `meta`이고 "보고 정보 저장" 버튼으로 저장한다(`:318`). 저장은 저장 순간의 `deck` prop을 펼치고 `meta`만 마운트 때 사본에서 가져온다(`:59, 90`). 자료는 프로젝트의 별도 파일이다.
3. 진행 API `GET /api/projects/{name}/progress`는 단계 다섯(`purpose`, `sources`, `structure`, `editing`, `review`)의 상태(`not_started`, `ready`, `needs_review`)와 사유 코드, 그리고 `jobs`를 돌려준다(`pipeline/progress.py`). 화면용 함수 `api.getProgress`가 있으나(`client.ts:308`) 부르는 화면은 없다. 보고 목적은 제목이 비면 `not_started`(`title_missing`), 아니면 명시 선택 기록이 없어 항상 `needs_review`(`report_type_unconfirmed`)다. 사유는 고정 목록이 아니라 `list[str]`이고 일부는 문자열 조합(`artifact_{...}`, `input_{...}`, `review_{...}`)이다(`:47-120`). 준비됨에도 사유가 붙는다(자료 `extraction_review_unavailable`, 자동 검사 `draft_checks_only`, 사람 검토 `manual_pass_not_final`). 검토 단계는 세 부분이 모두 같은 상태가 아니면 `needs_review`이고 단계 수준 사유가 없다(`:132-139`). 내보내기 기록이 있으면 프로젝트 잠금 안에서 렌더 계획과 품질 평가를 계산한다(`server/app.py:1243-1290`).
4. 사용량 문구는 다섯 곳 이상에 기본으로 보인다. `formatUsage` 호출 네 파일(구조안 결과 `StructureScreen.tsx:651`, 장 생성 합계와 실패 장 단서 `:745-750`, 구성 재작성 `StoryRewritePanel.tsx:260`, 장 재생성과 축약 `GeneratePanel.tsx:237`, 도식 생성 `DiagramAuthoringDialog.tsx:425`)과, `formatUsage`를 쓰지 않는 호출 횟수 문구(`StoryRewritePanel.tsx:263`), 내부 파일 이름 `ai-usage.jsonl`이 든 단서(`StructureScreen.tsx:23-24`)다. 사용량 기록 파일은 서버가 쓴다. 화면 시험에는 사용량이 보인다고 단언하는 줄이 `StructureScreen.test.tsx`에만 21줄 있다.

6. 실패 문구는 대부분 서버가 보낸 `detail` 문자열이다(`messageOf`, `jobResult`). FastAPI 입력 검증 오류는 `msg`를 모아 그대로 보인다(`client.ts:104-112`). 서버에 닿지 못하면 "서버에 연결하지 못했습니다. 앱을 다시 시작해 주세요."다(`:90-91`). 원장의 원인 분류 `error_class`는 `input`, `ai_output`, `connection`, `base_changed`, `cancelled`, `ledger`의 여섯이다. 화면이 이 분류를 쓰는 곳은 장 생성 묶음의 요약(`StructureScreen.tsx:278-299`)뿐이다.
7. 원인 분류에는 네 가지 빈틈이 있다.
   - 예기치 않은 예외가 `input`, 상태 500으로 분류된다(`server/app.py:436-437`). 리뷰 탐침에서 `RuntimeError`가 `{error_class: input, status: 500, code: None}`으로 남았다.
   - 장 생성 묶음은 `_classify`를 거치지 않고 `error_class="input"`을 직접 쓰는 곳이 넷이다. 적용 때 덱이나 자료를 읽지 못함(`:1848`, 코드 `apply_failed` 또는 `project_missing`), 저장 실패(`:1876`, `StorageError`, `OSError`, `ValueError`, `LedgerError`를 모두 `apply_failed`), 원장 결과를 읽지 못함(`:1908`, `result_unreadable`), 묶음의 예기치 않은 오류 뒤 강제 정리(`:1951`)다. `_classify`의 `StorageError` 갈래도 `input`이다(`:432-433`).
   - 제공자 예외의 클래스는 원인과 맞지 않는다. ChatGPT 연결은 호출 중의 시간 초과, 연결 끊김, 요청 미완료, 응답 스키마 미지원까지 `ProviderNotAvailable`로 던지고(`codex.py:115, 120, 162, 164, 313, 316`), Claude 연결은 미로그인과 한도 초과를 `ProviderCallFailed`로 던진다(`subscription.py:220-226`). 서버는 둘을 `connection`, 503, 코드 없음으로 묶는다. 리뷰 탐침에서 두 예외 모두 `{connection, 503, None}`이었다.
   - `ConnectionConflict`(409, 코드 없음)는 원인이 넷이다. 선택이 바뀜(`connections.py:266`, `app.py:457`), 로그인 진행 중(`:270`), 계정 신원 변경(`:274`), 생성 중 설정 변경 시도(`:174`)다. 앞의 셋은 등록 단계의 HTTP 오류로 화면에 온다(`app.py:757-767`).
8. 원인 분류가 없는 종결이 있다. 작업의 `interrupted`와 `remote_completion_unknown`은 원장에 원인 분류를 남기지 않고 화면이 503 `job_interrupted`로 합성한다(`api/jobs.ts:38-40`). 묶음의 남은 장은 `interrupted`이고 코드만 갖는다(`provider_failed`, `ledger_failed`, `held_stale_plan`, `chain_broken`, `project_missing`, 또는 코드 없음, `server/app.py:1772-1827, 1945-1947`). 앞 장이 예기치 않은 오류로 실패해도 남은 장의 코드는 `provider_failed`다(`:1799-1800`, 리뷰 탐침). 완료 여부 불명을 다시 생성하면 사용량이 한 번 더 기록될 수 있다는 확인이 이미 화면에 있다(`StructureScreen.tsx:38-39`).
9. 생성 중 잠금: 프로젝트 화면의 `aiBusy`는 구조안 화면의 바쁨(`generating`), 편집 화면의 바쁨(`diagramGenerating`, 도식 생성과 템플릿 전환 전 저장이 함께 씀), 진행 작업 확인 전, 이 프로젝트의 장 생성 묶음(`batchHere`) 중 하나라도 참이면 목록 이동, 자료 탭, 편집 탭, 내보내기, 스냅샷 복구, 서버 내용 다시 읽기, AI 설정, 검수 이력을 잠근다(`ProjectView.tsx:106-108`, 머리 버튼들). 구조안 화면은 후보형인 구조안 생성 중에도, 장 생성 묶음을 조회하는 동안에도, 다시 등록과 이어서 조회할 때도 바쁨을 올린다(`StructureScreen.tsx:198, 309, 365, 468`). 구조안 화면은 자기 작업 중 입력 묶음(`fieldset`) 전체를 잠근다(`:624`). 승인과 다시 생성 버튼은 묶음과 별도로 각각 `busy`를 본다(`:678, 764`).
10. 화면 바쁨 신호는 화면이 내려갈 때 새어 나간다. 구조안 생성과 이어서 조회는 언마운트로 조회가 중단되면 `onBusyChange(false)`를 부르지 않는다(`StructureScreen.tsx:244, 375, 408`). 다시 마운트했을 때 작업이 이미 끝났으면 이 값을 내리는 경로도 없다(`:377-390`). `StoryRewritePanel`과 `DocumentChangePanel`도 같은 `setGenerating`을 받는다(`:770, 784`). 지금은 생성 중 이동이 잠겨 드러나지 않았다.
11. 같은 탭이 등록한 묶음을 프로젝트 화면이 모른다. `batchHere`는 진행 작업 조회로만 바뀌고, 그 조회는 처음 열 때, 창 초점, 진행 작업이 이미 있을 때의 1초 타이머, 취소 버튼에서만 일어난다(`ProjectView.tsx:48-75`). 리뷰 실험(가짜 CLI 관문 모드)에서 한 탭이 승인으로 묶음을 등록하고 3초 동안 그 탭의 진행 작업 조회는 승인 전 검사 1회뿐이었고 상단 진행 안내는 없었다. 지금은 구조안 화면의 `generating`이 대신 잠가 드러나지 않았다.
12. 구조안 후보에는 반영 직전 서버 재비교가 없다. 후보형 종류의 반영 방식은 셋으로 갈린다.
   - 재작성과 수리: 반영 요청이 후보의 기준 ETag를 `If-Match`로, 자료 fingerprint를 함께 보낸다. 서버가 다시 비교한다(`client.ts:232-235`).
   - 장 재생성과 축약: 반영 직전에 작업을 다시 조회해 서버가 계산한 낡음 이유로 막는다(`GeneratePanel.tsx:147-172`, β R9). 반영 자체는 편집 화면의 덱 전체 PUT이다.
   - 도식: 작업 종료 때 낡음 이유로 오류를 내고, 후보가 작성 창의 초안으로 들어가 반영 전 "입력과 배치 확인"이 저장 ETag를 보낸다(`DiagramAuthoringDialog.tsx:212, 263`).
   - 구조안: 승인은 덱 전체 PUT이고 `If-Match`는 후보의 기준이 아니라 이 탭의 전역 저장 ETag다. 서버의 반영 처분은 PUT 성공 뒤에 보내고, 거절되면 버림으로 바꾼다(`StructureScreen.tsx:536-550`). 다시 마운트한 구성 화면은 진행 중이던 구조안 작업을 이어서 조회해 끝나면 낡음 검사 없이 초안에 올리고 안내도 띄우지 않는다(`:361-371`). 같은 화면에 머문 경로만 경고한다(`:233-236`). 리뷰 실험(두 화면 인스턴스, 가짜 CLI): 원장은 후보를 `stale`(`sources_changed`)로 기록했는데 다시 마운트한 화면은 안내 없이 옛 자료 기준 구조안을 올렸고, 승인하자 덱의 장 제목이 옛 자료 기준으로 바뀌었다.
   - 구조안 생성 결과는 도착하면 확인 없이 초안, 보고 계획, 보고 질문을 바꾼다(`:176-192, 233`). 다시 마운트 경로만 바뀐 초안이 있으면 묻는다(`:381-385`).
13. 구성 화면의 초안, 보고 계획, 보고 질문은 마운트 때 사본이고(`:82-84`), 주안점과 목표 장수는 화면의 지역 상태라 저장되지 않으며 미저장 판정에도 들어가지 않는다(`:86-87, 151-155`). 탭을 바꾸면 사라진다.
14. 편집 화면은 덱을 마운트 때 한 번 받고 덱 전체를 저장한다. 저장 ETag는 프로젝트 이름을 키로 한 모듈 전역 값이다(`client.ts:122`). β 리뷰 R1(critical)은 이 공유 값이 다른 경로에서 갱신되면서 편집 화면의 옛 덱이 묶음이 만든 장을 덮은 사례다.
15. β R1 수정은 탭 이름으로 갈린다(`ProjectView.tsx:85-105`). 묶음이 끝났을 때 이 탭의 저장 ETag가 서버와 다르면, 지금 탭이 구조안이면 덱을 다시 읽고 그 밖이면 충돌 안내("다른 창이나 프로그램에서 먼저 저장되었습니다.")를 띄운다. 기준 조회의 412는 "저장본이 바뀜"으로 읽는다(`74165ad`). 구조안 탭에서 덱을 다시 읽으면 전역 ETag와 `deck` prop은 새 값이 되지만 구성 화면의 초안 사본은 옛 값이라, 그 뒤 승인이 다른 탭의 구조를 옛 사본으로 덮을 수 있다(지금 코드에도 있는 이음매).
16. 장 생성 묶음은 서버가 장마다 결과를 덱에 쓰고, 다음 장 전에 덱 ETag가 자기가 쓴 값인지 확인한다(사슬). 사슬은 자료를 보지 않는다. 자료가 바뀐 뒤 처음 적용하려는 장(이미 AI 호출을 마친 장)만 `sources_changed` 후보가 되고, 남은 장은 코드 없이 `interrupted`이며, 묶음은 `chain_broken`이다(`server/app.py:1768-1774, 1826-1827, 1853-1858`).
17. 원인 분류의 허용값은 두 곳에 따로 있다. 원장 쓰기 검사 `ERROR_CLASSES`(`storage/job_ledger.py:63`, 쓰기 때만 검사, 열에 CHECK 제약 없음)와 응답 모델 `ErrorClass = Literal[...]`(`models/jobs.py:15`)다. 둘을 묶는 시험은 없다. 응답 모델이 고정 목록이므로 원장 행 하나라도 모르는 값을 가지면 작업 조회, 작업 목록, 진행 API가 모두 500이 된다(리뷰 탐침: 세 라우트 500, 실행기 메모리를 읽는 `/api/jobs/active`만 200). 값을 넓히면 OpenAPI와 화면 타입이 바뀌어 같은 커밋에서 재생성해야 한다(`test_openapi.py`).
18. 진행 작업 조회 실패와 작업 조회 실패는 다르다. 작업 조회(`GET jobs/{id}`)는 원장을 읽고, 진행 작업 확인(`GET /api/jobs/active`)은 실행기 메모리를 읽는다(`server/app.py:2056-2059`). β R8의 상황에서는 앞의 것만 실패한다. 화면은 작업 조회가 실패하면 "작업 상태를 확인하지 못했습니다. 계속 확인합니다."를 보이고 끝없이 다시 조회한다(`api/jobs.ts:7`). 리뷰 탐침(조회가 계속 503)에서 200ms 동안 18회 조회했고 입력 묶음은 잠긴 채였다.
19. 새 작업 등록은 진행 중인 작업이 있으면 409(`generation_active`)로 거절된다. 대기열은 없다(D2b 9절 5항).
20. 창 닫기: 웹 모드는 `beforeunload` 경고가 저장하지 않은 변경, 업로드, 진행 중 AI 작업(`generating` 포함)에 뜬다(`ProjectView.tsx:140`). 독립 앱은 진행 중 AI 작업을 main 프로세스가 "계속 작업 / 취소 후 닫기"로 묻는다(D2b-5c). 독립 앱은 창이 하나다(`desktop/main.cjs:165, 236`).

### 4.1 다섯 단계와 지금 탭의 대응

| 3 구성 | 구조안 탭 | 옮긴다. 문서 전체 변경과 근거 이동 패널(JSON 입력)은 접힌 "고급 작업" 영역으로 옮겨 단계의 주 행동과 섞지 않는다. 주안점 입력란 명칭과 요청 전달은 그대로 |
| 4 편집 | 편집 탭 | 옮긴다. 수치 대조, 비교와 요약 검토, 분량 경고 패널은 장별 확인이라 편집에 남는다. 직접 수정은 D3c |
| 5 검토와 내보내기 | 내보내기 버튼, 품질 요약, 검수 이력 탭 | 한 화면에 모은다. 자동 검사(내보낸 파일 기준임을 문구로 밝힌다), 사람 검토, 파일 저장의 세 상태를 따로 보이고, 제출본 자격(PowerPoint 렌더, 서명된 독립 검수, 제출본 게시)은 그 아래 별도 영역에 둔다 |

프로젝트 전체에 걸린 요소의 위치는 다음과 같다.

| 요소 | 지금 | D3a에서 |
|---|---|---|
| 저장 상태 | 편집 화면 | 상단 머리(아래 규칙) |
| 진행 중 작업 안내와 "그 작업 취소" | 탭 위 문단 | 상단 머리의 작업 표시. 취소 버튼을 함께 둔다 |
| 원장을 열 수 없다는 안내 | 탭 위 문단 | 상단 머리의 작업 표시 자리 |
| 충돌 안내와 "서버 내용 다시 읽기" | 탭 위 문단 | 본문 위 알림 영역(지금과 같은 역할) |
| 품질 안내("현재 산출물은 검수 전 초안입니다") | 모든 탭 위 | 검토와 내보내기 화면과 내보내기 버튼 근처 |
| 내보내기 결과 요약 | 모든 탭 위 | 검토와 내보내기 화면 |
| 스냅샷 복구, 충돌로 보존한 변경 | 탭 줄의 버튼 | 상단 머리의 보조 행동. 보존 건수에서 바로 연다(C18) |
| AI 설정 | 탭 위 패널 | 상단 머리의 드로어. 내용(계정, 모델, Effort)은 D4가 바꾸고 D3a는 위치만 옮긴다 |

- 덱을 열 수 없는 상태(`needs_recovery`, `newer_format`, `unreadable_manifest`, 최초 덱 읽기 실패)는 다섯 단계 셸을 띄우지 않고 지금 화면을 유지한다.
- 복구 화면은 단계가 아니다. 열린 동안 단계 목록의 현재 표시(`aria-current`)를 두지 않고, 단계를 고르면 복구 화면을 닫고 그 단계로 간다(복구 화면의 이탈 확인을 거친다). 복구 화면의 "다시 만들 화면으로 옮기기"는 단계 이름을 넘기고, 장을 순서와 제목으로 보이며, 옮긴 뒤 그 장을 미리 고른다(C24).
- 단계 화면은 지금처럼 전환 때 언마운트한다. 숨긴 채 마운트를 유지하면 화면이 옛 사본을 든 채 전역 ETag만 새로 바뀌는 이음매(사실 14, 15)가 다시 생기기 때문이다.
- 사용자 문구의 탭 이름(사실 22)과 서버 문구의 "새로고침"을 단계 이름과 보존 흐름의 행동으로 바꾼다. 브라우저 탭을 뜻하는 문구는 예외다.

상단 머리의 저장 상태는 다음 규칙으로 정한다. 지금 편집 화면의 자동 저장 상태만 옮기면, 보고 정보나 구성 초안을 고친 채 머리에 "저장됨"이 남아 R01 완료 기준(미저장을 완료로 표시하지 않음)에 어긋난다.

| 현재 단계 | 저장 상태의 출처 |
|---|---|
| 보고 목적 | 폼이 저장본과 다르면 "변경사항 있음", 저장 중, 실패, 충돌은 그 저장의 결과 |
| 자료 | 열린 자료가 저장본과 다르면 "변경사항 있음", 그 밖은 마지막 자료 저장의 결과 |
| 구성 | 초안이나 보고 질문이 저장본과 다르면 "변경사항 있음"(승인 전 초안은 저장되지 않는 값임을 문구로 밝힌다). 문서 변경과 재작성 패널의 적용하지 않은 입력, 저장하지 못한 생성 결과도 같은 상태로 보인다(D3a-2 리뷰 R3) |
| 편집 | 지금의 자동 저장 상태 |
| 검토와 내보내기 | 검수 기록 폼이 있으면 그 상태, 없으면 표시하지 않는다 |

β R1의 분기(사실 15)는 탭 이름이 아니라 "그 화면이 저장본과 다른 사본을 들고 있는가"로 다시 쓴다.

- 미저장 사본을 들고 있으면(보고 목적 폼이 바뀜, 편집에 미저장 변경, 구성 초안이 저장본과 다름) 충돌 안내를 띄운다. 이 탭이 직접 시작한 묶음이면 "다른 창이나 프로그램" 대신 "생성한 장이 반영되었습니다. 저장하지 않은 변경은 보존한 뒤 다시 읽어 주세요"처럼 사실에 맞게 안내한다.
- 사본이 저장본과 같거나 묶음 동안 읽기 전용이었으면, 그 화면을 새 덱으로 다시 마운트한다(사본까지 새로 만든다). 덱을 읽기만 하는 단계(자료, 검토)는 덱을 다시 읽는다.
- 이 규칙은 D3a-2의 시험(아래 순서 시나리오 포함)과 α 묶음 리뷰의 실제 서비스 두 탭 재현으로 확인한다.

배치는 제품 설계 3절과 시안을 따른다. 좌측 단계 목록 216px, 본문 유동 폭, 상단 머리에 프로젝트 제목, 저장 상태, 작업 표시, 현재 AI 연결이다. 좁은 창의 기준은 D2a-5의 1000px를 가져오지 않고 시안의 값을 쓴다. 1100px 이하에서 단계 목록을 줄이고 편집 화면의 속성 패널을 캔버스 아래로 내린다. 780px 이하에서 단계 목록을 가로 띠로 바꾸고 단계마다 상태 문구를 함께 보인다(접어도 다섯 단계의 상태가 한눈에 보이게 한다). 편집 화면의 쌓임 기준은 뷰포트가 아니라 본문 폭으로 바꾼다(단계 목록이 생기면 같은 뷰포트에서 본문이 216px 좁아지기 때문이다. 1024px 창에서 지금 CSS로 계산한 캔버스 폭은 약 252px다). 1024×720에서의 실제 캔버스 폭은 D3a-2가 측정해 기록한다. 측정 전에는 캔버스 폭의 합격선을 두지 않는다.

### 4.2 현재 단계와 단계 상태를 따로 보인다 (R01, C1, C11, C15, C20)

- 현재 보고 있는 단계는 선택 막대와 `aria-current="step"`으로 보인다. 단계 상태는 진행 API의 값을 상태 표시 컴포넌트(D2a-5)로 보인다. 두 표시는 서로 다른 요소다. 선택한 단계를 완료로 보이지 않는다.
- 화면이 보완하는 상태: 현재 단계에 미저장 변경이 있으면 서버의 상태 대신 "작성 중"을 보인다(제품 설계 3절 배치도의 "구성 작성 중"). 그 단계의 작업이 진행 중이면 "생성 중"을 보인다.
- 조회 시점: 프로젝트를 열 때, 공통 알림 지점(4.5)의 "저장 성공"과 "작업 종결" 뒤, 창 초점을 얻을 때다. 진행 API 1회의 소요 시간을 D3a-3이 합성 프로젝트(내보내기 기록 있음)로 측정하고, 자동 저장마다 부를지 마지막 저장 뒤 한 번으로 합칠지 그 측정으로 정한다.
- 조회가 실패하면 단계 상태를 "확인하지 못함"으로 보이고 준비됨으로 두지 않는다. 이 상태는 상태 표시 컴포넌트에 새 종류(`unknown`, 물음표 아이콘, 중립 회색, 문구 "확인하지 못함")로 더하고, 확정 커밋에서 제품 설계 4절 상태표에 행을 더한다.
- 사유 코드: 서버 모델에서 사유를 고정 목록(`Literal`)으로 바꿔 OpenAPI 타입에 나오게 하고, 화면 문구 표가 그 타입을 빠짐없이 덮는지 타입 검사로 확인한다(응답 계산만 바뀌므로 저장 형식 변경이 아니다). 화면이 모르는 코드를 만나면 "상태를 확인해 주세요"를 보이고 준비됨으로 두지 않는다.
- 준비됨에 붙는 사유(`extraction_review_unavailable`, `draft_checks_only`, `manual_pass_not_final`)는 단계 목록에 보이지 않고 그 단계 화면의 한계 안내로 보인다.
- 보고 목적은 D3b 전까지 제목이 있으면 확인 필요다. 문구는 행동 지시가 아니라 사실 설명이다: "보고 유형을 직접 골랐는지는 아직 기록하지 않습니다." D3a 랩업에 "보고 목적은 준비됨을 보일 수 없다"를 적는다. D3a와 D3b 사이에 릴리스는 없다.
- 구성의 낡음 사유(`stale_story_plan`)는 판정 계약을 바꾸지 않는다(C15 판단). 문구는 원인을 정확히 말한다: "자료, 보고 정보, 장 구성(편집 단계의 장 순서와 템플릿 포함)이 바뀌어 구성을 다시 확인해야 합니다."
- 검토 단계: 단계 목록의 준비됨은 "초안 확인됨"으로 보이고 체크 아이콘을 쓰지 않는다. 준비됨이 제출 가능을 뜻하지 않기 때문이다(제품 설계 4절 "저장됨은 보고 품질 통과를 뜻하지 않는다"). 세 부분이 섞인 상태의 단계 수준 사유를 서버가 돌려주게 하고(C20, 예: `human_review_pending`), 문구는 "사람 검토가 남았습니다"처럼 남은 부분을 말한다.
- 진행 API의 `jobs`는 단계 목록의 해당 단계 옆에 "생성 중"과 "6장 중 1장 실패" 같은 요약을 보이는 데 쓴다. 장 요약은 성공, 실패(원인 분류 있음), 중단(앞 장 때문에 멈춤), 보류(구성 낡음), 이전 입력 기준 후보를 나눠 센다.

### 4.3 원인별 실패 안내와 진단 상세 (R11 화면, R12, C4, C6, C17, C23)

실패 안내는 제품 설계 5절 D의 세 요소를 갖는다: 무슨 일이 생겼는가, 무엇이 보존됐는가, 지금 할 수 있는 일. 세 요소를 그리는 공용 컴포넌트 하나를 두고 생성 화면들이 이를 쓴다. 입력은 "원장의 작업 또는 장 행"이나 "HTTP 오류" 둘 중 하나다. 동의 대화 상자 취소처럼 실패가 아닌 결과는 이 컴포넌트를 쓰지 않는다.

서버는 실패를 던지는 자리마다 코드를 붙인다. 예외 클래스로 코드를 정하지 않는다(사실 7). 한 자리가 둘 이상의 원인을 함께 받으면(Claude 연결의 호출 중 CLI 오류) 가를 수 없다고 적고 넓은 행으로 보낸다. 결과의 `api_error_status`로 한도 초과를 따로 가를 수 있는지는 D3a-4가 대응표를 만들 때 확인하고, 가를 수 있으면 `provider_limit` 행을 더한다. `ProviderError`와 `ConnectionConflict`에 `code` 속성을 두고, `codex.py`, `subscription.py`, `connections.py`, `app.py`의 각 `raise`에서 지정한다. 등록 단계의 HTTP 오류 처리기(`app.py:757-804`)도 응답 본문에 같은 코드를 싣는다. D3a-4는 `raise` 자리 대응표(파일:행, 지금 클래스, 붙일 코드)를 구현 첫 커밋에 시험 자료로 둔다.

원장 행의 판정은 "작업 상태 → 원인 분류 → 코드" 순서다.

| 원인 | 판정 조건 | 무엇이 보존됐는가 | 지금 할 수 있는 일(주 행동) |
|---|---|---|---|
| 입력: 고칠 수 있음 | `input`이고 화면이 아는 코드(`stale_story_plan`, `rewrite_protected_evidence`, 도식 장 거절 등) | 입력은 그대로 | 해당 단계나 입력으로 이동 |
| 입력: 코드 없음 | `input`이고 코드가 없거나 모르는 코드(없는 장 404, 템플릿 불일치 422 등) | 입력은 그대로 | "입력을 확인한 뒤 다시 생성". 이동할 단계를 추측하지 않는다. 422 입력 검증 문구는 고정 한국어 문구로 보이고 서버 문구는 진단 상세로 보낸다 |
| AI 출력 | `ai_output` | 입력은 그대로, 응답 원문은 진단 상세 | 같은 입력으로 다시 생성 |
| 연결: 설치 없음 | 코드 `provider_missing` | 입력은 그대로 | AI 연결 열기 |
| 연결: 로그인 필요 | 코드 `login_required`(연결 상태 확인에서 로그인이 없다고 판정한 자리, `connections.py:276`, ChatGPT의 `codex.py:356`) | 입력은 그대로 | AI 연결 열기 |
| 연결: 시간 초과, 연결 끊김 | 코드 `provider_timeout`, `provider_disconnected` | 입력은 그대로 | 잠시 뒤 다시 생성. 반복되면 AI 연결 확인 |
| 연결: 지원하지 않는 기능 | 코드 `provider_unsupported`(ChatGPT의 스키마 미지원) | 입력은 그대로 | 다른 AI 연결로 바꾸기(AI 설정 드로어) |
| 연결: 기타 제공자 오류 | `connection`이고 위 코드가 아님. Claude 연결의 호출 중 CLI 오류는 로그인 문제와 한도 초과가 한 자리(`subscription.py:220-226`)에서 나와 서버가 가를 수 없으므로 이 행이다(코드 `provider_call_failed`) | 입력은 그대로 | "로그인 상태와 사용 한도를 확인한 뒤 잠시 뒤 다시 생성". AI 연결 열기를 보조 행동으로 둔다 |
| 선택 또는 신원 변경 | 코드 `selection_changed`, `identity_changed` | 입력은 그대로 | AI 설정에서 전송 대상 확인 뒤 다시 생성 |
| 로그인 진행 중 | 코드 `login_pending` | 입력은 그대로 | 로그인을 마친 뒤 다시 생성 |
| 기준 변경 | `base_changed`(코드 `base_changed`, `sources_changed`) | 결과는 이전 입력 기준 후보 | 장 후보: 후보 보기 또는 현재 입력으로 다시 생성. 구조안 후보: 다시 생성 또는 버리기(구조안 후보 보기는 지금 없다) |
| 저장과 적용 실패 | 새 분류 `storage`(코드 `apply_failed`, `result_unreadable`, `StorageError`) | 결과는 원장의 후보로 남음 | 복구 화면에서 후보 보기. 저장 공간과 폴더 권한 확인 |
| 프로젝트 없음 | 코드 `project_missing` | 없음 | 프로젝트 목록으로 |
| 작업 기록 | `ledger` | 편집과 내보내기는 계속 가능 | 앱 다시 시작 |
| 예기치 않은 오류 | 새 분류 `internal` | 입력은 그대로 | 다시 시도. 진단 상세에 작업 ID, 시각, 작업 종류를 보여 서버 로그와 대조하게 하고, 반복되면 이 정보를 개발자에게 전달하라고 안내 |
| 취소 | `cancelled` | 반영된 장 수, 보관된 후보 | 안내만(필요하면 다시 생성) |
| 중단 | 상태 `interrupted`, 원인 분류 없음 | 반영된 장 수 | 그 장 다시 생성. 복구 화면의 "결과 없이 끝난 작업" |
| 완료 여부 확인 필요 | 상태 `remote_completion_unknown` | 알 수 없음 | 다시 생성(사용량이 한 번 더 기록될 수 있다는 확인을 거침, 지금 화면의 확인 유지) |
| 보류 | 장 행 코드 `held_stale_plan` | 반영된 장 | 구성 다시 확인(구성 복구 안내) |
| 앞 장 때문에 중단 | 장 행 `interrupted`이고 코드 `stopped_after_error`, `ledger_failed`, `chain_broken`, 또는 코드 없음 | 반영된 장 | 실패한 장의 원인 안내를 따름 |

- 서버 변경: `_classify`의 마지막 갈래를 `internal`로, `StorageError` 갈래를 `storage`로 바꾼다. 묶음 경로의 직접 기록 네 곳(사실 7)을 같은 규칙으로 고친다(강제 정리는 `internal`, 원장 쓰기 실패는 `ledger`, 저장 실패와 결과 읽기 실패는 `storage`, 프로젝트 없음은 `storage`와 코드 `project_missing`). 묶음 남은 장의 코드는 앞 장의 원인을 따른다: 연결 실패 뒤는 지금의 `provider_failed`를 유지하고, 그 밖의 실패 뒤는 `stopped_after_error`로 바꾼다. 이미 원장에 기록된 `provider_failed`는 그대로 읽는다.
- 원장 재시작 조정(`reconcile_job`, `reconcile_chapter`, `parent_outcome`)은 원인 분류를 읽지 않고 코드 세 값(`held_stale_plan`, `stale_story_plan`, `chain_broken`)만 비교하므로 영향이 없다(`storage/job_ledger.py:551-624`).
- 허용값 두 목록(`ERROR_CLASSES`, `ErrorClass`)에 `storage`와 `internal`을 함께 더하고, 두 집합이 같은지 확인하는 시험을 둔다. 응답 모델이 바뀌므로 같은 커밋에서 OpenAPI와 화면 타입을 재생성한다.
- 읽기 경로를 먼저 관대하게 바꾼다. 원장 행의 원인 분류가 응답 모델이 모르는 값이면 `internal`로 읽고 원래 값은 진단 상세용 필드에 남긴다. 작업 조회, 작업 목록, 진행 API는 이런 행이 있어도 200이다. 이 변경은 새 값을 쓰는 변경보다 먼저 커밋한다.
- "무엇이 보존됐는가"는 화면이 아는 사실로 쓴다. 서버 문구를 그대로 보이는 것은 "무슨 일이 생겼는가" 칸뿐이고, 422 입력 검증 문구는 그 칸에서도 고정 문구로 바꾼다.
- 작업이 만들어지기 전의 실패도 같은 컴포넌트로 보인다: 로컬 서비스에 닿지 못함(앱 다시 시작), 다른 작업 진행 중 409 `generation_active`(그 작업 취소, 지금의 `ActiveJobNotice`), 등록 기준 변경 412(서버 내용 다시 읽기), 동의 없음 428(동의 대화 상자), 원장 열기 실패 503(앱 다시 시작), 등록 검사의 `stale_story_plan` 409(구성 복구 안내).
- 진단 상세: 기본으로 접혀 있는 영역에 오류 코드, 원래 원인 분류, 응답 원문(형식 오류일 때), 사용량, 작업 ID와 시각을 넣는다.
- 사용량(R12): 사실 4의 모든 위치(호출 횟수 문구와 실패 장 단서 포함)를 진단 상세로 옮긴다. 실패 장 단서는 사용량 합계의 정확성 설명이므로 사용량과 함께 옮기고, 내부 파일 이름 대신 "정확한 기록은 프로젝트 폴더의 사용량 기록 파일"로 쓴다. 사용량 기록 파일은 바꾸지 않는다. 판정은 "기본 상태에서 보이지 않고, 진단 상세를 펼치면 보인다"이고, 화면 시험(`not.toBeVisible`과 펼친 뒤 `toBeVisible`)과 헤드리스 확인(`isVisible`)이 같은 판정을 쓴다. 시험은 위치 목록이 아니라 "`usage` 표시 요소가 모두 접힌 진단 상세 안에 있다"로 건다.
- 기본 화면의 JSON(사실 5): 문서 전체 변경과 근거 이동은 접힌 "고급 작업"으로 옮긴다(4.1). 보존 실패 때의 덱 JSON 복사 상자는 데이터 손실을 막는 탈출구라 예외로 남긴다. 서명 검수 JSON 파일 입력은 제출본 자격 영역의 파일 선택으로 두고 JSON 내용은 보이지 않는다. 두 예외는 확정 커밋에서 제품 설계 1절에 날짜와 사유로 적는다.
- D2a 이월 (3), (4)의 충돌 문구는 이 컴포넌트로 다시 쓴다. "새로고침" 대신 보존 흐름의 행동(서버 내용 다시 읽기, 보존한 변경 보기)을 안내한다.
- 작업 종결 알림(`JobAnnouncer`)은 성공, 실패, 취소, 중단을 다른 문구로 알린다(C23).

### 4.4 생성 중 이동과 편집 (C7, C12, C13, C16, C21)

잠금과 "생성 중" 표시는 화면이 보고하는 바쁨이 아니라 서버의 진행 작업(`activeJob`의 종류와 프로젝트)으로 정한다. 화면 바쁨은 그 화면 안의 입력 잠금에만 쓴다(사실 10). 작업을 등록한 화면은 등록 응답을 받은 직후 프로젝트 화면의 진행 작업을 갱신한다(등록 응답의 작업을 바로 반영하고 진행 작업을 다시 조회한다, 사실 11).

생성 작업은 두 종류로 나뉜다.

- 후보형 작업(구조안 생성, 도식, 구성 재작성과 수리, 편집 단계의 장 재생성, 축약): 결과가 후보로 남고 사용자가 반영할 때까지 덱을 쓰지 않는다. 반영 직전 재비교 방식은 종류마다 다르다(사실 12). 구조안은 재비교가 없으므로 D3a-5가 먼저 보강한다(아래).
- 덱을 직접 쓰는 작업(장 생성 묶음, 구성 단계의 "이 장 다시 생성" 포함): 서버가 장마다 덱을 쓴다. 편집 화면은 덱 전체를 저장하므로 묶음 중 같은 덱의 편집을 열면 두 쓰는 쪽이 생긴다.

D3a의 범위(결정 Q1의 A, 사용자 결정 2026-10-10)와 그에 따른 설계 판단은 다음 표다. 사용자가 고른 것은 "장 생성 묶음 중 같은 프로젝트의 덱 편집은 읽기 전용"이고, 나머지 칸은 그 결정에서 이어지는 설계 판단이다.

| 서버의 진행 작업 | 단계 이동, 목록으로, 다른 프로젝트 | 덱 편집(보고 정보, 구성, 편집, 구성의 재작성과 문서 변경 적용) | 자료 편집 | 내보내기, 스냅샷 복구, 다시 읽기, 보존한 변경 복원 | 검수 기록과 제출본 영역 | AI 설정 |
|---|---|---|---|---|---|---|
| 이 프로젝트의 후보형 작업 | 허용 | 허용. 단 그 작업을 띄운 화면의 입력은 잠근다(아래) | 허용 | 허용 | 허용 | 잠금 |
| 이 프로젝트의 장 생성 묶음 | 허용 | 읽기 전용 | 허용(아래 비용) | 잠금 | 잠금 | 잠금 |
| 다른 프로젝트의 작업 | 허용 | 허용 | 허용 | 허용 | 허용 | 잠금 |

- 후보형 작업을 띄운 화면의 입력: 구조안 생성 중 구성 화면의 초안과 보고 질문은 잠근다. 생성 결과가 도착하면 초안을 확인 없이 바꾸기 때문이다(사실 12 마지막 항목). 다른 단계의 편집은 허용한다. 구성 화면을 떠났다 돌아왔을 때 결과가 이미 도착했고 초안이 바뀌었으면 지금처럼 묻는다.
- 구조안 후보 보강(critical 반영): ① 다시 마운트 경로도 머문 경로와 같이 낡음 이유를 검사하고 같은 안내를 띄운다. ② 승인 직전에 후보 작업을 다시 조회해(장 재생성의 반영 직전 재조회와 같은 방식) 낡았으면 승인하지 않고 "다시 생성 또는 버리기"를 안내한다. 이 보강 없이 후보형 작업 중 이동을 허용하지 않는다. 같은 탭에서 "구조안 생성 → 자료 수정 → 구성 복귀 → 승인"이 처음 가능해지기 때문이다.
- 묶음 중 덱 편집을 읽기 전용으로 두는 것은 사용자 안내이고, 묶음과 사용자 저장의 경합을 실제로 막는 것은 서버의 `If-Match`와 사슬 검사다. 읽기 전용 편집 화면에는 "생성 중인 장은 끝나면 보입니다"를 보이고, 묶음이 끝나면 4.1의 규칙대로 그 화면을 새 덱으로 다시 마운트한다(미저장 변경이 없으므로 충돌 안내를 띄우지 않는다).
- 묶음 중 자료 편집의 비용: 사슬은 자료를 보지 않으므로, 자료를 고친 뒤 처음 끝나는 장(AI 호출을 이미 마친 장)은 이전 입력 기준 후보가 되고 남은 장은 중단되며 묶음은 `chain_broken`이다(사실 16). 자료를 한 번 고치면 AI 호출 하나가 반영되지 않는다. 자료 화면은 묶음 중 편집을 허용하되 저장 전에 이 사실을 알린다.
- 구성 단계의 "이 장 다시 생성"은 묶음이라 덱을 읽기 전용으로 만든다. 편집 단계의 같은 이름 버튼은 후보형이다. D3a-5가 두 버튼의 안내 문구를 다르게 하고(구성 단계: "다시 생성하는 동안 문서 편집이 잠깁니다"), 이름을 바꿀지는 화면 확인에서 정한다.
- 묶음 사슬의 관련 입력 단위 완화와 장 단위 저장(결정 Q1의 B)은 저장 단위를 바꾸므로 D3c로 넘긴다. A에서는 묶음 중 덱을 쓰는 화면 경로를 막으므로 사슬이 사용자 편집으로 끊기지 않는다.
- 대기열(C12): 만들지 않고 409 거절을 유지한다. A에서는 한 번에 한 작업이라는 제약이 사용자의 이동과 편집을 막지 않는다. 대기열은 대기 작업의 재바인딩 검사(D2 계약 행동 규칙 3)를 새로 만든다. 확정 커밋에서 구현 설계 6절의 "직렬화한다"에 날짜와 정정을 적는다.
- AI 설정 잠금은 제품 설계 5절 G의 "변경은 다음 작업부터 적용"과 다르다. 서버가 생성 중 설정 변경을 409로 거절하기 때문이다(`connections.py:172-174`). D4가 "다음 작업부터 적용"을 구현할 때 푼다(2절 표).
- β R8(C13): 조회 실패 횟수의 임계값을 두지 않는다. 근거가 되는 측정값이 없기 때문이다. 작업 조회가 실패하는 동안 그 작업을 띄운 화면의 입력은 잠근 채 두고, 그 작업의 취소와 "다시 확인"만 연다. 단계 이동은 위 표로 이미 가능하므로 화면 전체가 묶이지 않는다. 진행 작업 확인(`/api/jobs/active`)이 그 작업을 더 이상 진행 중으로 돌려주지 않는데 작업 조회는 계속 실패하면 조회를 멈추고, 4.3의 "작업 기록" 행과 같이 "작업 기록을 읽지 못해 결과를 확인하지 못했습니다. 앱을 다시 시작해 주세요"로 바꾼다(사실 18). 복구 화면도 같은 원장을 읽으므로 그쪽으로 안내하지 않는다. 묶음 중이면 덱 편집의 읽기 전용도 유지한다.
- D2a 이월 (2)(C16): 구성 초안만 고친 채 단계를 옮기면, 초안은 덱이 아니어서 저장되지 않는다. 이동 전에 확인을 묻는다.
- 주안점과 목표 장수: 구성 화면의 지역 상태를 프로젝트 화면의 상태로 끌어올려 단계 이동 사이에 보존한다(저장하지 않는다, 사실 13). 요구 R15의 "저장/오류 후 복구"와 제품 설계 8절 목표 ④(실패 후 입력 재작성 없이 재개)에 맞추기 위해서다.
- D2a 이월 (18)(C21): 자료와 구성 화면의 폼 입력은 충돌 때 보존하지 않는다. D3a-5가 생성 중 이동과 편집으로 충돌이 실제로 늘어나는 경로가 있는지 시험으로 확인하고 구현 또는 방치 확정을 정한다.
- 확정 커밋에서 제품 설계 7절 둘째 항목과 구현 설계 6절 셋째 문단에 2026-10-10 정정(장 생성 묶음 중 같은 프로젝트의 덱 편집은 읽기 전용, D3c에서 다시 판단)을 적는다.

### 4.5 공통 알림 지점, 여러 탭, 웹 모드 탭 닫기 (C10, C14)

- 공통 알림 지점: 저장 성공(덱 PUT, 재작성과 문서 변경과 근거 이동 적용, 보존본 복원, 스냅샷 복원, 자료 저장과 업로드), 작업 등록 응답, 작업 종결을 `client.ts`의 공통 처리 한 곳에서 화면 안 이벤트로 낸다. D3a-3의 진행 API 다시 조회와 D3a-5의 진행 작업 갱신이 이 이벤트를 쓴다. D3a-3이 이 지점을 만들고 D3a-6은 채널 송신만 더한다.
- β R15(C14): 같은 출처의 탭 사이에 `BroadcastChannel`로 위 이벤트를 알린다. 채널 객체는 탭마다 하나만 만든다. 표준상 보낸 객체는 자기 메시지를 받지 않으므로 같은 탭의 반영은 공통 알림 지점이 직접 한다. "작업 시작"은 등록 응답을 받은 뒤에만 보낸다(그 전에 보내면 받은 탭의 조회가 빈 결과를 받는다).
- 수신 동작은 진행 작업 조회와 진행 API 조회만 허용한다. 수신 탭은 덱을 읽지 않고 전역 저장 ETag를 바꾸지 않는다. 덱이 바뀐 것은 지금처럼 묶음 종결의 기준 조회(β R1 분기)와 다음 저장의 412가 알린다. 메시지 내용은 믿지 않고 서버를 다시 조회하므로 순서가 뒤바뀌어도 늦은 응답은 버려진다(`ProjectView.tsx:49-52`). 채널이 없는 환경에서는 지금처럼 창 초점 조회로 돌아간다. 독립 앱은 창이 하나라 영향이 없다.
- 웹 모드 탭 닫기(C10)는 방치 확정이다(결정 Q2의 A, 사용자 결정 2026-10-10). 근거는 셋이다. 개정판의 배포 형태는 독립 앱이고 독립 앱은 창 닫기에서 이미 묻는다(D2b-5c). 웹 모드에서 탭을 닫아도 작업 결과는 남는다: 장 생성 묶음은 덱에, 구조안 후보는 구성 단계를 다시 열 때 초안 후보로, 그 밖의 후보와 결과 없는 종결은 복구 화면에 보인다. 브라우저는 새로고침과 탭 닫기를 구별해 주지 않으므로, 서버가 취소하게 만들면 새로고침도 작업을 취소할 위험이 있다. 다시 열 조건은 D6의 사람 사용 검증에서 웹 모드로 쓰다가 원치 않는 AI 호출이 기록되는 경우이고, D6 기록 항목에 "웹 모드 사용 여부"를 넣어 관측한다. 기록 위치는 D2b 2.6의 선례를 따른다. 확정 커밋에서 로드맵 방치 확정 문단에 올리고, 제품 설계 7절과 D2b 계획 3절의 해당 행에 날짜와 사유를 적고, 로드맵 D6 관측 항목에 다시 열 조건을 더한다.

### 4.6 크기 토큰과 버튼 계층 (C3, C19)

- 크기 토큰: 본문 글자 15~16px, 제목 24~28px, 입력 높이 40px 이상, 주요 버튼 44px(WCAG 2.5.5의 44×44와 같다), 여백 8/16/24/32px, 패널 모서리 8~12px(제품 설계 4절). 범위로 적힌 값은 시안(`docs/design/2026-10-02-revision-wireframe.html`)의 값을 쓰고 시안 값을 주석에 적는다. 화면 바탕 `--color-bg`와 패널 `--color-panel`의 구별을 셸 배치에 적용한다.
- 버튼 계층: 주 행동, 보조, 텍스트 행동, 위험 행동의 넷이다. 단계와 상태별 주 행동은 다음 표다. 행동할 수 있는 상태에서 주 행동은 정확히 1개다.

| 단계 | 상태 | 주 행동 |
|---|---|---|
| 보고 목적 | 항상 | 보고 정보 저장 |
| 자료 | 항상 | 파일 선택(파일 업로드). 같은 영역의 "자료 추가"는 빈 자료를 만드는 보조 행동이다 |
| 구성 | 초안 없음 또는 낡음 | 구조안 생성 |
| 구성 | 유효한 초안 | 승인하고 내용 생성 |
| 편집 | 항상 | 없음(편집은 자동 저장이고 주 행동은 장별 패널 안에 있다). 이 단계는 "정확히 1개" 시험에서 뺀다 |
| 검토와 내보내기 | 항상 | 초안 PPTX 내보내기 |

- 위험 행동 계층: 제출본 게시, 스냅샷 복원, 보존본 복원과 지우기, 후보 버리기, 보존하지 못한 변경을 버리고 되돌리기, 자료 삭제. 장 내용 교체를 동반한 승인은 구성 단계의 주 행동으로 두고, 지워질 기존 장 수를 버튼 옆 주의 문구로 누르기 전에 보인다(2026-10-10 D3a-1 리뷰 R13 반영. 위험 계층으로 바꾸면 그 상태의 주 행동이 0개가 된다).

  D3a-7(화면 확인)은 리뷰 대상이 아니라 증거 생산이다. 두 탭 재현 스크립트의 새 구조 개작, 반영 커밋의 재리뷰, 최종 화면 확인 재실행은 위 추정에 들어 있지 않다. D2b는 예산을 다 써서 반영 커밋을 다시 리뷰하지 못했으므로, 착수 전 결정에 이 셋의 포함 여부를 함께 묻는다.
- 리뷰 지시: 발견을 심각도와 상관없이 모두 보고하고, 찾는 즉시 결과 파일에 덧붙인다. 같은 화면이나 같은 전역 상태를 건드리는 설계는 실제 서비스로 재현해 보라고 명시한다. 필터링은 메인 세션이 중복을 걷어 낸 뒤 한 번에 한다.
