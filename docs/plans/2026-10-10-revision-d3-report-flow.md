## 1. D3의 범위와 분할

구현 설계 7절은 D3를 "목적별 입력/패턴, 구성/편집/검토 5단계, 사용량 문구 정리"로 정의하고 R01, R09, R11, R12, R15, R16을 건다. 다음 단계로 넘어가는 기준은 네 가지다. ① IR 포함 10유형의 저장, 생성, 편집 보존 ② 드롭다운과 시각 구조가 다른 대표 페이지 ③ 직접 요소 편집, 저장, PPTX 일치 ④ 긴 작업 중 이동과 취소, 실패 재개다.

이 범위는 성격이 다른 세 덩어리라 셋으로 나눈다(사용자 결정 2026-10-10).

| 묶음 | 내용 | 저장 형식 | 끝나면 관측되는 것 |
|---|---|---|---|
| D3a 화면 골격 | 다섯 작업 단계 화면과 상단 머리, 단계 상태 표시, 크기 토큰과 버튼 계층, 원인별 실패 안내와 진단 상세(R11 화면, R12), 생성 중 이동과 편집, 여러 탭 처리 | 바꾸지 않는다 | 관문 기준 ④와 R01의 현재/완료 분리 |
| D3b 보고 목적 | 보고 유형의 명시 선택 기록, IR Pitch Deck 저장값, 10종 드롭다운과 유형별로 시각 구조가 다른 예시 화면, 유형별 추가 입력, 원하는 결과 네 가지의 저장과 표시 | 바꾼다(한 번) | 관문 기준 ①②, R09 |
| D3c 직접 수정 | 구현 설계 10절의 직접 수정 데이터 계약(안정적인 요소 ID, 논리 좌표, 명령 단위 되돌리기, 출력 fingerprint 무효화), PPTX가 같은 값을 소비, AI 재생성 때 사용자 수정 보존, 장 후보를 서버가 현재 덱에 적용하는 경로, 동기 생성 래퍼 6개의 제거와 시험 이전 | 바꾼다 | 관문 기준 ③, R16 |

분할 원칙은 둘이다.

- D3a는 저장 형식(덱, manifest, 원장의 열)을 바꾸지 않는다. 0.2.0과 같은 자료 폴더를 쓰는 공존 판정(D2a-1)을 다시 열지 않기 위해서다. 형식이 바뀌는 일은 D3b와 D3c에 모으고, 각 묶음이 공존 판정을 한 번씩 한다.
- D3a가 먼저다. 다섯 단계 화면의 틀이 있어야 D3b의 보고 목적 화면과 D3c의 편집 화면이 그 안에 들어간다. D3c의 상세는 D3a와 D3b에서 확정된 실제 구조를 보고 쓴다(로드맵 원칙: 단계별 상세 계획은 착수 시점에 작성한다).

D3 관문은 D3c까지 끝나야 통과한다. D3a나 D3b만 끝난 상태를 D3 관문 통과로 기록하지 않는다. 묶음마다 끝나면 랩업 보고 뒤 사용자와 상의하고 다음 묶음으로 넘어간다(단계 경계 규칙).

> 2026-10-10 기록: 단계표의 R15는 개정 요구 목록에서 2026-10-02에 "구현/검증 완료"다(구조안 입력란 명칭). D3는 R15를 다시 구현하지 않고, D3a-2가 구성 화면을 옮길 때 명칭과 요청 전달이 유지되는지를 회귀 시험으로 확인한다. 이 문서에서 "β R15"는 D2b-β 묶음 리뷰의 발견 번호이고 요구 R15와 다르다.

## 3. 현재 코드에서 확인한 사실 (기준 `28ab86d`)

1. 앱은 프로젝트 목록과 프로젝트 화면 둘이다(`App.tsx`). 프로젝트 화면(`ProjectView.tsx`)은 탭 4개(자료, 구조안, 편집, 검수 이력)와 버튼 2개(초안 PPTX 내보내기, 스냅샷 복구)를 한 줄 `nav`에 둔다. 처음 여는 탭은 자료이고, 이 프로젝트의 장 생성 묶음이 돌고 있으면 구조안이다. 저장 상태 표시는 편집 화면에만 있다(D2a-5).
2. 자료 탭(`SourcesScreen.tsx`)에 "보고 정보"(제목, 보고 유형, 보고자, 피보고자)와 "입력 자료"가 함께 있다. 보고 정보는 덱의 `meta`이고 자료는 프로젝트의 별도 파일이다. 같은 탭에서 덱 저장과 자료 저장이 함께 일어난다.
3. 진행 API `GET /api/projects/{name}/progress`는 단계 다섯(`purpose`, `sources`, `structure`, `editing`, `review`)의 상태(`not_started`, `ready`, `needs_review`)와 사유 코드, 그리고 `jobs`를 돌려준다(`pipeline/progress.py`). 화면용 함수 `api.getProgress`가 있으나(`client.ts:309`) 부르는 화면은 없다. 보고 목적은 명시 선택 기록이 없어서 제목이 있으면 항상 `needs_review`(`report_type_unconfirmed`)다.
4. 사용량 문구는 세 곳에 있다. 구조안 결과 아래(`StructureScreen.tsx:651`), 장 생성 합계와 "실패한 장의 사용량은 이 합계에 포함되지 않았습니다" 안내(`:745-750`), 구성 재작성 결과 아래(`StoryRewritePanel.tsx:260`)다. 문구는 `api/usage.ts`의 `formatUsage`가 만든다. 사용량 기록 파일 `ai-usage.jsonl`은 서버가 쓴다.
5. 실패 문구는 대부분 서버가 보낸 `detail` 문자열이다(`messageOf`, `jobResult`). 원장의 원인 분류 `error_class`는 `input`, `ai_output`, `connection`, `base_changed`, `cancelled`, `ledger`의 여섯이다(`storage/job_ledger.py:63`). 화면이 이 분류를 쓰는 곳은 장 생성 묶음의 요약(`StructureScreen.tsx:278-299`)뿐이다. 구조안 형식 오류는 화면이 문구 두 종을 따로 만든다(`:178-180`).
6. 원인 분류에 두 가지 빈틈이 있다. 첫째, 예기치 않은 예외도 `input`(입력 오류), 상태 500으로 분류된다(`server/app.py:436-437`). 화면이 분류만 보고 "입력을 확인하세요"라고 안내하면 틀린 안내가 된다. 둘째, `connection`에는 성격이 다른 실패가 섞여 있다. 설치나 로그인이 없어 호출을 시작하지 못한 경우(`ProviderNotAvailable`), 호출은 했으나 시간 초과나 한도나 연결 종료로 실패한 경우(`ProviderCallFailed`), 생성 중 연결 설정과 충돌한 경우(`ConnectionConflict`, 409)다. 지금은 셋을 구별하는 코드가 없고 문구에만 차이가 있다.
7. 생성 중 잠금: 프로젝트 화면의 `aiBusy`는 구조안 화면의 바쁨(`generating`), 도식 생성, 진행 작업 확인 전, 이 프로젝트의 장 생성 묶음 중 하나라도 참이면 목록 이동, 자료 탭, 편집 탭, 내보내기, 스냅샷 복구, 서버 내용 다시 읽기, AI 설정을 잠근다(`ProjectView.tsx:100-103`, 머리 버튼들). 구조안 화면은 후보형인 구조안 생성 중에도, 장 생성 묶음을 조회하는 동안에도, 다시 등록과 이어서 조회할 때도 바쁨을 올린다(`StructureScreen.tsx:198, 309, 365, 468`). 그래서 지금은 후보형 작업인 구조안 생성 중에도 다른 탭으로 갈 수 없다. 이 바쁨의 주석("다른 탭 진입을 막는다")은 서버 묶음 작업 이전의 화면 루프 시절 것이다. 구조안 탭은 도식 생성과 업로드로만 잠근다. 구조안 화면은 자기 작업 중 입력 묶음(`fieldset`) 전체를 잠근다(`StructureScreen.tsx:624`). 편집 화면의 장 재생성과 축약은 패널만 바쁨으로 둔다.
8. 편집 화면은 덱을 마운트 때 한 번 받고 덱 전체를 저장한다. 저장 ETag는 프로젝트 이름을 키로 한 모듈 전역 값이다(`client.ts:122`). 같은 탭의 여러 화면과 저장 경로가 이 값을 함께 쓴다. β 리뷰 R1(critical)은 이 공유 값이 다른 경로에서 갱신되면서 편집 화면의 옛 덱이 묶음이 만든 장을 덮은 사례다.
9. 장 생성 묶음은 서버가 장마다 결과를 덱에 쓰고, 다음 장 전에 덱 ETag가 자기가 쓴 값인지 확인한다(사슬). 다르면 남은 장을 적용하지 않고 `chain_broken`이나 `base_changed`로 끝낸다(D2b-4). 자료가 바뀌면 `sources_changed`로 따로 기록한다(β 리뷰 R5, R18).
10. 진행 작업 조회는 창 초점을 얻을 때와, 진행 중 작업이 있는 동안 1초 간격으로 한다(`ProjectView.tsx:60-75`). 진행 중 작업이 없는 탭은 다른 탭이 새 작업을 시작해도 초점을 얻기 전까지 모른다(β R15).
11. 작업 조회가 실패하면 화면은 "작업 상태를 확인하지 못했습니다. 계속 확인합니다."를 보이고 조회를 끝없이 계속한다(`api/jobs.ts:7`). 그동안 구조안 화면은 바쁨 상태라 다른 일을 할 수 없다(β R8).
12. 새 작업 등록은 진행 중인 작업이 있으면 409로 거절된다. 대기열은 없다(D2b 9절 5항).
13. 창 닫기: 웹 모드는 `beforeunload` 경고가 저장하지 않은 변경, 업로드, 진행 중 AI 작업에 뜬다. 독립 앱은 진행 중 AI 작업을 main 프로세스가 "계속 작업 / 취소 후 닫기"로 묻는다(D2b-5c).
14. 디자인 토큰은 색 17개, 초점선 굵기, 작은 모서리, 여백 일부만 정의돼 있다(`styles.css`). 크기 토큰과 버튼 계층은 없다. 좁은 창 기준은 D2a-5가 쓴 1000px 이하다(D2 계획 D2a-5 위치 항목).
15. β R1 수정은 탭 이름으로 갈린다(`ProjectView.tsx:86-98`). 묶음이 끝났을 때 이 탭의 저장 ETag가 서버와 다르면, 지금 탭이 구조안이면 덱을 다시 읽고 그 밖이면 충돌 안내를 띄운다. 기준 조회의 412는 "저장본이 바뀜"으로 읽는다(`74165ad`). D3a-2가 탭을 단계로 바꾸면 이 분기의 기준을 다시 정해야 한다.
16. 원인 분류의 타입은 서버 모델의 고정 목록(`ErrorClass = Literal[...]`, `models/jobs.py:15`)이다. 값을 더하면 OpenAPI와 화면 타입(`frontend/src/api/types.ts`)이 바뀌고, 같은 커밋에서 재생성해야 한다(`test_openapi.py`).

## 4. D3a 설계

### 4.1 다섯 단계와 지금 탭의 대응

| 단계 | 지금 위치 | D3a에서 |

| 1 보고 목적 | 자료 탭의 "보고 정보" | 자기 화면. 입력 항목과 저장 계약은 그대로(제목, 보고 유형 9종, 보고자, 피보고자). 유형 드롭다운과 예시 화면은 D3b |

| 3 구성 | 구조안 탭 | 그대로 옮긴다. 주안점 입력란 명칭과 요청 전달(요구 R15) 회귀 |

β R1의 분기(사실 15)는 탭 이름이 아니라 "그 화면이 덱 사본을 들고 저장하는가"로 다시 쓴다. 보고 목적(덱의 `meta` 폼)과 편집은 충돌 안내를 띄우고, 구성은 지금처럼 덱을 다시 읽고, 자료와 검토와 내보내기는 덱을 저장하지 않으므로 다시 읽는다. 이 규칙은 D3a-2의 회귀 시험과 α 묶음 리뷰의 실제 서비스 두 탭 재현으로 확인한다.

스냅샷 복구와 "충돌로 보존한 변경"은 상단 머리의 보조 행동으로 옮기고, 보존 건수에서 바로 연다(C18). AI 설정은 상단 머리의 드로어로 옮긴다. 드로어의 내용(계정, 모델, Effort)은 D4가 바꾸고 D3a는 위치만 옮긴다.

배치는 제품 설계 3절을 따른다. 좌측 단계 목록 216px, 본문 유동 폭, 상단 머리에 프로젝트 제목, 저장 상태, 진행 중 작업 표시, 현재 AI 연결이다. 좁은 창(1000px 이하, D2a-5와 같은 기준)에서는 단계 목록을 접고 머리의 단계 선택으로 바꾼다. 확인 폭은 D2a와 같은 1440px, 1024px, 512px와 200% 확대다.

### 4.2 현재 단계와 단계 상태를 따로 보인다 (R01, C1, C11, C15, C20)

- 현재 보고 있는 단계는 선택 막대와 `aria-current`로 보인다. 단계 상태(시작 전, 준비됨, 확인 필요)는 진행 API의 값을 상태 표시 컴포넌트(D2a-5)로 보인다. 두 표시는 서로 다른 요소다. 선택한 단계를 완료로 보이지 않는다.
- 조회 시점: 프로젝트를 열 때, 저장이 성공한 뒤, 작업이 끝난 뒤, 창 초점을 얻을 때다. 조회가 실패하면 단계 상태를 "확인하지 못함"으로 보이고 준비됨으로 두지 않는다.
- 사유 코드마다 한 줄 문구를 둔다. 문구 표는 D3a-3이 만들고 시험이 모든 사유 코드에 문구가 있는지 확인한다. 보고 목적은 D3b 전까지 항상 확인 필요다. D3a에서는 "보고 유형을 확인해 주세요"를 보인다. D3a와 D3b 사이에 릴리스는 없다.
- 구성의 낡음 사유(`stale_story_plan`)는 판정 계약을 바꾸지 않고 문구만 정한다(C15). 문구는 "보고 정보나 장 제목이 바뀌어 구성을 다시 확인해야 합니다"처럼 무엇이 원인일 수 있는지를 함께 알린다.
- 검토와 내보내기는 세 부분(자동 검사, 사람 검토, 파일)을 따로 보이고, 단계 목록에는 셋을 합친 한 줄을 보이되 하나라도 확인 필요면 확인 필요로 보인다(C20의 단계 수준 사유).
- 진행 API의 `jobs`는 단계 목록의 해당 단계 옆에 "생성 중"과 "6장 중 1장 실패" 같은 요약을 보이는 데 쓴다.

### 4.3 원인별 실패 안내와 진단 상세 (R11 화면, R12, C4, C6, C17)

실패 안내는 제품 설계 5절 D의 세 요소를 갖는다: 무슨 일이 생겼는가, 무엇이 보존됐는가, 지금 할 수 있는 일. 세 요소를 그리는 공용 컴포넌트 하나를 두고 생성 화면들이 이를 쓴다.

| 원인 | 조건 | 지금 할 수 있는 일(주 행동) |
|---|---|---|
| 입력 | `error_class=input`이고 사용자가 고칠 수 있는 코드(구성 낡음, 도식 장 거절 등) | 해당 단계나 입력으로 이동 |
| 입력: 코드 없음 | `error_class=input`이고 코드가 없거나 화면이 모르는 코드(없는 장 404, 템플릿 불일치 422, 저장소 오류 등) | 서버 문구를 "무슨 일" 칸에 보이고 "입력을 확인한 뒤 다시 생성"을 안내. 이동할 단계를 추측하지 않는다 |
| AI 출력 | `ai_output` | 같은 입력으로 다시 생성 |
| 연결: 시작 불가 | 새 코드 `provider_unavailable` | AI 연결 열기 |
| 연결: 호출 실패 | 새 코드 `provider_call_failed` | 잠시 뒤 다시 생성, 반복되면 AI 연결 확인 |
| 연결: 설정 충돌 | `ConnectionConflict` 409 | 진행 중 작업이 끝난 뒤 다시 생성 |
| 기준 변경 | `base_changed`, `sources_changed` | 후보 보기 또는 현재 입력으로 다시 생성 |
| 취소 | `cancelled` | 남은 결과 안내(반영된 장 수, 보관된 후보) |
| 작업 기록 | `ledger` | 편집과 내보내기는 계속 가능함을 알림 |
| 예기치 않은 오류 | 새 분류 `internal` | 다시 시도, 반복되면 진단 상세를 복사 |

- 서버: `_classify`의 마지막 갈래를 `input`에서 `internal`로 바꾸고, 제공자 예외에 코드 `provider_unavailable`과 `provider_call_failed`를 붙인다. 원장의 `error_class`는 TEXT 열이고 허용값 검사는 파이썬(`ERROR_CLASSES`)에 있으므로 원장의 열과 형식 기록은 바뀌지 않는다. 그러나 응답 모델의 `ErrorClass`는 고정 목록이므로(사실 16) OpenAPI와 화면 타입이 바뀐다. 같은 커밋에서 재생성한다. 원장 행을 읽는 경로가 모르는 값을 만날 때 어떻게 보이는지도 시험으로 고정한다. 이 판단은 리뷰에서 다시 확인받는다(가정 1).
- "무엇이 보존됐는가"는 화면이 아는 사실로 쓴다: 입력은 그대로임, 이미 반영된 장 수, 후보가 원장에 남았는지. 서버 문구를 그대로 보이는 것은 "무슨 일이 생겼는가" 칸뿐이다.
- 진단 상세: 기본으로 접혀 있는 영역에 오류 코드, 응답 원문(형식 오류일 때), 사용량을 넣는다. 사용량 문구(R12)는 기본 화면에서 이 영역으로 옮기고, 사용량 기록 파일은 바꾸지 않는다. 사용자가 펼쳐야 보인다.
- D2a 이월 (3), (4)의 충돌 문구는 이 컴포넌트로 다시 쓴다. "새로고침" 대신 보존 흐름의 행동(서버 내용 다시 읽기, 보존한 변경 보기)을 안내한다.

### 4.4 생성 중 이동과 편집 (C7, C12, C13, C16, C21)

생성 작업은 두 종류로 나뉜다.

- 후보형 작업(구조안 생성, 도식, 구성 재작성과 수리, 장 재생성, 축약): 결과가 후보로 남고 사용자가 반영할 때까지 덱을 쓰지 않는다. 반영 직전 서버가 ETag와 fingerprint를 다시 비교하고 다르면 이전 입력 기준 후보로 남긴다(D2b). 그래서 이 작업 중의 이동과 편집은 저장 계약을 바꾸지 않고 허용할 수 있다.
- 덱을 직접 쓰는 작업(장 생성 묶음): 서버가 장마다 덱을 쓴다. 편집 화면은 덱 전체를 저장하므로(사실 8), 묶음 중 같은 덱의 편집을 열면 두 쓰는 쪽이 생긴다. 지금은 사슬 검사가 묶음을 멈추고 사용자의 저장은 412로 막히므로 데이터는 잃지 않지만, 사용자는 묶음이 멈추거나 저장이 계속 충돌하는 화면을 보게 된다.

D3a의 범위(결정 Q1의 A, 사용자 결정 2026-10-10):

| 진행 중인 작업 | 단계 이동 | 덱 편집(보고 정보, 구성, 편집) | 자료 편집 | 내보내기, 스냅샷 복구, 다시 읽기 | AI 설정 |
|---|---|---|---|---|---|
| 후보형 작업 | 허용 | 허용(결과는 이전 입력 기준 후보가 될 수 있음) | 허용 | 허용 | 잠금(서버 임대가 409) |
| 이 프로젝트의 장 생성 묶음 | 허용 | 읽기 전용 | 허용(남은 장은 `sources_changed`로 보류) | 잠금 | 잠금 |
| 다른 프로젝트의 작업 | 허용 | 허용 | 허용 | 허용 | 잠금 |

- 장 생성 묶음 중 덱 편집을 읽기 전용으로 두는 이유는 사실 8과 9다. 장 단위 저장으로 바꿔 묶음 대상이 아닌 장의 편집을 허용하는 안(결정 Q1의 B)은 저장 단위를 바꾸므로 요소 단위 저장을 정의하는 D3c와 함께 한다.
- 묶음 사슬의 "관련 입력 단위 완화"(C7 후반)는 B와 같은 이유로 D3c로 넘긴다. A에서는 묶음 중 덱을 쓰는 화면 경로가 없으므로 사슬이 사용자 편집으로 끊기지 않는다.
- 대기열(C12): 만들지 않고 409 거절을 유지한다. A에서는 한 번에 한 작업이라는 제약이 사용자의 이동과 편집을 막지 않는다. 대기열은 대기 작업의 재바인딩 검사(D2 계약 행동 규칙 3)를 새로 만든다.
- β R8(C13): 조회 실패 횟수의 임계값을 두지 않는다. 근거가 되는 측정값이 없기 때문이다. 대신 이동과 편집이 허용되므로 조회 실패가 화면 전체를 묶지 않는다. 구성 화면의 입력 묶음은 "작업 상태를 확인하지 못함" 동안 풀고, 안내에 "다시 확인" 행동을 둔다. 서버가 작업을 진행 중으로 다시 알려 주면 그때 다시 잠근다.
- D2a 이월 (2)(C16): 구성 초안만 고친 채 단계를 옮기면, 초안은 덱이 아니어서 저장되지 않는다. 이동 전에 확인을 묻는다.
- D2a 이월 (18)(C21): 자료와 구성 화면의 폼 입력은 충돌 때 보존하지 않는다. 생성 중 편집을 허용하면 충돌이 늘 수 있으므로, D3a-5에서 실제로 늘어나는 경로가 있는지 시험으로 확인하고 구현 또는 방치 확정을 정한다.

### 4.5 여러 탭과 웹 모드 탭 닫기 (C10, C14)

- β R15(C14): 같은 출처의 탭 사이에 `BroadcastChannel`로 "작업 시작", "작업 종결", "저장"을 알린다. 받은 탭은 진행 작업과 진행 API를 다시 조회한다. 조회 간격 같은 숫자를 새로 두지 않는다. 독립 앱은 창이 하나라 영향이 없다. 채널이 없는 환경에서는 지금처럼 창 초점 조회로 돌아간다.
- 웹 모드 탭 닫기(C10)는 방치 확정이다(결정 Q2의 A, 사용자 결정 2026-10-10). 근거는 셋이다. 개정판의 배포 형태는 독립 앱이고 독립 앱은 창 닫기에서 이미 묻는다(D2b-5c). 웹 모드에서 탭을 닫아도 작업 결과는 원장의 후보로 남고 다시 열면 복구 화면에 보인다. 브라우저는 새로고침과 탭 닫기를 구별해 주지 않으므로, 서버가 취소하게 만들면 새로고침도 작업을 취소할 위험이 있다. 다시 열 조건은 D6의 사람 사용 검증에서 웹 모드로 쓰다가 원치 않는 AI 호출이 기록되는 경우다. 기록 위치는 D2b 2.6의 선례를 따른다. 계획 확정 커밋에서 로드맵 방치 확정 문단에 올리고, 제품 설계 7절과 D2b 계획 3절의 해당 행에 날짜와 사유를 적는다. 로드맵 D6 관측 항목에 다시 열 조건을 더한다.

### 4.6 크기 토큰과 버튼 계층 (C3, C19)

- 크기 토큰: 본문 글자 15~16px, 제목 24~28px, 입력 높이 40px 이상, 주요 버튼 44px, 여백 8/16/24/32px, 패널 모서리 8~12px(제품 설계 4절). 범위로 적힌 값은 D3a-1이 한 값을 고르고 근거(시안 값)를 주석에 적는다.
- 버튼 계층: 주 행동, 보조, 텍스트 행동, 위험 행동의 넷이다. 한 단계 화면에 주 행동은 하나다(제품 설계 1절). 화면 시험이 단계 화면마다 주 행동 버튼 수가 1개 이하인지 확인한다.

## 9. 가정과 미확인

1. 원장에 새 원인 분류 `internal`을 쓰는 것은 저장 형식 변경이 아니라고 본다. 열은 TEXT이고 허용값 검사는 파이썬에만 있다. D2b 빌드는 배포되지 않았으므로 옛 빌드가 새 값을 읽는 경로는 없다. 리뷰에서 다시 확인받는다.
2. 다섯 단계 배치가 사용자에게 현재 상태를 더 잘 구별하게 하는지는 D6의 사용성 검증 전까지 미확인이다.
3. `BroadcastChannel`은 Chromium과 Electron에서 같은 출처 탭 사이에 동작한다. 시험 환경(jsdom)에서는 모의로 확인하고, 실제 동작은 헤드리스 Chromium 두 탭으로 확인한다.
4. 크기 토큰의 범위 값(15~16px 등)에서 고른 한 값이 1024px와 200% 확대에서 핵심 행동을 가리지 않는지는 화면 확인으로 본다.
