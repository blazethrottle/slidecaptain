## 1. 범위

D3 관문에서 이 Mac이 판정할 수 있는 항목 가운데 남은 하나(D3c 확인 기록 5절 "AI 재생성은 별도 후보로 만들고 덮기 전에 비교", 판정 "일부(이전 묶음 후보 제외)")를 닫는다. 같은 모양의 도식 후보(SC-02)를 함께 닫는다.

한 입구, 두 기제다. 복구 화면이 미처분 AI 후보의 공통 입구가 되지만, 장 후보와 도식 후보는 반영하는 방식이 처음부터 다르다.

| 묶음 | 대상 후보 | 반영 기제 | 끝나면 관측되는 것 |
|---|---|---|---|
| W1 장 후보 | 장 다시 생성(`chapter`), 장 축약(`condense`), 장 생성 묶음의 하위 장(`chapters`) 가운데 종결되고 처분이 `held`나 `stale`인 것 | 지금의 서버 적용 경로(`/apply/preview`, `/apply`)와 비교 화면(`CandidateCompareDialog`)을 복구 화면에서 연다 | 새 묶음이 생긴 뒤에도 이전 묶음의 낡은 장 후보를 복구 화면에서 비교하고 반영한다. 반영하면 덱이 바뀌고 후보가 목록에서 사라진다 |
| W2 도식 후보 | 도식(`diagram`) 작업의 종결된 `held`나 `stale` 후보 | 복구 화면이 편집 단계로 옮겨 도식 작성 창을 그 후보와 함께 다시 연다. 반영은 작성 창의 지금 흐름(작성 폼에 불러오기, 입력과 배치 확인, 반영)이다 | 작성 창을 닫은 뒤 도착한 도식 후보를 앱 안에서 작성 폼에 불러와 반영한다 |
| W3 문서와 확인 | 설계 결정 2개의 기록, 상위 문서 정정 문단, 화면 확인, D3 관문 판정 갱신 | 해당 없음 | D3c 확인 기록 5절의 해당 행이 "통과"로 바뀌거나 남은 이유가 적힌다 |

하지 않는 것:

- 구조안(`structure`), 보고 계획 재작성(`rewrite`), 제한된 수정(`repair`) 후보의 반영 입구. 구조안은 구성 화면이 지금처럼 자기 후보를 찾고, 재작성과 수정은 덱 전체 후보라 D2b-5c대로 보기와 버리기만 한다. 이번 결함(C1, SC-02)은 장과 도식에서만 재현됐다.
- 서버 적용 라우트의 판정 규칙 변경. 이전 묶음의 하위 장도 지금 라우트가 이미 받는다(3절 사실 2).
- 도식 후보의 서버 적용 라우트. 도식은 작성 창의 확인(구성 계획 대조, 배치 측정)을 거쳐 반영하므로 장 후보 라우트로 옮기지 않는다(3절 사실 5).
- 로드맵 이월표의 다른 "D3 마무리 묶음" 항목 (2), (3), (7)~(13). 넣을지는 7절 Q1이다.
- 실제 AI 호출. 상시 규칙대로 가짜 CLI만 쓴다.

## 3. 지금 코드에서 확인한 사실 (기준 `ba5f7ea`)

1. 작업 목록 라우트(`GET /api/projects/{name}/jobs`, `server/app.py`의 `_project_jobs`)는 미종결 작업, 처분이 `held`나 `stale`인 모든 행, 하위 장 가운데 `held`나 `stale`이 있는 모든 묶음, 그리고 종류와 대상 장마다 가장 최근 행을 돌려준다. 그래서 이전 묶음의 낡은 장 후보와 창을 닫은 뒤 도착한 도식 후보는 이미 복구 화면 목록에 있다(`RecoveryScreen.tsx`의 `candidatesOf`).
2. 장 후보 적용 라우트(`_candidate_ref`)는 묶음 행이면 `chapter_id`로 하위 장을 찾고, 그 묶음이 가장 최근인지 보지 않는다. 판정 기준은 부모 행의 `relevance_hash`에 든 장별 `c1:` 해시이고, 표지가 없는 D3c 이전 묶음 행은 409 `not_applicable`이다. 미종결 하위 장은 409 `not_terminal`, 이미 처분한 후보는 409 `candidate_settled`, 같은 프로젝트에 미종결 묶음이 있으면 적용 라우트만 409 `batch_active`이고 미리 보기는 200에 `blocked_reasons`의 맨 앞이 `batch_active`다. 도식 등 다른 종류는 409 `not_applicable`이다.
3. 비교 화면(`editor/CandidateCompareDialog.tsx`)은 프로젝트 이름, 작업 ID, 묶음이면 장 ID, 장 이름, 후보 슬롯을 받고, 반영과 그 결과 처리는 부르는 화면에 맡긴다(`onApply(selection, baseEtag)`, `onStaleBase`, `onRegenerate`, `regenerateHint`). 지금 부르는 곳은 구성 화면(가장 최근 묶음만, `StructureScreen.tsx`의 `latest`)과 편집 화면 생성 패널(장 다시 생성과 장 축약 작업만) 둘이다.
4. 복구 화면은 `ProjectView`가 `showRecovery`일 때 단계 화면 대신 그린다(단계 화면 다섯 개는 모두 `!showRecovery` 조건). 복구 화면을 열기 전에 `leaveScreen`이 편집 화면의 남은 편집을 저장한다. 그래서 복구 화면이 열려 있는 동안 저장하지 않은 편집기 상태가 없다. 복구 화면은 지금 `deck`만 받고 덱을 바꾸는 콜백이 없다. 복구 화면을 닫으면(`closeRecovery`) `ProjectView`가 덱을 비우고 서버에서 다시 읽은 뒤 단계 화면을 그린다. 그래서 복구 화면에서 반영한 뒤 옛 덱이 단계 화면에 남는 경로는 지금 구조에 없다.
5. 반영 요청(`api.applyCandidate`)은 요청 계층에 `etagKey`와 `notify: saved`를 주므로 응답의 ETag를 저장 ETag 캐시에 넣고 저장 알림을 낸다. 부르는 화면이 할 일은 받은 덱을 화면 상태에 넣는 것이다(구성 화면은 `onDeckChange(saved)`). 응답 ETag만 캐시에 남고 덱 상태가 옛 덱이면 다음 자동 저장이 반영을 덮는다(D3c-6 리뷰 G11의 모양).
6. 도식 작업은 등록 본문 전체를 `params`로 남긴다(`chapter_id`, `topic`, `role`, `claim_ids`, `instructions`, 기존 도식을 바꾸면 `mode: "replace"`). `JobView`는 `params`와 `target`을 이미 화면에 내보내므로 형식과 OpenAPI 변경이 필요 없다. 도식의 낡음 사유는 `deck_changed`, `unknown_deck`, `sources_changed`, `unknown_sources`이고, 덱의 어느 곳이 바뀌어도 `deck_changed`다(`_basis_reasons`).
7. 도식 작성 창(`editor/DiagramAuthoringDialog.tsx`)은 열 때의 덱을 `base`로 고정하고, 덱이 바뀌면 보이던 후보를 지운다. 후보는 "작성 폼에 불러오기"를 누를 때 `applied`로 처분하고, 입력을 고치면(`edit`) 보이던 후보를 `dismissed`로 처분한다(`dropCandidate`). 반영은 새 도식이면 덱 교체(`editor.replace`, 다음 저장이 `If-Match`를 보냄), 기존 도식이면 문서 변경 미리 보기와 적용(`applyDocumentChange`)이다. 둘 다 그때의 덱을 기준으로 다시 검사한다. 생성 중 기준이 바뀐 결과는 지금 버림으로 처분한다.
8. 새 도식의 장 ID는 `availableId("diagram", ...)`로 덱에 없는 첫 번호를 고른다. 그래서 창을 닫은 뒤 다른 도식을 하나 더 만들면, 닫기 전 후보의 `chapter_id`가 이미 다른 도식의 ID일 수 있다.
9. 편집 화면은 `closeRecovery(stage, chapterId)`로 장을 미리 골라 열린다. 도식 작성 창을 여는 길은 "도식 추가"(`createDiagramDraft`)와 도식 장의 "도식 수정"(`editDiagramDraft`) 둘뿐이다.

## 4. 설계

### 4.1 사용자 결정과 해석

이 계획은 2026-10-14 최종 리뷰 종합 3절의 선택지 A(합친 뒤 방향 ①)를 따른다. 방향 ②(구성 화면이 모든 묶음에서 낡은 후보를 찾음)와 ③(생성 패널이 묶음 하위 행을 후보로 보임)은 고르지 않았다. ①은 모든 미처분 후보를 이미 나열하는 화면에 입구를 두므로 구성 화면, 편집 화면, 도식에서 생기는 같은 모양을 한 곳에서 닫는다.

### 4.2 W1: 장 후보의 "비교하고 반영"

- 복구 화면의 후보 행 가운데 종류가 `chapter`, `condense`, `chapters` 하위 장이고, 상태가 종결이고, 결과에 슬롯이 있는 행에 "비교하고 반영" 버튼을 둔다. 지금의 "편집(구성) 단계로 옮겨 다시 생성"과 "버리기"는 그대로 둔다.
- 버튼은 비교 화면을 연다. 제목은 지금 행의 장 이름(`chapterLabel`)이고, 후보 슬롯은 행의 결과다. 묶음 하위 장이면 `chapterId`를 넘긴다.
- `onApply`는 `api.applyCandidate(project, jobId, {chapter_id?, ...selection}, baseEtag)`를 부르고, 성공하면 받은 덱을 새 콜백 `onDeckSaved(deck)`로 `ProjectView`의 `setDeck`에 넘긴 뒤 후보 목록을 다시 읽는다. 반영된 후보는 처분이 `applied`라 목록에서 빠진다. 덱을 넘기는 이유는 복구 화면이 장 이름과 "슬라이드가 없는 장" 판정에 그 덱을 쓰기 때문이다. 단계 화면의 덱은 복구 화면을 닫을 때 서버에서 다시 읽으므로(사실 4) 이 콜백에 기대지 않는다. 계획 리뷰는 이 다시 읽기가 실패하는 경우(오류 안내만 남고 덱이 비는 경우)도 본다.
- 실패 처리는 구성 화면의 `applyCompare`와 같은 분류를 쓴다. 412는 `onConflict`(배너의 "서버 내용 다시 읽기"), 5xx는 "저장했는지 확인하지 못함" 경로(`ProjectView`의 `setConflict("unconfirmed")`와 같은 콜백), 409 `candidate_settled`는 목록 다시 읽기와 안내, 409 판정 실패와 `batch_active`와 `not_applicable`은 안내와 목록 다시 읽기다.
- `onStaleBase`(미리 보기 뒤 이 탭이 모르는 저장본)는 비교 화면을 닫고 `onConflict`와 `STALE_BASE` 안내를 보인다(구성 화면과 같다).
- `onRegenerate`: 슬라이드가 없는 장이면 지금의 "구성 단계로 옮겨 다시 생성"과 같은 이동을 한다. 내용이 있는 장이면 넘기지 않고 `regenerateHint`로 "편집 단계의 '이 장 다시 생성'"을 안내한다(구성 화면과 같은 문구).
- 묶음 실행 중: 복구 화면은 이미 `restoreLockedReason`을 받는다. 같은 이유가 있으면 "비교하고 반영"은 열 수 있되(비교는 보인다) 비교 화면의 반영이 막힌다. 서버 미리 보기가 `batch_active`를 돌려주므로 화면 쪽 추가 판정은 두지 않는다. 열린 채 묶음이 시작되면 적용 라우트의 409 `batch_active`가 막는다.
- 안내 문구: 지금의 "반영은 해당 화면에서 합니다."를 "장 후보는 여기서 비교하고 반영할 수 있습니다. 도식 후보는 도식 작성 창에서 엽니다. 덱 전체 후보는 보기와 버리기만 합니다."로 바꾼다(문구는 리뷰에서 다듬는다).

### 4.3 W2: 도식 후보를 작성 창과 함께 다시 열기

D2b-5b ⑧이 남긴 "대화 상자의 입력과 후보의 입력을 맞추는 규칙"을 아래로 정한다.

- 복구 화면의 도식 후보 행에 "도식 작성 창에서 열기"를 둔다. 누르면 복구 화면을 닫고 편집 단계로 옮긴 뒤, 편집 화면이 도식 작성 창을 그 후보와 함께 연다. 전달은 `closeRecovery("editor", chapterId, { diagramJobId })`처럼 작업 ID만 넘기고, 편집 화면이 `api.getJob`으로 행을 다시 읽는다(옮기는 사이 다른 탭의 처분을 반영하기 위해).
- 작성 폼의 시작값(draft):
  - `params.mode === "replace"`이고 지금 덱에 그 장이 도식 장으로 있으면 `editDiagramDraft(deck, chapter_id)`에서 시작해 제목, 역할, 주장을 `params`의 값으로 덮는다(생성 요청 때의 입력이다).
  - `mode`가 없으면(새 도식) `createDiagramDraft(deck)`에서 시작해 제목, 역할, 주장을 `params`로 채운다. `params.chapter_id`가 지금 덱에 없으면 그 ID를 쓰고, 이미 있으면(사실 8) 새 번호를 쓴다. 장 ID는 후보 내용에 들어가지 않으므로 바꿔도 후보의 뜻이 변하지 않는다.
  - `replace`인데 그 장이 지금 덱에 없거나 도식 장이 아니면 작성 창을 열지 않는다. 복구 화면에서 "이 도식이 덱에서 빠져 작성 창에서 열 수 없습니다."를 보이고 보기와 버리기만 둔다.
  - 지시문(`instructions`)도 `params`에서 채운다. 다시 생성할 때 같은 지시가 남는다.
- 후보 표시: 작성 창은 시작할 때 이 후보를 지금의 "AI 후보 검토"(`GeneratedDiagramReview`)로 보이고 `generationJob`을 그 작업 ID로 둔다. 시작값을 채우는 일은 `edit`을 거치지 않는다. `edit`은 보이던 후보를 버리므로, 여는 순간 처분이 바뀌면 안 된다. 처분은 지금처럼 "작성 폼에 불러오기"가 `applied`, 입력을 고치거나 다시 생성하면 `dismissed`다.
- 낡음 규칙: 행의 `stale_reasons`를 읽는다.
  - 비어 있거나 `deck_changed`만 있으면 "작성 폼에 불러오기"를 연다. `deck_changed`이면 "후보를 만든 뒤 덱이 바뀌었습니다. 불러온 뒤 입력과 배치 확인이 지금 덱으로 다시 확인합니다."를 보인다. 불러온 내용은 반영 전에 지금 덱 기준의 확인(사실 7)을 반드시 거치므로, 다른 장의 변경이 후보를 무효로 만들지 않는다.
  - `sources_changed`, `unknown_sources`, `unknown_deck`이 있으면 검토 내용은 보이되 "작성 폼에 불러오기"를 막고 "자료가 바뀌어 이 후보의 근거를 지금 자료와 대조할 수 없습니다. 현재 입력으로 다시 생성해 주세요."를 보인다. 장 후보 적용 판정이 자료 변경을 막는 것(`sources_changed`)과 같은 기준이다.
- 작성 창이 이미 열려 있으면(다른 도식을 작성 중) 이 경로는 생기지 않는다. 복구 화면을 열 때 `leaveScreen`이 편집 화면을 떠나기 때문이다.

### W1-a 서버 계약 고정 (작음)

- 계약 시험: 묶음 A(내용 있는 장 X의 하위 장이 `stale`) 뒤에 묶음 B가 종결된 상태에서, A의 X 후보를 미리 보기와 적용으로 반영하면 200이고 처분이 `applied`이며 B의 행은 바뀌지 않는다. 지금 코드에서 통과해야 한다(새 코드 없음). 통과하지 않으면 그 원인을 W1-a의 수정 범위로 삼고 계획을 정정한다.
- 계약 시험: 도식 작업 행의 `params`에 `topic`, `role`, `claim_ids`, `instructions`, `mode`가 남고 작업 목록 응답에 그대로 실린다.

### W1-b 복구 화면의 장 후보 비교와 반영

- 회귀 RED(지금 코드에서 실패): 두 묶음 순서(D3c 확인 기록의 `s3b-older`와 같은 원장 상태)의 복구 화면에 "비교하고 반영"이 있고, 누르면 비교 화면이 열린다. 반영 뒤 `ProjectView`의 덱이 응답 덱이다.
- 회귀 RED: 같은 세션 순서(β 묶음 리뷰 S1의 jsdom 재현: 묶음 뒤 빈 장 하나를 구성 화면에서 다시 생성)에서도 옆 장의 후보가 복구 화면에서 반영된다.
- 계약 시험: 412, 5xx, 409 `candidate_settled`, 409 판정 실패, 409 `batch_active`의 화면 처리(4.2). 반영 성공 뒤 다음 자동 저장의 `If-Match`가 응답 ETag다. 이 시험은 `api` 함수를 통째로 모의하지 않고 `fetch`만 모의해 요청 계층의 ETag 캐시를 지난다(위키 같은 절의 "함수를 통째로 모의" 대응).
- 계약 시험: 부모(`ProjectView`)를 포함한 단위에서 반영한 뒤 복구 화면을 닫고 편집 단계로 가면 캔버스가 반영된 덱을 그린다. 복구 화면을 닫을 때의 다시 읽기를 지운 변형이 이 시험에 잡혀야 한다(위키 같은 절의 "부모와 자식의 값 전달" 대응).
- 고정: 도식, 구조안, 재작성, 수리 행에는 "비교하고 반영"이 없다. 미종결 하위 장 행에는 반영과 버리기가 없다(지금 규칙 유지).

- 계약 시험: 4.3의 시작값 규칙 세 갈래(기존 도식, 새 도식과 ID 충돌, 빠진 도식), 낡음 규칙 두 갈래(`deck_changed`만, `sources_changed`), "작성 폼에 불러오기" 뒤 `applied` 1회, 입력 수정 뒤 `dismissed` 1회.
- 계약 시험: 다시 연 후보를 불러와 확인하고 반영하면 덱에 그 도식이 들어간다(새 도식은 덱 교체 뒤 자동 저장의 `If-Match`, 기존 도식은 문서 변경 적용). 이 시험도 `fetch`만 모의한다.

## 8. 리뷰 계획과 비용

- 계획 리뷰는 Q3의 결정 뒤에 띄운다. 지시문에는 심각도 정의를 고정하고, 걸러 내지 말고 전부 적게 하며, 두 반영이 만나는 경로(W1의 덱 갱신과 편집 화면의 자동 저장, W2의 처분과 작성 창의 `edit`)를 실제 서비스로 재현하게 한다. "변형이 끝나면 대기로 두지 말고 보고서를 이어서 쓴다"를 넣는다.
- 리뷰 비용은 세션 기록 usage 합산(입력 + 출력 + 캐시 쓰기)으로 적고 집계식을 함께 적는다(최종 리뷰 핸드오프 4절).
- 리뷰 담당은 `git worktree` 사본에서만 일하고 포트 범위를 따로 쓴다. 이번 범위는 10200~10219로 둔다.
