## 태스크 A: 저장을 직렬화하고 착지 뒤 잔여 변경을 다시 저장한다

**재현 (2026-09-02, 인계 폴더 `useDeckEditor.critical.test.tsx` F1, F3, F4, F10)**

- F1: E1 저장 PUT 진행 중 Ctrl+Z 로 S 로 돌아오면, 자동 저장 효과가 `deck === savedDeck.current`(S) 로 조기 반환하고, PUT 착지 뒤 `savedDeck = E1` 이 되지만 S 를 다시 저장하는 코드가 없다. 서버는 E1, 화면은 S, 표시는 '저장 중' 영구 정체. 탭 전환이나 내보내기의 플러시만이 S 를 올린다.
- F4: E1 PUT 진행 중 E2 편집 → 두 PUT 동시 진행 → E2 응답이 먼저 오면 '저장됨', 뒤늦은 E1 응답이 `savedDeck` 을 E1 로 되돌리지만 재저장은 없다. 서버 최종 = E1, 화면 = E2, 표시 '저장됨'.
- F3: 저장 타이머 전 Ctrl+Z 로 저장본과 같아지면 '저장 대기' 표시가 남는다.
- F10: `onDeckChange` 가 렌더마다 새 함수면 언마운트 플러시 효과(deps `[saveNow]`)가 저장 중 렌더마다 정리 함수를 실행해 PUT 을 연사한다 (실측 200ms 에 36회). 현재 호출자(ProjectView)는 안정된 `setDeck` 을 넘겨 발동하지 않는다.

**변경 (`frontend/src/state/useDeckEditor.ts`)**

- 저장을 **한 줄로 직렬화**한다: `saveChain` ref 에 진행 중 저장 프라미스를 두고, `saveNow(target)` 은 그 뒤에 이어 붙인다. 겹친 PUT 이 없어지므로 역순 착지(F4)가 원천 차단된다.
- **착지 뒤 잔여 변경 재저장**: PUT 성공 뒤 `deckRef.current !== target` 이면(그사이 편집이나 되돌리기가 있었으면) `deckRef.current` 를 즉시 다시 저장 예약한다(체인에 붙인다). F1 의 S 가 이 경로로 올라간다. 되돌리기로 저장본과 같아진 경우는 "저장할 것 없음" 으로 끝난다.
- **저장할 것 없음의 판정**: `doPut(target)` 은 `target === savedDeck.current` 면 PUT 없이 true 를 돌려준다. 자동 저장 효과의 조기 반환 분기는 진행 중 저장이 없으면 `setSaveState("저장됨")` 으로 표시를 되돌린다(F3). 진행 중 저장이 있으면 그 착지 처리가 표시를 정한다.
- **콜백 안정화**: `onDeckChange` 를 ref 에 담아 `saveNow` 가 ref 를 호출하게 하고, 언마운트 플러시 효과의 deps 를 빈 배열로 둔다(F10). `flushSave` 는 진행 중 체인을 먼저 기다린 뒤 잔여 변경을 저장한다.
- 스냅샷 규칙(첫 저장, `snapshotNext`)과 `replace`, `undo`, `redo`, `apply` 의 의미는 바꾸지 않는다.

**테스트 (실패부터, `frontend/src/state/useDeckEditor.save.test.tsx`)**: F1 → 착지 뒤 두 번째 PUT 이 자동으로 S 를 보내고 최종 상태가 '저장됨' 이다. F4 → PUT 은 순차로 나가고(둘째는 첫째 착지 뒤 시작) 마지막 PUT 본문이 E2 다. F3 → 되돌리기로 저장본과 같아지면 '저장됨' 이다. F10 → 불안정한 콜백을 넘겨도 200ms 동안 PUT 은 1회다. 저장 실패 뒤 다음 편집이 저장을 시도한다(체인이 실패 상태에 머물지 않는다). `flushSave` 는 진행 중 저장이 끝난 뒤 잔여 편집까지 올린다. 추가로 **무작위 시나리오 불변조건 테스트**(고정 시드로 편집, 되돌리기, 다시 실행, 지연 착지, 실패 1회를 섞은 시퀀스 30개): 모든 프라미스가 정착하면 저장 상태는 '저장됨' 이고 마지막 PUT 본문이 화면 덱과 같다 (적대 리뷰 범위 판정 반영). 기존 `EditorScreen.test.tsx` 의 저장 관련 단언(첫 저장 스냅샷, 플러시)은 그대로 통과해야 한다.

## 태스크 B: 낡은 미리보기에서는 편집을 열지 않고, 실측 오류를 저장 오류와 분리한다

**재현 (인계 폴더 `EditorScreen.staleplan.test.tsx` F5, `useDeckEditor.critical.test.tsx` F2)**

## 실행 순서

태스크 A → 태스크 B → 태스크 C → 문서 정정 → 독립 리뷰 → 수정 반영 → main 머지 → push.

문서 정정: 로드맵 이월표의 해당 행(FC-01, 05, 08 신규 3행과 FC-04, 14, 16 기등재 3행)을 처리 완료로, 진행 상태에 이 묶음 항목 추가. 적대 리뷰가 찾은 기존 결함 1건을 이월표에 신규 등재: `replace()` 가 켠 `snapshotNext` 가 디바운스 전 되돌리기로 소비되지 않은 채 남아 무관한 다음 저장에 스냅샷이 찍힌다(F3. 이 묶음은 스냅샷 규칙을 바꾸지 않으므로 범위 밖). 설계서 7.2(저장 사고 대비)에 "저장은 직렬화하고 착지 뒤 잔여 변경을 재저장한다", 6절(편집 화면)에 "미리보기는 최신 덱 기준 계획일 때만 편집을 연다" 를 날짜와 사유를 달아 추가.

## 이 계획이 틀렸을 가능성

- 저장 직렬화로 체인이 길어지면 빠른 연속 편집에서 마지막 저장이 늦어진다. 디바운스(1.2초)가 이미 편집을 묶어 주므로 실사용에서 체인 길이는 1~2 다. 관찰되면 "체인 실행 시점에 `deckRef.current` 를 보내 중간 저장을 합치는" 최적화를 다음 묶음에서 한다.
- 낡은 계획일 때 편집을 막으면 300ms 남짓의 창에서 클릭이 무시된다. 흐림 표시가 그 이유를 알려 주지만, 파일럿에서 "클릭이 안 먹는다" 는 관찰이 나오면 클릭을 대기열에 두는 방식으로 바꾼다.
- 편집기의 저장 실패로 화면 이탈이 막히면 서버가 죽은 상태에서 사용자가 갇힌다. 배너에 "저장 상태를 확인" 안내를 두고, 스냅샷 복구는 서버가 살아 있을 때만 의미가 있으므로 같은 규칙을 적용해도 실해가 없다. 서버 사망 시의 탈출구(강제 이탈)는 5A A 의 재시도 수단 항목에서 다룬다.
