## 1. 범위

D3 관문 기준 가운데 이 묶음이 맡는 것은 ① IR 포함 10유형의 저장, 생성, 편집 보존과 ② 드롭다운과 시각 구조가 다른 대표 페이지다(D3 계획 1절). 요구는 R09다. D3 관문은 D3c까지 끝나야 통과한다.

| 영역 | 내용 |
|---|---|
| 저장 | 보고 유형의 명시 선택 기록, IR Pitch Deck 저장값, 유형별 추가 입력, "전달할 핵심 내용", 원하는 결과 네 가지(기타 직접 입력 포함). 덱 형식 판정과 0.2.0 공존 판정을 이 묶음에서 한 번 한다 |
| 화면 | 보고 목적: 10종 드롭다운, 유형 설명과 추천 구성, 유형마다 시각 구조가 다른 예시 화면과 크게 보기, 유형별 추가 입력, 핵심 내용, 원하는 결과, 자동 저장. 구성: 장 후보의 카드 목록, 핵심 내용의 연결 표시, 실행 단계 표시와 경과 시간 |
| 생성 | 구조안, 장 생성, 재작성 지시문에 IR 유형, 핵심 내용, 원하는 결과, 유형별 추가 입력을 전달한다. 원하는 결과와 모델 추천의 연결은 D4다 |
| 서버 계약 | 구조안 후보의 낡음 판정을 덱 전체가 아니라 구조안 입력 기준으로 바꾼다(D3a-5 리뷰 R9). 작업의 실행 단계를 기록해 알린다 |

하지 않는 것: 실제 생성 품질의 확인(AI 호출이 필요하므로 별도 사용자 승인과 호출 예산 없이 하지 않는다), 모델 추천과 Effort 표시(D4), 자료 텍스트 자동 저장(D5, R13), 직접 수정(D3c).

## 3. 지금 코드에서 확인한 사실 (기준 `afe9138`)

1. 보고 유형은 9종이다(`models/story.py`의 `ReportType`). 덱의 `meta.report_type`과 구성 계획의 `structure.story_plan.brief.report_type` 두 곳에 쓰인다. 기본값은 `research`이고, 기본값과 사용자의 명시 선택을 구별할 기록이 없다(`pipeline/progress.py`가 제목만 있으면 보고 목적을 "확인 필요"로 둔다).
2. 화면의 보고 정보는 제목, 보고 유형, 보고자, 피보고자 넷이다(`ReportPurposeScreen.tsx`). 저장은 "보고 정보 저장" 버튼으로 덱 전체를 PUT한다. 자동 저장이 없다.
3. 형식 판정(`storage/project_format.py`): 형식 1은 0.2.0이 읽을 수 있는 덱, 형식 2는 그렇지 않은 덱이다. 지금은 보고 유형 두 곳이 0.2.0의 3종(`research`, `approval`, `strategy`) 밖이면 2다. 형식 1에서 2로 바뀌는 저장은 강제 스냅샷을 남긴다. `Deck.schema_version`은 1로 두었다(0.2.0은 필드 검증 뒤에 버전을 검사하므로 새 유형 덱의 표시가 나아지지 않는다, 2026-10-08 실측). 덱 스키마의 해시를 고정해 스키마가 바뀌면 시험이 실패하게 했다.
4. 0.2.0의 `Deck`과 `DeckMeta`는 모르는 필드를 읽을 때 버리고 저장할 때 지운다(D2 계획 사실 5). 따라서 새 항목을 덱 안에 두면, 3종 유형 덱을 0.2.0이 한 번 저장하는 것만으로 새 항목이 경고 없이 사라진다. 지금의 형식 판정은 이 경우를 형식 1로 본다.
5. 생성 지시문(`pipeline/prompts.py`)은 제목, 보고 유형 안내(`REPORT_TYPE_GUIDES`), 피보고자, 유형 규칙(`REPORT_TYPE_RULES`)을 넣는다. 재작성(`pipeline/rewrite.py`)과 도식 생성도 보고 유형을 쓴다. 유형 안내는 9종만 있다.
6. 구조안 후보의 낡음은 덱 ETag가 등록 때와 같은지로만 판정한다(`server/app.py`의 `_job_views`). 장 후보는 그 장의 관련 입력 해시(`relevance_hash`)로 판정한다. 그래서 보고자 이름만 바꿔도 구조안 후보가 "이전 입력 기준"이 된다.
7. 작업의 진행 정보는 `queued`, `running`, `cancel_requested` 셋이다(`models/jobs.py`의 `ActiveJob.stage`). 구조안 생성 안의 단계(자료 확인, 생성, 연결 확인)는 기록하지 않는다.
8. 화면 시안에는 10종 유형의 이름, 한 줄 설명, 추천 구성, 추가 입력, 유형별 대표 페이지가 있다(`docs/design/2026-10-02-revision-wireframe.html`의 `purposes` 배열과 예시 렌더 함수). 예시는 합성 자료다.
9. 보고 목적 화면은 D3a에서 주 행동 막대(보고 정보 저장)를 갖고, 머리의 저장 상태는 이 화면에서 저장한 뒤에만 "저장됨"을 보인다(D3a-7 사용자 결정 A19).

### 4.2 저장 계약 (D3b-1)

- `ReportType`에 `ir`(IR Pitch Deck)를 더한다. 화면의 이름은 "IR Pitch Deck"이다.
- `DeckMeta`에 보고 목적 묶음을 더한다. 이름과 모양은 구현에서 정하되 다음 값을 담는다.
  - `report_type_confirmed`: 사용자가 유형을 직접 골랐는가. 화면에서 유형을 고르거나 지금 값을 확인하면 참이 된다. 기존 덱은 거짓으로 읽는다.
  - `key_message`: 이 보고서에서 전달할 핵심 내용. 빈 문자열이 기본이다.
  - `desired_outcome`: `facts`(사실 및 데이터 중심, 기본), `business_plan`(사업 기획안), `persuasion`(투자자 및 의사결정자 설득), `other`(기타). `other`의 설명 문장은 따로 두고, 다른 선택지로 바꿔도 지우지 않는다(제품 설계 6절).
  - 유형별 추가 입력: 제품 설계 5절 B 표의 "추가로 받는 정보"를 유형마다 이름 있는 칸으로 둔다(예: 주간 업무의 보고 기간, IR의 투자 단계). 모든 칸은 선택 입력이고 비면 "미정"으로 생성에 전달한다. 유형을 바꿔도 다른 유형의 입력은 지우지 않는다.
- 형식 판정: 형식 2의 조건에 "새 항목 가운데 기본값이 아닌 것이 있다"를 더한다. Q1이 A이면 형식 2 덱은 `schema_version` 2로 쓴다. 형식 1에서 2로 바뀌는 저장의 강제 스냅샷과 이전 기록은 지금 규칙을 그대로 쓴다.
- 진행 API: 제목이 있고 `report_type_confirmed`가 참이면 보고 목적은 준비됨이다. 핵심 내용은 비어 있어도 준비됨을 막지 않는다(제품 설계: 모든 항목을 필수로 바꾸지 않는다). 대신 사유로 "핵심 내용 없음"을 알린다.
- 고정 시험: 0.2.0 왕복 시험(`test_legacy_compat.py`)에 새 항목 덱의 경우를 더한다. Q1이 A이면 0.2.0이 그 덱을 열지 않고 내용이 그대로인지, 새 항목이 없는 3종 덱은 지금처럼 형식 1로 남는지 본다.
- D2a 이월 (19), (20): Q1의 결과로 판단한다. A이면 새 항목 덱에서는 0.2.0이 쓰기 전에 거절되므로 (20)의 경합이 그 덱에서는 생기지 않는다. 새 항목이 없는 3종 덱의 경합과 (19)의 감지 경고는 지금처럼 릴리스 안내로 둔다.

### 4.3 구조안 후보의 낡음 판정 (D3b-2, R9)

- 구조안 작업을 등록할 때 구조안 입력의 해시를 원장에 남긴다. 입력은 구조안 지시문이 실제로 읽는 값이다: 제목, 보고 유형, 피보고자, 보고 목적 묶음(4.2), 보고 질문, 주안점과 원하는 결과 입력, 목표 장수, 자료 지문, 도식 장의 보존 대상. 보고자 이름과 미리보기 설정처럼 지시문에 들어가지 않는 값은 뺀다.
- 판정은 장 후보와 같은 방식이다: 입력 해시가 같으면 덱 ETag가 바뀌어도 낡음이 아니고, 해시가 다르면 "이전 입력 기준"이다. 해시를 남기지 않은 옛 행은 지금처럼 ETag로 판정한다.
- 시험: 보고자만 바꾼 저장 뒤 후보가 낡음이 아님, 핵심 내용을 바꾸면 낡음, 자료를 바꾸면 낡음, 옛 행은 ETag 판정. 해시 입력 목록이 지시문 생성 함수가 읽는 값과 같은지 확인하는 시험을 둔다(지시문이 새 값을 읽기 시작했는데 해시에서 빠지면 낡은 후보를 적용하게 된다).

### 4.4 생성 전달 (D3b-3)

- `REPORT_TYPE_GUIDES`에 IR Pitch Deck을 더한다(제품 설계 5절 B 표의 구성 패턴).
- 구조안, 장 생성, 재작성, 도식 생성의 지시문에 핵심 내용, 원하는 결과(기타는 사용자 문장), 그 유형의 추가 입력을 넣는다. 빈 값은 "미정"으로 넣고, 지시문에 "미정인 기간, 성과, 담당을 만들지 않는다"는 지금 규칙을 그대로 둔다.
- 원하는 결과와 보고 유형은 다른 축이다. IR을 골라도 설득을 강제하지 않는다.
- 시험은 지시문 문자열의 포함 여부와 "미정" 처리를 본다. 실제 생성 품질은 확인하지 않는다(1절).

### 4.5 보고 목적 화면 (D3b-4, D3b-5)

- 배치: 왼쪽에 드롭다운, 유형 설명, 추천 구성, 입력 항목. 오른쪽에 예시 화면. 1100px 이하 본문 폭에서는 예시를 드롭다운 아래로 내린다. 입력 순서는 제목, 보고자, 피보고자, 핵심 내용, 보고 유형과 그 유형의 추가 입력, 원하는 결과다.
- 드롭다운 10종의 순서와 이름은 시안과 제품 설계 5절 B를 따른다.
- 자동 저장: 입력이 멈추고 짧은 지연 뒤 저장한다. 지연 값은 측정 전에 합격선을 두지 않고, 편집 화면의 지금 자동 저장 지연을 출발점으로 쓴다. "저장됨"은 서버 확인 뒤에 보인다. ETag 충돌과 이탈 플러시와 묶음 중 읽기 전용은 지금 계약을 유지한다. 저장 중 단계를 옮기면 지금처럼 플러시를 기다린다.
- 예시 화면(Q3 A 기준): 유형마다 시안의 대표 페이지를 옮긴다. 모두 "예시" 표시가 있고 합성 자료다. 크게 보기는 대화 상자로 연다. 예시는 장식이 아니라 정보이므로 그림마다 대체 텍스트로 "주간 업무 보고 예시: 완료, 진행, 지원 필요 상태 보드" 같은 설명을 단다.
- 시험: 유형 10개가 모두 서로 다른 예시 구조를 갖는다(예시의 구조 요약을 비교한다), 유형을 바꿔도 다른 유형의 추가 입력과 기타 설명이 남는다, 자동 저장이 지연 뒤 한 번 나가고 그동안 입력이 이어지면 다시 미룬다, 유형을 고르면 진행 API의 보고 목적이 준비됨이 된다.

### 4.6 구성 화면 (D3b-6)

- 장 후보를 표에서 카드 목록으로 바꾼다. 카드는 순서, 주제, 결론 한 줄, 템플릿, 근거 유무를 보이고, 위로, 아래로, 삭제, 장 다시 생성, 후보 버리기를 지금처럼 제공한다. 상세 근거는 펼쳐 본다. 지금 표의 접근 이름(예: "1번 장 주제")과 키보드 동작은 유지한다.
- 핵심 내용을 구성 화면 위쪽에 읽기 전용으로 보이고 "보고 목적에서 고치기"로 잇는다. 같은 내용을 다시 입력하게 하지 않는다.
- 실행 단계: 서버가 구조안 작업의 단계(`sources`: 자료 확인, `generating`: 구성 생성, `linking`: 연결 확인)와 단계 시작 시각을 기록해 작업 응답과 진행 작업 응답에 싣는다. 화면은 완료한 단계와 지금 단계, 시작부터의 경과 시간을 보인다. 측정한 예상 시간이 없으므로 백분율과 남은 시간을 보이지 않는다.
- B8: 이 탭이 시작하지 않은 작업의 실패 알림에서, 이미 그 단계에 있으면 "단계로 이동" 대신 "결과 다시 보기"가 그 화면을 새로 연다.

## 5. 태스크

D3a처럼 저장과 생성 계약(α)을 먼저 끝내고, 화면(β)을 그 위에 얹는다.

| 태스크 | 내용 | 끝나면 관측되는 것 |
|---|---|---|
| D3b-1 저장 계약과 형식 | 4.2 전체 | 새 항목의 저장과 다시 읽기, 기존 덱의 기본값 읽기, 형식 판정과 강제 스냅샷, 0.2.0 왕복 시험(Q1 결과), 진행 API의 보고 목적 준비됨. OpenAPI와 타입 재생성 일치 |
| D3b-2 구조안 낡음 판정 | 4.3 | 보고자만 바꾼 저장 뒤 구조안 후보가 낡음이 아님. 해시 입력 목록과 지시문 입력의 일치 시험 |
| D3b-3 생성 전달 | 4.4 | 네 지시문에 핵심 내용, 원하는 결과, 추가 입력이 들어감. IR 유형 안내 |
| D3b-4 보고 목적 화면 | 4.5의 입력과 자동 저장, Q2 | 10종 드롭다운, 유형별 추가 입력, 핵심 내용, 원하는 결과, 자동 저장, 4.6 주 행동 표 갱신 |
| D3b-5 예시 화면 | 4.5의 예시, Q3 | 유형 10개의 서로 다른 예시 구조, 크게 보기, 좁은 폭 배치, 대체 텍스트 |
| D3b-6 구성 화면 | 4.6 | 카드 목록, 핵심 내용 연결, 실행 단계와 경과 시간, B8 |
| D3b-7 화면 확인과 관통 | 6절 | 6절 표 |

α는 D3b-1~3, β는 D3b-4~7이다. α가 끝나면 랩업 보고 뒤 사용자와 상의하고 β로 넘어간다.

## 6. 수용 기준

자동 검사: D3a와 같다(백엔드 전체, 프런트 전체 forks와 threads, desktop, 토큰 검사, 빌드, OpenAPI와 타입 일치, 0.2.0 왕복, 공개 저장소 감사, 공백 검사, CI 두 OS).

화면 확인(웹 모드 헤드리스 Chromium, 합성 프로젝트, 가짜 CLI, 실제 AI 호출 0회):

| 항목 | 판정 |
|---|---|
| 10종 저장과 재열기 | 유형마다 저장 뒤 새로고침하면 같은 유형, 추가 입력, 핵심 내용, 원하는 결과가 보임 |
| 예시 화면 | 유형을 바꾸면 예시 구조가 바뀜(10개 모두 서로 다름), 크게 보기가 열리고 닫힘, 512×360과 1024×720에서 가로 넘침 없음 |
| 자동 저장 | 입력을 멈추면 서버에 한 번 저장되고 머리가 "저장됨", 두 탭 충돌 때 충돌 안내 |
| 보고 목적 준비됨 | 유형을 고른 뒤 단계 목록의 보고 목적이 준비됨 |

| 실행 단계 | 가짜 CLI 관문 모드에서 구조안 생성 중 단계 표시와 경과 시간이 바뀜 |
| 0.2.0 공존 | Q1 결과대로 0.2.0이 새 항목 덱을 다루는지(0.2.0 코드를 별도 프로세스로 실행) |
| 배치와 키보드 | D3a 6절의 배치, 키보드, 초점 가림 측정을 보고 목적과 구성에서 다시 돌림 |
