# 개정판 D2b 작업 원장 계획

작성: 2026-10-08 (서울 기준). D2a 종결 보고 뒤 사용자가 "작업 계속 이어서 진행"을 지시했다. 이 지시를 D2b 계획서 착수의 승인으로 기록한다. 같은 날 사용자는 「사용자 결정」 절의 네 가지(장 생성 방식, 기존 동기 라우트, 저장 중 이탈 임시본, 적대 리뷰 규모)에서 모두 추천안을 택했다. 세션은 그 응답에 앞서 "리뷰 결과를 반영해 계획서를 고치고 확정 커밋까지 하겠다"고 알렸다. 그래서 이 문서의 승인 범위는 계획서 작성, 3관점 적대 리뷰, 반영과 확정 커밋까지다. 구현 착수와 구현 단계의 리뷰 규모는 사용자가 따로 결정한다.

상위 문서는 다음과 같다. [D2 계획 6절](2026-10-08-revision-d2-common-foundation.md#6-d2b-계약-상세-계획은-d2a-뒤)의 D2b 계약이 출발점이고, 그 계약의 출처는 [기술 설계 6절](../architecture/2026-10-02-desktop-revision.md#6-작업-원장-취소와-복구)과 [제품 설계 7절](../design/2026-10-02-revision-product-ux.md#7-저장-동의와-긴-작업)이다. 이 계획서는 상위 문서를 재정의하지 않는다. 상위 문서와 다르게 정하는 부분은 「상위 문서와 다르게 정하는 것」 절에 이유와 함께 모은다.

> 2026-10-08 개정: 초안(`6051aed`, 보완 `da96ea7`, 결정 기록 `68e3b6f`)에 대한 3관점 적대 리뷰(발견 89건)를 반영해 다시 썼다. 판정 내역은 「독립 검토 반영」 절에 있다.

## 1. 이번 단위의 목표

AI 생성 작업을 HTTP 요청 하나의 수명에서 떼어 내어, 서비스가 기록하고 관리하는 작업으로 바꾼다. 목표는 넷이다.

- R11의 중단 복구: 앱을 강제 종료하거나 재시작해도 생성 작업의 결과와 실패가 사라지지 않는다. 원격 호출이 끝났는지 모르는 작업은 그 사실을 표시하고, 자동으로 다시 호출하지 않는다.
- R11의 결과 보존: 생성을 시작한 뒤 그 생성의 입력(덱, 자료, 대상 장)이 바뀌었으면 결과를 자동으로 반영하지 않고 "이전 입력 기준 후보"로 남긴다. 늦게 도착한 결과가 새 편집을 덮지 않는다. 화면이 보지 못하고 끝난 결과도 다시 찾을 수 있다.
- R01의 생성 상태: 화면은 "생성 중", "취소 요청됨", "완료 여부 확인 필요", "6장 중 1장 실패"를 세션과 재시작을 넘어 같은 원천(원장)에서 읽는다.
- D2 완료 관문: 기술 설계 7절의 "변경, 저장, 충돌, 중단 복구 상태를 모의 서버와 실제 저장으로 검증"을 D2a 결과와 합쳐 통과로 기록할 수 있게 한다.

## 2. 핵심 설계 결정

### 2.1 장 생성은 서버가 차례로 적용하는 묶음 작업으로 한다 (사용자 결정 2026-10-08: A)

지금 구조안 승인 루프(`StructureScreen.approve`)는 화면이 장마다 생성 요청을 보내고 결과를 받을 때마다 덱을 저장한다(사실 6). 장 N+1의 기준 ETag는 장 N의 저장 뒤에야 생긴다.

| 선택지 | 결과 | 판정 |
|---|---|---|
| A. 묶음 작업 1개(채택) | 승인 뒤 화면이 "장 생성 묶음" 작업 하나를 등록한다. 서버가 장을 차례로 생성하고 장마다 ETag 사슬을 검사해 저장한다. 탭을 옮기거나 새로고침해도 작업이 계속되고, 재시작 뒤에는 어느 장까지 적용됐는지가 원장에 남는다 | 계약의 "세션을 넘어 남는 6장 중 1장 실패"와 "임대는 작업 수명에 묶는다"를 만족한다 |
| B. 장마다 작업 1개를 화면이 연결 | 화면이 장 작업이 끝날 때마다 다음 장 작업을 등록한다 | 화면이 닫히면 남은 장의 등록이 멈추고, 등록하지 않은 장은 원장에 남지 않는다 |

묶음 작업은 등록 때 고정한 ETag에서 출발하고, 자기가 저장한 덱의 ETag를 다음 장의 기대값으로 쓴다. 다른 주체가 덱을 바꾸면 사슬이 끊기고, 그 장의 결과는 이전 입력 기준 후보로 남으며 남은 장은 시작하지 않는다. 생성 중 잠금(사실 7)은 이 단위에서도 유지하므로, 사슬이 끊기는 경우는 다른 창이나 탭, 0.2.0, 손으로 고친 파일이다. 0.2.0은 서비스 잠금을 모르므로 ③ 검사와 ⑤ 저장 사이에 0.2.0이 쓴 내용은 막지 못한다(D2a 이월 20과 같은 한계). 독립 앱에서 창을 닫으면 서비스가 끝나므로 작업도 끝난다. 그때의 처리는 D2b-5c가 맡는다.

### 2.2 기존 동기 생성 라우트 6개는 원장 위의 얇은 래퍼로 남긴다 (사용자 결정 2026-10-08: A)

| 선택지 | 결과 | 판정 |
|---|---|---|
| A. 래퍼로 유지(채택) | 기존 6개 라우트가 작업을 등록하고 끝날 때까지 기다린 뒤 지금과 같은 응답을 돌려준다. 실행 경로는 원장 하나뿐이다 | 시험을 다시 쓰지 않고 실행 경로를 하나로 만든다 |
| B. 제거 | 모든 생성 시험을 작업 API로 다시 쓴다 | 관문 회귀 시험을 옮기는 동안 검증 공백이 생긴다 |

래퍼 규칙(5.4절)은 "지금 라우트와 같은 검사 순서, 같은 상태 코드, 같은 취소 동작"이다. 래퍼는 요청이 취소되거나 연결이 끊기면 작업에 취소를 한 번 요청한다. 지금 생성은 요청 수명에 묶여 있고 이 성질을 고정한 시험이 5건 있으며(사실 13), 화면은 D2b-5까지 래퍼를 쓰기 때문이다. 계약의 "브리지 요청 취소와 작업 취소의 분리"는 새 작업 API에 적용한다. 화면이 작업 API로 옮긴 뒤에는 탭을 옮기거나 새로고침해도 작업이 계속된다.

이 선택의 비용은 둘이다. D3가 래퍼를 지울 때 시험 약 70곳(사실 13)을 작업 API로 옮겨야 하고, 그때까지 OpenAPI와 브리지 경로 목록에 두 표면이 함께 있다. 래퍼 제거와 시험 이전은 로드맵 D3 이월 항목으로 올린다.

### 2.3 실행기는 전용 스레드의 이벤트 루프에서 돈다

실행기를 요청 처리 루프에서 돌리면 세 가지가 깨진다. 첫째, 공용 시험 픽스처처럼 `with` 없이 만든 `TestClient`는 요청마다 루프를 새로 열고 닫으므로 요청 안에서 만든 작업이 요청과 함께 취소된다(사실 14). 둘째, 실행기가 임대 해제를 기다리는 중 순수 asyncio 취소가 한 번 더 들어오면 지금의 `anyio.CancelScope` 보호가 듣지 않아 임대가 영구히 남을 수 있다(사실 16). 셋째, 프로젝트 잠금은 `threading.RLock`이라 같은 루프의 코루틴이 잠금을 쥔 채 `await`하면 다른 코루틴이 그대로 들어온다(사실 17).

그래서 실행기는 전용 스레드 하나에서 자기 이벤트 루프를 돌린다. 2026-10-08 구현 정정: 이 루프는 앱마다가 아니라 프로세스에 하나 둔다(작업 루프). 시험 스위트는 앱을 수백 번 만들므로 앱마다 스레드와 루프를 열면 파일 핸들이 쌓인다. 원장과 실행 중 작업은 앱마다 따로다. 독립 앱과 웹 모드는 프로세스에 앱이 하나다. 래퍼와 작업 API는 `asyncio.run_coroutine_threadsafe`로 작업을 넘기고, 요청 루프에서는 결과만 기다린다. 래퍼는 `run_coroutine_threadsafe`가 돌려준 Future를 기다리지 않고 실행기가 따로 만든 대기 Future를 기다린다. 앞의 것을 기다리다 요청이 취소되면 그 취소가 작업 태스크로 바로 전달되기 때문이다. 요청 루프가 닫혀도 작업은 실행기 루프에 남는다. 덱과 원장을 함께 바꾸는 구간은 실행기 루프에서 `await asyncio.to_thread(동기 함수)` 한 번으로 실행한다. 그러면 잠금, 원장 쓰기, `save_deck`이 한 작업 스레드 안에서 일어난다. 실행기 스레드는 앱 수명 종료(lifespan)와 명시적 `close()`에서 멈춘다. 시험은 `close()`를 픽스처 정리에서 부른다.

2026-10-08 실험(`backend-lab/thread_loop_probe2.py`, 가짜 CLI): 전용 스레드 루프에서 `SubscriptionProvider.complete`를 실행하고 바깥에서 한 번 취소했다. 바깥의 `concurrent.futures.Future`는 즉시 취소로 끝났지만, 가짜 CLI는 3초 시점에 살아 있었고 6초 시점에 정리됐으며 실행기 루프에 남은 태스크는 0개였다. 따라서 실행기는 바깥 Future가 아니라 **실행기 루프 안 태스크의 실제 종료**를 기다린 뒤에 임대를 놓고 종결 상태를 쓴다.

### 2.4 실행 상태와 결과 후보의 처분을 나눈다

원장 행은 두 축을 따로 기록한다. 실행 상태는 기술 설계 6절의 상태 이름을 쓰고, 결과 후보의 처분은 `candidate_status`(`none`, `held`, `applied`, `stale`, `dismissed`)로 기록한다. 이렇게 하면 `succeeded`의 뜻을 바꾸지 않고도 "적용됨", "이전 입력 기준 후보", "사용자가 버림"을 구별할 수 있다. 묶음 작업의 부모 행은 모든 장이 적용됐을 때만 `succeeded`다. 일부 장이 실패하거나 사슬이 끊기면 부모는 `failed`이고, 부모의 `outcome`(`all_applied`, `partial`, `chain_broken`, `held_stale_plan`, `cancelled`)이 장별 결과를 요약한다.

후보의 처분은 계약 규칙 (8)의 "후보 보기 / 현재 입력으로 다시 생성"을 따른다. 이 단위는 장 후보를 서버가 현재 덱에 직접 적용하는 경로를 만들지 않는다. 그 경로는 D3 이월이다.

### 2.5 D2b를 두 묶음, 여덟 태스크로 나눈다

| 묶음 | 태스크 | 끝나면 관측되는 것 |
|---|---|---|
| D2b-α 원장과 실행기 | D2b-1 원장 저장소와 판정 함수, D2b-2 실행기와 작업 API와 가짜 CLI, D2b-3 후보형 생성 6종의 래퍼 이전 | 화면은 그대로이고 모든 생성이 원장을 거친다. 래퍼의 응답, 상태 코드, 취소 동작은 지금과 같다. 화면에서 생성 결과를 놓쳐도 원장에 후보가 남는다(화면에서 다시 찾는 기능은 β) |
| D2b-β 묶음 작업과 화면 | D2b-4 장 생성 묶음 작업, D2b-5a 진행 작업 조회와 구조안 승인, D2b-5b 후보형 화면의 작업 연결과 후보 처분, D2b-5c 상태 표시와 복구 화면과 창 닫기, D2b-6 재시작 관통과 패키지 확인과 화면 확인 | 화면이 원장을 읽는다. 실제 프로세스를 죽였다 살리는 관통이 통과한다 |

α가 끝나면 묶음 리뷰를 받고 사용자와 상의한 뒤 β로 넘어간다(단계 경계 규칙). α만 끝난 상태를 D2 관문 통과로 기록하지 않는다.

### 2.6 저장 중 이탈 시 로컬 임시본은 구현하지 않는다 (사용자 결정 2026-10-08: 방치 확정)

D2 계획 「상위 문서와 다르게 정하는 것」 3항이 이 판단을 D2b로 넘겼다. 제품 설계 7절의 원문은 "저장 중 이탈/종료는 완료를 기다리거나 실패 시 복구 가능한 로컬 임시본을 남긴다"이다.

- "완료를 기다린다" 갈래: 저장 대기, 저장 중, 저장 실패이면 화면의 `beforeunload` 경고와 독립 앱의 닫기 대화 상자가 이미 이탈을 막는다(`ProjectView.tsx`, `EditorScreen.tsx`, `desktop/main.cjs`). 남는 경우는 사용자가 대화 상자에서 "종료"를 골라 `shutdown()`이 진행 중인 브리지 요청(저장 포함)을 끊는 경우와 앱 강제 종료다.
- "로컬 임시본" 갈래: 렌더러에 파일 쓰기 권한을 주려면 preload IPC를 넓혀야 하고, 이는 D1의 브리지 보안 경계를 바꾼다. D2b 뒤에는 AI 생성 결과가 원장에 남으므로, 남는 손실은 자동 저장 지연(1.2초, `StatusIndicator.tsx` 주석) 안의 입력이다.
- 판정: 구현하지 않는다. 로드맵 방치 확정 문단에 올리고, 개정 계획 R11 행과 제품 설계 7절에 날짜와 사유를 적는다.
- 다시 열 조건: D6의 사람 사용 검증에서 강제 종료나 "종료" 선택으로 편집을 잃은 사례가 한 건이라도 기록되면 다시 판단한다. 로드맵 D6 관측 항목으로 등재한다.

## 4. 현재 코드에서 확인한 사실

코드 기준은 `17902b4`(D2a 종결)다. 문서 커밋 `6051aed`부터 `68e3b6f`까지 코드 변경은 없다. 2026-10-08 리뷰가 재확인했다.

1. 생성 라우트는 6개다: 구조안(`generate/structure`), 장 생성(`generate/chapter/{id}`), 축약(`.../condense`), 도식(`generate/diagram`), 구성 재작성 미리보기(`story-plan/rewrite`), 구성 수리 미리보기(`story-plan/repair`). 모두 `_require_ai_consent`로 `X-AI-Consent` 헤더를 검사하고(없으면 428), `generation_service(x_ai_selection)` 안에서 AI를 부르고, 결과를 응답으로만 돌려준다.
2. 생성 임대 `AIConnections.generation(selection_id)`는 프로세스 메모리의 카운터 `_active`다. 이미 다른 생성이 진행 중이면 `_idle()`이 대기 없이 `ConnectionConflict`(409, 문구 "AI 생성이 진행 중입니다. 완료 후 연결 설정을 변경해 주세요.")를 낸다. 즉 지금은 프로세스 전체에서 생성이 한 번에 하나다. 임대를 잡을 때 선택 식별자, 로그인 대기 여부, 로그인 상태, 모델 목록을 다시 확인한다. 로그인 상태를 이전에 본 적이 있으면 만료는 정체성 변경으로 처리되어 409가 되고, 처음 보는 경우에만 503(`ProviderNotAvailable`)이다(`connections.py:165-170, 271-276`). 생성 중에는 모델 선택 변경과 로그인 시작도 409로 막힌다. 설정 응답의 `busy`는 `_active`만 본다.
3. `_record_success`는 결과가 `ok`이면 마지막 성공 시각을 갱신하고, 기록할 제공자와 모델을 완료 시점의 선택에서 읽는다. 임대 중에는 선택을 바꿀 수 없으므로 지금은 시작 때와 같다. 사용량은 서비스 메서드가 생성 한 번에 한 줄(형식 재시도와 축약 호출 합산, 취소로 끝나도 `outcome: failed`)을 `ai-usage.jsonl`에 쓴다. 쓰기 실패는 경고 로그만 남긴다.
4. 검사 순서는 종류마다 다르다. 도식, 재작성, 수리는 임대 전에 `If-Match` 누락(428), 낡은 `If-Match`(412), 프롬프트 사전 검증(422, 409 `rewrite_protected_evidence`)을 동기로 거절하고, 자료 fingerprint를 요청 시점에 계산해 임대 뒤와 생성 뒤에 다시 비교한다. 생성 도중 덱이 바뀌면 412, 자료가 바뀌면 409를 돌려주고 마지막 성공 시각을 갱신하지 않는다. 구조안은 덱의 어느 장이든 도식이면 거절하고, 장 생성은 대상 장이 도식일 때, 축약은 대상 장이나 보낸 슬롯이 도식일 때 거절한다(`DiagramGenerationUnsupported`, 422). 장 생성의 없는 장은 404, 축약의 템플릿 불일치는 422, 구성 계획 낡음은 409 `stale_story_plan`이다.
5. 덱의 ETag는 `save_deck`이 다시 검증한 덱을 `model_dump_json(indent=2)`로 쓴 UTF-8 바이트의 SHA-256이다. 스냅샷과 manifest 쓰기는 덱 바이트에 영향을 주지 않는다. 리뷰 실험에서 시험 덱 5개의 사전 계산 바이트와 실제 쓰기 바이트가 모두 같았다. 사전 계산과 쓰기는 저장소의 같은 함수를 써야 한다.
6. 구조안 승인 루프는 화면 코드에 있다. 승인 반영 `PUT`(스냅샷 포함) 뒤 슬라이드가 없는 장을 차례로 생성하고 장마다 `PUT`으로 저장하며 `onDeckChange`와 ETag 캐시(`etags`)를 갱신한다. 장 생성 예외는 그 장을 "실패"로 두고 다음 장으로 가지만, 구성 계획 낡음이면 남은 장을 "보류"로 바꾸고 멈춘다. 형식 오류는 "실패"와 응답 원문을 보이고 계속한다. 장 결과 저장이 412이면 미저장본(`generation_unsaved`)을 보존하고 멈춘다. 장마다 사용량을 모아 합계와 "결과 없는 실패" 여부를 보이고, 미검증 숫자의 합집합을 경고로 보인다. 진행 표시(대기, 생성 중, 완료, 실패, 취소, 보류)는 화면 상태에만 있다.
7. 생성 중에는 `ProjectView`가 목록 이동, 자료 탭, 편집 탭, 내보내기, 스냅샷 복구, 서버 내용 다시 읽기를 잠그고 창 닫기에 경고를 띄운다. 잠금의 원천은 구조안 화면과 도식 대화 상자의 `onBusyChange`다. 프로젝트를 열면 첫 탭은 자료 탭이다. 장 재생성과 축약(`GeneratePanel`)은 편집 화면 안에서 패널만 바쁨 상태로 두고, 결과는 사용자가 "반영"을 눌러야 편집 상태에 들어가며 그 장의 슬롯만 바꾼다. 축약의 입력은 화면의 저장 전 슬롯이다. 장을 바꾸면 늦게 온 응답을 버린다.
8. 취소 처리는 제공자마다 다르다. ChatGPT(`CodexProvider.complete`)는 취소되면 중지 신호를 보내고 하위 스레드 종료를 기다린 뒤, 그 사이 완료된 응답이 있어도 버리고 취소를 다시 던진다. Claude(`SubscriptionProvider.complete`)는 SDK 0.2.145 안에서 취소가 올라온다. SDK의 `close()`는 stdin을 닫고 5초 기다린 뒤 종료 신호를 보내며, 정리 중 두 번째 취소가 들어오면 종료 신호 단계를 건너뛰어 CLI 프로세스가 남는다(리뷰 실험 `cancel_probe_double.py`). 남은 프로세스는 SDK의 atexit 정리기가 SIGTERM만 보낸다. 구성 수리(`RepairCoordinator.run`)는 취소를 잡아 `stopped` 결과를 정상 반환한다.
9. 구성 수리 라우트만 클라이언트 연결 끊김을 0.2초 간격으로 감시해 생성을 취소한다(`watch_disconnect`). 다른 라우트도 요청 작업이 취소되면(서버 종료, ASGI 전송 취소) 생성과 임대 획득이 함께 취소된다.
10. 독립 앱은 `desktop_service.serve`가 uvicorn을 `timeout_graceful_shutdown=5`로 실행하고, 부모 프로세스의 stdin이 닫히면 종료를 요청하고 10초 안에 끝나지 않으면 스스로 강제 종료한다. Electron은 11초에 SIGKILL한다(`desktop/runtime.cjs:265-289`). 앱 수명 종료 처리(`lifespan`)는 AI 연결 정리만 한다. 서비스마다 `desktop_instance_id`(32자리 hex)를 받는다. 브리지는 OpenAPI 경로 목록만 통과시키고 동시 요청 상한이 128이며(`desktop/main.cjs:122`), 서비스 요청에 시간 제한을 두지 않는다. 메인 프로세스는 세션 토큰을 가진 `service.request`로 서비스를 직접 부를 수 있다. 닫기 대화 상자의 버튼은 "종료 / 계속 작업"이다.
11. 웹 모드(`__main__ serve`)도 시작할 때 자료 폴더 잠금(`acquire_service_lock`)을 얻는다. 잠금 상태는 `held`, `unsupported`(잠금 미지원 파일 시스템 또는 쓰기 권한 없는 폴더), `none`(잠금을 쓰지 않는 실행, 시험 기본값)이다. 자료 폴더 루트의 점 파일은 프로젝트 목록과 0.2.0 목록에 영향이 없다.
12. 진행 모델 응답(`ProjectProgress`)에는 D2a-6이 비워 둔 `jobs: list[Any] | None` 자리가 있고, 화면은 아직 진행 API를 부르지 않는다(화면 연결은 D3). 상태 표시 컴포넌트(`StatusIndicator`)는 편집 화면의 저장 상태 한 칸에서만 쓰이고, "생성 중"은 호출자가 주는 속성이다.
13. 백엔드 생성 시험은 `TestClient`와 `StubProvider`로 동기 라우트를 부른다. 6개 생성 경로를 부르는 시험은 16개 파일, 70곳(적용 라우트 포함)이다. 요청 취소가 임대를 푸는지 고정한 시험이 5건 있다(`test_ai_connections.py:152-237`). 임대 전 거절 순서를 고정한 시험이 있다(`test_diagram_generation.py:339-353`의 `status_checks == 0`, `test_story_plan_rewrite.py:251-276`). 생성 도중 기준 변경의 412/409를 고정한 시험이 12건이다(`test_diagram_generation.py:297-322`, `test_story_plan_rewrite.py:118-146`). 루트 파일 집합을 요청 전후로 비교하는 시험이 있다(`test_export_history.py`, `test_export_quality.py`).
14. 공용 픽스처 `client`는 `TestClient`를 `with` 없이 만든다. 이때 Starlette는 요청마다 새 이벤트 루프를 열고 닫으므로, 요청 안에서 만든 백그라운드 작업은 요청이 끝날 때 취소된다(리뷰 실험 `bg_task.py`). lifespan도 돌지 않는다.
15. Claude CLI 경로는 환경 변수 `SLIDECAPTAIN_CLAUDE_CLI`, SDK 동봉 CLI, PATH 순으로 고른다(`auth_status.py:39-59`). 이 Mac에는 사용자가 로그인한 `claude`가 PATH에 있고, 개발 가상환경에는 SDK 동봉 실제 CLI가 있다. 독립 앱의 서비스는 셸 환경을 물려받는다. 기본 선택은 Claude Sonnet이다.
16. 지금 `generation_service`의 임대 해제는 `anyio.CancelScope(shield=True)`로 보호되는데, 순수 asyncio 취소가 두 번 들어오면 보호 범위 안의 `await`에 취소가 들어온다(리뷰 실험 `shield_raw_cancel.py`).
17. 프로젝트 잠금은 프로젝트별 `threading.RLock`이다. 같은 이벤트 루프의 코루틴이 잠금을 쥔 채 `await`하면 다른 코루틴이 같은 잠금에 들어온다(리뷰 실험 `rlock_coroutines.py`).
18. 화면 시험은 가짜 타이머를 쓰지 않고, Testing Library의 기본 대기 시간은 1000ms다. 공용 모의 API는 없고 각 시험 파일이 `vi.mock`으로 일부 함수만 모의한다(D2a-2 정정).

## 5. 공통 계약

### 5.1 원장 위치와 연결

- 위치: 자료 폴더 루트의 `.slidecaptain-jobs.sqlite3`(Python 표준 `sqlite3`). 원장 파일은 `create_app`에서 열거나 만들고, 이후 요청 경로는 파일을 새로 만들지 않는다.
- 설정: `journal_mode=DELETE`, `synchronous=FULL`을 명시한다. 이 환경의 SQLite 3.50.4에서 파일 DB의 기본값과 같지만, 기본값이 다른 빌드를 대비한다. WAL을 쓰지 않는 이유는 자료 폴더가 iCloud나 OneDrive 같은 동기화 폴더에 있을 수 있고, 서비스 하나만 쓰므로 WAL의 동시성이 필요 없기 때문이다. 원장 형식 번호는 `PRAGMA user_version`이다. 더 새 번호면 원장을 열지 않는다.
- 연결: 연결 하나를 `check_same_thread=False`로 열고 원장 전용 `threading.Lock`으로 감싼다. 잠금 순서는 항상 프로젝트 잠금 다음 원장 잠금이다. `store.root`가 없는 저장소는 같은 방식의 메모리 원장(`:memory:`) 연결 하나를 쓴다. 재시작 조정 시험은 파일 저장소와 파일 원장으로 한다.
- 원장을 열 수 없을 때(손상, 더 새 형식, 권한): 서비스는 시작하고 편집, 저장, 내보내기를 허용한다. 작업 등록과 래퍼만 503과 `code: "job_ledger_unavailable"`로 막는다. 원장 파일은 지우거나 덮어쓰지 않는다.
- 쓰기 실패: 결과 후보 쓰기가 실패하면 작업은 `failed`(`code: "ledger_write_failed"`)로 끝내되 래퍼는 메모리의 결과를 응답으로 돌려준다. 적용 대상 ETag 기록이 실패하면 덱을 저장하지 않는다.

### 5.2 행 구조

작업 행: 작업 ID, 프로젝트 이름, 종류, 요청 ID, 요청 매개변수 해시, 실행 상태, 시도 수(형식 재시도 포함), 등록 인스턴스 ID, 고정 입력(제공자, 모델, 선택 식별자, 기준 ETag, 자료 fingerprint, 종류별 관련 입력 해시, 종류별 매개변수 JSON), 원격 호출 시각, 결과 JSON(종류별 응답 모델 전체: 사용량, 미검증 숫자, 형식 오류 원문 포함), `candidate_status`, 오류(원인 분류 `error_class`, HTTP 상태, `detail`, `code`), 부모 행의 `outcome`, 등록, 시작, 종료 시각. D4가 채울 계정 프로필, Effort, 동의 리비전 열은 만들어 두고 비운다.

하위 행(묶음의 장): 부모 작업 ID, 장 ID, 순서, 실행 상태, 시도 수, 원격 호출 시각, 결과 JSON(`ChapterResult` 전체), `candidate_status`, 적용 대상 ETag, 적용 결과 ETag, 오류, 시작과 종료 시각. 남은 장을 `interrupted`로 둘 때의 사유는 하위 행의 `error_code`에 둔다(`held_stale_plan`, `provider_failed`). 원장의 프로젝트 이름은 NFC로 정규화하고, 목록 순서는 시각 문자열이 아니라 등록 순번이다(D2b-1 리뷰 R13, R19).

원인 분류 `error_class`는 `input`(입력 오류), `ai_output`(AI 출력 오류), `connection`(연결과 제공자 오류), `base_changed`(기준 변경), `cancelled`, `ledger`다. R11 완료 기준의 세 분류를 원장에 담고, 화면 문구 정리는 D3가 한다.

### 5.3 상태 전이

작업 행과 하위 행은 아래 표의 전이만 허용한다. 모든 원장 쓰기는 "기대한 현재 상태일 때만 갱신"(compare-and-set)으로 하므로, 종료 처리나 재시작 조정이 먼저 쓴 종결 상태를 늦게 깨어난 코루틴이 덮지 못한다. 표 밖의 전이는 예외로 막는다. 기술 설계 6절 그림에 없는 전이는 「상위 문서와 다르게 정하는 것」 1항에 모았다.

| 출발 | 도착 | 일으키는 주체와 조건 |
|---|---|---|
| (없음) | `queued` | 등록 라우트, 등록 검사 통과 |
| `queued` | `running` | 실행기, 임대 획득과 고정 입력 재비교 통과 |
| `queued` | `failed` | 실행기, 임대 획득 실패(선택 변경, 로그인, 모델) 또는 고정 입력 불일치. 원격 호출 0회 |
| `queued` | `cancelled` | 취소 API 또는 래퍼 취소, 임대 획득 전. 임대 획득 중이면 획득이 끝나기를 기다려 놓은 뒤 |
| `queued` | `interrupted` | 재시작 조정, 종료 처리 |
| `running` | `validating` | 실행기, 결과를 원장에 저장 |
| `running` | `failed` | 실행기, 제공자 오류, 결과 없는 실패 |
| `running` | `cancel_requested` | 취소 API 또는 래퍼 취소 |
| `running` | `interrupted` | 재시작 조정과 종료 처리, 원격 호출 시각 없음 |
| `running` | `remote_completion_unknown` | 재시작 조정과 종료 처리, 원격 호출 시각 있음, 결과 없음 |
| `validating` | `succeeded` | 실행기, 검증 통과(후보형은 `candidate_status=held`, 묶음 하위 행은 적용 완료) |
| `validating` | `failed` | 실행기, 형식 오류 확정 또는 적용 단계 오류. 결과는 남긴다 |
| `cancel_requested` | `cancelled` | 실행기, 제공자 태스크가 실제로 끝남. 결과가 있으면 남기고 `candidate_status=held`로 두되 적용하지 않는다 |
| `cancel_requested` | `interrupted` | 재시작 조정과 종료 처리, 원격 호출 시각 없음(기술 설계 그림에 있는 전이) |
| `cancel_requested` | `remote_completion_unknown` | 재시작 조정과 종료 처리, 원격 호출 시각 있음 |

묶음 부모 행은 마지막 장이 끝나면 `validating`을 거쳐 종결한다. 종결 상태는 하위 행에서 계산한다. 모든 장이 `succeeded`이면 `succeeded`(`outcome: all_applied`)이고, 취소로 끝나면 `cancelled`이며, 그 밖에는 `failed`와 해당 `outcome`이다. 하위 행은 시작하지 않은 장이 `queued`로 대기한다.

### 5.4 등록 검사와 실행 검사, 래퍼의 응답

- 등록 검사: 등록 라우트(작업 API와 래퍼)는 지금 라우트가 임대 전에 하는 동기 검사를 모두 같은 순서로 한다. 동의 428, `If-Match`가 필요한 종류의 누락 428, 낡은 `If-Match` 412, 선택 헤더가 현재 선택 식별자와 다르면 409(로그인 확인 없이), 요청 형식과 프롬프트 사전 검증 422/409, 도식 장 거절 422, 없는 장 404, 자료 읽기 422, 서비스 전체에 실행 중인 작업이 있으면 409(5.6). 이 검사를 통과해야 행을 만든다. 거절하면 행을 만들지 않는다.
- 입력 고정: 등록 검사에서 읽은 덱 ETag와 자료 fingerprint, 종류별 관련 입력 해시를 행에 쓴다. 실행기는 임대를 잡은 직후 같은 값을 다시 읽어 비교하고, 하나라도 다르면 원격 호출 없이 `failed`(`base_changed` 또는 `sources_changed`)로 끝낸다.
- 생성 뒤 판정: 결과를 저장한 뒤 다시 비교한다. 다르면 결과는 `candidate_status=stale`로 남는다. 래퍼는 지금처럼 덱 변경과 덱 읽기 불가에 412, 자료 변경에 409를 돌려준다. `_record_success`는 판정이 같을 때(`stale`이 아닌 `ok`)에만 부르고, 작업에 고정한 제공자와 모델로 기록한다.
- 오류 표현: 작업 안에서 일어난 실패는 행에 `error_class`, HTTP 상태, `detail`, `code`를 남긴다. 래퍼는 종결 행에서 지금과 같은 JSON 응답을 다시 만든다. 대응은 다음과 같다. `ConnectionConflict` 409, `ProviderNotAvailable`과 `ProviderCallFailed` 503, `StaleStoryPlan` 409 `stale_story_plan`, `ProtectedEvidenceChanged` 409와 그 코드, 자료 없음 422, 기준 변경 412와 409, 원장 503.
- 래퍼의 취소: 요청이 취소되거나(서버 종료 포함) 수리 라우트가 연결 끊김을 감지하면 작업에 취소를 한 번 요청한다. 수리 라우트의 연결 끊김 감시는 D2b-5b까지 유지한다.
- 래퍼의 요청 ID: 요청마다 새로 만든다.

### 5.5 취소와 종료

- 취소 요청: 실행 상태를 `cancel_requested`로 바꾸고 실행기 루프의 제공자 태스크에 `cancel()`을 **한 번만** 보낸다. 같은 작업에 대한 두 번째 취소 요청은 상태만 확인하고 아무것도 보내지 않는다. 제공자 태스크는 별도 태스크로 두고 실행기는 `asyncio.shield`로 실제 종료를 기다린다. 그래서 실행기 쪽에 들어온 취소가 제공자 정리 구간에 전달되지 않는다.
- 종결: 제공자 태스크가 취소로 끝나면 `cancelled`, 값으로 끝나면(수리의 `stopped`, 늦게 온 응답) 결과를 남기고 `cancelled`, 제공자 오류로 끝나면 오류를 남기고 `cancelled`다. 임대는 제공자 태스크가 실제로 끝난 뒤에 놓는다. 이 경로는 실행기 스레드의 동기 호출(`lease.__exit__`)이라 요청 취소의 영향을 받지 않는다.
- 취소 지연: `cancel_requested`의 최대 지속 시간을 정하지 않는다. Claude 정리는 실측 약 6초(2.3절)이고 SDK 코드상 최대 15초다(5초 대기, 종료 신호 뒤 5초, 강제 종료 뒤 5초). 그동안 화면은 "취소 요청됨"이고 임대는 유지된다. 첫 실측 분포를 D2b-6에서 기록한다.
- 시작 전 취소: `queued`에서 임대 획득 중이면 획득이 끝나기를 기다려 놓은 뒤 `cancelled`로 끝낸다(지금 `generation_service`의 보호와 같은 규칙).
- 종료 순서(lifespan 종료와 `close()`): ① 새 등록을 503 `service_stopping`으로 거절한다 ② 실행 중 작업에 취소를 한 번 보낸다 ③ 최대 5초 기다린다. 5초는 서비스의 강제 종료 시간 10초에서 uvicorn의 종료 대기 5초를 뺀 값이다(사실 10) ④ 그래도 미종결인 행만 5.6의 판정 함수로 compare-and-set 한다(`queued`, `running`, `cancel_requested`는 `interrupted` 또는 `remote_completion_unknown`, 후보형 `validating`은 결과가 있으므로 종결, 묶음 하위 행의 `validating`은 그대로 두고 재시작 조정의 적용 재개에 맡긴다. D2b-1 리뷰 R21) ⑤ 실행기 루프를 멈춘다. Claude 정리가 ③보다 길면 CLI 프로세스는 SDK atexit 정리기의 SIGTERM에 맡긴다. 이 한계는 가정 1에 적는다.

### 5.6 실행기와 재시작 조정

- 실행기는 미종결 작업을 서비스 전체에서 하나만 둔다. 지금 임대가 생성 둘째를 409로 거절하므로 대기열을 두지 않는다. 409 판정은 원장 행이 아니라 **이 서비스 실행기가 가진 작업**으로 한다. 409 응답은 `code: "generation_active"`와 진행 중 작업의 요약(작업 ID, 프로젝트, 종류, 대상, 상태, 시작 시각)을 담고, 문구는 "다른 AI 생성이 진행 중입니다. 끝난 뒤 다시 시도하거나 그 작업을 취소해 주세요."다. 설정 응답의 `busy`는 실행기의 작업도 반영한다.
- 재시작 조정: 서비스가 시작할 때 `data_dir_lock == "held"`이면 다른 인스턴스 ID로 등록된 미종결 행을 아래 표대로 조정한다. 잠금이 `unsupported`나 `none`이면 조정하지 않고, 다른 인스턴스의 미종결 행은 조회 응답에 `owner: "other_instance"`로 표시해 화면이 "다른 실행의 작업, 상태 확인 필요"로 보인다. 이 행들은 409 판정에 쓰지 않는다. 계약의 "재시작 조정은 잠금을 쥔 서비스만 한다"를 그대로 따른다.

| 행 | 재시작 조정 결과 |
|---|---|
| `queued` 작업, 묶음의 시작하지 않은 장 | `interrupted`. 자동으로 시작하지 않는다(계약 규칙 4) |
| `running`과 `cancel_requested`, 원격 호출 시각 없음 | `interrupted` |
| `running`과 `cancel_requested`, 원격 호출 시각 있음, 결과 없음 | `remote_completion_unknown` |
| 후보형 `validating`(결과 있음) | 원격 호출 없이 생성 뒤 판정을 다시 해 `succeeded`(`held` 또는 `stale`) 또는 `failed`(형식 오류) |
| 묶음 하위 행 `validating`, 결과가 형식 오류이거나 슬롯이 없음 | `failed`(`ai_output`). 결과는 형식 판정 전에 저장되므로 생기는 경우다(D2b-1 리뷰 R7) |
| 묶음 하위 행 `validating`, 덱을 읽을 수 없음 | 판정을 미루고 행을 그대로 둔다. 다음 시작에서 다시 판정한다(리뷰 R8) |
| 묶음 하위 행 `validating`, 적용 대상 ETag 없음 | 원격 호출 없이 사슬 검사(5.7)와 적용을 재개한다. 임대를 쓰지 않는다 |
| 묶음 하위 행, 적용 대상 ETag 있음 | 현재 덱 ETag가 대상과 같으면 적용 완료, 기준과 같으면 적용 전으로 보고 사슬 검사와 적용을 재개한다. 둘 다 아니면 덱에 그 장의 슬라이드가 결과와 같은 슬롯으로 있으면 "적용됨, 이후 변경"(`succeeded`)으로, 아니면 `candidate_status=stale`로 둔다 |
| 묶음 부모 | 작업 행 판정을 쓰지 않는다. 하위 행을 조정한 뒤 `parent_outcome`으로 종결 상태를 계산한다. 남은 장은 생성하지 않는다. 하위 행에 `remote_completion_unknown`이나 사유 없는 `interrupted`가 있으면 부모는 `failed`, `outcome: partial`이다. 우선순위는 `cancelled`, `held_stale_plan`, `chain_broken`, `partial` 순이다(리뷰 R9) |

### 5.7 묶음 작업의 장 순서와 장별 오류

쓰기 순서: 한 장의 결과와 남은 장의 처리처럼 여러 행을 함께 바꾸는 경우는 원장의 `batch()`로 한 트랜잭션에 쓰고, 하위 행을 먼저, 부모를 마지막에 바꾼다(D2b-1 리뷰 R15).

장마다 순서: ① 하위 행을 `running`으로 바꾸고 원격 호출 시각을 남긴다 ② 결과를 하위 행에 저장하고 `validating`으로 바꾼다 ③~⑥을 하나의 동기 함수로 `to_thread` 한 번에 실행한다. ③ 프로젝트 잠금 안에서 현재 ETag가 사슬의 기대값(마지막으로 적용 결과 ETag가 기록된 하위 행, 없으면 부모의 기준 ETag)과 같은지, 자료 fingerprint가 고정값과 같은지, 그 장이 아직 구조안에 같은 템플릿으로 있고 슬라이드가 없는지 확인한다 ④ 저장소가 쓸 바이트로 ETag를 계산해 적용 대상 ETag로 기록한다 ⑤ 덱을 저장한다(스냅샷 없음) ⑥ 적용 결과 ETag를 기록하고 `succeeded`로 바꾼다.

| 장의 결과 | 그 장 | 남은 장 | 부모 `outcome` |
|---|---|---|---|
| 적용 완료 | `succeeded`, `applied` | 계속 | |
| 형식 오류(재시도 1회 뒤) | `failed`, `ai_output`, 결과 원문 보존 | 계속(지금 루프와 같다) | `partial` |
| 제공자 오류(`ProviderCallFailed`, `ProviderNotAvailable`) | `failed`, `connection` | `interrupted`(지금 루프는 계속한다. 같은 연결로 남은 장마다 실패할 호출을 보내지 않으려는 변경이다) | `partial` |
| 구성 계획 낡음(`stale_story_plan`) | `failed`, `input` | `interrupted`, 사유 `held_stale_plan`(화면의 "보류") | `held_stale_plan` |
| ③ 사슬 불일치 | `succeeded` 아님: 실행 상태 `failed`(`base_changed`), `candidate_status=stale` | `interrupted` | `chain_broken` |
| ⑤ 저장 예외(검증 오류, 디스크) | `failed`(`code: "apply_failed"`), `candidate_status=held` | `interrupted` | `partial` |
| 취소 | 진행 장은 5.5 규칙, 적용한 장은 유지 | `cancelled` | `cancelled` |

### 5.8 후보의 처분과 오래된 판정

- 후보형 결과는 `candidate_status=held`로 남는다. 화면이 결과를 반영하면 `applied`, 버리면 `dismissed`로 바꾼다(`POST .../jobs/{id}/candidate`, 본문 `{action: "applied" | "dismissed"}`). 묶음의 `stale` 장 후보는 "후보 보기"와 "현재 입력으로 다시 생성"과 "버리기"를 제공한다.
- 판정 기준(`stale_reasons`): 구조안, 도식, 재작성, 수리는 덱 ETag 또는 자료 fingerprint가 다르면 `deck_changed`, `sources_changed`다. 장 재생성과 축약은 관련 입력만 본다. 그 장이 구조안에 없으면 `chapter_missing`, 템플릿이 다르면 `template_changed`, 자료가 다르면 `sources_changed`, 구성 계획이 다르면 `story_plan_changed`, 축약은 요청 슬롯 해시와 화면의 현재 슬롯이 다르면 `slots_changed`(화면이 판정)다. 덱의 다른 부분이 바뀐 것은 `deck_changed_elsewhere`로 알리기만 하고 반영을 막지 않는다. 지금 화면이 다른 장 편집과 무관하게 반영을 허용하기 때문이다.
- `stale`은 결과가 있는 종결 작업에만 조회 때 계산한다. 덱이나 자료를 읽을 수 없으면 `stale_reasons: ["unknown"]`이다. 조회 응답은 기준 ETag와 현재 ETag도 돌려준다(기술 설계 6절의 "생성 기준 리비전과 현재 리비전 표시").
- 1절 목표에서 "모델 선택"은 판정 조건에서 뺐다. 임대가 실행 중 선택 변경을 막으므로 결과는 고정 선택으로 만들어진다. 지금 수리의 `unchanged()`가 선택을 비교하던 것은 이 규칙으로 대체한다.

### 5.9 작업 API와 조회

- 라우트: `POST /api/projects/{name}/jobs`(등록, 본문 `{request_id, kind, params}`, 종류별 매개변수는 구별 유니언 모델, 헤더 `X-AI-Consent`, `X-AI-Selection`, 필요한 종류는 `If-Match`. 새 작업 202, 병합 200), `GET /api/projects/{name}/jobs`(최근 작업과 처분되지 않은 후보, 미종결 우선, `cache: no-store`), `GET /api/projects/{name}/jobs/{id}`(실행 상태, 하위 행, 결과, `candidate_status`, `stale_reasons`, 기준과 현재 ETag), `POST .../jobs/{id}/cancel`, `POST .../jobs/{id}/candidate`, `GET /api/jobs/active`(서비스 전체의 실행 중 작업 요약 또는 없음).
- 진행 API의 `jobs`는 `GET .../jobs` 목록 항목과 같은 모델로 채운다(화면 연결은 D3).
- 요청 ID: 화면이 버튼을 누를 때 한 번 만들고, 등록 응답을 받지 못한 재시도에는 같은 ID를 쓴다. 등록이 실패로 확정되거나 사용자가 "다시 생성"을 누르면 새 ID를 만든다. 같은 프로젝트, 같은 요청 ID, 같은 종류와 매개변수 해시이면 기존 작업을 돌려준다(종결된 작업 포함). 매개변수가 다르면 409 `request_id_conflict`다.
- 조회: 앞 응답을 받은 뒤 다음 조회를 예약한다. 간격의 초기값은 1초이고 근거는 없다. D2b-6에서 조회 요청 수와 화면 반영 지연을 기록해 다시 정한다. 조회가 실패하면 "작업 상태를 확인하지 못했습니다"와 "다시 확인" 버튼을 보이고 조회는 계속한다. 간격은 훅 인자로 받아 시험에서 바꿀 수 있게 한다.

## 6. 태스크

### 모든 태스크의 공통 규칙

- TDD로 진행한다. 계획서의 시험은 **RED**(지금 코드의 틀린 동작을 겨냥해 실패부터 확인하는 시험)와 **고정**(지금도 맞는 동작이 깨지지 않게 묶는 회귀 시험)으로 나눠 적는다. RED마다 "지금 코드의 틀린 동작"을 한 줄로 적는다. 새 API가 없어서 생기는 404나 가져오기 오류는 RED의 실패로 치지 않는다. 지금 코드에서도 맞는 동작은 고정이다.
- 새 라우트나 응답 모델 필드를 더하는 커밋은 같은 커밋에서 OpenAPI, 프런트 타입, 브리지 경로 목록(`check_desktop_routes.py --write`)을 재생성하고 desktop 테스트를 돌린다. 화면 시험은 각 시험 파일의 `vi.mock` 목록에 새 API 함수의 기본 모의를 더한다.
- 상태 변경 라우트는 `X-Requested-With: SlideCaptain` 헤더 규약을 따르고, 작업을 등록하는 라우트는 `X-AI-Consent` 관문을 지난다.
- 백엔드 시험은 고정 시간 대기를 쓰지 않는다. 실행기의 `wait(job_id)`(동기 시험에서는 `client.portal.call` 또는 실행기의 동기 대기 함수)와 단계마다 멈추는 관문 제공자를 쓴다. 백그라운드 실행을 검증하는 새 시험은 `with TestClient(...)`로 만들고, 픽스처 정리에서 실행기 `close()`를 부른다.
- 화면 시험은 실제 1초 대기를 쓰지 않는다. 조회 간격 인자와 "지금 다시 조회" 함수를 쓴다.
- 화면을 작업 API로 옮길 때 기존 단언은 지우지 않고 새 모의로 바꾼다. 지우는 단언은 사유를 커밋에 적는다. 클라이언트의 `api.generateChapter`, `condenseChapter`, `generateStructure`, `rewriteStory`, `repairStory`, `generateDiagram`은 이름과 반환 형식을 유지한 채 "등록 뒤 종결까지 조회"로 바꾼다. 그러면 단발 흐름 시험은 그대로 두고 재진입 시험만 새로 쓴다.
- Windows 전용 분기의 RED는 macOS에서 실패부터 볼 수 없다. 그런 시험은 CI의 Windows 작업에서 처음 실패를 확인한다고 커밋에 적는다.
- 모든 시험과 수동 확인은 실제 Claude 호출을 막은 상태에서 한다. 별도 프로세스 시험과 패키지 확인은 서비스 환경의 `SLIDECAPTAIN_CLAUDE_CLI`를 가짜 CLI나 존재하지 않는 경로로 지정하고, 시작 직후 그 값이 들어갔는지 단언한다. PATH의 실제 `claude`와 SDK 동봉 CLI가 쓰이지 않아야 한다.
- 생성 텍스트와 문서에 엠대시와 중점을 쓰지 않는다.

### D2b-4 장 생성 묶음 작업

- 종류 `chapters`: 매개변수는 생성할 장 ID 목록이다. 등록 검사는 대상 장 목록에 도식 장이 있으면 422로 거절하고, 구성 계획 낡음을 등록 때 확인한다. 화면은 승인 반영 `PUT`을 끝낸 뒤 그 응답 ETag를 `If-Match`로 주어 등록한다.
- 5.7의 장 순서와 장별 오류 표, 5.6 표의 묶음 행 조정(적용 재개)을 구현한다. 사용량은 장마다 한 줄씩 지금처럼 기록한다.
- RED(지금 코드의 틀린 동작):
  - 저장 중 종료(필수 RED 1): ④와 ⑤ 사이, ⑤와 ⑥ 사이에 예외를 주입한 뒤 재시작 조정이 적용 여부를 바르게 판정하고 남은 장을 생성하지 않는다. 지금은 화면이 장 결과를 메모리에 둔 채 저장하므로, 저장 중 앱이 죽으면 결과와 진행 표시가 모두 사라진다.
  - 강제 종료 직전 완료(필수 RED 2): ②와 ③ 사이에 끊은 뒤 재시작 조정을 돌리면, 제공자 호출 0회로 그 장이 적용되거나 이전 입력 기준 후보로 남는다. ①과 ② 사이에 끊으면 그 장은 `remote_completion_unknown`이고 호출 0회다. 지금은 응답 전 종료 시 결과가 사라지고 화면을 다시 열면 그 장이 "슬라이드 없음"으로 보여 재승인이 비용을 다시 쓴다.
  - 계정 만료(필수 RED 4): 묶음 도중 장과 장 사이에 로그인이 만료되면 그 장은 `failed`(`connection`)이고 남은 장은 `interrupted`이며 호출은 만료된 장 1회뿐이다. 지금 루프는 남은 장마다 실패할 요청을 보낸다.
  - 늦은 성공 응답의 묶음 쪽(필수 RED 6): 관문 제공자가 응답하기 전에 다른 저장이 덱을 바꾸면 그 장은 적용되지 않고 `stale` 후보로 남으며 덱은 다른 저장의 내용 그대로다. 지금 루프는 412 뒤 그 결과를 미저장본으로 보존하지만 원장 후보처럼 재시작을 넘어 장 단위로 남지 않는다.
- 고정: 지금 승인 루프와 같은 덱(슬라이드 순서, 공통 슬롯 빈 값), 하위 행의 미검증 숫자와 사용량이 지금 루프가 화면에 모으는 값과 같음, 형식 오류 장의 원문 보존, 구성 계획 낡음의 보류.

### D2b-5a 진행 작업 조회와 구조안 승인

- 조회 훅(5.9)을 `ProjectView`에 둔다. 프로젝트를 열면 `GET /api/jobs/active`와 `GET .../jobs`를 먼저 부르고, 응답 전에는 생성 중과 같은 잠금을 건다(문구 "작업 상태를 확인하는 중"). 미종결 작업이 이 프로젝트의 묶음이면 구조안 탭의 진행 표시를 그 작업으로 채운다. 다른 프로젝트의 작업이면 머리에 "다른 프로젝트에서 AI 생성이 진행 중입니다"와 취소 버튼을 보인다. 창이 초점을 얻을 때 다시 조회한다.
- 승인 순서: ① 로그인과 동의 확인(`aiHeaders`) ② 승인 반영 `PUT` ③ 묶음 등록. 동의 거절과 로그인 실패는 덱을 바꾸지 않는다. 등록이 409나 503으로 실패하면 "장 구성은 저장했고 내용 생성은 시작하지 못했습니다"와 원인, "내용 생성 다시 시작" 버튼을 보인다.
- 덱 따라가기: 하위 행이 `succeeded`로 바뀔 때마다와 부모가 종결될 때 `getDeck`으로 덱과 ETag를 다시 읽어 `onDeckChange`로 올린다.
- 하위 상태별 화면 표시와 행동: `queued` 대기, `running`과 `validating` 생성 중, `succeeded` 완료, `failed` 실패(이 장 다시 생성), `interrupted`는 사유가 `held_stale_plan`이면 보류(구성 복구 안내), 아니면 중단(이 장 다시 생성), `cancelled` 취소, `remote_completion_unknown` 완료 여부 확인 필요(다시 생성 전에 "완료 여부를 확인하지 못했습니다. 다시 생성하면 AI 사용량이 한 번 더 기록될 수 있습니다" 확인), `stale` 후보는 후보 보기, 현재 입력으로 다시 생성, 버리기. "다시 생성"은 그 장들만 담은 새 묶음을 새 요청 ID로 등록한다.
- 사용량 합계, "결과 없는 실패" 표시, 미검증 숫자, 형식 오류 원문은 하위 행 결과에서 계산한다. 실패 요약("6장 중 1장 실패")은 가장 최근 묶음에서 계산하되, 그 뒤 슬라이드가 생긴 장은 완료로 보인다. 새 승인이나 재작성 적용 뒤에는 이전 요약을 숨긴다. 편집 탭 자동 전환은 이 화면에서 등록한 작업이 실패 장 없이 끝났을 때만 한다.

### D2b-5b 후보형 화면의 작업 연결과 후보 처분

## 7. 가정과 미확인

1. Claude 취소: 실행기 규칙(취소 한 번, 정리 구간 보호) 아래에서 CLI 프로세스가 정리된다는 것은 2.3의 실험 1회와 리뷰 실험으로만 확인했다. 종료 처리의 5초 안에 정리가 끝나지 않으면 CLI 프로세스는 SDK atexit 정리기(SIGTERM)에 맡겨진다. D2b-2에서 세 경우를 시험으로 고정한다.
2. 제공자는 멱등 호출을 지원하지 않는다. 원격 실행을 정확히 한 번이라고 보증하지 않는다(기술 설계 6절). 요청 ID 병합은 이 앱 안의 중복 등록만 막는다.
3. 잠금이 `unsupported`인 폴더에서는 다른 인스턴스의 미종결 행을 조정하지 않으므로, 그런 행이 "확인 필요"로 계속 보일 수 있다. 정리는 D6의 자료 폴더 화면이 맡는다.
4. 원장 행 크기는 결과 JSON이 정한다. 보존 기간과 정리 기준은 실제 사용의 원장(D6 사람 사용 검증 또는 승인된 실호출 관통)에서 분포를 본 뒤 정한다. 합성 관통에서는 최대 결과 크기만 기록한다. 그때까지 원장은 지우지 않는다. 프로젝트를 지우거나 옮기거나 같은 이름으로 새로 만들면 옛 행이 새 프로젝트의 목록에 보일 수 있다. 앱에는 프로젝트 삭제와 이름 변경 기능이 없으므로 이 단위에서는 행의 기준 ETag가 현재 덱 이력과 맞지 않는 행을 "다른 덱의 후보"로 표시하는 데서 멈춘다.
5. 동기화 폴더 위의 SQLite는 WAL이 아니어도 동기화 도중 파일이 바뀔 위험이 남는다. 안내는 D6가 맡는다.
6. D2b-α 동안 화면은 래퍼를 쓴다. 독립 앱 브리지의 fetch는 응답 헤더를 기본 300초까지만 기다리는 것으로 알려져 있다(undici 기본값, 이 저장소에서 실측하지 않음). 그보다 긴 래퍼 요청은 화면에서 실패로 보이지만 결과는 원장에 남는다. 화면이 그 결과를 읽는 경로는 β에서 생긴다.
7. 숫자의 출처: 300초는 `SubscriptionProvider`의 기본 시간 한도(`subscription.py:170`)다. 묶음 작업 하나의 최대 길이는 장 수에 장당 최대 길이(시간 한도와 형식 재시도 1회)를 곱한 값이다. 128은 `desktop/main.cjs:122`, 5초 종료 대기는 사실 10에서 계산했다. 조회 간격 1초는 근거 없는 초기값이다.

## 상위 문서와 다르게 정하는 것

1. 상태 전이: 기술 설계 6절 그림에 없는 전이를 쓴다. `queued→failed`(임대 획득 실패, 고정 입력 불일치), `queued→cancelled`, `queued→interrupted`, `cancel_requested→remote_completion_unknown`, `validating→failed`, `running→remote_completion_unknown`(그림의 "재시작에서 실행 중으로 남은 작업"을 원격 호출 여부로 나눈 것). 그림은 정상 흐름만 그리고, 시작 전 실패와 시작 전 취소와 재시작 시점의 각 상태를 따로 그리지 않았기 때문이다.
2. 실행 상태와 후보 처분의 분리: 상태 이름 9종에 더해 `candidate_status`와 부모 `outcome`을 둔다. `succeeded`의 뜻은 그림대로 "검증까지 끝난 성공"이며, 묶음 부모는 모든 장이 적용됐을 때만 `succeeded`다.
3. 동의 검사 시점: D2 계획 6절은 "대기 작업은 실행 직전에 임대, 선택, 동의를 다시 검사한다"고 적는다. 동의는 등록 시점에만 검사한다. 지금 동의는 요청 헤더일 뿐 저장된 기록이 없어 실행 직전에 다시 검사할 대상이 없다. D4가 영속 동의를 만들면 실행 직전 검사로 옮긴다.
4. 고정 입력: 기술 설계 6절의 "계정/모델/Effort/동의 리비전" 가운데 제공자, 모델, 선택 식별자만 고정하고 나머지는 빈 열로 둔다. 값의 원천이 D4에서 생긴다.
5. 직렬화 대신 거절: D2 계획 6절 행동 규칙 (1)은 "같은 프로젝트의 충돌 작업은 직렬화한다"이다. 이 단위는 대기열 없이 실행 중 작업이 있으면 새 등록을 409로 거절한다. 지금도 임대가 생성 둘째를 409로 거절하고 화면이 생성 중 다른 생성을 잠그므로 대기열이 쓰일 경로가 없다. 대기열은 대기 작업의 재바인딩 검사와 긴 대기를 새로 만든다. 생성 중 편집과 이동을 허용하는 D3에서 다시 판단한다.
6. 래퍼의 취소: 계약의 "브리지 요청 취소와 작업 취소의 분리"는 작업 API에만 적용한다. 래퍼는 지금처럼 요청 취소와 연결 끊김을 작업 취소로 바꾼다(2.2).
7. 장 재생성과 축약의 반영: 계약 규칙 (8)은 "적용은 서버가 현재 ETag와 입력 fingerprint를 다시 비교"한다. 장 재생성과 축약은 편집 화면이 저장 전 상태를 가지므로 화면이 반영하고, 서버는 관련 입력 단위의 `stale_reasons`를 돌려준다(5.8). 남는 위험은 조회 시점과 반영 시점 사이에 관련 입력이 바뀌는 경우이며, 반영 직전에 화면이 조회를 한 번 더 한다.
8. 생성 중 편집 허용(제품 설계 7절)은 이 단위에서 하지 않는다. 묶음 사슬은 덱 ETag로 엄격하게 비교한다(2.1).
9. 웹 모드 탭 닫기 뒤의 작업 계속(제품 설계 7절의 "볼 수 없는 상태에서 계속 돌리지 않는다")은 D3다. 독립 앱의 창 닫기는 D2b-5c가 맡는다.
10. 원인 구분 안내: D2 계획 9절은 R11의 "원인 구분 안내"를 D2b와 D3에 함께 걸었다. 이 단위는 원장의 원인 분류와 시험까지 하고, 화면 문구 정리는 D3로 넘긴다. 문구 정리는 다섯 작업 단계의 화면 재배치와 함께 해야 같은 안내를 두 번 고치지 않기 때문이다.
11. 저장 중 이탈 임시본(D2 계획 「다르게 정하는 것」 3항이 넘긴 것)은 구현하지 않고 방치 확정으로 올린다(2.6).
12. 묶음 작업의 제공자 오류: 지금 승인 루프는 제공자 오류 뒤에도 남은 장을 계속 시도한다. 묶음 작업은 남은 장을 `interrupted`로 둔다(5.7). 같은 연결로 실패할 호출을 장마다 보내지 않으려는 변경이다.
