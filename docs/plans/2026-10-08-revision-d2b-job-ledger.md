# 개정판 D2b 작업 원장 계획

작성: 2026-10-08 (서울 기준). D2a 종결 보고 뒤 사용자가 "작업 계속 이어서 진행"을 지시했다. 이 지시를 D2b 계획서 착수의 승인으로 기록한다. 승인 범위는 이 계획서의 초안 작성과 커밋까지다. 독립 적대 리뷰의 실행과 규모, 10절의 설계 선택, 구현 착수는 사용자가 따로 결정한다.

상위 문서는 다음과 같다. [D2 계획 6절](2026-10-08-revision-d2-common-foundation.md#6-d2b-계약-상세-계획은-d2a-뒤)의 D2b 계약이 출발점이고, 그 계약의 출처는 [기술 설계 6절](../architecture/2026-10-02-desktop-revision.md#6-작업-원장-취소와-복구)과 [제품 설계 7절](../design/2026-10-02-revision-product-ux.md#7-저장-동의와-긴-작업)이다. 이 계획서는 상위 문서를 재정의하지 않는다. 상위 문서와 다르게 정하는 부분은 「상위 문서와 다르게 정하는 것」 절에 이유와 함께 모은다.

## 1. 이번 단위의 목표

AI 생성 작업을 HTTP 요청 하나의 수명에서 떼어 내어, 서비스가 기록하고 관리하는 작업으로 바꾼다. 목표는 넷이다.

- R11의 중단 복구: 앱을 강제 종료하거나 재시작해도 생성 작업의 결과와 실패가 사라지지 않는다. 원격 호출이 끝났는지 모르는 작업은 그 사실을 표시하고, 자동으로 다시 호출하지 않는다.
- R11의 결과 보존: 생성 뒤 입력(덱, 자료, 모델 선택)이 바뀌었으면 결과를 적용하지 않고 "이전 입력 기준 후보"로 남긴다. 늦게 도착한 결과가 새 편집을 덮지 않는다.
- R01의 생성 상태: 화면은 "생성 중", "취소 요청됨", "완료 여부 확인 필요", "6장 중 1장 실패"를 세션과 재시작을 넘어 같은 원천(원장)에서 읽는다.
- D2 완료 관문: 기술 설계 7절의 "변경, 저장, 충돌, 중단 복구 상태를 모의 서버와 실제 저장으로 검증"을 D2a 결과와 합쳐 통과로 기록할 수 있게 한다.

## 2. 핵심 설계 결정

### 2.1 장 생성은 서버가 차례로 적용하는 묶음 작업으로 한다 (사용자 결정 대기, 추천안)

지금 구조안 승인 루프(`StructureScreen.approve`)는 화면이 장마다 생성 요청을 보내고, 결과를 받을 때마다 덱을 저장한다(사실 6). N+1번째 장의 기준 ETag는 N번째 장의 저장 뒤에야 생긴다.

| 선택지 | 결과 | 판정 |
|---|---|---|
| A. 묶음 작업 1개(추천) | 승인 뒤 화면이 "장 생성 묶음" 작업 하나를 등록한다. 서버가 장을 차례로 생성하고 장마다 ETag 사슬을 검사해 저장한다. 화면을 떠나거나 다시 열어도 작업이 계속되고, 재시작 뒤에는 어느 장까지 적용됐는지가 원장에 남는다 | 계약의 "세션을 넘어 남는 6장 중 1장 실패"와 "임대는 작업 수명에 묶는다"를 그대로 만족한다 |
| B. 장마다 작업 1개를 화면이 연결 | 화면이 장 작업이 끝날 때마다 다음 장 작업을 등록한다. 지금 구조와 가깝다 | 화면이 닫히면 남은 장의 등록이 멈춘다. 등록하지 않은 장은 원장에 없으므로 "대기" 상태가 재시작을 넘지 못한다 |

A를 택하면 계약 행동 규칙 (8)의 "적용 직전 ETag 비교"가 장마다 일어난다. 묶음 작업은 시작할 때 고정한 ETag에서 출발하고, 자기가 저장한 덱의 ETag를 다음 장의 기대값으로 쓴다. 다른 주체가 덱을 바꾸면 사슬이 끊기고, 그 장의 결과는 이전 입력 기준 후보로 남으며 남은 장은 시작하지 않는다. 생성 중에는 지금도 구조안 탭 밖으로 이동과 편집이 잠겨 있으므로(사실 7) 이 단위에서 사슬이 끊기는 경우는 다른 창, 0.2.0, 손으로 고친 파일뿐이다. 생성 중 편집 허용(제품 설계 7절)은 D3가 이 사슬 검사를 관련 입력 단위로 완화하면서 다룬다.

### 2.2 기존 동기 생성 라우트 6개는 원장 위의 얇은 래퍼로 남긴다 (사용자 결정 대기, 추천안)

| 선택지 | 결과 | 판정 |
|---|---|---|
| A. 래퍼로 유지(추천) | 기존 6개 라우트가 작업을 등록하고 끝날 때까지 기다린 뒤 지금과 같은 응답을 돌려준다. 실행 경로는 원장 하나뿐이다. 백엔드 시험 16개 파일의 생성 호출 약 65곳이 그대로 관문 회귀 시험으로 남는다 | 시험 재작성 없이 단일 실행 경로를 얻는다. 화면은 새 작업 API로 옮기고, 래퍼 제거는 D3에서 화면이 래퍼를 쓰지 않음을 확인한 뒤 한다 |
| B. 제거 | 모든 생성 시험을 작업 API로 다시 쓴다 | API 표면은 하나가 되지만, 관문(동의 428, 도식 거절, 형식 재시도 1회) 회귀 시험을 옮기는 동안 검증 공백이 생긴다 |

래퍼에서도 동작이 하나 바뀐다. 지금 구성 수리(`story-plan/repair`)는 클라이언트 연결이 끊기면 생성을 취소한다(사실 9). 래퍼로 옮기면 연결이 끊겨도 작업은 계속되고 결과는 원장에 남는다. 취소는 작업 취소 API로만 한다. 계약의 "브리지의 요청 취소는 작업 취소와 분리한다"를 따른 변경이다.

### 2.3 D2b를 두 묶음으로 나눈다

| 묶음 | 태스크 | 끝나면 관측되는 것 |
|---|---|---|
| D2b-α 원장과 실행기 | D2b-1 원장 저장소, D2b-2 실행기와 작업 API, D2b-3 후보형 생성 6종의 이전 | 화면은 그대로인데 모든 생성이 원장을 거친다. 재시작 조정과 필수 RED 시험 6종 중 5종이 통과한다 |
| D2b-β 묶음 작업과 화면 | D2b-4 장 생성 묶음 작업, D2b-5 화면 연결, D2b-6 재시작 관통과 패키지 확인 | 화면이 원장을 읽는다. 실제 프로세스를 죽였다 살리는 관통이 통과한다 |

D2b-α가 끝나면 묶음 리뷰를 한 번 받고, 사용자와 상의한 뒤 D2b-β로 넘어간다(단계 경계 규칙). α만 끝난 상태를 D2 관문 통과로 기록하지 않는다.

### 2.4 저장 중 이탈 시 로컬 임시본은 구현하지 않는다 (사용자 결정 대기, 추천안)

D2 계획의 「상위 문서와 다르게 정하는 것」 3항이 이 판단을 D2b로 넘겼다. 이 계획은 판단을 다시 미루지 않는다. 판정은 "구현하지 않고 로드맵 방치 확정 문단에 올린다"이다.

- 근거: D2b 뒤에는 AI 생성 결과가 응답이 아니라 원장에 남으므로, 비용을 쓴 결과의 손실 경로가 닫힌다. 남는 손실은 편집 화면의 자동 저장 지연 시간 안에 친 글자가 앱 강제 종료로 사라지는 경우다. 창 닫기와 이탈은 이미 미저장 경고(`beforeunload`)가 막는다.
- 비용: 렌더러에 파일 쓰기 권한을 주려면 preload IPC를 넓혀야 하고, 이는 D1의 브리지 보안 경계(사실 10)를 바꾼다.
- 다시 열 조건: 사람 사용 검증(D6)에서 강제 종료로 편집을 잃은 사례가 한 건이라도 기록되면 다시 판단한다.

## 3. 범위 밖

| 항목 | 담당 단계 |
|---|---|
| 생성 중 편집과 화면 이동 허용, 관련 입력 단위의 후보 판정 완화, 다섯 작업 단계의 진행 표시 배치 | D3 |
| 생성 화면의 실패 안내 전체, 원인별 문구 정리, 사용량 문구 제거(R12) | D3 |
| 기존 동기 생성 라우트 6개의 제거(2.2에서 A를 택한 경우) | D3 |
| 계정 프로필, Effort, 동의 리비전의 값 채우기(원장의 자리만 둔다), 동의 철회 시 진행 중 작업 취소 요청 | D4 |
| 이번 생성에 포함할 자료의 선택 | D5 |
| 원장 행의 보존 기간과 정리 | 6절 가정 4에 따라 행 크기를 실측한 뒤 결정 |

이 단위의 실제 AI 호출은 0회다. 생성 경로는 모의 제공자와 가짜 CLI로 검증한다. main 머지와 릴리스도 범위 밖이다.

## 4. 현재 코드에서 확인한 사실

코드 기준은 `17902b4`(D2a 종결)다.

1. 생성 라우트는 6개다: 구조안(`generate/structure`), 장 생성(`generate/chapter/{id}`), 축약(`.../condense`), 도식(`generate/diagram`), 구성 재작성 미리보기(`story-plan/rewrite`), 구성 수리 미리보기(`story-plan/repair`). 모두 `_require_ai_consent`로 `X-AI-Consent` 헤더를 검사하고(없으면 428), `generation_service(x_ai_selection)` 안에서 AI를 부르고, 결과를 응답으로만 돌려준다. 서버는 결과를 저장하지 않는다.
2. 생성 임대 `AIConnections.generation(selection_id)`는 프로세스 메모리의 카운터 `_active`다. 이미 다른 생성이 진행 중이면 `_idle()`이 대기 없이 `ConnectionConflict`(409)를 낸다. 즉 지금은 **프로세스 전체에서 생성이 한 번에 하나**다. 임대를 잡을 때 선택 식별자, 로그인 대기 여부, 로그인 상태, 모델 목록을 다시 확인한다. 생성 중에는 모델 선택 변경과 로그인 시작도 409로 막힌다.
3. `_record_success`는 결과가 `ok`이면 마지막 성공 시각을 갱신하는데, 기록할 제공자와 모델을 **완료 시점의** `ai_connections.selection`에서 읽는다. `_append_usage`는 사용량을 프로젝트의 `ai-usage.jsonl`에 쓰고, 쓰기 실패는 경고 로그만 남긴다.
4. 도식, 재작성, 수리는 `If-Match`로 기준 ETag를 받고, 생성 전후에 ETag와 자료 fingerprint(`sources_fingerprint`)를 다시 비교한다. 구조안, 장 생성, 축약은 기준 ETag를 받지 않는다. 장 생성과 축약과 구조안은 덱에 도식 장이 있으면 생성 전에 거절한다(`DiagramGenerationUnsupported`).
5. 덱의 ETag는 `deck.json` 바이트의 SHA-256이다(`file_store.py`). 따라서 저장할 덱의 직렬화 결과로 저장 뒤 ETag를 미리 계산할 수 있다.
6. 구조안 승인 루프는 화면 코드에 있다. 승인 반영 `PUT`(스냅샷 포함) 뒤 슬라이드가 없는 장을 차례로 생성하고, 장마다 `PUT`으로 저장한다. 저장이 412이면 미저장본을 보존하고(D2a-2) 남은 장을 시도하지 않는다. 진행 표시(대기, 생성 중, 완료, 실패, 취소, 보류)는 화면 상태에만 있어 새로고침이나 재시작으로 사라진다.
7. 생성 중에는 `ProjectView`가 목록 이동, 자료 탭, 편집 탭, 내보내기, 스냅샷 복구, 서버 내용 다시 읽기를 잠그고, 창 닫기에 경고를 띄운다. 구조안 탭만 잠그지 않는다(진행 표시가 그 화면에 있다). 장 재생성과 축약(`GeneratePanel`)은 편집 화면 안에서 패널만 바쁨 상태로 두고, 결과는 사용자가 "적용"을 눌러야 편집 상태에 들어간다.
8. 취소 처리는 제공자마다 다르다. ChatGPT(`CodexProvider.complete`)는 작업이 취소되면 중지 신호를 보내고 하위 스레드가 끝나기를 기다린 뒤 취소를 다시 던진다. Claude(`SubscriptionProvider.complete`)는 SDK의 `query` 비동기 생성기를 `asyncio.wait_for` 안에서 소비할 뿐 취소 처리가 따로 없다. 생성기가 닫힐 때 SDK가 Claude Code 하위 프로세스를 끝내는지는 **확인하지 않았다**(가정 1).
9. 구성 수리 라우트만 클라이언트 연결 끊김을 0.2초 간격으로 감시해 생성을 취소한다(`watch_disconnect`).
10. 독립 앱은 `desktop_service.serve`가 uvicorn을 `timeout_graceful_shutdown=5`로 실행하고, 부모 프로세스의 stdin이 닫히면 종료를 요청하고 10초 안에 끝나지 않으면 강제 종료한다. 앱 수명 종료 처리(`lifespan`)는 AI 연결 정리만 한다. 독립 앱은 서비스마다 `desktop_instance_id`(32자리 hex)를 받는다. 웹 모드에는 이 값이 없다. 브리지는 OpenAPI 경로 목록(`desktop/api-routes.json`)만 통과시키고 동시 요청 상한이 128이다.
11. 자료 폴더 루트에는 D2a-3의 잠금 파일(`.slidecaptain-service.lock`, `.slidecaptain-service.json`)이 있다. 프로젝트 목록은 폴더만 읽으므로 점으로 시작하는 파일은 목록에 영향이 없다. D2a의 0.2.0 실측에서도 루트의 점 파일은 0.2.0 목록을 깨지 않았다.
12. 진행 모델 응답(`ProjectProgress`)에는 D2a-6이 비워 둔 `jobs: list[Any] | None` 자리가 있다. 상태 표시 컴포넌트의 "생성 중"은 호출자가 주는 속성이다(D2a-5).
13. 백엔드 생성 시험은 `TestClient`와 `StubProvider`(응답 목록을 차례로 돌려주는 모의 제공자)로 동기 라우트를 부른다. 백그라운드 작업을 결정적으로 기다리는 수단은 아직 없다.

## 5. 태스크

### 모든 태스크의 공통 규칙

- TDD로 진행한다. 시험은 **RED**(지금 코드에서 틀린 동작을 겨냥해 실패부터 확인하는 시험)와 **고정**(지금도 맞는 동작이 깨지지 않게 묶는 회귀 시험)으로 나눠 적는다.
- 새 라우트나 응답 모델 필드를 더하는 커밋은 같은 커밋에서 OpenAPI, 프런트 타입, 브리지 경로 목록(`check_desktop_routes.py --write`)을 재생성하고 desktop 테스트를 돌린다. 공용 모의 API(`frontend/src/test/fixtures.ts`)에 새 함수의 기본 성공 모의를 더한다.
- 상태 변경 라우트는 `X-Requested-With: SlideCaptain` 헤더 규약을 따르고, 작업을 등록하는 라우트는 `X-AI-Consent` 관문을 지난다.
- 백그라운드 작업을 기다릴 때 고정 시간 대기(`sleep`)를 쓰지 않는다. 실행기가 시험용 대기 수단(`await runner.wait(job_id)`, 단계마다 멈추는 관문 제공자)을 제공하고, 시험은 그것만 쓴다.
- 생성 텍스트와 문서에 엠대시와 중점을 쓰지 않는다.

### D2b-1 원장 저장소와 상태 전이

- 위치와 형식: 자료 폴더 루트의 `.slidecaptain-jobs.sqlite3`(Python 표준 `sqlite3`). 자료 폴더가 iCloud나 OneDrive 같은 동기화 폴더에 있을 수 있으므로 WAL을 쓰지 않고 `journal_mode=DELETE`, `synchronous=FULL`로 연다. 한 자료 폴더는 서비스 하나만 쓰므로(D2a-3) WAL의 동시성이 필요 없다. 원장 형식 번호를 `PRAGMA user_version`에 둔다. 더 새 번호면 원장을 열지 않는다.
- 행 구조(작업): 작업 ID, 프로젝트 이름, 종류, 요청 ID(프로젝트 안에서 유일), 상태, 시도 수, 등록 서비스의 인스턴스 ID, 고정 입력(제공자, 모델, 선택 식별자, 기준 ETag, 자료 fingerprint, 종류별 매개변수 JSON), 원격 호출을 보낸 시각, 결과 후보 JSON, 적용 대상 ETag(저장 직전에 계산해 기록), 적용 결과 ETag, 오류 코드와 문구, 등록, 시작, 종료 시각. D4가 채울 계정 프로필, Effort, 동의 리비전 열은 만들어 두고 비운다. 묶음 작업의 장별 결과는 하위 행(작업 ID, 장 ID, 순서, 상태, 결과 후보, 적용 대상 ETag, 적용 결과 ETag, 오류)으로 둔다.
- 상태: `queued`, `running`, `validating`, `succeeded`, `cancel_requested`, `cancelled`, `interrupted`, `remote_completion_unknown`, `failed`. 상태 전이는 한 함수만 쓰고, 기술 설계 6절의 그림에 없는 전이는 예외로 막는다. 결과 후보와 상태 변경은 한 트랜잭션에 쓴다.
- 서비스 인스턴스 ID: 독립 앱은 `desktop_instance_id`를 쓰고, 웹 모드와 시험은 `create_app`이 시작할 때 새로 만든다. 재시작 조정의 기준은 잠금 상태가 아니라 이 ID다. 잠금이 `unsupported`(파일 시스템이 잠금을 지원하지 않음)일 때도 조정이 동작하게 하려는 것이다. 그 경우 두 서비스가 같은 폴더를 쓰면 한쪽이 다른 쪽의 실행 중 작업을 중단으로 바꿀 수 있다. 이 한계는 D2a-3의 경고와 함께 가정 3에 적는다.
- 재시작 조정: 서비스가 시작할 때, 다른 인스턴스 ID로 등록된 미종결 작업을 아래 규칙으로 바꾼다. 원격 호출을 보내지 않은 `queued`와 `running`은 `interrupted`다. 보낸 뒤 결과 후보가 없는 `running`과 `cancel_requested`는 `remote_completion_unknown`이다. 결과 후보가 있는 `validating`은 다시 호출하지 않고 검증과 적용을 재개한다(계약 규칙 5). 적용 대상 ETag가 기록된 행은 현재 덱 ETag와 비교해, 같으면 적용 완료로, 기준 ETag와 같으면 적용 전으로 판정한다. 둘 다 아니면 이전 입력 기준 후보로 남긴다(D2a-1의 pending 판정과 같은 방식).
- 원장을 열 수 없을 때(파일 손상, 더 새 형식, 권한): 서비스는 시작하고 편집, 저장, 내보내기를 허용한다. 생성 등록만 503과 `code: "job_ledger_unavailable"`로 막는다. 원장 파일은 지우거나 덮어쓰지 않는다.
- 웹 모드와 독립 앱이 같은 원장을 쓴다. 0.2.0은 원장을 모른다.
- RED: 그림에 없는 전이의 거절. 같은 요청 ID 두 번 등록이 같은 작업을 돌려줌. 재시작 조정의 네 경우(미전송, 전송 뒤 후보 없음, 후보 있음, 적용 대상 ETag 기록 뒤 끊김의 세 판정). 손상된 원장 파일로 시작해도 덱 저장은 되고 생성 등록만 503. `user_version`이 더 크면 열지 않고 파일 불변.
- 고정: 원장 파일이 루트에 있어도 프로젝트 목록이 같다(현재 앱과 0.2.0 왕복 시험 `test_legacy_compat.py`에 원장 파일을 더한다).

### D2b-2 실행기와 작업 API

- 실행기: 앱 이벤트 루프 안의 단일 실행기다. 지금 임대가 프로세스 전체에서 생성 하나만 허용하므로(사실 2), 실행기는 대기열에서 한 번에 한 작업만 꺼낸다. 같은 프로젝트에는 미종결 작업을 하나만 둔다. 둘째 등록은 요청 ID가 같으면 기존 작업을 돌려주고, 다르면 409와 `code: "project_job_active"`로 거절한다(계약 규칙 1, 2). 다른 프로젝트의 작업은 대기열에서 기다린다.
- 임대와 관문(계약의 "임대와 관문"): 동의 헤더는 등록할 때 검사하고 그 사실을 행에 남긴다. 계정별 영속 동의가 없으므로(D4) 실행 직전에 다시 검사할 동의 기록이 없다. 실행 직전에는 임대를 잡으면서 선택 식별자, 로그인, 모델 목록을 다시 검사한다(지금의 `generation()` 그대로). 선택 식별자가 등록 때와 다르면 작업을 `failed`(`code: "selection_changed"`)로 끝내고 새 선택으로 조용히 다시 묶지 않는다(계약 규칙 3). 임대는 작업이 `running`에 들어갈 때 잡고 종결 상태에서 놓는다.
- 입력 고정: 등록 요청의 `If-Match`(있으면)와 매개변수를 행에 쓴다. 실행을 시작하면 임대를 잡은 직후 덱 ETag와 자료 fingerprint를 읽어 고정한다. 등록 때 `If-Match`를 받은 종류는 시작 시점의 ETag가 다르면 호출하지 않고 `failed`(`code: "base_changed"`)로 끝낸다.
- 사용량과 성공 기록: `_append_usage`는 호출마다 지금처럼 쓴다. `_record_success`는 완료 시점의 선택이 아니라 작업에 고정한 제공자와 모델로 기록한다.
- 취소: `POST .../jobs/{id}/cancel`은 상태를 `cancel_requested`로 바꾸고 실행 중인 코루틴을 취소한다. 제공자가 실제로 끝날 때까지 `cancelled`로 바꾸지 않는다(계약 규칙 7). 취소 요청 뒤 결과가 도착하면 후보를 저장하되 적용하지 않고 `cancelled`로 끝낸다. 형식 재시도 1회 상한과 도식 거절은 실행기 안에서 지금과 같은 서비스 코드를 거친다.
- 종료 처리: `lifespan` 종료 때 자기 인스턴스의 미종결 작업에 재시작 조정과 같은 함수를 적용한다. 강제 종료에서는 이 처리가 돌지 않으므로 재시작 조정이 정본이고, 종료 처리는 같은 결과를 일찍 남기는 보조다.
- 라우트(모두 `/api/projects/{name}/jobs` 아래): `POST`(등록, 본문 `{request_id, kind, params}`, 새 작업 202, 병합 200), `GET`(최근 작업 목록, 미종결 우선), `GET /{job_id}`(상태, 장별 결과, 후보, `stale` 판정), `POST /{job_id}/cancel`. 화면은 1초 간격으로 조회한다. 조회는 브리지 동시 요청 상한(128) 안에서 한 요청만 쓴다.
- 래퍼(2.2 A): 구조안 라우트를 첫 래퍼로 바꾼다. 래퍼는 작업을 등록하고 끝날 때까지 기다린 뒤 지금과 같은 응답 모델을 돌려준다. 클라이언트 연결이 끊겨도 작업은 계속된다.
- RED: 같은 프로젝트의 둘째 등록 409와 요청 ID 병합. 다른 프로젝트 작업의 대기와 순서. 선택 변경 뒤 대기 작업의 `selection_changed`(재바인딩 0회). 로그인 만료(필수 RED 4: 계정 만료)에서 호출 0회와 `failed`. 취소 응답 지연(필수 RED 3): 관문 제공자가 취소를 무시하고 늦게 응답하면 그동안 `cancel_requested`이고, 끝에 `cancelled`이며 후보는 적용되지 않는다. `_record_success`가 고정 모델로 기록됨. 래퍼 연결 끊김 뒤에도 작업이 끝까지 가고 후보가 남음.
- 고정: 구조안 라우트의 기존 시험 전부(동의 428, 도식 거절, 형식 재시도, 사용량 기록).

### D2b-3 후보형 생성 6종의 이전

- 후보형은 결과를 서버가 덱에 적용하지 않고 후보로 돌려주는 종류다: 구조안, 장 재생성, 축약, 도식, 구성 재작성, 구성 수리. 6개 라우트를 모두 래퍼로 바꾼다. 각 종류의 생성 전후 검사(사실 4)는 실행기의 "시작 시 고정"과 "결과 저장 뒤 `stale` 판정"으로 옮기고, 라우트 안의 중복 검사는 지운다.
- `stale` 판정: 작업 조회 응답은 결과 후보와 함께 "고정한 ETag와 자료 fingerprint가 지금도 같은가"를 돌려준다. 다르면 `stale: true`다. 기존 적용 라우트(`story-plan/rewrite/apply`, 도식 적용)는 지금처럼 서버에서 다시 비교한다. 장 재생성과 축약은 사용자가 "적용"을 누를 때 화면이 `stale`을 확인한다(D2b-5).
- 구성 수리는 연결 끊김 감시(`watch_disconnect`)를 지운다(2.2의 동작 변경). 수리의 `unchanged` 콜백은 고정 입력 비교로 대체한다.
- RED: 자료 수정과 결과 도착의 경합(필수 RED 5): 관문 제공자가 응답하기 전에 자료를 바꾸면 후보는 남고 `stale: true`이며 덱은 그대로다. 늦은 성공 응답(필수 RED 6, 후보형 쪽): 응답 전에 덱을 저장하면 후보가 `stale: true`이고 재작성 적용 라우트가 409로 거절한다. 수리의 연결 끊김 뒤 후보 보존.
- 고정: 6개 라우트의 기존 시험 전부. 백엔드 생성 시험 16개 파일이 수정 없이 통과해야 한다. 수정이 필요하면 그 시험이 바뀐 계약(예: 수리 연결 끊김)을 겨냥한 것인지 커밋에 적는다.

D2b-3이 끝나면 D2b-α 묶음 리뷰를 받는다.

### D2b-4 장 생성 묶음 작업

- 종류 `chapters`: 매개변수는 생성할 장 ID 목록이다. 화면이 승인 반영 `PUT`을 끝낸 뒤 그 응답 ETag를 `If-Match`로 주어 등록한다.
- 장마다 순서: ① 하위 행을 `running`으로 바꾸고 원격 호출 시각을 남긴다 ② 결과를 하위 행 후보로 저장한다 ③ 덱 잠금 안에서 현재 ETag가 사슬의 기대값과 같은지, 자료 fingerprint가 고정값과 같은지, 그 장이 아직 구조안에 같은 템플릿으로 있고 슬라이드가 없는지 확인한다 ④ 저장할 덱의 ETag를 계산해 적용 대상 ETag로 기록한다 ⑤ 덱을 저장한다(스냅샷 없음, 지금 루프와 같다) ⑥ 적용 결과 ETag를 기록하고 하위 행을 `succeeded`로 바꾼다. ③에서 어긋나면 그 장의 후보를 이전 입력 기준 후보로 남기고 남은 장은 `interrupted`로 끝낸다(계약 규칙 8). 형식 오류인 장은 `failed`로 표시하고 다음 장으로 간다(지금 루프와 같다, 계약 규칙 6).
- 저장 중 종료(필수 RED 1)는 ④와 ⑤, ⑤와 ⑥ 사이에 예외를 주입해 재시작 조정이 적용 여부를 바르게 판정하는지 본다.
- 강제 종료 직전 완료(필수 RED 2)는 ②와 ③ 사이에 끊은 뒤 재시작 조정을 돌려, 제공자 호출 0회로 그 장이 적용되거나 이전 입력 기준 후보로 남는지 본다. ①과 ② 사이에 끊으면 그 장은 `remote_completion_unknown`이고 호출 0회다.
- 늦은 성공 응답(필수 RED 6, 묶음 쪽): 관문 제공자가 응답하기 전에 다른 저장이 덱을 바꾸면 그 장은 적용되지 않고 덱은 다른 저장의 내용 그대로다.
- 고정: 지금 승인 루프의 결과와 같은 덱(슬라이드 순서, 공통 슬롯 빈 값, 미검증 숫자 합집합), 도식 장 거절.

### D2b-5 화면 연결

- 공통 조회 훅: 작업 등록, 1초 조회, 종결 시 중단, 화면을 다시 열면 그 프로젝트의 미종결 작업을 찾아 조회를 이어 간다.
- 구조안 승인 루프는 `chapters` 작업 하나로 바꾼다. 장별 진행 표시는 원장의 하위 행에서 읽는다. 새로고침이나 재시작 뒤 구조안 탭을 열면 "6장 중 1장 실패"와 실패한 장만 다시 생성하는 버튼이 보인다. 생성 중 잠금(사실 7)은 원장의 미종결 작업 여부로 판단한다.
- 장 재생성, 축약, 도식, 재작성, 수리, 구조안은 작업 API로 옮긴다. 후보가 `stale`이면 자동 적용하지 않고 "이전 입력 기준 후보" 표시와 "후보 보기 / 현재 입력으로 다시 생성"을 보인다.
- 상태 표시: D2a-5의 `running` 속성과 진행 모델의 `jobs`를 원장에 연결한다. "취소 요청됨"과 "완료 여부 확인 필요"는 새 상태 값으로 상태 표시 컴포넌트에 더한다. 문구는 제품 설계 4절의 상태 규칙을 따른다.
- 복구 화면: D2a-2의 미저장본 목록에 이전 입력 기준 후보를 같은 목록으로 보인다(계약 "보존과의 관계").
- RED: 조회 중 화면 재마운트 뒤 같은 작업을 이어 조회. 재시작 뒤 열린 화면의 "6장 중 1장 실패" 표시. `stale` 후보의 자동 적용 거절. 취소 요청됨과 완료 여부 확인 필요 표시.
- 고정: 동의 거절 시 요청을 보내지 않음(`AiConsentDeclined`), 412 뒤 미저장본 보존(D2a-2), 창 닫기 경고.

### D2b-6 재시작 관통과 패키지 확인

- 실제 프로세스 관통: 시험이 별도 프로세스로 서비스를 띄우고(가짜 CLI 제공자, 시험용 자료 폴더), 장 생성 묶음을 등록한 뒤 관문에서 멈춘 상태로 `SIGKILL`한다. 같은 폴더로 서비스를 다시 띄워 원장, 덱, 제공자 호출 횟수를 확인한다. Windows는 `TerminateProcess` 경로를 CI에서 확인한다.
- Claude 취소 확인(가정 1): `SubscriptionProvider`의 `cli_path`를 오래 자는 가짜 CLI로 바꿔 작업을 취소하고, 가짜 CLI 프로세스가 남는지 확인한다. 남으면 취소 시 하위 프로세스를 끝내는 처리를 더한다.
- 패키지 확인: macOS 패키지 앱에서 `sqlite3` 모듈이 포함되어 원장이 열리는지, `SLIDECAPTAIN_DATA_DIR`를 별도 폴더로 지정해 확인한다. Windows 패키지는 회사 PC 확인 대상으로 남긴다.
- 화면 확인: 헤드리스 Chromium으로 구조안 승인, 새로고침 뒤 진행 복원, 취소, 이전 입력 기준 후보 표시를 확인하고 `docs/qa/`에 기록한다. 사람의 시각 판정이 아님을 적는다.

## 6. 가정과 미확인

1. Claude SDK의 `query` 생성기가 닫힐 때 Claude Code 하위 프로세스가 끝나는지 확인하지 않았다(사실 8). D2b-6에서 가짜 CLI로 확인하고, 그 전까지 Claude 작업의 취소는 "요청을 보냈다"까지만 표시한다.
2. 제공자는 멱등 호출을 지원하지 않는다. 원격 실행을 정확히 한 번이라고 보증하지 않는다(기술 설계 6절). 요청 ID 병합은 이 앱 안의 중복 클릭만 막는다.
3. 잠금이 `unsupported`인 파일 시스템에서 두 서비스가 같은 폴더를 쓰면, 재시작 조정이 살아 있는 다른 서비스의 작업을 중단으로 바꿀 수 있다. D2a-3이 이미 이 실행을 경고하므로 추가 장치는 두지 않는다.
4. 원장 행 하나의 크기는 결과 후보 JSON이 정한다. 보존 기간과 정리 기준은 숫자를 감으로 정하지 않고, D2b-6 관통에서 행 크기와 작업 수를 실측한 뒤 정한다. 그때까지 원장은 지우지 않는다.
5. 동기화 폴더(iCloud, OneDrive) 위의 SQLite는 WAL이 아니어도 동기화 도중 파일이 바뀔 위험이 남는다. 자료 폴더를 동기화 폴더에 두지 말라는 안내는 D6의 자료 폴더 화면이 맡는다.

## 7. 수용 기준 (D2b)

- 필수 RED 6종(저장 중 종료, 강제 종료 직전 완료, 취소 응답 지연, 계정 만료, 자료 수정과 결과 도착의 경합, 늦은 성공 응답)이 수정 전 코드에서 실패하고 수정 뒤 통과한다. 각 시험의 위치를 결과 절에 적는다.
- 실제 프로세스 관통(D2b-6)에서 재시작 뒤 제공자 호출 0회, 적용된 장과 실패한 장과 완료 여부 불명 장의 구분이 원장과 덱에서 일치한다.
- 백엔드 전체, 화면 전체, desktop, 토큰 검사, 화면 빌드, OpenAPI와 타입과 브리지 경로 일치, 0.2.0 왕복 시험, 공개 저장소 감사가 통과하고, Windows와 macOS CI가 성공한다.
- 실제 AI 호출 0회. 사용자의 실제 자료 폴더에서 새 앱을 실행하지 않는다.
- 이 기준을 모두 충족하면 D2a 결과와 합쳐 D2 관문을 통과로 기록한다. Windows 실기기의 독립 앱 확인은 D2a처럼 별도 남은 확인으로 적는다.

## 상위 문서와 다르게 정하는 것

1. 기술 설계 6절은 "계정/모델/Effort/동의 리비전"을 실행 시 고정한다고 적는다. 이 단위는 제공자, 모델, 선택 식별자만 고정하고 계정 프로필, Effort, 동의 리비전은 빈 열로 둔다. 그 값의 원천이 D4에서 생기기 때문이다(D2 계획 6절과 같다).
2. D2 계획 6절은 "대기 작업은 실행 직전에 임대, 선택, 동의를 다시 검사한다"고 적는다. 동의는 등록 시점에만 검사한다. 지금 동의는 요청 헤더일 뿐 저장된 기록이 없어 실행 직전에 다시 검사할 대상이 없다. D4가 영속 동의를 만들면 실행 직전 검사로 옮긴다.
3. 제품 설계 7절의 "생성 중 화면 이동과 편집 허용"은 이 단위에서 하지 않는다. 생성 중 잠금(사실 7)을 유지하고, 묶음 작업의 ETag 사슬은 엄격하게 비교한다(2.1). D3가 관련 입력 단위로 완화한다.
4. D2 계획 「상위 문서와 다르게 정하는 것」 3항이 D2b로 넘긴 "저장 중 이탈 시 로컬 임시본"은 구현하지 않고 방치 확정으로 올린다(2.4).
5. 기존 구성 수리 라우트의 "연결이 끊기면 취소" 동작을 없앤다(2.2). 계약의 "브리지 요청 취소와 작업 취소의 분리"를 따른다.
