## 1. 범위

D3 관문 기준 가운데 이 묶음이 맡는 것은 ③ 직접 요소 편집, 저장, PPTX 일치다(D3 계획 1절). 요구는 R16이다. D3 관문은 이 묶음이 끝나야 통과하며, 관문 판정 자료는 D3c-8이 모은다.

| 묶음 | 내용 | 끝나면 관측되는 것 |
|---|---|---|
| α 직접 수정 | 직접 수정의 저장 계약과 형식 등급, 레이아웃 엔진의 수정값 적용(미리보기와 PPTX가 같은 값), 편집 화면의 직접 수정 모드(이동, 글자 크기, 색, 숨기기, 되돌리기 단위, 키보드 조작) | 일반 페이지의 요소를 옮기고 꾸민 뒤 저장, 새로고침, PPTX에서 같은 값. 기존 덱의 바이트, ETag, 지문 불변 |
| β 재생성 보존 | 장 후보를 서버가 현재 덱에 적용하는 경로(C9), 재생성 후보와 현재본의 비교와 고른 범위 반영, 구조안 재승인의 수정 삭제 확인, 미저장본 복원 전 차이 요약(C22), 동기 생성 래퍼 6개 제거와 시험 이전(C8), 화면 확인과 D3 관문 자료 | AI 재생성이 사용자 수정을 조용히 덮지 않음. 래퍼 경로 0개 |

α가 끝나면 랩업 보고 뒤 사용자와 상의하고 β로 넘어간다(단계 경계 규칙).

하지 않는 것:

- 도식 페이지의 직접 수정(사용자 결정 Q3). 도식은 지금의 도식 작성 창으로 고친다.
- 요소 크기 조절. R16의 완료 기준과 제품 설계 5절 E에 크기를 바꾸는 조작이 없고, 크기를 바꾸면 표, 카드, 단계 행의 줄바꿈과 행 높이를 다시 계산해야 한다. 구현 설계 10절의 "논리 좌표와 크기" 가운데 크기는 저장 계약에 칸을 두지 않는다. 확정 커밋에서 구현 설계 10절에 정정을 적는다.
- 장 단위 저장과 묶음 사슬의 관련 입력 단위 완화(사용자 결정 Q2). 장 생성 묶음 중 같은 프로젝트의 덱 편집은 지금처럼 읽기 전용이다.
- 실제 AI 생성 품질의 확인(별도 사용자 승인과 호출 예산 없이 하지 않는다). 실제 PowerPoint 표시 대조와 한글 입력기(IME) 조합 입력은 회사 PC와 사람 확인이다.

## 3. 지금 코드에서 확인한 사실 (기준 `88a6572`)

1. 덱의 슬라이드에는 템플릿 유형과 슬롯 내용만 있고 좌표와 글자 크기는 없다(`models/deck.py` 머리 설명). 본문 장의 제목은 구조안의 `chapter.topic`, 표지의 보고자는 `meta.presenter`에서 그린다. `Slide`는 `chart`와 `text_spans`가 비면 직렬화에서 뺀다. 기본값 필드를 그냥 더하면 기존 모든 덱의 ETag와 지문이 바뀐다(D3b 사실 7).
2. 레이아웃 엔진(`layout/engine.py`의 `build_render_plan`)은 장마다 `build_slide`로 프레임 목록을 만들고, 비교 차트가 있으면 표 프레임을 차트와 조건 문구 프레임으로 바꾸고, 부분 강조(`apply_text_spans`)를 적용한다. 프레임 이름은 `장ID:슬롯`이다(예: `title`, `bullets`, `conclusion`, `card_2`, `card_2_badge`, `step_3_labels`, `row_1_category`, `page_number`). 목록 슬롯(불릿, 카드의 불릿)은 프레임 하나의 여러 문단이다. 프레임 이름이 한 슬라이드 안에서 유일하다는 시험은 없다.
3. 미리보기와 PPTX는 같은 렌더 계획(`models/render.py`)을 읽는다. PPTX 라이터는 `Frame`의 x, y, w, h, fill, border, radius, valign, table, chart와 `Para`의 font_pt, color, bold, align, bullet, runs를 읽고 도형 이름에 프레임 이름을 쓴다. 채움이나 테두리가 없는 고정 글상자는 줄바꿈을 끄고 엔진이 끊은 `lines`를 한 줄씩 쓴다. 따라서 글자 크기를 바꾸면 엔진 안에서 줄바꿈부터 다시 계산해야 미리보기와 PPTX가 같다.
4. 부분 강조 적용은 이미 "프레임 폭에서 안쪽 여백(채움이나 테두리가 있을 때)과 불릿 들여쓰기를 뺀 폭으로 다시 줄바꿈하고, 필요한 높이가 프레임 높이를 넘으면 경고를 더하는" 계산을 한다(`layout/expression.py`). 템플릿 빌더가 처음 줄바꿈에 쓴 폭이 이 식과 모든 템플릿에서 같은지는 확인하지 않았다(가정 1).
5. 미리보기는 서버가 계산한다. 편집 화면은 덱이 바뀌면 300ms 뒤 `POST /api/projects/{name}/render-plan`을 부르고, 새 계획이 오기 전에는 낡은 계획으로 편집을 열지 않는다(`planStale`, 2026-09-03 FC-05). 화면 배율은 미리보기 폭을 페이지 폭(pt)으로 나눈 값이다.
6. 편집 화면은 프레임을 눌러 고르고, 고른 프레임을 다시 누르면 그 자리에서 문구를 고친다. 문구 수정은 `applyTextEdit`가 슬롯 칸으로 옮긴다(제목은 `chapter.topic`, 아이브로우와 부제는 슬라이드, 보고자는 메타). 미리보기의 프레임은 키보드 초점을 받지 않는다(`tabIndex`, `role` 없음).
7. 되돌리기는 덱 전체의 과거, 현재, 미래 목록이고 100개까지 남긴다(`state/deckStore.ts`). 편집 한 번이 한 항목이다. 문구 입력 중에는 브라우저의 텍스트 되돌리기가 동작하도록 덱 되돌리기가 끼어들지 않는다. 자동 저장은 1,200ms 뒤이고, 412 뒤에는 자동 저장을 멈추며, 단계 이동과 언마운트 때 남은 편집을 저장한다. 장 생성 묶음 중에는 읽기 전용이다.
8. 지문과 슬라이드 내용의 관계:

   | 지문 | 슬라이드 내용이 들어가는가 | 수정값이 들어가면 생기는 일 |
   |---|---|---|
   | 내보내기 입력 지문(`pipeline/quality.py`, `output_dump`, 프리셋, 렌더 계획) | 들어간다 | 그 뒤 내보낸 파일의 검토 기록은 낡음이 된다. 구현 설계 10절의 "출력 fingerprint 무효화"가 따로 일하지 않아도 성립한다 |
   | 수치 검토, 의미 검토 지문(`output_dump`) | 들어간다 | 두 검토는 저장된 결과가 아니라 매번 다시 계산하므로 사용자가 다시 할 일은 생기지 않는다 |
   | 구성 계획 지문(`story_fingerprint`) | 들어가지 않는다(장 정의와 메타 세 칸) | 수정값으로 계획이 낡지 않는다. 제목 문구 수정은 지금처럼 장 정의를 바꾼다(D3a C15 판단 유지) |
   | 장 후보 관련 입력(`c1:템플릿|장 정의|계획과 보고 정보`) | 들어가지 않는다 | 수정값으로 장 후보가 낡지 않는다 |
   | 구조안 후보 반영 기준(`s1:` 해시의 (나)) | 들어간다 | 처분하지 않은 구조안 후보가 있을 때 요소를 옮기면 그 후보는 낡는다. 승인이 슬라이드를 덮으므로 의도한 동작이다 |

9. 형식 판정: 덱 내용 등급은 1~3이고 등급 3이면 `schema_version` 2로 쓴다. 이 앱이 읽는 manifest 최대 형식은 3이다(`MAX_SUPPORTED_FORMAT`). 덱 JSON 스키마는 `test_project_format`의 해시 시험이 고정하고, 그 설명은 스키마를 바꾸는 태스크가 형식 판정을 함께 정하라고 적는다. 0.2.0과 D3a, D3b 빌드의 `Slide`는 모르는 필드를 읽을 때 버리고 저장할 때 지운다.
10. 기존 장 내용을 바꾸는 경로와 지금 동작:

    | 경로 | 지금 동작 |
    |---|---|
    | 편집 화면의 장 생성과 장 축약(`GeneratePanel`) | 후보 작업을 만들고, 반영 직전에 작업을 다시 조회한 뒤 화면이 덱의 그 장 슬롯을 통째로 바꿔 PUT(스냅샷)하고 처분 `applied`를 따로 기록한다. 서버는 처분을 강제하지 않는다. 아이브로우와 부제는 남긴다 |
    | 장 생성 묶음(`_apply_chapter`) | 장에 슬라이드가 없고 사슬 ETag가 같을 때만 쓴다. 아니면 결과를 낡은 후보로 남긴다. 구성 화면은 낡은 후보에 "후보 보기"(원문 텍스트)와 "현재 입력으로 다시 생성"만 둔다 |
    | 구성 화면의 재승인 | 장 정의가 바뀐 장의 슬라이드를 지우고(`kept`) 스냅샷과 함께 PUT한 뒤 묶음을 등록한다 |
    | 재작성 반영(`story-plan/rewrite/apply`) | 기존 슬라이드를 보존한다(`preserved_chapter_ids`) |
    | 문서 변경 반영(`document-changes`) | 사용자가 현재 덱에서 만든 덱 후보를 장별로 비교해 확인한 뒤 반영한다 |
    | 템플릿 전환(`applyTemplateSwitch`) | 화면이 슬롯을 다른 템플릿으로 옮긴다. 프레임 이름의 뜻이 바뀐다 |
    | 도식 작성 창의 교체 | 도식 페이지만 바꾼다(이 묶음의 대상 아님) |

11. 동기 생성 래퍼는 6개다(구조안, 장 생성, 장 축약, 도식 생성, 재작성, 구조 수리, `server/app.py`의 `_run_wrapped`). 화면은 더 이상 부르지 않는다(`api/client.ts`에 호출 없음, 생성 타입에만 남음). 백엔드 시험의 참조는 2026-10-13 실측으로 104곳이다(구조안 45곳 15개 파일, 장 생성 34곳 10개, 장 축약 16곳 8개, 재작성 6곳 3개, 구조 수리 2곳 2개, 도식 1곳 1개, 파일은 겹친다). D3 계획의 "약 70곳"은 이 실측으로 바꾼다.
12. 미리보기의 표 경계선은 화면 전용 상수(`#D0D7E2`, `editor/Preview.tsx`)이고 렌더 계획에 표 경계색이 없다. PPTX 라이터는 표 칸의 채움과 여백만 쓰고 경계선은 python-pptx 기본 표 스타일에 맡긴다.

## 4. 설계

### 4.1 사용자 결정 (2026-10-13)

| 번호 | 질문 | 결정 | 결과 |
|---|---|---|---|
| Q1 | 직접 수정값을 0.2.0이 지우는 위험 | A: 새 형식으로 막는다 | 직접 수정이 있는 덱은 새 등급으로 쓰고 0.2.0과 이전 개정판 빌드는 열지 못한다(4.2) |
| Q2 | 장 단위 저장으로 묶음 중 편집을 허용할지 | A: 지금처럼 읽기 전용 | E3, E4를 하지 않는다 |
| Q3 | 도식 페이지의 직접 수정 | A: 일반 페이지만 | 도식 슬라이드에는 수정값을 두지 않는다 |
| Q4 | 진행 방식과 계획 리뷰 | A: α와 β 두 묶음, 계획 리뷰 3관점 3명과 바뀐 절 재리뷰 1명 | 7절 |

### 4.2 저장 계약과 형식 (D3c-1)

`Slide`에 `direct_edits`를 더한다. 비어 있으면 직렬화에서 빼고 스키마에서 기본값 표기를 뺀다(D3b-1의 `_omittable`과 같은 이유). 그래서 수정값이 없는 기존 덱의 바이트, ETag, 모든 지문이 그대로다.

| 칸 | 뜻 |
|---|---|
| `elements` | 요소별 수정. 열쇠는 프레임 이름에서 장 ID를 뺀 부분(예: `title`, `card_2`)이다. 값은 아래 `ElementEdit` |
| `text_paths` | 사용자가 직접 고친 슬롯 문구의 위치. 슬롯 덤프 안의 JSON Pointer(예: `/bullets/2/text`, `/conclusion`)다. 재생성 비교가 "내가 고친 문구"를 고르는 데 쓴다(4.6) |

`ElementEdit`의 칸은 모두 선택이고 빈 객체는 받지 않는다.

| 칸 | 값 | 출처 |
|---|---|---|
| `x_pt`, `y_pt` | 슬라이드 왼쪽 위 기준의 절대 좌표(pt, 렌더 계획과 같은 단위). 둘은 함께 있거나 함께 없다 | 구현 설계 10절의 논리 좌표 |
| `font_pt` | 그 요소에서 가장 큰 문단의 글자 크기. 1~4,000 | PowerPoint가 받는 글자 크기 범위(OOXML `sz`는 1/100pt 단위로 100~400,000) |
| `text_color` | 프리셋 색 역할 이름(강조 밴드의 `tone`과 같은 목록) | 프리셋이 바뀌면 색이 따라 바뀌게 하는 기존 원칙(`CalloutSlots` 설명) |
| `fill` | 채움이 있는 요소의 채움 색 역할 이름 | 같음 |
| `hidden` | 참이면 출력에서 뺀다(삭제) | 제품 설계 5절 E |

규칙:

- 삭제는 슬롯 내용을 지우지 않고 `hidden`으로 표시한다. 필수 슬롯(예: 요약의 결론)을 지우면 덱 검증이 실패하고, 제품 설계의 "삭제 요소를 자동으로 다시 채우지 않는다"는 원문이 남아 있어야 지킬 수 있기 때문이다. 숨긴 요소의 문구는 데이터에 남으므로 수치 검토와 의미 검토는 그 문구를 계속 읽는다. 검토 화면의 확인할 항목에 숨긴 요소를 장별로 보인다(4.5).
- 도식 슬라이드에는 `direct_edits`를 받지 않는다(Q3, 검증 오류).
- 검증은 `text_paths` 가운데 지금 슬롯에서 풀리지 않는 위치를 버린다(`report_details`의 빈 칸 버림과 같은 정규화). `elements`의 열쇠는 형식만 검사한다. 지금 렌더에 없는 요소의 열쇠는 렌더 때 무시하고 데이터에는 남긴다(빈 아이브로우를 다시 채우면 그 요소의 수정이 돌아온다).
- 템플릿 전환은 그 장의 `direct_edits`를 비운다(4.4).

형식:

- 어느 슬라이드에든 `direct_edits`가 있으면 덱 내용 등급 4, `schema_version` 3으로 쓴다. `MAX_SUPPORTED_FORMAT`과 `SUPPORTED_SCHEMA_VERSIONS`를 4와 3까지로 올린다. 등급 3을 다시 쓰지 않는 이유는 D3b 빌드가 등급 3 덱을 열어 저장하면 수정값을 지우기 때문이다. 등급 4이면 D3b 빌드는 manifest를 보고 "더 새 형식"으로 거절한다(D3b가 D3a 빌드에 쓴 방식).
- 0.2.0은 `schema_version` 3을 거절하므로 "복구 필요"로 보인다(D3b와 같음). D3b의 0.2.0 되돌림 표시 조건 "manifest 번호가 3이고 디스크 원문 등급이 그보다 낮음"을 "manifest 번호가 3 이상이고 디스크 원문 등급이 그보다 낮음"으로 넓힌다.
- 등급 전이(3 이하에서 4, 4에서 3 이하)는 기존 형식 기록과 강제 스냅샷 규칙을 그대로 쓴다. 수정을 모두 되돌려 `direct_edits`가 사라지면 등급이 내려간다.
- E8: 프로젝트를 열 때 0.2.0 되돌림 표시가 붙은 스냅샷이 있으면 머리에 "다른 앱이 이 프로젝트를 이전 내용으로 되돌렸습니다. 복구 화면에서 되돌리기 전 내용을 볼 수 있습니다." 안내와 복구 화면 연결을 띄운다. 복구 화면의 표시 이름은 "다른 앱에서 되돌리기 전"으로 바꾼다(0.2.0만이 아니다).
- 릴리스 안내에 "직접 수정한 프로젝트는 0.2.0과 이전 개정판에서 열 수 없다"를 더한다.

### 4.3 렌더 적용과 PPTX (D3c-2)

수정값은 렌더 계획을 만든 뒤에 덧칠하지 않고 엔진 안에서 줄바꿈과 경고보다 먼저 적용한다. 렌더 계획 위에 덧칠하면 `lines`와 경고가 수정 전 상자를 설명하게 되어 미리보기와 PPTX가 다시 어긋난다(세로 정렬 사고와 같은 계열, `models/render.py` 설명).

순서: `build_slide` → 비교 차트 치환 → 직접 수정 적용 → 부분 강조 적용. 부분 강조는 바뀐 글자 크기로 다시 끊는다.

| 수정 | 적용 |
|---|---|
| 숨기기 | 그 프레임과 그 프레임의 용량 경고를 뺀다 |
| 위치 | x, y를 바꾼다. 페이지 안으로 자른다(0 ≤ x ≤ 페이지 폭 - w, y도 같다). 프리셋이 바뀌어 페이지가 작아져도 이 규칙으로 페이지 안에 남는다 |
| 글자 크기 | 비율 = 새 크기 / 그 프레임에서 가장 큰 문단의 크기. 모든 문단에 같은 비율을 곱하고 1/100pt로 반올림한다(OOXML의 저장 단위). 문단마다 사실 4의 폭 식으로 다시 줄바꿈하고, 필요한 높이가 프레임 안쪽 높이를 넘으면 그 슬롯의 용량 경고를 더한다. 경고는 기존 "분량" 확인 항목에 보인다 |
| 글자 색 | 모든 문단의 색을 그 역할의 색으로 바꾼다. 부분 강조의 강조색 run은 그대로 둔다 |
| 채움 색 | 채움이 있는 프레임만 바꾼다. 글자 색 수정이 없으면 글자 색을 기존 휘도 함수(`readable_text_color`)로 다시 정한다 |

- 표 프레임과 차트 프레임은 위치와 숨기기만 받는다. 글자 크기를 바꾸면 열 폭과 행 높이를 다시 계산해야 하기 때문이다. 화면은 이 두 종류에서 글자 크기와 색 칸을 보이지 않는다. 엔진은 받은 값을 무시한다(검증 오류로 만들지 않는 이유: 템플릿 전환 없이 같은 슬롯이 표에서 차트로 바뀔 수 있다).
- 쪽 번호 프레임은 수정 대상이 아니다.
- 렌더 계획의 직렬화에 새 칸을 더하지 않는다. 더하면 수정값이 없는 덱의 렌더 계획도 바뀌어 기존 내보내기의 검토 기록이 모두 낡는다.
- PPTX 라이터는 바꾸지 않는다. 같은 렌더 계획을 읽으므로 미리보기와 같은 값이 된다. D3c-2는 python-pptx로 PPTX를 다시 읽어 도형의 위치(EMU), 글자 크기, 색, 숨긴 도형의 부재가 렌더 계획과 같은지 시험한다.
- 시험으로 고정할 전제: 한 슬라이드의 프레임 이름은 유일하다(가정 2). 수정값이 없을 때 엔진 결과는 지금과 바이트가 같다. 모든 템플릿에서 같은 글자 크기로 다시 끊은 줄이 처음 줄과 같다(가정 1, 다르면 그 템플릿의 폭 식을 따로 둔다).

### 4.4 편집 화면의 직접 수정 (D3c-3)

배치와 모드:

- 편집 화면에 "직접 수정" 버튼을 둔다. 누르면 "수정 완료"로 바뀌고 직접 수정 모드가 된다. "수정 완료"는 모드 종료이며 저장 완료 표시와 다르다(제품 설계 5절 E). 저장은 지금의 자동 저장이 한다.
- 지금의 프레임 고르기와 그 자리 문구 수정은 모드 밖에서도 그대로 둔다(기존 사용 흐름을 바꾸지 않는다). 모드는 이동, 방향키, Delete, 서식 변경을 연다.
- 장 생성 묶음 중(읽기 전용)과 도식 장에서는 모드를 열지 않는다. 읽기 전용이 되면 모드를 닫는다.

조작:

| 조작 | 동작 | 되돌리기 단위 |
|---|---|---|
| 끌기 | 고른 요소의 본체나 이동 손잡이를 끈다. 누른 곳에서 Windows의 기본 끌기 시작 거리(`SM_CXDRAG`, 4px)를 넘어야 끌기로 본다. 끄는 동안은 화면에서만 옮기고(덱을 바꾸지 않음), 놓을 때 한 번 저장한다. 포인터 이동량을 화면 배율로 나눠 pt로 바꾸고 페이지 안으로 자른다 | 끌기 하나 |
| 방향키 | 1pt, Shift+방향키는 6pt(PowerPoint의 기본 격자 간격 0.083인치) | 누름 하나 |
| 위치 칸 | 속성 패널의 가로, 세로 위치(pt). Enter나 초점 이동 때 반영한다 | 반영 하나 |
| 글자 크기, 글자 색, 채움 색 | 속성 패널. 글자 크기 선택지는 프리셋의 글자 역할 크기와 직접 입력이다 | 반영 하나 |
| 숨기기 | 버튼이나 Delete. 숨긴 요소는 캔버스에 없으므로 속성 패널에 장별 "숨긴 요소" 목록과 "다시 보이기"를 둔다 | 하나 |
| 문구 수정 | 지금과 같다. 고친 위치를 `text_paths`에 더한다 | 지금과 같다 |

- 초점과 선택: 모드에서는 프레임이 키보드 초점을 받는다(그리는 순서대로 Tab). 초점이 옮겨 가면 선택도 옮겨 간다. 각 프레임의 접근 이름은 역할과 문구 앞부분이다(예: "결론 상자, 매출이 늘었다").
- 입력 중 보호: 문구 입력란, 숫자 칸, 선택 상자에 초점이 있으면 Delete, 방향키, 되돌리기를 캔버스가 가로채지 않는다(지금의 문구 입력 규칙을 넓힌다).
- 끌기의 끝: 놓으면 반영한다. Escape, `pointercancel`, 포인터 잡기 해제는 취소하고 원래 자리로 돌린다. 끄는 중에 장이 바뀌거나 모드가 닫히거나 읽기 전용이 되면 취소한다. 놓은 뒤 새 렌더 계획이 오기 전에는 놓은 자리에 그린 채 다음 끌기를 막는다(사실 5의 낡은 계획 규칙).
- 템플릿 전환은 그 장의 `direct_edits`를 비우고 "이 장의 직접 수정 n건을 지웠습니다. 되돌리기로 되찾을 수 있습니다."를 알린다. 전환과 비우기는 되돌리기 하나다.
- E6: 미리보기의 표 경계선을 PPTX가 실제로 그리는 경계와 맞춘다. 먼저 python-pptx 기본 표 스타일이 PowerPoint와 LibreOffice에서 그리는 경계를 확인하고, 렌더 계획 직렬화를 바꾸지 않는 범위에서 맞춘다. 맞출 수 없으면 차이를 기록한다.

### 4.5 검토와의 관계 (D3c-2, D3c-3)

- 수정값은 내보내기 입력 지문을 바꾸므로 그 뒤 내보낸 파일의 검토 기록은 자동으로 낡음이 된다(사실 8). 이 동작을 시험으로 고정한다(위치만 옮긴 덱에서 기존 검토 기록이 `stale`).
- 검토 화면의 확인할 항목에 "숨긴 요소" 줄을 더해 장과 요소를 보인다. 자동 판정이 아니라 확인 안내다. 근거 표시(각주 등)를 숨긴 경우를 사용자가 놓치지 않게 하기 위해서다.
- 수치 검토와 의미 검토는 슬롯 문구를 읽으므로 숨긴 요소도 계속 검토한다. 결과 문구에 그 장에 숨긴 요소가 있음을 덧붙인다.

### 4.6 재생성 보존과 후보 적용 (D3c-5, D3c-6)

원칙: AI가 만든 새 내용은 언제나 후보로 먼저 오고, 현재본과 비교한 뒤 사용자가 고른 범위만 반영한다. 위치, 글자 크기, 색, 숨기기 수정은 새 내용에 같은 요소가 있으면 그대로 남는다. 사용자가 직접 고친 문구는 기본으로 남기고, 새 문구를 고를 수 있다.

서버 적용 경로(D3c-5):

- 새 라우트 `POST /api/projects/{name}/jobs/{job_id}/apply`. 본문은 `chapter_id`와 `keep_text_paths`(남길 사용자 문구 위치)이고 `If-Match`에 덱 ETag를 받는다. 대상은 장 생성과 장 축약 작업, 묶음의 장 행이며 처분이 `held`나 `stale`인 결과다.
- 한 프로젝트 잠금 안에서 한다: 덱과 자료를 읽는다 → ETag가 다르면 412 → 장이 있고 템플릿이 같고 관련 입력(`c1:` 해시)과 자료 지문이 후보를 만들 때와 같은지 본다. 덱 ETag의 차이는 막지 않는다(다른 장이나 서식을 고친 것은 후보의 입력이 아니다). 다르면 409와 사유(지금 사유 목록) → 후보 슬롯에 `keep_text_paths`가 가리키는 현재 문구를 옮긴다(두 슬롯 모두에서 풀리는 위치만) → `direct_edits`는 그대로 두고 `text_paths`는 남긴 위치만 남긴다 → 스냅샷과 함께 저장 → 원장에 처분 `applied`. 원장 전이가 실패하면 저장하지 않는다.
- 미리 보기 라우트 `POST .../jobs/{job_id}/apply/preview`는 같은 판정과 합치기를 저장 없이 해서 합친 슬라이드와 "새 내용에 없어 적용되지 않는 수정" 목록을 돌려준다. 합치기 규칙은 서버 한 곳에만 둔다(화면과 서버에 따로 두면 어긋난다).
- 편집 화면의 장 생성과 장 축약 반영은 화면의 덱 PUT 대신 이 라우트를 쓴다. 그래서 장 후보의 처분은 서버가 강제한다(E10). 구조안 승인은 지금처럼 화면이 덱을 PUT한 뒤 처분을 기록한다. 승인은 장 구성 전체와 사용자가 고친 초안을 함께 쓰므로 서버 적용으로 옮기려면 구조안 초안 편집까지 서버 계약에 넣어야 하고, 서버는 승인 처분을 거절하면 후보를 버리게 이미 되어 있기 때문이다(D2b-β 리뷰 R4).
- 묶음의 `_apply_chapter`는 바꾸지 않는다(빈 장에만 쓴다). 이미 내용이 있는 장의 묶음 결과는 지금처럼 낡은 후보로 남고, 사용자는 구성 화면의 비교에서 이 경로로 반영한다.
- E9: 장 생성과 장 축약 등록 검사에 구성 계획의 현재성(`require_current_story`)을 더해 등록 단계에서 409 `stale_story_plan`을 낸다. 지금은 등록(202) 뒤 실행에서 같은 409로 끝나 화면이 실패한 작업을 하나 더 보인다.

비교 화면(D3c-6):

- 편집 화면의 생성 패널과 구성 화면의 "후보 보기"를 같은 비교 화면으로 바꾼다. 왼쪽은 현재본, 오른쪽은 합친 결과의 미리보기(미리 보기 라우트의 슬라이드를 기존 렌더 계획 라우트로 그림)다.
- 아래에 사용자가 직접 고친 문구를 위치별로 보이고(`text_paths`), 칸마다 "내 문구 유지"(기본)와 "새 문구 사용"을 고른다. 새 내용에 없어 적용되지 않는 요소 수정은 목록으로 알린다.
- 판정이 막으면(관련 입력이나 자료가 바뀜) 비교는 보이되 반영을 막고 "현재 입력으로 다시 생성"을 연다(제품 설계 7절).
- 구성 화면의 재승인: 슬라이드를 지울 장 가운데 직접 수정(`direct_edits`)이 있는 장이 있으면 승인 전에 "이 장들의 직접 수정이 지워집니다. 승인 직전 상태는 스냅샷으로 남습니다." 확인을 띄운다.
- E7: 미저장본(보존본) 복원 전에 장별 차이 요약(바뀐 장, 더해진 장, 빠진 장, 직접 수정이 다른 장)을 보인다. 복원은 지금처럼 확인 뒤에 한다.

### 4.7 동기 생성 래퍼 제거 (D3c-7)

- 6개 라우트와 `_run_wrapped`, OpenAPI의 경로, 생성 타입을 지운다. 데스크톱 브리지의 경로 목록에 이 경로가 있으면 함께 지운다.
- 시험 104곳은 작업 API 도우미(등록하고 끝날 때까지 기다린 뒤 결과를 돌려줌)로 옮긴다. 래퍼가 동기로 내던 상태 코드 가운데 등록 검사의 코드(404, 409, 422)는 작업 API 등록이 같은 코드를 내고, 실행 중 실패는 작업 행의 원인 분류로 본다. 옮기기 전에 시험 파일마다 "래퍼 응답 코드 → 작업 API에서 보는 자리" 대응을 표로 만들고, 단언을 약하게 바꾸는 이전이 없는지 그 표로 리뷰한다.
- 래퍼에만 있던 성질(요청 취소가 작업 취소를 부름, 처분 `delivered`)의 시험은 지우고 목록을 남긴다. 원장의 `delivered` 값은 옛 행을 읽어야 하므로 허용값에서 지우지 않는다.
- 이 태스크는 β의 마지막 코드 태스크다(D3 계획 7절). D3c-8은 증거 생산이다.
