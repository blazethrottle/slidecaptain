## 1. 범위

D3 관문 기준 가운데 이 묶음이 맡는 것은 ③ 직접 요소 편집, 저장, PPTX 일치다(D3 계획 1절). 요구는 R16이다. D3 관문은 이 묶음이 끝나야 통과하며, 관문 판정 자료는 D3c-8이 모은다.

| 묶음 | 내용 | 끝나면 관측되는 것 |
|---|---|---|
| α 직접 수정 | 직접 수정의 저장 계약과 형식 등급, 요소 열쇠 함수, 레이아웃 엔진의 수정값 적용(미리보기와 PPTX가 같은 값), 편집 화면의 직접 수정 모드(이동, 글자 크기, 색, 숨기기, 되돌리기 단위, 키보드와 초점), 숨긴 근거 표시의 검토 연결 | 일반 페이지의 요소를 옮기고 꾸민 뒤 저장, 새로고침, PPTX에서 같은 값. 기존 덱의 바이트, ETag, 지문, PPTX 바이트 불변(기본 프리셋, 4.4) |
| β 재생성 보존 | 장 후보를 서버가 현재 덱에 적용하는 경로(C9), 재생성 후보와 현재본의 비교와 칸별 선택, 구조안 재승인의 수정 삭제 확인, 보존본 복원 전 차이 요약(C22), 동기 생성 래퍼 6개 제거와 시험 이전(C8), 화면 확인과 D3 관문 자료 | AI 재생성이 사용자 수정을 비교 없이 덮지 않음. 래퍼 호출 0회 |

α가 끝나면 랩업 보고 뒤 사용자와 상의하고 β로 넘어간다(단계 경계 규칙).

하지 않는 것:

- 도식 페이지의 직접 수정(사용자 결정 Q3). 도식은 지금의 도식 작성 창으로 고친다.
- 요소 크기 조절. R16의 완료 기준과 제품 설계 5절 E에 크기를 바꾸는 조작이 없고, 크기를 바꾸면 표, 카드, 단계 행의 줄바꿈과 행 높이를 다시 계산해야 한다. 그 결과 상자 높이가 그대로라 글자를 키우면 대부분의 요소가 곧바로 분량 경고가 된다(경고 없이 받는 최대 배율이 아이브로우와 부제 1.00, 표지 날짜 1.07, 단계 라벨 1.11, 장 제목 1.43, 재리뷰 RR2 실측). 사용자가 이 제약을 받아들였다(Q5 A, 4.1).
- 사용자가 고친 문구의 위치 기록. 재생성 때 문구 보존은 비교 화면의 단위별 선택과, 원장에 남은 마지막 AI 반영 결과와의 비교 표시가 맡는다(4.1 해석, 4.8).

확정 커밋(2026-10-13)에서 고친 상위 문서: 구현 설계 10절(크기 제외, 거리 좌표, 문구 보존은 비교 화면의 선택과 표시), 제품 설계 5절 E(같은 문구 보존 정정, Enter와 손잡이 규칙), 제품 설계 7절과 구현 설계 6절의 2026-10-10 정정 문단(E3 결과), D3 계획 C8의 수(사실 12).
- 여러 줄 문구 입력. 지금 입력란은 한 칸을 한 문단으로 받는다(사실 6).
- 장 단위 저장과 묶음 사슬의 관련 입력 단위 완화(사용자 결정 Q2). 장 생성 묶음 중 같은 프로젝트의 덱 편집은 지금처럼 읽기 전용이고, 새 적용 라우트도 묶음 중에는 거절한다(4.8).
- 실제 AI 생성 품질의 확인(별도 사용자 승인과 호출 예산 없이 하지 않는다). 실제 PowerPoint 표시 대조, 한글 입력기(IME)의 실제 조합 입력, 터치 끌기, 화면 낭독기는 회사 PC와 사람 확인이다.

## 3. 지금 코드에서 확인한 사실 (기준 `88a6572`)

1. 덱의 슬라이드에는 템플릿 유형과 슬롯 내용만 있고 좌표와 글자 크기는 없다(`models/deck.py` 머리 설명). 본문 장의 제목은 구조안의 `chapter.topic`, 표지의 보고자는 `meta.presenter`에서 그린다. `Slide`는 직렬화 함수(`expression_serialization`) 하나로 `chart`와 `text_spans`가 비면 뺀다. pydantic은 같은 모델의 두 번째 직렬화 함수를 오류 없이 받고 마지막 것만 쓰므로, 함수를 따로 더하면 기존 생략 규칙이 조용히 꺼진다(리뷰 저장 S5 실험). 기본값 필드를 그냥 더하면 기존 모든 덱의 ETag와 지문이 바뀐다(D3b 사실 7).
2. 레이아웃 엔진(`layout/engine.py`의 `build_render_plan`)은 장마다 `build_slide`로 프레임 목록을 만들고, 비교 차트가 있으면 표 프레임을 차트(`chart`)와 조건 문구(`chart_conditions`) 프레임으로 바꾸고, 부분 강조(`apply_text_spans`)를 적용한다. 프레임 이름은 `장ID:슬롯`이고 목록 항목은 0부터 센 순번이다(예: `title`, `bullets`, `conclusion`, `footnote`, `card0`~`card3`, `left_card`, `step0_badge`, `step0`, `step0_labels`, `row0_category`, `row0_primary`, `row0_items`, `text`(강조 밴드), `cover_title`, `presenter`, `page_number`). 카드의 배지, 제목, 불릿, 꼬리는 프레임 `card{i}` 하나의 문단들이다. 이름은 템플릿, 목록 길이, 공통 슬롯과 선택 칸의 유무, 비교 차트 여부로 정해진다. 21개 구성에서 한 슬라이드 안의 이름 중복은 0건이었다(리뷰 저장 C2).
3. 미리보기와 PPTX는 같은 렌더 계획(`models/render.py`)을 읽는다. PPTX 라이터는 일반 페이지의 글상자에 줄바꿈을 켜고 문단 원문(`para.text`나 `runs`)을 쓴다. 엔진이 끊은 `lines`를 한 줄씩 쓰는 것은 도식 페이지뿐이다(리뷰 저장 S11). 그래서 일반 페이지의 PPTX 줄바꿈은 PowerPoint가 정하고, 엔진의 다시 끊기는 미리보기와 용량 경고를 위한 것이다. 라이터는 글자 크기를 `Pt(font_pt)`, 행간을 `Pt(font_pt * line_spacing)`으로 쓰는데 `Pt`와 `sz` 변환이 버림이라 소수 크기가 0.01pt 작게 기록될 수 있다. 도식 경로는 이미 `Emu(round(x * 100) * 127)`로 쓴다(리뷰 저장 S8). python-pptx는 글자 크기 1~4,000pt, 행간 0~1,584pt를 받으므로 행간 계수 1.4에서 글자 크기가 약 1,131pt를 넘거나 어느 문단이든 1pt 아래가 되면 그 덱의 PPTX 내보내기 전체가 실패한다(리뷰 저장 S6, S7 실험).
4. 빌더의 줄바꿈 함수는 `break_paragraph`이고, "프레임 폭 - 안쪽 여백(채움이나 테두리가 있을 때) - 불릿 들여쓰기 x (단계 + 1)" 폭으로 다시 끊으면 21개 구성의 문단 184개가 처음 줄과 모두 같았다(리뷰 저장 C1). 부분 강조의 줄바꿈 함수 `_styled_lines`는 공백을 남겨 100개가 달랐고, 번들 글꼴이 아닌 프리셋에서는 예외를 던진다(리뷰 저장 S10). 빌더의 용량 경고는 `lines`가 아니라 구역별 높이(카드의 소제목 고정 높이와 불릿 구역, 단계 행의 소제목과 부제)로 따로 계산한다(리뷰 저장 S12). 경고의 `slot`과 프레임 이름의 대응은 표로 있지 않고, 미리보기는 접두어 규칙으로 맞춘다(리뷰 저장 S13). `apply_text_spans`는 강조 대상 프레임이 없으면 예외를 던진다(리뷰 저장 S9).
5. 미리보기는 서버가 계산한다. 편집 화면은 덱이 바뀌면 300ms 뒤 `POST /api/projects/{name}/render-plan`을 부르고, 새 계획이 오기 전에는 캔버스 전체를 흐리게(불투명도 0.55) 옛 계획으로 그리며 편집을 열지 않는다(`planStale`). 문구 확정 뒤 새 계획이 그려지기까지 이 Mac의 웹 모드에서 309~338ms였다(리뷰 화면 X1, 10회). 덱을 33ms 간격으로 60번 바꾸면 그동안 계획 요청은 0회였다(X2). 화면 배율은 처음 그릴 때와 창의 `resize` 때만 재므로, 창 크기는 그대로인데 미리보기 폭이 바뀌면 낡는다(X3에서 17px 변화로 약 2.7% 차이).
6. 편집 화면은 프레임을 눌러 고르고, 고른 프레임을 다시 누르면 문구 입력란을 연다. 입력란은 고른 프레임 위가 아니라 캔버스의 고정 위치에 뜨고, Enter와 Shift+Enter 모두 확정, Escape는 입력을 버린다. 한글 조합 중의 Enter를 구별하지 않는다(리뷰 화면 X4, S28). 문구 수정은 `applyTextEdit`가 슬롯 칸으로 옮긴다(제목은 `chapter.topic`, 아이브로우와 부제는 슬라이드, 보고자는 메타). 미리보기의 프레임은 키보드 초점을 받지 않는다. 속성 패널에는 결론, 불릿, 요점, 각주, 표 칸, 표지 칸의 입력란이 없어 키보드만으로는 이 문구를 고칠 수 없다(X5, 리뷰 화면 S5).
7. 되돌리기는 덱 전체의 과거, 현재, 미래 목록이고 100개까지 남긴다(`state/deckStore.ts`). 덱 편집 하나가 한 항목이며, 속성 패널 입력란은 글자 하나가 덱 편집 하나다. 문구 입력 중에는 브라우저의 텍스트 되돌리기가 동작하도록 덱 되돌리기가 끼어들지 않는다(입력 요소 종류로만 판정). 자동 저장은 1,200ms 뒤이고, 412 뒤에는 자동 저장을 멈추며, 단계 이동과 언마운트 때 남은 편집을 저장한다. 장 생성 묶음 중에는 읽기 전용이다. 충돌, 서버 내용 다시 읽기, 템플릿 전환 전 저장 중에는 일부 조작을 잠그거나 화면을 `inert`로 둔다.
8. 지문과 슬라이드 내용의 관계:

   | 지문 | 슬라이드 내용이 들어가는가 | 수정값이 들어가면 생기는 일 |
   |---|---|---|
   | 내보내기 입력 지문(`pipeline/quality.py`, `output_dump`, 프리셋, 렌더 계획) | 들어간다 | 그 뒤 내보낸 파일의 검토 기록은 낡음이 된다. 구현 설계 10절의 "출력 fingerprint 무효화"가 따로 일하지 않아도 성립한다 |
   | 수치 검토, 의미 검토 지문(`output_dump`) | 들어간다 | 두 검토는 저장된 결과가 아니라 매번 다시 계산하므로 사용자가 다시 할 일은 생기지 않는다 |
   | 구성 계획 지문(`story_fingerprint`) | 들어가지 않는다(장 정의와 메타 세 칸) | 수정값으로 계획이 낡지 않는다. 제목 문구 수정은 지금처럼 장 정의를 바꾼다(D3a C15 판단 유지) |

   | 구조안 후보 반영 기준(`s1:` 해시의 (나)) | 들어간다 | 처분하지 않은 구조안 후보가 있을 때 요소를 옮기면 그 후보는 낡는다. 승인이 슬라이드를 덮으므로 의도한 동작이다 |

9. 형식 판정: 덱 내용 등급은 1~3이고 등급 3이면 `schema_version` 2로 쓴다. 이 앱이 읽는 manifest 최대 형식은 3이다(`MAX_SUPPORTED_FORMAT`). 디스크 바이트 판정(`deck_format_of_bytes`)과 등급 함수(`level_of`)의 최댓값은 3이고, 되돌림 감지와 마지막 쓰기 지문 기록은 `3`을 8곳에 고정해 두었다(`project_format.py:212, 239, 249, 263, 275`, `file_store.py:409, 450, 457`, 리뷰 저장 S3, S4). 덱 JSON 스키마는 `test_project_format`의 해시 시험이 고정한다. 0.2.0과 D3a, D3b 빌드의 `Slide`는 모르는 필드를 읽을 때 버리고 저장할 때 지운다. 보존본(drafts)은 검증 없이 원문을 담는다(리뷰 저장 S20).
10. 기존 장 내용을 바꾸는 경로와 지금 동작:

11. 작업 원장:
    - 처분 전이표(`CANDIDATE_TRANSITIONS`)에 `stale → applied`가 없다. 자료를 되돌려 낡음 사유가 사라진 `stale` 후보의 `applied`도 409다(리뷰 서버 S1 실측 B2). 구조안 승인은 이 거절을 받으면 화면이 후보를 버린다.
    - 범용 처분 라우트(`POST .../jobs/{id}/candidate`)는 장 생성과 장 축약 행을 덱 변경 없이 `held → applied`로 바꾼다. 반영을 막는 낡음 사유가 있어도 200이다(S3 실측 B1).
    - 묶음 등록은 부모 행의 `relevance_hash`를 `None`으로 두고, 하위 행에는 관련 입력 열이 없으며 조회의 낡음 사유도 계산하지 않는다(S4). 지금 조회 코드는 묶음 행의 `relevance_hash`를 풀지 않는다.
    - 단독 작업 행에는 적용 대상 ETag 열이 없다(묶음 하위 행에만 있다). 열을 더하면 원장 형식 번호가 올라 이전 빌드가 원장을 열지 못한다(S4, S5).
    - 덱 PUT은 실행 중 묶음을 보지 않는다. 묶음 중 PUT은 200이고 묶음은 `chain_broken`으로 끝난다(S6 실측 A).
    - 재시작 조정은 미종결 하위 행의 처분 열을 덮어쓸 수 있다(S13).
12. 동기 생성 래퍼는 6개다(구조안, 장 생성, 장 축약, 도식 생성, 재작성, 구조 수리, `server/app.py`의 `_run_wrapped`). 화면은 더 이상 부르지 않는다. 2026-10-13 계측(TestClient 전송 계층을 감싼 pytest 플러그인)으로 시험의 래퍼 호출은 238회, 시험 188개, 파일 22개다(구조안 63회, 장 생성 44회, 장 축약 20회, 도식 65회, 재작성 42회, 구조 수리 4회). 이와 별도로 `httpx.ASGITransport`로 부르는 시험 3개(매개변수 포함 6경우)가 있고, 시험 밖 소비자 `backend/scripts/quality_pilot.py`가 래퍼 둘을 부르며 시험 4개 파일이 이 스크립트를 쓴다(리뷰 서버 S14). D3 계획의 "약 70곳"과 1판의 "104곳"(경로 문자열이 든 줄 수)은 이 실측으로 바꾼다. 결과 스키마 다섯(`ChapterResult`, `StructureResult`, `DiagramGenerationResult`, `StoryRewriteResult`, `StoryRepairResult`)은 래퍼 라우트만 참조해 OpenAPI에 실리며, 화면 파일 5개가 이 타입을 쓴다(S16).
13. 미리보기의 표 경계선은 화면 전용 상수(`#D0D7E2`)이고 렌더 계획에 표 경계색이 없다. PPTX 라이터는 표 스타일 `{5C22544A-7EE6-4342-B048-85BDC9FD1C3A}`(Medium Style 2 - Accent 1)를 쓰고, 첫 행 표시와 줄무늬를 끄며, 머리행과 `body_fills`가 있는 칸만 채움을 쓰고 경계선은 쓰지 않는다. 기본 표의 본문 칸 채움과 경계선은 그 내장 스타일이 정한다(리뷰 저장 S26, 실제 표시는 미확인).

결정의 해석 둘을 기록한다.

- Q1의 "직접 수정값"은 위치, 글자 크기, 색, 숨기기다. 문구 수정은 지금도 슬롯에 저장되고 0.2.0이 읽을 수 있으므로 형식 등급을 올리지 않는다. 1판은 문구를 고친 위치(`text_paths`)를 같은 칸에 기록해, 문구만 고친 덱까지 0.2.0에서 열리지 않게 만들었다(리뷰 저장 S1, 서버 S9). 2판은 위치 기록을 없앴다.
- 구현 설계 10절의 "수정해 둔 문구를 보존한다"는 덱에 저장한 기록이 아니라 비교 화면으로 지킨다. 재생성 후보는 반영 전에 반드시 비교 화면을 거치고, 사용자가 단위마다 "지금 문구"와 "새 문구"를 고른다(4.8). 위치 기록은 목록 항목을 넣거나 빼면 다른 항목을 가리키고, 후보의 목록 길이와 순서가 다르면 엉뚱한 칸에 문구를 붙였기 때문에 없앴다(리뷰 저장 S2, 서버 S10, 화면 S29). 대신 미리 보기가 원장에 남은 그 장의 마지막 AI 반영 결과와 지금 문구를 단위마다 비교해 "직접 고친 문구"를 표시한다(재리뷰 RR7). 원장은 행을 지우지 않으므로 반영한 후보의 결과가 남는다. 기본 선택: 다시 생성은 "직접 고친 문구" 단위를 "지금 문구 유지", 나머지를 "새 문구"로 둔다. 장 축약은 문구를 줄이는 것이 목적이므로 모든 단위를 "새 문구"로 두고 표시만 한다(리뷰 화면 S30). 마지막 반영 기록이 없는 장(작업 원장이 생기기 전 0.2.0에서 만든 장, 문서 변경 반영으로 바뀐 장)은 표시 없이 모두 "새 문구"이고 그 사실을 비교 화면에 적는다. 반영 버튼 옆에 "직접 고친 문구 n곳이 새 문구로 바뀝니다"를 보인다.

### 4.2 저장 계약과 형식 (D3c-1)

`Slide`에 `direct_edits`를 더한다. 값은 요소 열쇠에서 `ElementEdit`로 가는 사전이다. 수정값의 유무와 뜻은 슬라이드만으로 정해지므로 정규화는 `Slide`의 검증 함수에서 하고, 형식 등급은 정규화한 뒤의 값으로 계산한다(재리뷰 RR6). 비어 있으면 직렬화에서 빼고, 기존 `expression_serialization`을 넓혀 처리한다(직렬화 함수를 더하지 않는다, 사실 1). 스키마에서 기본값 표기를 뺀다(D3b-1의 `_omittable`과 같은 이유). 그래서 수정값이 없는 기존 덱의 바이트, ETag, 모든 지문이 그대로다.

`ElementEdit`의 칸은 모두 선택이다. 빈 객체와 모든 칸이 `null`인 객체는 거절하지 않고 정규화 ④가 버린다(D3c-1 리뷰 F3: 화면과 서버가 같은 규칙으로 지우게 하기 위해서다). NaN과 무한대, 불리언이나 문자열로 쓴 숫자는 받지 않는다(`allow_inf_nan=False`, 엄격한 형, 리뷰 저장 S23, D3c-1 리뷰 F4).

| 칸 | 값 | 출처 |
|---|---|---|
| `dx_pt`, `dy_pt` | 엔진이 정한 자리에서 옮긴 거리(pt, 렌더 계획과 같은 단위). 둘은 함께 있거나 함께 없다 | 구현 설계 10절의 논리 좌표. 절대 좌표가 아니라 거리로 두는 이유는 아이브로우를 나중에 넣거나 프리셋이 바뀌어 템플릿 자리가 움직여도 옮긴 요소가 함께 움직이게 하기 위해서다(리뷰 저장 S21) |
| `font_scale` | 그 요소 글자의 배율(양의 유한수). 실제 적용 범위는 4.4가 OOXML 한계로 자른다. 화면 칸은 "가장 큰 문단의 크기(pt)"로 보이고 배율로 바꿔 저장한다 | 절대 크기로 저장하면 가장 큰 문단이 내용에 따라 바뀌는 요소(단계 본문의 소제목과 선택 칸인 부제)에서 사용자가 건드리지 않았는데 배율이 바뀐다(재리뷰 RR17) |
| `text_color` | 글자 색 역할 이름. 4.3의 글자 색 목록 | 프리셋이 바뀌면 색이 따라 바뀌게 하는 기존 원칙(`CalloutSlots` 설명) |
| `fill` | 채움 색 역할 이름. 4.3의 채움 색 목록 | 같음 |
| `hidden` | 참이면 출력에서 뺀다(삭제) | 제품 설계 5절 E |

규칙:

- 요소 열쇠는 프레임 이름에서 장 ID를 뺀 부분이다. 열쇠의 집합은 새 순수 함수 `frame_keys(slide)`가 정한다. 이 함수는 템플릿, 목록 길이, 공통 슬롯과 선택 칸의 유무만 보고 레이아웃 계산을 하지 않는다(장 제목과 메타는 이름 집합을 바꾸지 않는다, 재리뷰 C4). 열쇠마다 할 수 있는 수정 종류(4.3 표, 채움이 있는지 포함)도 함께 돌려준다. 비교 차트의 `chart`와 `chart_conditions`, 표의 `table`은 한 열쇠 `table`로 묶는다(4.3). D3c-1은 21개 구성에서 `frame_keys`가 `build_slide`가 만드는 이름 집합(묶음 적용 뒤)과 같다는 시험을 둔다.
- 정규화(`Slide` 검증, 화면의 `useDeckEditor.apply`에서도 같은 규칙): ① `frame_keys`에 없는 열쇠를 버린다. ② 그 열쇠가 받지 않는 수정 종류를 버린다(강조를 끈 카드처럼 채움이 없어진 요소의 `fill` 등). ③ 효과가 없는 값을 버린다: `hidden: false`, 둘 다 0인 거리, 1인 배율. ④ 빈 객체가 된 열쇠를 버린다. ⑤ 열쇠를 이름 순으로 둔다. 그래서 카드를 지우거나 아이브로우를 비우거나 숨김을 다시 보이기로 풀거나 원래 자리로 되돌리면 그 수정이 사라지고, 보이지 않는 수정이 덱을 새 등급에 묶어 두지 않는다(리뷰 저장 S19, S24, 화면 S12, S31, 재리뷰 RR23). 화면에도 같은 정규화를 두는 이유는 PUT 응답이 정규화한 덱을 돌려주지 않아 화면 덱이 서버와 어긋나기 때문이다(재리뷰 RR5). 화면의 열쇠 함수와 백엔드 `frame_keys`가 같은 결과를 내는지는 고정 파일 시험으로 묶는다(D3b의 `PURPOSE_SCREEN_FIELDS` 방식).
- 글자 색과 채움 색이 프리셋의 원래 값과 같은지는 프리셋을 알아야 판정되므로 서버 정규화에 넣지 않는다. 화면이 수정 종류마다 "원래대로" 선택지를 두고, 고르면 그 칸을 지운다(재리뷰 RR23).
- 위치 거리는 저장하는 쪽(화면)에서 "엔진의 자리 + 거리"가 페이지 안이 되도록 잘라서 저장한다. 엔진의 자르기는 프리셋이나 내용이 바뀌어 저장된 거리가 범위를 벗어난 경우에만 쓰인다. 화면이 엔진의 자리를 알 수 있게 렌더 계획의 프레임에 기본 자리 칸을 싣되, 수정값이 있는 프레임에만 싣고 없으면 직렬화에서 뺀다(재리뷰 RR3, 4.4).
- 강조 밴드의 채움은 직접 수정의 `fill`이 아니라 슬롯의 `tone`으로 바꾼다. 같은 일을 하는 조작이 둘이 되지 않고, 0.2.0도 읽는 값이라 등급이 오르지 않는다(재리뷰 RR25).
- 목록 항목을 넣고 빼고 옮기는 화면 편집(`slotOps`)은 같은 편집 안에서 그 목록의 순번 열쇠를 함께 옮긴다. 지운 항목의 수정은 버리고 뒤 항목의 번호를 당긴다. 표의 행과 열 편집은 열쇠 `table` 하나라 옮길 것이 없다. 순번 열쇠가 있는 목록: 카드(`card{i}`), 단계(`step{i}`, `step{i}_badge`, `step{i}_labels`), 분류 행(`row{i}_category`, `row{i}_primary`, `row{i}_items`).
- 삭제는 슬롯 내용을 지우지 않고 `hidden`으로 표시한다. 필수 슬롯(예: 요약의 결론)을 지우면 덱 검증이 실패하고, 제품 설계의 "삭제 요소를 자동으로 다시 채우지 않는다"는 원문이 남아 있어야 지킬 수 있기 때문이다.
- 도식 슬라이드에는 `direct_edits`를 받지 않는다(Q3, 검증 오류).
- 템플릿 전환은 그 장의 `direct_edits`를 비운다(4.5).

형식:

- 어느 슬라이드에든 `direct_edits`가 있으면 덱 내용 등급 4, `schema_version` 3으로 쓴다. 등급 3을 다시 쓰지 않는 이유는 D3b 빌드가 등급 3 덱을 열어 저장하면 수정값을 지우기 때문이다. 등급 4이면 D3b 빌드는 manifest를 보고 "더 새 형식"으로 거절한다(D3b가 D3a 빌드에 쓴 방식, 리뷰 저장 C5에서 0.2.0, D3b, 중간 빌드 모두 확인).
- 고칠 곳: `deck_level`, `level_of`(최댓값 4), `deck_format_of_bytes`(`schema_version` 3이거나 어느 슬라이드에든 `direct_edits`가 있으면 4), `MAX_SUPPORTED_FORMAT` 4, `SUPPORTED_SCHEMA_VERSIONS` (1, 2, 3). 사실 9의 `3` 고정 8곳은 "이 앱만 읽는 등급(3 이상)"으로 넓힌다. 이 가운데 같은 등급 저장에서 manifest를 먼저 쓰는 조건(`file_store.py:450`)은 이전 빌드를 막는 장치이므로 등급 4에서도 필요하다(D3b 재리뷰 RR6과 같은 이유).
- 등급 전이(3 이하에서 4, 4에서 3 이하)는 기존 형식 기록과 강제 스냅샷 규칙을 그대로 쓴다. 수정을 모두 되돌려 `direct_edits`가 사라지면 등급이 내려간다. 같은 등급 4 덱을 연속 저장해도 manifest의 기록이 늘지 않는다(1판대로 만든 시제품에서는 저장마다 거짓 내림과 올림이 한 쌍씩 쌓였다, 리뷰 저장 S3).
- 0.2.0은 `schema_version` 3을 거절하므로 "복구 필요"로 보인다. 0.2.0이 등급 4 덱을 되돌린 뒤 이 앱이 열면 되돌리기 직전 스냅샷에 되돌림 표시가 붙는다(1판대로면 표시가 0개였다, 리뷰 저장 S4).
- 보존본 저장(`save_draft`)은 덱 검증에 성공하는 보존본이면 서버가 계산한 `schema_version`으로 바로잡아 둔다. 그러면 D3b 빌드는 수정값이 든 보존본의 복원을 거절한다. 봉투의 내용 해시는 바로잡은 뒤의 덱으로 계산한다. 검증에 실패한 덱도 버리지 않는 원칙은 그대로다(리뷰 저장 S20, 재리뷰 RR21).
- E8: 프로젝트를 열 때 가장 최근 되돌림 기록 뒤에 이 앱의 저장이 아직 없으면 머리에 "다른 앱이 이 프로젝트를 이전 내용으로 되돌렸습니다. 복구 화면에서 되돌리기 전 내용을 볼 수 있습니다." 안내와 복구 화면 연결을 띄운다. 복구 화면의 표시 이름은 "다른 앱에서 되돌리기 전"으로 바꾼다. 조건을 "되돌림 표시가 있으면"으로 두면 기록이 지워지지 않아 그 프로젝트를 열 때마다 영구히 뜬다(재리뷰 RR19). 이 조건은 새 저장 칸 없이 manifest의 기록 순서로 판정한다.
- 릴리스 안내에 더한다: 위치, 글자 크기, 색, 숨기기를 직접 수정한 프로젝트는 0.2.0과 이전 개정판에서 열 수 없다. 0.2.0이 되돌린 뒤에도 이전 개정판은 이 앱에서 그 프로젝트를 한 번 저장하기 전까지 그 프로젝트를 거절한다(리뷰 저장 S25). 열기만 해서는 형식 기록을 쓰지 않으므로 풀리지 않는다(D3c-1 리뷰 F10).
- 작업 원장의 열, 처분 값, 형식 번호는 바꾸지 않는다. 묶음 부모의 `relevance_hash`에 새 표지의 값을 담는 것(4.8)은 이전 빌드가 풀지 않는 칸이다. D3c-5는 D3c가 쓴 원장을 D3b 빌드가 별도 프로세스로 목록 조회해 200임을 시험한다(리뷰 저장 S27).

### 4.3 요소 종류와 허용 조작 (D3c-1, D3c-3)

| 요소 종류 | 열쇠 예 | 이동 | 글자 크기 | 글자 색 | 채움 색 | 숨기기 | 문구 수정 |
|---|---|---|---|---|---|---|---|
| 일반 글상자(제목, 아이브로우, 부제, 결론, 불릿, 요점, 각주, 강조 밴드, 표지와 구분 칸) | `title`, `bullets`, `conclusion`, `footnote`, `text`, `cover_title` | 손잡이 | 예 | 예 | 채움이 있으면(강조 밴드는 슬롯의 `tone`) | 예 | 예 |
| 목록 항목 상자(카드, 비교 카드, 단계 본문, 분류 행 칸) | `card1`, `left_card`, `step0`, `row2_items` | 손잡이 | 예 | 예 | 채움이 있으면 | 예 | 예 |
| 단계 번호 | `step0_badge` | 본체 | 아니오 | 예 | 예 | 예 | 아니오(자동 번호) |
| 단계 라벨 | `step0_labels` | 손잡이 | 예 | 예 | 채움이 있으면 | 예 | 예 |
| 표와 비교 차트 묶음 | `table` | 본체 | 아니오 | 아니오 | 아니오 | 예(근거 표시) | 표 칸만 지금처럼 |
| 쪽 번호 | `page_number` | 아니오 | 아니오 | 아니오 | 아니오 | 아니오 | 아니오 |

- 표와 비교 차트를 한 열쇠로 묶는 이유: 차트의 조건 문구(정의, 단위, 기간, 분모)는 차트의 필수 근거 표시라 따로 숨기거나 키우면 엔진이 지키던 "세 줄 안" 조건과 근거 표시가 깨진다. 또 같은 표에서 비교 차트를 켜고 끌 때 옮긴 위치가 따라가야 한다(리뷰 저장 S14, S18).
- 글자 크기와 색을 바꾸지 않는 표와 차트: 글자 크기를 바꾸면 열 폭과 행 높이를 다시 계산해야 한다.
- 근거 표시: 각주(`footnote`), 표와 차트 묶음, 그리고 숫자가 든 칸(수치 검토의 대상 칸, `numeric_fields`)이 있는 요소다. 수치 검토가 실제로 평가했는지와 상관없이 정한다(D3c-2 리뷰 F2: 평가 항목은 구성 계획이 없거나 자료가 바뀌면 비어 같은 숨김이 잡히기도 하고 빠지기도 했다). 이 요소를 숨기면 4.6의 검토 연결이 걸린다.
- 우리말 역할 이름 표(예: `conclusion` = "결론 상자", `card1` = "2번 카드", `step0_badge` = "1단계 번호", `row2_items` = "3번 행 항목", `table` = "표")는 D3c-3이 열쇠 종류마다 하나씩 정하고, 접근 이름, 속성 패널, 숨긴 요소 목록, 비교 화면이 같은 표를 쓴다(리뷰 화면 S26, S29). 백엔드의 `frame_keys`와 화면의 이름 표가 같은 열쇠 종류를 덮는지는 고정 파일 시험으로 지킨다(D3b의 `PURPOSE_SCREEN_FIELDS` 방식). 용량 경고의 `slot`에서 요소 열쇠로 가는 대응과 수치 검토 칸 경로에서 요소 열쇠로 가는 대응도 엔진의 함수 하나씩으로 두고, 화면이 쓰는 경고 대응은 같은 고정 파일 시험으로 묶는다(재리뷰 RR11, RR22). 그려지지 않는 칸(표지와 구분 장의 공통 슬롯 등)은 열쇠가 없다.
- 글자 색 목록: 기본 글자색(`text`), 결론 강조색(`accent`), 강조색 1, 2(`accent1`, `accent2`), 주의(`danger`), 정상(`ok`), 진한 글자(`ink`), 옅은 글자(`ink_soft`), 흰 글자(`background`). 채움 색 목록: 강조 밴드의 `tone` 목록에 결론 상자 채움(`box_fill`)을 더한다(리뷰 저장 S15). 화면은 역할마다 우리말 이름과 지금 프리셋의 색 견본을 보이고, 역할 식별자를 보이지 않는다. 강조 밴드의 기존 색 선택 상자도 같은 이름과 견본으로 바꾼다(리뷰 화면 S22). 글자와 채움의 대비가 4.5:1 아래면 속성 패널에 경고한다(WCAG 2 AA 본문 기준).

### 4.4 렌더 적용과 PPTX (D3c-2)

글자 크기:

- 글자 크기는 빌더 안에서 적용한다. `build_slide`가 요소별 글자 배율을 받고, 문단을 만드는 함수와 용량 경고를 내는 함수가 같은 배율을 쓴다. 글자 역할 크기를 직접 읽는 함수는 `layout/templates.py`에 20개이고 표와 쪽 번호를 빼면 17개다(`_bullet_paras`, `common_slot_warnings`, `_common_slot_frames`, `_title_frame`, `_footnote_frame`, `_conclusion_box_frame`, `_conclusion_warning`, `_title_warning`, `_footnote_warning`, 빌더 아홉 개, 재리뷰 RR26). 렌더 계획을 만든 뒤 덧칠하면 빌더가 처음 크기로 낸 경고가 남고, 프레임 전체 높이로 다시 판정하면 카드의 소제목 넘침 같은 구역 경고를 놓친다(리뷰 저장 S12). D3c-2는 요소마다 배율 1.0과 1.2에서 문단 크기와 경고 슬롯을 비교하는 시험으로 두 쪽이 같은 배율을 쓰는지 지킨다.
- 배율은 문단 크기, 줄바꿈, 경고에만 쓴다. 프레임과 구역의 높이, `slide_geometry`의 세로 자리, AI 생성의 용량 계약(`content_geometry`, `capacity_contract`)은 바꾸지 않는다(재리뷰 RR2). 그래서 키운 글자가 상자를 넘치면 분량 경고가 되고, 화면은 그 요소가 경고 없이 받는 최대 크기를 서버의 같은 판정식으로 계산해 칸 옆에 보인다(4.5, 사용자 결정 Q5).
- 줄바꿈은 빌더와 같은 `break_paragraph`를 쓰고 `_styled_lines`를 쓰지 않는다(사실 4).
- 엔진은 배율을 두 한계로 자른다: 가장 큰 문단이 `floor(1,584 / 행간 계수)`pt를 넘지 않고(OOXML 행간 상한 1,584pt), 가장 작은 문단이 1pt 아래로 내려가지 않는다(OOXML 글자 크기 하한). 자르면 그 요소에 "글자 크기를 n pt로 맞췄습니다" 경고를 더한다. 프리셋이 바뀌어 저장값이 한계를 넘는 경우도 같다(리뷰 저장 S6, S7). 문단 크기는 1/100pt로 반올림한다.
- 프리셋의 가독성 하한(본문 역할 12pt, 각주 역할 9pt, `FontRoles.enforce_floors`)은 직접 수정에서 막지 않고, 그 아래로 줄인 요소에 "읽기 하한(본문 12pt) 아래입니다" 경고를 더한다. 막으면 기본 크기가 하한과 같은 본문과 불릿을 전혀 줄일 수 없기 때문이다(재리뷰 RR18). 판정은 역할이 아니라 문단 크기로 한다: 기본 크기가 하한 이상인 문단을 하한 아래로 줄이면 경고한다. 그래서 하한이 없는 제목과 부제를 11pt대로 줄여도 경고가 붙고, 이것은 의도한 확장이다(D3c-2 리뷰 F3). 이 경고와 PowerPoint 범위로 자른 경고는 종류 `font_size`로 표시해 분량 경고와 구분한다(4.6).
- 문단이 없는 요소(빈 불릿 상자)는 배율을 무시하고 화면은 글자 크기 칸을 보이지 않는다(재리뷰 RR17).

나머지 수정은 빌더 뒤, 비교 차트 치환 뒤, 부분 강조 앞에 적용한다:

| 수정 | 적용 |
|---|---|
| 숨기기 | 그 요소의 프레임에 숨김 표시를 달고(아래 직렬화 규칙) 그 요소의 용량 경고를 뺀다. PPTX 라이터와 미리보기는 숨김 표시가 있는 프레임을 그리지 않는다. 프레임을 계획에 남기는 이유는 "다시 보이기"와 숨기기 되돌리기를 새 계획 없이 바로 그리고 초점을 줄 수 있게 하기 위해서다(재리뷰 RR14). 숨긴 표 묶음은 비교 차트 치환을 건너뛴다(차트를 만들 수 없는 상태도 숨겨서 피할 수 있게, 재리뷰 RR20). 숨긴 프레임을 가리키는 부분 강조도 적용하되 그 경고는 뺀다. 강조 데이터가 남고 숨긴 프레임에도 강조가 적용돼 있으므로 다시 보이면 새 계획 없이 강조까지 그린다(리뷰 저장 S9, D3c-2 리뷰 F5에서 구현에 맞춰 고침) |
| 위치 | 엔진의 자리에 `dx_pt`, `dy_pt`를 더하고 페이지 안으로 자른다(0 ≤ x ≤ 페이지 폭 - w, y도 같다). 표 묶음은 원래 표 프레임의 크기로 한 번 자르고 같은 거리를 차트와 조건 문구에 더한다(재리뷰 RR20) |
| 글자 색 | 모든 문단의 색을 그 역할의 색으로 바꾼다. 부분 강조의 강조색 run은 그대로 둔다 |
| 채움 색 | 채움이 있는 프레임만 바꾼다. 원래 글자색을 휘도 함수(`readable_text_color`)로 정하던 요소(강조 카드, 단계 번호, 분류 행 칸)는 글자 색 수정이 없으면 새 채움으로 다시 정한다. 나머지 요소는 원래 글자색을 유지한다(결론 상자의 강조색이 검정으로 바뀌지 않게, 리뷰 저장 S16). 강조 밴드는 슬롯의 `tone`이 채움을 정한다(4.2) |

직렬화와 PPTX:

- 렌더 계획의 `Frame`에 선택 칸 셋을 더한다: 엔진의 기본 자리(`base_x`, `base_y`)와 숨김 표시(`hidden`). 수정값이 있는 프레임에만 싣고 없으면 직렬화에서 뺀다. 그래서 수정값이 없는 덱의 렌더 계획 바이트와 내보내기 지문은 그대로다. 수정값이 있는 덱은 어차피 지문이 바뀐다(사실 8). 2판의 "새 칸을 더하지 않는다"를 이 범위로 좁힌다(재리뷰 RR3, RR14).
- 수정값이 없으면 적용 단계를 건너뛰고 엔진 결과는 지금과 바이트가 같다.
- PPTX 라이터는 글자 크기(`sz`)만 도식 경로처럼 `Emu(round(pt * 100) * 127)`로 쓰고, 행간은 지금 식(`Pt(font_pt * line_spacing)`)을 둔다. 행간까지 반올림하면 기본 프리셋의 본문 행간이 1679에서 1680으로 바뀌어 수정값이 없는 덱의 PPTX 바이트가 바뀐다(재리뷰 RR1 실측). 기본 프리셋 크기에서 `sz`는 두 계산이 같다. 그래서 기본 프리셋을 쓰고 수정값이 없는 덱의 PPTX 바이트는 그대로이고 D3c-2가 이것을 시험한다. 수정한 요소의 행간은 0.01pt 작게 기록될 수 있으므로 PPTX 대조는 행간에 0.01pt 허용 오차를 둔다. 라이터는 숨김 표시가 있는 프레임을 건너뛴다. 덱별 디자인 값에 18.4pt 같은 소수 크기를 넣은 덱은 수정값이 없어도 `sz`가 버림 대신 반올림으로 0.01pt 크게 기록돼 PPTX 바이트가 바뀐다. 더 정확한 쪽이고 내보내기 지문(덱과 렌더 계획으로 계산)은 바뀌지 않으므로 받아들이고, 그 범위를 시험으로 고정한다(D3c-2 리뷰 F1).
- D3c-2의 PPTX 대조는 python-pptx로 다시 읽어 도형의 위치(EMU 정수 비교), 글자 크기(`sz`), 색, 숨긴 도형의 부재를 본다. 일반 페이지의 줄바꿈 위치는 PowerPoint가 정하므로 대조 대상이 아니다(가정 5).
- 시험으로 고정할 전제: `frame_keys` 일치(4.2), 수정값 없는 렌더 계획과 PPTX 바이트 불변, 템플릿별 다시 끊기 동일성, 문단과 경고의 같은 배율, 숨김과 부분 강조, 숨김과 비교 차트(만들 수 없는 차트 포함), 한계 근처 글자 크기의 내보내기 성공.

### 4.5 편집 화면의 직접 수정 (D3c-3)

모드:

- 편집 화면에 "직접 수정" 버튼(`aria-pressed`)을 둔다. 누르면 "수정 완료"로 바뀌고 직접 수정 모드가 된다. "수정 완료"는 모드 종료이며 저장 완료 표시와 다르다(제품 설계 5절 E). 저장은 지금의 자동 저장이 한다.
- 모드를 여는 조건: 읽기 전용이 아니고, 충돌(412) 상태가 아니고, 서버 내용 다시 읽기와 템플릿 전환 전 저장 중이 아니고, 도식 작성 창이 닫혀 있고, 도식 장이 아니다. 모드 중 조건이 깨지면 끌기를 취소하고, 확정 전 입력 가운데 유효한 값을 반영한 뒤 모드를 닫는다(리뷰 화면 S9).

| 화면 차이 | 모드 밖 | 모드 안 |
|---|---|---|
| 요소 고르기, 문구 수정 | 지금처럼(누르기, 다시 누르기, Enter) | 같음 |
| 이동 손잡이 | 없음 | 고른 요소에 보임 |
| 속성 패널 | 지금 구역 | 위치, 글자, 색, 숨기기 구역을 더함 |
| 안내 | 없음 | "요소를 고르세요. 문구는 다시 누르거나 Enter, 위치는 손잡이나 방향키로 고칩니다." |
| Delete, 방향키 | 동작하지 않고 "직접 수정을 누르면 옮기거나 숨길 수 있습니다"를 상태 문구로 알림 | 숨기기, 이동 |
| 숨긴 요소 | 미리보기 모서리에 "숨긴 요소 n개"와 목록 연결 | 속성 패널의 장별 목록과 "다시 보이기" |

포인터:

- 누르는 규칙은 화면 시안을 따른다: 글상자는 손잡이로만 끌고, 본체 누름은 지금처럼 고르기와 문구 수정이다. 표 묶음과 단계 번호는 본체로 끈다(4.3 표, 제품 설계 5절 E, 리뷰 화면 S4).
- 끌기는 누른 곳에서 4 CSS px를 넘어야 시작한다(Windows의 기본 끌기 시작 거리 `SM_CXDRAG` 4px를 CSS 픽셀로 쓴다). 그보다 작은 이동은 방향키와 위치 칸으로 한다(리뷰 화면 S20).
- 화면 배율은 끌기를 시작할 때(`pointerdown`) 캔버스의 실제 폭(`getBoundingClientRect`)으로 다시 잰다. 표시 배율은 `ResizeObserver`로 갱신한다(E11, 리뷰 화면 S3).
- 끌기 상태는 렌더 상태가 아니라 ref에 둔다. `pointerup`이 동기로 반영하고 상태를 비운다. 그 뒤에 오는 `lostpointercapture`는 무시하고, `pointerup` 없이 온 `lostpointercapture`, `pointercancel`, Escape, 창의 초점 잃음은 취소한다. 덱 객체가 끌기 시작 때와 다르면(되돌리기, 다른 탭의 반영) 놓아도 반영하지 않는다. 끄는 중에는 되돌리기와 다시 실행을 받지 않는다(리뷰 화면 S10).
- 모드에서 고른 프레임과 손잡이에는 `touch-action: none`을 둔다(리뷰 화면 S27).

놓은 뒤의 표시(리뷰 화면 S1):

- 위치와 숨기기는 상태를 따로 두지 않고 계산한다. 그리는 위치는 "프레임의 기본 자리 + 현재 덱의 거리"를 같은 규칙으로 자른 값이다. 기본 자리는 계획에 기본 자리 칸이 있으면 그 값, 없으면(계획을 만들 때 수정이 없던 프레임) 계획의 위치다(4.4). 숨김도 현재 덱으로 정하고, 숨긴 프레임도 계획에 남아 있으므로 다시 보이기와 숨기기 되돌리기도 바로 그린다. 그래서 놓는 순간 새 자리에 그려지고, 되돌리기나 다른 편집 뒤에도 따로 지울 상태가 없으며, 계획 계산이 실패해도 표시가 멈추지 않는다(재리뷰 RR3, RR14).
- 글자 크기와 색은 새 계획이 와야 그릴 수 있으므로 그 요소만 흐리게 표시한다. 문구 수정의 캔버스 전체 흐림은 지금 그대로다.
- 끌기는 계획이 낡은 동안에도, 계획을 만든 덱과 지금 덱의 열쇠 집합과 목록 길이가 같을 때만 허용한다(위치, 글자, 색, 숨김 편집만 있었을 때). 목록 항목을 넣거나 뺀 직후에는 옛 계획의 `card0` 자리에 다른 카드가 그려져 있으므로 새 계획을 기다린다(재리뷰 RR15). 문구 입력은 지금처럼 낡은 계획에서 열지 않는다.

키보드와 초점:

- 프레임은 모드 안팎 모두 키보드 초점을 받는다(`role="button"`, 그리는 순서대로 Tab). 초점이 프레임에 가면 그 프레임을 고른다. 초점과 선택은 늘 같고, Delete와 방향키는 그 요소에 걸린다. 이동 손잡이는 `tabIndex=-1`이다(리뷰 화면 S40). 표 묶음은 첫 프레임 하나만 Tab 정지로 두고 어느 프레임을 눌러도 `table`을 고른다. 쪽 번호는 Tab 정지에서 뺀다. 캔버스는 `tabIndex=-1`로 초점을 받는다(초점 표의 "캔버스"). 접근 이름은 "역할 이름, 문구 첫 줄"이다. 탭 정지 수는 D3c-4가 재서 기록한다(리뷰 화면 S26, 재리뷰 RR12).
- Enter는 문구 수정을 연다(문구 수정이 있는 요소). Space는 고른다. 프레임은 `div`라 둘 다 `keydown`에서 처리하고 Space의 기본 동작(화면 내림)을 막는다(리뷰 화면 S5, 재리뷰 RR12).
- 문단이 여럿인 요소(불릿, 요점, 카드, 비교 카드, 단계 본문, 분류 행 나열)에서 Enter는 첫 문단을 열고, 표에서는 첫 칸을 연다. 입력란 안의 Tab과 Shift+Tab은 지금 입력을 확정하고 같은 요소의 다음과 이전 문단(표는 다음과 이전 칸)을 연다. 마지막 문단에서 Tab은 확정하고 입력란을 닫아 초점을 그 프레임으로 돌린다. 그래서 키보드만으로 모든 문구를 고칠 수 있다(재리뷰 RR13).
- Delete와 Backspace(Mac의 delete 키), 방향키는 모드 안에서 초점이 캔버스의 프레임에 있을 때만 듣고 `preventDefault`로 화면 스크롤을 막는다. 되돌리기와 다시 실행은 화면 전체에서 듣되 입력란, 선택 상자, `contenteditable`, 열린 대화 상자에서는 듣지 않는다(리뷰 화면 S6, S7).
- 방향키는 1pt, Shift+방향키는 10pt 옮긴다. 두 값은 화면 시안의 값이다. PowerPoint의 Shift+방향키는 크기 조절이라 다르다(가정 8, 리뷰 화면 S19). 이동 결과는 배율과 상관없이 위치 칸의 값과 `role="status"` 문구("가로 120pt, 세로 80pt")로 알린다(재리뷰 RR12).
- 같은 요소에서 키를 누르고 있는 동안의 방향키(`KeyboardEvent.repeat`)는, 지금 덱이 직전 방향키 편집이 만든 덱 객체와 같을 때만 되돌리기 이력의 마지막 항목을 바꿔 쓴다. 그사이 자동 저장 응답이나 서버 적용이 끼어들었으면 새 항목이다. 키를 새로 누르면 새 항목이다. 그래서 길게 누른 이동은 되돌리기 한 번으로 돌아간다(리뷰 화면 S2, 재리뷰 RR16).

| 일 | 초점이 가는 곳 |
|---|---|
| 누르기, Space | 그 프레임 |
| 숨기기 | 그리는 순서의 다음 프레임, 없으면 캔버스 |
| 목록의 "다시 보이기" | 그 프레임(숨긴 프레임도 계획에 있으므로 바로 줄 수 있다) |
| 되돌리기, 다시 실행 | 바뀐 프레임이 있으면 그 프레임, 없으면 캔버스 |
| 장 바꾸기 | 캔버스 |
| 모드 종료 | "직접 수정" 버튼 |
| 비교 화면 닫기 | 그 화면을 연 버튼 |

입력란:

- 위치 칸(가로, 세로 pt, 지금 자리를 보이고 바꾸면 거리로 저장), 글자 크기 칸은 Enter, 초점 이동, 칸이 사라질 때 유효한 값을 반영한다. 글자 크기의 범위 밖 값은 반영하지 않고 안내한다. 위치의 페이지 밖 값은 4.2대로 페이지 안으로 잘라 반영하고, 칸을 실제 값으로 돌린 뒤 "페이지 안으로 맞췄습니다(가로 n pt)"를 알린다(D3c-3 리뷰 F5). 확정 전 입력이 있으면 저장 상태에 "입력 중"을 더해 창 닫기 경고를 띄운다(리뷰 화면 S17, S24).
- 글자 크기 칸의 선택지는 프리셋의 글자 역할 크기이고, 직접 입력 범위는 1pt부터 72pt(화면 시안의 상한)까지다. 칸 옆에 "요소 안 글자를 같은 비율로 바꿉니다"와 "이 상자에서 넘치지 않는 최대 크기: n pt"를 적는다. 최대 크기는 고른 요소에 대해 서버가 빌더와 같은 판정식으로 계산해 돌려준다. 렌더 계획 직렬화를 바꾸지 않도록 렌더 계획과 따로 묻는 라우트로 둔다(리뷰 화면 S21, 재리뷰 RR2). 읽기 하한 아래로 줄이면 4.4의 경고가 보인다.
- 위치, 글자 크기, 글자 색, 채움 색마다 "원래대로" 선택지를 둔다. 고르면 그 수정 칸을 지운다(4.2, 재리뷰 RR23).
- 문구 입력란은 고른 프레임 자리에 연다. 한글 조합 중(`isComposing`)의 Enter는 확정하지 않는다. Escape 우선순위는 입력 취소, 끌기 취소, 선택 해제 순이고 Escape는 모드를 닫지 않는다(리뷰 화면 S16, S28, S36).
- 반복 더블클릭과 다시 누르기는 진행 중 입력의 원문을 잃지 않는다(지금 동작, D3c-3이 시험으로 고정, 리뷰 화면 S35).

템플릿 전환과 표:

- 템플릿 전환은 그 장의 `direct_edits`를 비운다. 전환 전 확인 목록에 "직접 수정 n건(위치, 글자 크기, 색, 숨김)"을 더하고, 전환 뒤에는 "이 화면에서 되돌리기로 되찾을 수 있습니다. 전환 직전 상태는 스냅샷으로도 남습니다."를 알린다(리뷰 화면 S11).
- E6: 미리보기의 표 모양(본문 칸 채움과 경계선)을 PPTX가 쓰는 내장 표 스타일 Medium Style 2 - Accent 1의 정의(ECMA-376의 내장 표 스타일 정의)에 맞춘다. PPTX 바이트는 바꾸지 않는다. 실제 PowerPoint 표시는 회사 PC 확인이다(리뷰 저장 S26).

### 4.6 검토와의 관계 (D3c-2)

- 수정값은 내보내기 입력 지문을 바꾸므로 그 뒤 내보낸 파일의 검토 기록은 자동으로 낡음이 된다(사실 8). 위치만 옮긴 덱에서 기존 검토 기록이 `stale`이 되는 시험으로 고정한다.
- 숨긴 근거 표시(4.3)는 제품 설계 5절 E와 구현 설계 10절대로 검토를 통과로 두지 않는다(리뷰 화면 S13). 품질 보고에 `hidden_evidence` 검사를 더해, 근거 표시를 숨긴 장이 있으면 실패로 두고 장과 요소를 보인다. 보고 전체가 "고칠 것 있음"이 되므로 통과로 세지 않는다. 근거 표시 판정은 4.3의 수치 검토 경로 대응 함수로 "숫자가 든 칸이 있는 요소"를 찾는다(D3c-2 리뷰 F2). 보고 문구는 장 번호, 장 제목, 우리말 요소 이름(서버 `role_name`, 화면 `roleName`과 같은 표를 고정 파일로 묶음)으로 적고, 내보내기 결과 화면은 이 문구를 점검 표를 펼치지 않아도 보인다(D3c-2 리뷰 F6).
- 글자 크기 경고(종류 `font_size`, 4.4)는 분량 넘침이 아니므로 `layout_capacity`에 세지 않는다. 경고가 있을 때만 `font_size` 검사를 더해 실패로 둔다(D3c-2 리뷰 F3). 수정값이 없는 덱의 보고는 그대로다.
- `hidden_evidence` 행은 숨긴 근거 표시가 있을 때만 검사 목록에 넣는다. 늘 넣으면 숨김이 없을 때 "대상 0인데 통과"가 되거나 모든 덱의 보고가 바뀐다. 화면의 검사 이름 표(`checkNames`)에 우리말 이름을 더한다(재리뷰 RR11).
- 수치 검토 항목의 분류 값(`NumericReviewItem.code`)은 바꾸지 않는다. 새 값을 더하면 그 값이 든 내보내기 기록을 D3b 빌드가 엄격 검증으로 읽다 "기록 손상"으로 본다(재리뷰 RR11). 숨긴 요소가 없는 덱의 보고와 지문은 그대로다.
- 근거 표시가 아닌 요소를 숨긴 경우는 검토 화면의 확인할 항목에 "숨긴 요소" 줄로만 보인다(자동 판정 아님).

### 4.7 화면 계약: 서버가 덱을 바꾸는 조작 (D3c-5, D3c-6)

편집 화면의 저장 상태와 서버 적용을 잇는 순서다. 도식 작성 창이 이미 쓰는 순서를 따른다(리뷰 화면 S14, 서버 S12).

1. 비교 화면을 열기 전과 반영 직전에 `flushSave`를 부른다. 저장이 실패하거나 충돌이면 진행하지 않고 그 안내를 보인다. 미리 보기 라우트는 서버 저장본으로 계산하므로, 이 순서가 있어야 비교 화면의 "지금"이 화면과 같다.
2. 요청 중에는 편집 화면을 템플릿 전환 때처럼 잠근다.
3. 성공하면 응답의 덱을 `acceptSaved`로 받는다. 응답은 `ETag` 헤더를 달고, 클라이언트 함수는 `etagKey`와 저장 알림을 쓴다(문서 변경 적용과 같은 모양). 그사이 기준 덱이 바뀌었으면 받지 않는다(도식 경로와 같다).
4. 412는 편집기의 충돌 경로(`reportConflict`)로 보내 보존과 다시 읽기를 쓴다.
5. 반영 뒤의 되돌리기는 일반 편집이다. 덱은 되돌아가고 원장 처분은 `applied`로 남으므로 그 후보는 다시 반영할 수 없다. 비교 화면의 반영 버튼 옆에 이 사실을 적는다.
6. 적용 요청이 500, 503, 원장 오류로 끝나면 충돌로 보내지 않고 "반영 결과를 확인하지 못했습니다. 서버 내용을 다시 읽어 주세요."로 안내한다. 이때 덱은 반영되었을 수 있으므로(4.8의 틈) 다음 자동 저장을 멈추고 다시 읽기를 연다(재리뷰 RR8).

구성 화면에서 여는 비교 화면은 편집기 훅이 없으므로 다르게 잇는다(재리뷰 RR24). 반영이 성공하면 응답의 덱으로 부모의 `onDeckChange`를 부르고 ETag 캐시를 응답 헤더로 갱신한다. 412는 구성 화면의 기존 충돌 경로(보존과 부모 배너)로 보낸다. 승인 전 구조안 초안이 있으면 반영 뒤에도 초안을 유지하고, 그 뒤 승인이 만드는 덱(`kept`)이 반영된 슬라이드를 담는지 시험으로 고정한다.

### 4.8 재생성 보존과 후보 적용 (D3c-5, D3c-6)

원칙: AI가 만든 새 내용은 언제나 후보로 먼저 오고, 비교 화면에서 사용자가 단위마다 고른 뒤 반영한다. 기본 선택은 4.1의 둘째 해석대로다(다시 생성은 직접 고친 단위만 지금 문구, 장 축약은 모두 새 문구). 위치, 글자 크기, 색, 숨기기 수정은 새 내용에 같은 열쇠의 요소가 있으면 남긴다. 같은 열쇠는 같은 자리를 뜻하고 같은 내용을 뜻하지 않으므로, 목록 길이가 바뀐 목록의 순번 요소 수정은 기본으로 지우고 비교 화면에서 고르게 한다.

반영 단위(D3c-5가 템플릿 10종마다 표로 정하고 시험으로 고정한다):

- 문구 칸 하나가 한 단위다(결론, 각주, 강조 밴드 문구, 표지 칸 등). 목록은 목록 전체가 한 단위다(불릿, 요점, 카드, 단계, 분류 행, 비교 카드 하나). 표는 열과 행을 함께 한 단위로 본다. 목록 안의 항목마다 고르게 하지 않는 이유는 후보의 목록 길이와 순서가 다를 때 항목 순번이 다른 내용을 가리키기 때문이다(리뷰 서버 S10, 화면 S29).
- 그 결과 카드, 단계, 분류 행, 표 템플릿은 본문 전체가 한 단위라, 이 넷에서는 선택이 사실상 "새 본문 전체 또는 지금 본문 전체"다(재리뷰 RR7). 카드 네 개 중 하나만 고쳤다면 비교 화면이 그 단위에 "직접 고친 문구"를 표시하고, 사용자는 지금 본문을 지키거나 새 본문을 받는다. 이 제약을 상위 문서 정정(1절)과 사용자 보고에 적는다.
- 서버 함수 `merge_fields(template)`가 단위의 이름과 슬롯 칸을 정하고, 화면은 4.3의 우리말 이름 표로 보인다. 색 역할(`tone`), 항목 단계(`level`), 강조 여부(`emphasis`)는 그 칸이 든 단위를 따라간다.

서버 적용 경로(D3c-5):

- 새 라우트 `POST /api/projects/{name}/jobs/{job_id}/apply`와 저장하지 않는 `POST .../apply/preview`. 본문은 `keep_current`(지금 문구로 둘 단위 이름), `drop_edits`와 `unhide`(지울 요소 수정과 숨김을 풀 요소)이고, 묶음 행이면 `chapter_id`를 받는다. 단독 행은 `chapter_id`를 받지 않거나 `params.chapter_id`와 같아야 한다(리뷰 서버 S22). `keep_current`에 모르는 단위가 있으면 422다.
- 대상: 종결된 행만이다(작업 행은 `succeeded`, 묶음 하위 행은 종결 상태). 미종결 행은 409 `not_terminal`이다. 재시작 조정이 처분 열을 덮지 않게 하기 위해서다(리뷰 서버 S13). 처분은 `held`나 `stale`이다. `delivered`는 대상이 아니다.
- 판정: 장이 있고, 템플릿이 같고, 관련 입력(`c1:` 해시)과 자료 지문이 후보를 만들 때와 같은지 본다. 장 축약이면 작업 매개변수의 요청 슬롯과 지금 슬롯을 정규화해 비교하고 다르면 `slots_changed`로 막는다(리뷰 서버 S7). 후보의 기준 덱 ETag와 지금 덱 ETag의 차이는 막지 않는다(다른 장이나 서식을 고친 것은 후보의 입력이 아니다, `deck_changed_elsewhere` 안내만). 요청의 `If-Match`와 지금 덱 ETag의 비교는 이것과 다르다(아래 상태 코드 표, 리뷰 서버 S21).
- 묶음 장 후보의 판정 기준: 묶음 등록 때 장마다 `c1:` 해시를 계산해 부모 행의 `relevance_hash`에 새 표지(`b1:`)와 장 ID별 사전으로 담는다. 원장 형식 번호는 그대로이고, 지금 조회 코드는 묶음 행의 이 칸을 풀지 않으므로 이전 빌드의 조회가 깨지지 않는다. 표지가 없는 D3c 이전 묶음 행은 409 `not_applicable`로 막고 "현재 입력으로 다시 생성"만 둔다(리뷰 서버 S4).
- 묶음 실행 중: 같은 프로젝트에 미종결 묶음이 있으면 두 라우트 모두 409 `batch_active`다. 적용 라우트는 AI 임대를 쓰지 않아 실행기의 `generation_active`에 걸리지 않으므로 따로 막는다(리뷰 서버 S6).
- 합치기: 후보 슬롯에서 `keep_current`의 단위만 지금 슬롯 값으로 바꾼다. 합친 슬롯에서 문구가 그대로인 부분 강조만 남긴다(화면 `pruneChangedSpans`와 같은 규칙을 서버에 둔다). 비교 차트는 결과가 표 템플릿이고 덱 검증의 비교 조건을 통과하면 남기고, 아니면 지운다. 요소 수정은 `drop_edits`를 지우고 `unhide`의 숨김을 풀며, 합친 슬롯의 `frame_keys`에 없는 열쇠는 지운다. 미리 보기 응답은 합친 슬라이드, 합친 슬라이드의 용량 경고(키운 글자에 새 내용이 넘치는지, 재리뷰 RR26), 지워질 요소 수정과 부분 강조와 차트, 단위마다 "직접 고친 문구" 표시, 판정에 쓴 덱 ETag를 돌려준다(리뷰 서버 S8, S11, 화면 S31). "직접 고친 문구"는 그 장에 마지막으로 반영된 후보의 결과(`candidate_status = applied`인 장 생성, 장 축약 행이나 묶음 하위 행의 결과 슬롯)와 지금 슬롯을 단위마다 비교해 정한다(4.1).
- 순서와 원자성: 프로젝트 잠금 안에서 판정한다 → 원장 트랜잭션 안에서 처분을 `held`나 `stale`에서 `applied`로 바꾼다(비교 후 교체) → 같은 트랜잭션 안에서 스냅샷과 함께 덱을 저장한다 → 커밋한다. 저장이 실패하면 트랜잭션을 되돌려 처분이 그대로다. 남는 틈은 "덱 저장 성공 뒤 커밋 실패" 하나이고, 그 결과는 "덱에는 반영, 후보는 `held`, 화면은 새 ETag를 모름"이다. 화면은 4.7의 6번 안내로 다시 읽게 한다. 판정은 "지금 슬롯이 그 후보의 합친 결과와 같으면 덱을 다시 쓰지 않고 처분만 `applied`로 정리한다"(묶음의 `mark_applied_changed`와 같은 규칙)를 축약의 `slots_changed` 판정보다 먼저 본다. 그래서 같은 후보를 다시 열면 막히지 않고 정리된다(재리뷰 RR8). 저장 예외와 원장 예외를 각각 주입하는 시험을 둔다(리뷰 서버 S5). 덱을 저장하는 동안 원장 잠금과 SQLite 쓰기 잠금(`BEGIN IMMEDIATE`)을 쥐므로 실행기의 원장 쓰기가 그만큼 기다리고, 같은 자료 폴더를 여는 다른 프로세스의 원장 쓰기는 기본 대기 5초를 넘으면 실패한다(재리뷰 RR10). 이 Mac의 저장 시간은 D3c-8에서 기록한다(가정 10). 길면 "판정과 처분 교체를 먼저 커밋하고 저장한다" 안을 다시 검토한다.
- 처분 전이: `stale → applied`는 범용 전이표에 넣지 않고 적용 라우트 안에서만 허용한다. 범용 처분 라우트는 장 생성과 장 축약 행에 `applied`를 409로 거절하고 `dismissed`만 받는다. 묶음 장 행은 지금도 `applied`를 422로 거절하므로 그대로 둔다(재리뷰 RR9). 바뀌는 기존 시험은 `GeneratePanel.test.tsx`의 `settleCandidate(..., "applied")` 단언이다. 그래서 장 후보는 적용 라우트로만 반영되고(E10), 구조안 승인의 "서버가 `stale` 반영을 전이표로 거절하고 화면이 후보를 버린다"는 그대로다(리뷰 서버 S1, S2, S3). 처분 전이 집합 시험(`test_job_ledger.py`)과 화면의 `candidate_stale` 규칙은 바뀌지 않는다.

| 상태 | 뜻 |
|---|---|
| 428 | `If-Match` 없음 |
| 412 | `If-Match`가 지금 덱 ETag와 다름 |
| 409 | 판정 실패(`code`는 지금 낡음 사유 목록의 값), `batch_active`, `not_terminal`, `not_applicable` |
| 422 | 모르는 단위, 장 ID 불일치, 원장의 결과가 지금 슬롯 형식에 맞지 않음 |
| 503 | 덱이나 자료를 읽지 못함, 원장을 열지 못함, 덱 저장 실패(`deck_write_failed`, 덱 PUT의 저장 오류와 같은 문구) |

  새 `code`의 화면 문구와 실패 본문 고정 파일(`failure-bodies.json`)을 함께 갱신한다(리뷰 서버 S20).

- 편집 화면의 장 생성과 장 축약 반영은 이 라우트를 쓴다(4.7의 화면 계약). 사실 10의 처분 선기록과 부분 강조 422 유실은 이 전환으로 사라진다.
- 구조안 승인은 지금처럼 화면이 덱을 PUT한 뒤 처분을 기록한다. 승인은 장 구성 전체와 사용자가 고친 구조안 초안을 함께 쓰므로 서버 적용으로 옮기려면 초안 편집까지 서버 계약에 넣어야 하기 때문이다.
- 묶음의 `_apply_chapter`는 바꾸지 않는다(빈 장에만 쓴다). 이미 내용이 있는 장의 묶음 결과는 지금처럼 낡은 후보로 남고, 사용자는 구성 화면의 비교에서 이 라우트로 반영한다.

- E9: 장 생성과 장 축약의 작업 API 등록 검사에 구성 계획의 현재성(`require_current_story`)을 더해 409 `stale_story_plan`을 등록 단계에서 낸다. 위치는 자료 읽기(422) 뒤, 실행 중 작업 409 앞이다. 자료를 읽어야 판정할 수 있기 때문이다. 래퍼 경로는 D3c-7에서 지우므로 바꾸지 않는다. 화면은 등록 실패와 작업 실패를 같은 `isStaleStoryPlan`으로 다루므로 안내가 같다(리뷰 서버 S18).
