# Slide Captain MVP 설계서 (v0.1)

> 작성일 2026-08-27. 브레인스토밍을 거쳐 합의된 설계다.
> 배경과 요구사항의 원천은 [방법론 히스토리](../background/methodology-history.md)를 본다.
> 2026-09-01 개정: 1인 로컬 앱을 현재 제품으로 유지하면서 상업화 선택지를 보존하는 경계,
> Mac Mini를 기준으로 한 개발 환경, 데이터 전송 고지, 단계 5A 이후의 검증 관문을 추가했다.

## 1. 프로덕트 정의

### 1.1 문제와 목적

리서치 결과를 보고용 슬라이드(PPTX)로 만드는 과정에서 반복적으로 확인된 문제는 세 가지다.

1. 자료에서 덱까지 가는 조판 작업에 시간이 지나치게 든다.
2. AI 에이전트가 만드는 슬라이드의 품질과 규칙이 매번 달라, 수정에 다시 시간이 든다.
3. 화면 구성과 폰트 크기 조정을 텍스트 프롬프트로 주고받느라 시간과 토큰이 낭비된다.

이 앱의 목적은 다음과 같다.

1. 보고 슬라이드 작성의 효율화
2. 일관된 디자인과 화면 요소, 즉 일관된 품질의 산출물 보장
3. 세부 수정을 텍스트 프롬프트가 아니라 UI 조작으로 처리
4. 기본 템플릿과 사용자별 프리셋을 저장해, 보고의 맥락과 디자인 품질을 일정하게 유지
5. 내용 품질의 워크플로 강제: 결론부터 만들지 않도록, 구조 합의를 거친 뒤 채우는 순서를 화면 플로우로 강제

### 1.2 핵심 원칙

- **AI는 내용만, 배치는 코드가**: AI는 구조화된 콘텐츠(어느 장에 어떤 제목, 불릿, 표가 들어가는지)까지만 산출한다. 좌표, 폰트 크기, 여백은 결정론적 레이아웃 엔진이 프리셋에서 계산한다. 품질 비일관의 근본 원인(확률적으로 동작하는 LLM에 배치를 맡기는 구조)을 제거한다.
- **규격에 내용을 맞춘다**: 내용에 맞춰 규격을 줄이는 방향(자동 맞춤)은 균일성을 깨므로 쓰지 않는다. 고정 규격에서 용량을 역산해 생성 단계에서 계약으로 걸고, 넘치면 글자가 아니라 내용을 조정한다.
- **사용자 직접 수정은 최우선 신호**: 사용자가 UI에서 고친 프리셋 범위의 값은 "이번만 / 프리셋에 저장"으로 물어 규칙에 환류한다.

## 2. 아키텍처

### 2.1 기술 스택

| 층 | 선택 | 근거 |
|---|---|---|
| 백엔드 | Python + FastAPI | python-pptx가 PPTX 분야에서 읽기, 쓰기, 저수준 XML 접근을 모두 지원하는 사실상 표준. 한국어 어절 줄바꿈 주입과 역할 태깅 같은 핵심 기법이 저수준 접근을 요구하며, 양방향 목표(재수입)에는 읽기 능력이 필수. Node 진영 대안(pptxgenjs)은 생성 전용이라 부적합 |
| 프런트엔드 | React + TypeScript | 편집 UI(인라인 수정, 순서 변경)에 프레임워크가 필요. AI 코드 생성 지원이 가장 두터운 주류 기술 |
| 타입 공유 | OpenAPI 스키마에서 TS 타입 자동 생성 | 형식 정의의 진본을 백엔드 하나에 두고, 프런트 타입은 기계 생성해 언어 이원화의 어긋남을 도구로 차단 |
| 저장소 | 로컬 JSON 파일 | 1인 단계에는 파일로 충분. 저장 계층을 인터페이스로 추상화해 판매 단계에 DB(PostgreSQL JSONB 등) 구현으로 교체 가능하게 함 |
| AI 호출 | Claude Agent SDK (Python) | 공식 라이브러리. 프로바이더 인터페이스 뒤에 배치 (2.4절) |
| 개발과 자동 검증 | macOS 주 개발 + Windows, macOS CI | 셸 경로, 폰트 설치, 브라우저 동작 같은 OS 차이를 실행 환경에 가두고 결정론 코어의 동일 동작을 두 운영체제에서 확인 |

되돌릴 수 있는 결정으로 설계한다: PPTX 내보내기를 독립 모듈로 분리해, 훗날 포장 단계에서 스택을 재평가할 여지를 남긴다.

### 2.2 구성 요소

1. **화면(브라우저)**: 프로젝트 목록 → 자료와 목적 입력 → 구조안 승인 → 덱 편집(미리보기 + 구조화 수정) → 내보내기
2. **프로젝트 저장소**: 프로젝트 폴더(덱 JSON, 입력 자료, 스냅샷, 내보내기 폴더)를 관리한다. 저장소 인터페이스(프로젝트 생성과 목록, 덱 저장과 불러오기, 스냅샷 목록과 복원, 입력 자료 읽기와 쓰기와 목록, 내보내기 폴더 제공) 뒤에 파일 구현을 두고, API의 모든 파일 접근은 이 인터페이스만 거친다 (2026-08-28 단계 2에서 범위 확정)
3. **AI 프로바이더**: 프롬프트 조립 → Claude 호출 → 응답 스키마 검증. 교체 가능한 부품 (2026-08-28 단계 3 정밀화: 교체 지점은 원시 호출 `complete(prompt, schema)` 하나로 좁히고, 프롬프트 조립과 검증 게이트는 프로바이더와 무관한 공통부에 둔다. 프로바이더마다 프롬프트가 달라지면 품질 일관성 목적이 깨지기 때문이다)
4. **프리셋 모듈**: 모든 시각 수치의 상류 단일 진본. 좌표와 글자 크기는 항상 프리셋에서 계산된다
5. **레이아웃 엔진**: 덱과 프리셋에서 렌더 계획을 계산한다. 렌더 계획은 좌표, 글자 크기, 줄바꿈 결과에 시각 스타일(폰트, 색, 여백, 행간, 글머리표, 테두리 두께)까지 내장한 자기완결 계약이라, 미리보기와 PPTX 내보내기는 렌더 계획만 소비하고 프리셋을 다시 해석하지 않는다 (2026-08-28 단계 2에서 확정)
6. **PPTX 내보내기**: python-pptx 기반. 축적된 기법(어절 줄바꿈 속성, 역할 태깅) 내장
7. **CLI 진입점**: `serve`로 로컬 서버 기동, `export`로 서버 없이 내보내기 (인자와 기본값의 진본은 로드맵과 코드)

### 2.3 데이터 흐름

자료 + 목적 입력 → AI가 구조안(장 구성 표) 제안 → 화면에서 수정하고 승인 → AI가 장별 내용을 데이터로 채움 → 미리보기에서 구조화 수정(AI 호출 없음, 즉시 반영) → 필요한 장만 AI 재생성 → PPTX 내보내기

### 2.4 AI 프로바이더 구도

정책 근거(2026-09-01 재확인): Anthropic은 본인이 쓰는 Claude Agent SDK와 `claude -p`가 현재 구독 사용량에서 차감된다고 안내한다. 동시에 다른 사용자를 위한 제품이나 도구는 Claude Console의 API 키 또는 지원되는 클라우드 제공자를 이용하라고 안내하며, 유료 Claude 구독과 Claude API는 별도 상품이다. 따라서 본인 구독 프로바이더는 소유자 로컬 파일럿에만 사용하고, 유료 배포는 상업 약관이 적용되는 API 또는 당시 명시적으로 허용된 별도 프로그램을 사용한다. 정책은 바뀔 수 있으므로 배포 관문에서 다시 확인한다.

- [Anthropic 로그인과 제3자 도구 안내, 2026-09-01 확인](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)
- [Claude Agent SDK 구독 사용 안내, 2026-09-01 확인](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)
- [Claude API 접근과 상업 약관 안내, 2026-09-01 확인](https://support.claude.com/en/articles/8114521-how-can-i-access-the-claude-api)

| 단계 | 프로바이더 | 상태 |
|---|---|---|
| 1단계 본인 전용 | 본인 구독 호출: Agent SDK(Python)로 로그인된 Claude Code를 구동. 소유자 로컬 파일럿에만 사용 | v0.1 구현 |

### 2.5 로컬 우선 진화형 아키텍처

상업화를 고려한다는 이유로 v0.1에 인증, 결제, 다중 사용자 저장소를 미리 만들지 않는다. 대신 다음 네 계층을 분리한다.

| 계층 | 현재 상태 | 변경 원칙 |
|---|---|---|
| 문서 생성 코어 | 덱 모델, 검증, 레이아웃, PPTX 생성 | 사용자 인증, 결제, 저장 위치, 특정 AI 제공자에 의존하지 않는다 |
| 로컬 실행 프로필 | 1인, 로컬 파일, 127.0.0.1, 본인 AI 연결 | 현재 제품으로 유지한다. 로컬 프로필의 보안 가정을 외부 공개 API에 적용하지 않는다 |
| 유료 데스크톱 프로필 | 미구현 | 설치, 코드 서명, 업데이트, 사용권, 앱 관리형 API 또는 BYOK를 코어 밖에서 추가한다 |
| 관리형 서비스 프로필 | 미구현 | 사용자와 작업공간, 데이터 분리, 작업 대기열, 객체 저장소, 결제를 코어 밖에서 추가한다 |

아키텍처 불변 조건은 다음과 같다.

1. 현재 로컬 API를 LAN 또는 인터넷에 그대로 공개하지 않는다. 외부 공개에는 인증, 권한, TLS, 요청 제한, 다중 사용자 저장 전략을 별도 설계한다.
2. 인증, 사용권, 결제는 문서 생성 코어에 흩어 넣지 않고 실행 프로필 전용 연결부로 붙인다.
3. 저장소와 AI 제공자는 인터페이스 뒤에서 교체한다. 로컬 `Path`가 필요한 기능은 로컬 실행 프로필의 책임으로 한정한다.
4. `deck.json`을 다르게 해석하는 변경에는 마이그레이션과 되돌리기 경로가 먼저 있어야 한다.
5. OS별 셸, 폰트 설치, PowerPoint 자동화는 코어 밖에 둔다. 코어 테스트는 Windows와 macOS에서 같은 결과를 내야 한다.
6. 상업 기능은 외부 사용자의 반복 사용과 실제 결제 의사가 확인된 뒤 구현한다.

### 2.6 데이터 흐름과 신뢰 약속

v0.1의 사용자 고지는 다음 사실을 기준으로 한다.

1. 프로젝트, 업로드 원본, AI 입력용 추출 자료, 스냅샷, 내보낸 PPTX는 사용자가 지정한 로컬 프로젝트 폴더에 저장한다.
2. 구조안 생성, 장 생성, 축약, 형식 재시도 때는 해당 작업에 필요한 자료 원문과 보고 설정, 지시사항, 기존 초안이 현재 AI 제공자에게 전송될 수 있다.
3. 브라우저 탭을 연 뒤 첫 AI 호출 전에 제공자와 전송 범위를 알리고 명시적인 확인을 받는다. 탭을 닫으면 확인 상태는 끝나며 사용자는 호출 전에 취소할 수 있다.
4. v0.1은 문서 내용이나 사용 행동을 별도 분석 서버로 보내지 않는다.
5. 향후 운영 지표를 수집하더라도 문서 원문은 기본 수집 대상에서 제외하고, 수집 항목과 보존 기간을 사용자에게 먼저 알린다.
   로컬 기록 `ai-usage.jsonl`(4.4절)은 사용량만 담고 문서 내용을 담지 않는다 (2026-09-05 단계 5A C).
6. 제공자 측 보존, 학습, 국외 처리 여부는 앱이 단정하지 않는다. 배포 시점의 공식 정책과 계약을 확인해 연결 화면과 정책 문서에 표시한다.

로컬 API 의 상태 변경 요청(POST, PUT, DELETE) 은 화면이 붙이는 `X-Requested-With: SlideCaptain` 헤더가 있어야 하고, Origin 헤더가 있으면 호스트가 정확히 127.0.0.1 또는 localhost 여야 한다. 커스텀 헤더는 다른 사이트의 페이지가 붙이면 브라우저가 사전 확인을 먼저 보내고 이 서버는 CORS 를 열지 않으므로 본 요청이 나가지 않는다. 이것은 1인 로컬 앱의 방어이지 인증이 아니다 (2026-09-04 단계 5A A).

모든 AI 요청은 화면별로 고지를 복제하지 않고 공통 호출 관문을 통과한다. 구조안 생성, 장별 생성과 재생성,
사용자가 요청한 축약뿐 아니라 형식 재시도와 자동 축약도 처음 확인한 전송 범위에 포함한다. 자동 후속 호출은
같은 탭 세션에서 다시 확인받지 않지만, 최초 고지에 이 가능성을 분명히 적는다.

구현 (2026-09-04 단계 5A B): 고지는 브라우저 탭 단위다. 화면의 공통 관문(`frontend/src/api/aiGate.ts`)이 첫 AI 호출 전에
대화 상자를 띄우고, 확인하면 `sessionStorage` 키 `slidecaptain.ai-consent` 에 기억한 뒤 모든 AI 요청에
`X-AI-Consent: SlideCaptain` 헤더를 붙인다. 취소하면 호출 없이 "전송을 취소했습니다. 필요하면 다시 시도해 주세요." 로
끝나며 실패로 다루지 않는다. 서버의 생성 3종 라우트(구조안, 장 생성, 축약)는 이 헤더가 없으면 428 과
"AI 전송 확인이 필요합니다. 화면의 안내를 확인한 뒤 다시 시도해 주세요." 로 거절한다. 이 검사는 화면 코드가 헤더 부착을
잊는 사고만 막는 안전망이지 인증이 아니다. 대화 상자 문구는 위 1항부터 4항과 6항을 옮긴 것이다:
"AI 에게 자료를 보냅니다. 구조안 생성, 장 생성과 다시 생성, 축약을 누르면 이 프로젝트의 입력 자료 원문(엑셀 추출본 포함),
보고 정보, 지시사항, 기존 초안이 AI 제공자 <제공자와 모델> 에게 전송됩니다. 형식 오류로 자동 재시도하거나 분량 초과로
자동 축약할 때도 같은 범위가 다시 전송됩니다. 프로젝트 파일은 이 PC 의 프로젝트 폴더에만 저장되고, 이 앱은 문서 내용이나
사용 기록을 다른 분석 서버로 보내지 않습니다. 제공자가 전송된 내용을 보관하거나 학습에 쓰는지는 이 앱이 단정하지
않습니다. 제공자의 정책을 확인해 주세요. 이 확인은 지금 연 브라우저 탭에서만 유효하며, 탭을 닫고 다시 열면 다시
묻습니다." 버튼은 "전송에 동의하고 계속" 과 "취소" 다. 5항(향후 운영 지표)은 아직 수집 계획이 없어 대화 상자에 넣지
않았다. 탭 복제는 `sessionStorage` 를 복사하므로 복제된 탭은 다시 묻지 않고, `sessionStorage` 가 막힌 환경에서는
새로고침마다 다시 묻는다(3항과 완전히 같지는 않다).

## 3. 데이터 모델

### 3.1 프로젝트 폴더

```
projects/<프로젝트명>/
  deck.json      # 진본
  uploads/       # XLSX 같은 업로드 원본. 로컬 보존과 출처 확인 전용
  sources/       # AI 입력과 수치 대조에 쓰는 UTF-8 자료
  snapshots/     # 저장 시점 스냅샷 (전부 보존, 정리 없음)
  exports/       # 내보낸 PPTX (버전 붙여 보존)
  ai-usage.jsonl # AI 사용량 기록. 작업 1건 = 1줄, 문서 내용 없음 (4.4절, 2026-09-05 단계 5A C)
```

이 트리의 루트 기본값은 `~/slidecaptain-projects`(탐색기에서 보이는 사용자 홈 아래)이고, `serve --data-dir`로 바꿀 수 있다 (2026-08-28 단계 2 확정). 사용자가 탐색기로 `sources/`에 직접 넣은 마크다운, 텍스트, CSV도 입력 자료로 인정한다: 읽기는 폴더 탈출 방지만 검증하고, 앱이 만드는 이름(프로젝트, 자료 저장)에만 엄격한 규칙(한글, 영문, 숫자로 시작, 공백과 점과 밑줄과 붙임표만 허용, 80자 이내, 끝 마침표와 Windows 예약어 금지)을 적용한다.

단계 5A B의 XLSX 업로드(2026-09-04 구현)는 원본을 `uploads/<원본파일명>`에 보존하고, 추출본을
`sources/<원본파일명>.md`에 UTF-8로 저장한다 (예: `매출.xlsx` 는 `sources/매출.xlsx.md`. 2026-09-04 정정:
종전 서술 `sources/<원본파일명>.txt` 는 확장자가 달랐다). 추출본은 시트마다 값이 있는 셀만
`행 5: A=매출 | B=1234` 처럼 행 단위로 나열하고(빈 셀과 서식만 있는 셀은 쓰지 않는다), 수식은 수식과 저장된
계산값을 함께, 하이퍼링크는 표시 텍스트와 URL 을, 병합 범위는 시트 머리에 적는다. 숨김 시트는 제외한다. 상한과
잘린 위치 표시는 4.3절. `deck.json`의 `source_refs`와 AI 호출, 수치 대조는
추출본 파일명을 가리킨다. `uploads/` 원본은 자동으로 AI에 보내거나 수치 대조에 쓰지 않고, 사용자가
추출 내용과 출처를 확인할 때만 연다. 같은 이름의 원본과 추출본은 함께 교체하거나 모두 유지해 연결이
어긋나지 않게 한다 (재업로드 중 추출본 쓰기가 실패하면 직전 원본을 복원한다).

### 3.2 deck.json

세 덩어리로 구성한다. 스키마 버전 필드는 deck.json 최상위에 두고, 로드 시 지원 버전인지 검증하며 형식 변경 시 마이그레이션한다. (2026-09-01 판정 기준 명시: 버전을 올리는 변경은 기존 파일이 읽히지 않거나 다르게 해석되는 변경이다. 기본값이 있는 필드 추가와 읽을 때 무시되는 필드 제거는 버전을 유지한다. 로더가 정확히 일치하는 버전만 허용하므로 불필요한 상향은 기존 덱 전부를 읽지 못하게 만든다)

1. **메타**: 제목, 보고 유형(연구분석 / 승인요청 / 전략기획), 피보고자, 보고자, 프리셋 덮어쓰기 값 (2026-09-01 개정: 보고자(이름 또는 부서) 필드를 추가하고 표지의 보고자 칸을 슬롯이 아니라 이 값에서 렌더한다. 장 제목을 구조안의 topic에서 그리는 것과 같은 방식이다. 피보고자는 문체와 상세 수준의 기준으로만 쓰며 표지와 본문에 적지 않고, 표지 슬롯의 audience는 제거했다. 사유: 실전 파일럿 관찰 6, 보고 문서의 표지에는 보고 주체가 들어가고 피보고자는 적지 않는 것이 관례) (2026-08-28 개정: v0.1은 기본 프리셋 1종이라 "사용 프리셋" 식별자를 두지 않고, 덮어쓰기 값만 둔다. v0.2 프리셋 다중 관리 때 식별자 필드를 추가하고 스키마 버전으로 마이그레이션한다. 스키마 버전 필드는 메타가 아니라 deck.json 최상위에 있다)
2. **구조안**: 승인된 장 구성(순서, 장별 주제, 장별 결론 한 줄, 장별 템플릿 유형, 장별 근거 자료 매핑)
3. **슬라이드**: 장마다 "템플릿 유형 + 슬롯 내용"만 존재. **좌표와 글자 크기는 데이터에 없다.**

구조안과 슬라이드의 정합성은 모델 검증으로 강제한다: 장 id 중복 금지, 슬라이드는 구조안에 존재하는 장만 가리킬 수 있고, 장의 템플릿과 슬롯의 템플릿이 일치해야 한다. 위반은 저장과 로드 양쪽에서 걸리며 저장 시점에 422로 거부된다 (2026-08-28 단계 2 확정. 엔진의 중복 검사는 방어선으로만 유지한다). 같은 장을 가리키는 슬라이드 중복 금지, 표 칸 안 줄바꿈 금지도 이 검증 목록에 추가되었다 (2026-08-28 단계 3 확정. 전자는 덱 순서의 진본을 구조안으로 확정한 결정의 전제, 후자는 행 높이 계산과 균일성 보호를 위해서다).

### 3.3 프리셋

- 글자: 역할별 크기(제목, 소제목, 본문, 각주), 하한 규칙(본문 12pt, 각주 9pt), 한글과 영문 폰트
- 색: 기본 텍스트, 강조, 표 머리글, 배경
- 여백과 간격, 표 스타일(균일 규격), 페이지 규격(16:9), 언어(ko-KR)
- 전역 프리셋이 기본이고, 덱별로 일부 값만 덮어쓰기 가능
- 검증 (2026-09-04 단계 5A A): 모든 수치는 유한값이어야 하고 크기는 0 초과, 여백과 간격은 0 이상, 안전 비율은 0 초과 1 이하, 줄 간격은 0.5 이상이다. 내용 폭과 내용 높이(제목 영역과 각주 영역을 뺀 값, 레이아웃 엔진과 같은 산식)는 각각 100pt 이상이어야 한다. 덱별 덮어쓰기도 같은 검증을 받아 저장, 실측, 내보내기, 렌더 계획이 전부 422 로 답한다. 표 열 폭은 열이 많아도 모든 열이 양수이고 합이 프레임 폭과 같다

### 3.4 템플릿 (v0.1 6종)

템플릿 하나 = 슬롯 정의(내용 칸의 형식) + 배치 계산 규칙의 쌍.

| 템플릿 | 용도 |
|---|---|
| 표지 | 제목, 부제, 날짜, 보고자(메타에서 채움. 2026-09-01: 종전 "보고 대상"을 대체) |
| 핵심 요약 | 결론 강조 박스 + 요점 목록 |
| 불릿 + 강조박스 | 가장 흔한 본문 장. 주제형 제목 + 불릿 + 결론 박스 |
| 표 중심 | 비교표, 데이터 표. 열 병합 규칙 내장 |
| 2단 비교 | 옵션 비교, 전후 대비 카드 2개 |
| 간지 | 섹션 구분 |

제목은 주제형(그 장이 무엇을 말하는지)만 쓴다. 결론은 강조 박스에 둔다. 본문과 불릿과 표 칸은 압축 문체(명사형 종결, 조사 생략 허용)를 쓴다.

## 4. AI 파이프라인

### 4.1 호출 2종

1. **구조안 생성**: 자료 전문 + 보고 유형 + 피보고자 + 목표 장수 → 구조안 JSON. 사용자가 승인해야 다음으로 간다.
2. **장별 내용 생성**: 승인된 구조안 + 그 장의 근거 자료 → 슬롯 내용 JSON. 장 단위로 따로 호출해 "이 장만 다시"가 저비용으로 가능하다. 슬롯별 분량 한도(5.1절)를 프롬프트에 계약 조건으로 명시한다.

### 4.2 검증 게이트 (코드가 수행, 호출마다 자동)

1. **형식 검증**: 응답이 슬롯 스키마에 맞는지. 실패 시 1회 자동 재시도, 재실패 시 원문을 보여주고 수동 처리
2. **분량 검증**: 실측 줄수(5.2절)로 한도 초과를 확인. 초과 시 축약 재생성 요청
3. **수치 대조**: 생성 문장의 숫자를 추출해 sources/ 원자료에 존재하는지 대조. 원자료에 없는 숫자에는 화면 경고 표지. "근거 없는 수치 금지"를 프롬프트 당부가 아니라 기계 검증으로 강제한다 (2026-08-28 단계 3 정밀화: 두 자리 이상 숫자만 대조하고, 표지의 날짜 같은 메타성 필드는 제외한다(2026-09-01: 종전의 보고 대상 필드는 제거되었고 보고자는 슬롯이 아니라 메타에서 렌더하므로 대조 대상 자체가 아니다). 한 자리 정수는 개수 표현이 대부분이라 경고 소음이 되기 때문이며, 이만큼 보증 범위가 좁아진다)

### 4.3 XLSX 입력 범위와 한계 (2026-09-04 단계 5A B)

XLSX 는 `openpyxl` 로 읽어 값이 있는 셀만 텍스트로 추출한다(형식은 3.1절). 날짜와 시각과 경과시간은 서식이 아니라 값
기준의 고정 형식으로 쓰고, 퍼센트와 통화 서식은 원값 옆에 서식대로 표시한 값을 병기한다(규칙의 정본은 계획서
[2026-09-04-phase5a-b-xlsx-and-disclosure.md](../plans/2026-09-04-phase5a-b-xlsx-and-disclosure.md) 가정 3 과 4).
다음 상한을 넘으면 넘은 자리부터 생략하고 그 사실을 추출본 머리와 업로드 결과 안내에 남긴다(값은 `XlsxLimits` 한 곳에
있다).

| 상한 | 값 | 확인 시점 |
|---|---|---|
| 압축 해제 크기 (zip 항목 선언 크기 합) | 50MB | 파일을 열기 전 |
| 셀 요소 수 (서식만 있는 셀 포함) | 400,000 | 파일을 열기 전 |
| 보이는 시트 수 | 30 | 연 뒤 |
| 값이 있는 셀 수 (전체 시트 합계) | 200,000 | 연 뒤 |
| 추출 본문 글자 수 | 60,000 | 연 뒤 |

앞의 두 상한은 파일을 열기 전에 검사해 서식만 넓게 적용된 파일의 로드 비용을 막는다. 손상되었거나 xlsx 가 아닌
파일은 422 와 한국어 안내로 거절하고, xls 와 PDF 와 Word 는 아직 받지 않는다. 원본 크기 상한은 20MB(텍스트 자료는
5MB)다. 계산값 캐시가 없는 파일은 수식 셀이 "(계산값 없음)" 으로 남으므로 엑셀에서 다시 저장해 올리도록 안내한다.

### 4.4 AI 사용량 기록 (2026-09-05 단계 5A C)

생성 작업 1건(구조안 생성, 장 생성과 재생성, 수동 축약. API 요청 1건)이 끝날 때마다 프로젝트 폴더(3.1절)의
`ai-usage.jsonl` 에 한 줄(UTF-8, LF)을 덧붙인다. 작업이 실패해도 그때까지의 호출은 기록된다(프로바이더를 부르기 전에
나는 입력 오류는 제외). 기록 쓰기는 프로젝트 잠금 안에서 하고, 쓰기 실패는 로그만 남기고 생성 결과를 막지 않는다.
같은 합계가 생성 API 응답의 `usage` 필드(필수)로 화면에 내려가고, 화면은 구조안 결과와 장 생성 결과 아래에 한 줄로 보인다.
규칙의 정본은 계획서 [2026-09-04-phase5a-c-ai-usage.md](../plans/2026-09-04-phase5a-c-ai-usage.md) 가정 1부터 7 이다.

한 줄의 필드: `ts`(로컬 시간대 ISO 시각), `kind`(`structure`, `chapter`, `condense`), `chapter_id`, `outcome`(`ok`,
`format_error`, `failed`), `requested_model`(프로바이더에 요청한 별칭. 실제 모델과 다른 축), `summary`(작업 합계:
`calls`, `failed_calls`, `unmeasured_calls`, `models`, 입력과 출력과 캐시 읽기와 캐시 생성 토큰, `duration_ms` 와
`duration_api_ms`, `cost_usd`, `missing`, 그리고 호출별 `records`: `purpose`(`generate`, `format_retry`, `condense`), `ok`,
`usage`(원시 호출 1건의 실제 모델, 토큰, 시간, 턴 수, 비용값, 종료 사유, `token_source`)).

- **내용 없음**: 프롬프트, 자료, 지시사항, 응답 원문, 슬롯, 오류 문구 본문은 어떤 필드에도 넣지 않는다(2.6 의 5항).
  고정 열거값과 숫자와 서버가 만든 id 뿐이다. API 테스트가 기록 파일 전체에서 자료 문장과 지시사항과 응답 원문과
  프롬프트 고정 문구의 부재를 단언한다.
- **없는 값은 만들지 않는다**: SDK 가 주지 않은 값은 `null` 이고 화면은 그 항목만 "미확인" 으로 쓴다. 합계는 사용량이
  있는 호출 전부가 값을 줄 때만 계산하고 하나라도 없으면 `null` 과 `missing` 에 필드 이름을 적는다(부분 합계는 과소
  집계라 더 해롭다). 결과 메시지 없이 끊긴 호출은 합계에서 빼고 `unmeasured_calls` 로 세며 화면이 "측정되지 않은 호출
  N회 제외" 를 붙인다. 토큰은 SDK 의 `model_usage` 를 우선하고 `usage` 로 폴백하면 화면이 "대략" 을 붙인다. `0.0` 은 값이다.
- **`calls` 와 `num_turns` 는 다른 축이다**: `calls` 는 서비스가 프로바이더를 부른 횟수(형식 재시도와 자동 축약 포함,
  실패 포함)이고, `num_turns` 는 SDK 가 호출 한 번 안에서 돈 내부 턴 수다.
- **비용값의 의미**: `cost_usd` 는 SDK 가 가격표로 산정한 참고값이지 청구액이 아니다(구독 로그인에서는 별도 청구가 없다).
  화면 문구는 "참고 비용 ... (AI 도구가 계산한 값으로 실제 청구액이 아닙니다)" 다. 통화 환산과 프로젝트 누적 합계
  화면은 만들지 않았다(로드맵 이월표, 5B 후보).
- **화면 합계와 파일의 관계**: 구조안 승인 루프의 "장 생성 N회" 합계는 화면이 장별 응답을 더한 표시용 값이고 정본은
  파일이다. 결과 자체를 받지 못한 장(503 등)은 합계에서 빠지므로 화면이 "실패한 장의 사용량은 이 합계에 포함되지
  않았습니다" 단서를 붙인다.
- **실측 미확인**(D2 관통의 실호출 1회에서 확인): `usage` dict 의 키 이름, `model_usage` 가 실제로 채워지는지, 폴백 값이
  세션 누적인지 마지막 턴 값인지. 자동 테스트는 전부 가짜 프로바이더와 SDK 자료형으로 했다.

## 5. 레이아웃 엔진과 오버플로 정책

### 5.1 용량 계약

폰트, 상자 폭, 상자 높이가 프리셋으로 확정되어 있으므로, 각 슬롯의 최대 분량(줄수, 불릿 수, 표 행수)을 사전에 역산할 수 있다. 이 한도를 AI 생성의 계약 조건으로 걸어 넘침을 생성 단계에서 차단한다.

> 2026-09-02 정정: 계약은 "한 줄짜리 항목이 전부일 때" 를 기준으로 한 하한이다. 불릿류는 `floor((가용 높이 + 항목 간격) / (행간 높이 + 항목 간격))`, 표는 `floor(가용 높이 / (행간 높이 + 2 x 셀 세로 여백))` 로 계산하고, 실측(5.2)이 더하는 간격과 여백을 계약도 똑같이 뺀다. 종전 계약은 간격과 여백을 빼지 않아 실측보다 22~35% 많이 약속했고, 그 결과 AI 가 계약을 지켜도 분량 게이트가 초과 경고를 냈다 (Critical 소형 묶음 태스크 A). 계약과 실측이 같은 기하 함수(`card_geometry`, `cover_geometry`, `divider_geometry`)를 호출하는 것을 테스트가 강제한다. 표지와 간지도 칸별 1줄 계약과 넘침 경고를 갖는다 (태스크 C).

### 5.2 실측 검증

글자수가 아니라 실제 폰트의 글자 폭 데이터로 줄바꿈 지점을 계산해 정확한 줄수를 잰다(결정론적). 안전 여유율을 두어 미리보기와 PowerPoint 실제 렌더의 미세 차이를 흡수하고, 최종 확인은 렌더 검증(7.3절)이 담당한다.

### 5.3 해소 사다리

초과 시 아래 순서로 해소한다. **글자 크기 축소는 사다리에 없다** (하한 규칙).

| 순서 | 조치 | 방식 |
|---|---|---|
| 1 | AI에 축약 재생성 요청 (요지 유지, 한도 명시) | 자동 |
| 2 | 구조 조정 제안: 표 열 병합, 불릿 수 축소, 장 분할 | 앱이 제안, 사용자 승인 |
| 3 | 내용 강등 선택: 각주나 발표자 노트로 내릴 문장 선택 | 사용자 |

### 5.4 좌표 계산 원칙

좌표는 조정 대상이 아니라 프리셋 수치(여백, 기준선, 간격)에서 나오는 수식의 결과다. 같은 역할 요소(제목, 본문 영역, 각주, 쪽번호)는 모든 장에서 같은 위치다. 내용이 적으면 위 기준선 정렬을 유지하고 아래를 여백으로 남긴다(장별 세로 중앙 정렬 금지). 시각 요소(표, 향후 차트)는 템플릿이 정한 고정 프레임 안에 생성되며, 요소 크기에 맞춰 페이지가 변형되지 않는다. 본문 영역(제목, 쪽번호, 각주 제외)의 글자 크기 단계는 페이지당 2개 이하로 제한하고, 표지와 간지는 이 제한의 예외다 (2026-08-28 정정: 당초 문구 "한 페이지 2개 이하"는 이 설계서의 역할별 크기 구조(제목 + 본문 + 각주)와 모순되어 기본 프리셋부터 성립하지 않았다).

> 2026-09-02 정정: "장별 세로 중앙 정렬 금지" 는 PPTX 라이터에도 적용된다. 라이터는 렌더 계획의 `valign`(`top` 또는 `middle`)을 모든 텍스트 도형의 `bodyPr anchor` 로 항상 명시한다. 종전에는 채움과 테두리 프레임(자동도형)이 python-pptx 기본값(중앙)을 상속해 미리보기와 어긋났다 (Critical 소형 묶음 태스크 B).

## 6. 편집 화면

세 구역: 왼쪽 장 목록(순서 변경), 가운데 미리보기(클릭 선택), 오른쪽 속성 패널.

### 6.1 즉시 반영 조작 (AI 호출 없음)

| 조작 | 동작 |
|---|---|
| 텍스트 직접 수정 | 미리보기에서 클릭해 타이핑. 즉시 분량 실측, 초과 시 경고와 해소 사다리 |
| 장 순서 변경 | 드래그(순서만 변경) |
| 템플릿 교체 | 호환되는 슬롯은 자동 이사, 갈 곳이 없는 내용은 버리지 않고 보류 영역에 보관해 수동 배치 |
| 프리셋 값 조정 | 덱 전체 일괄 반영. 특정 장만 예외로 두는 기능은 없다 |
| 표 조작 | 열 병합, 행 삭제, 값 수정 |
| 불릿 추가와 삭제, 강조박스 수정 | 즉시 반영 |

미리보기 편집은 최신 덱 기준의 렌더 계획일 때만 열린다. 덱이 바뀐 뒤 새 계획이 오기까지는 미리보기를 흐리게 그리고 문단을 클릭해도 편집을 열지 않는다(프레임 선택은 된다). 낡은 계획의 인덱스로 편집을 열면 다른 문단을 덮어썼기 때문이다 (2026-09-03 저장 안전성 묶음).

### 6.2 AI 재생성 조작 (명시적 버튼)

"이 장 다시 생성"(지시문 입력 가능), "이 장 축약". 장 단위 호출.

### 6.3 프리셋 환류

프리셋 범위의 값을 고치면 "이번 덱만 적용 / 프리셋에 저장"을 묻는다. 저장하면 다음 덱부터 기본값이 된다.

## 7. 내보내기와 파일 안전

### 7.1 PPTX 내보내기

- 모든 텍스트 run에 ko-KR 언어 속성을 주입해 어절 단위 줄바꿈을 보장한다
- 모든 요소에 역할 태깅(몇 번 장의 어떤 슬롯인지)을 심는다. 향후 양방향 재수입의 열쇠다
- 임시 폴더에 먼저 저장한 뒤 최종 경로로 이동한다 (2026-08-28 정정: python-pptx는 한글 등 유니코드 경로에서도 저장이 가능함이 확인되어, 당초의 "ASCII 임시 경로 변환 필수" 전제를 철회한다. ASCII 보장이 실제로 필요한 곳은 렌더 검증(7.3)의 Windows PowerPoint 자동화뿐이며, 해당 기능의 상세 계획에서 재설계한다)
- 재내보내기 시 기존 파일을 덮어쓰지 않고 새 버전 파일로 저장한다(사용자가 PowerPoint에서 직접 고친 수정분의 소실 방지). 파일명은 `{제목}_v{3자리}.pptx`(v001부터 최대값+1)이고, 제목의 Windows 금지 문자는 밑줄로 치환한다
- 모든 텍스트 도형에 세로 정렬(anchor)을 렌더 계획 값으로 명시한다. 라이브러리 기본값에 기대지 않는다 (2026-09-02)

### 7.2 오류 처리

| 상황 | 처리 |
|---|---|
| AI 응답 형식 불일치 | 1회 자동 재시도 → 원문 표시 + 수동 반영 경로 |
| AI 호출 실패(미로그인, 한도 소진) | 원인별로 쉬운 말 안내 |
| 저장 사고 | 원자적 쓰기(같은 폴더의 고유 이름 임시 파일 후 교체, 2026-09-04 단계 5A A 에서 고정 이름을 고유 이름으로) + 프로젝트별 재진입 잠금 안에서 스냅샷과 쓰기를 한 단위로(같은 프로세스의 겹친 요청 직렬화. 별도 프로세스 잠금은 후속) + 저장과 복원 모두 직전 상태를 먼저 스냅샷으로 보존 + 복구 메뉴(복원 자체도 되돌릴 수 있음). 편집기의 자동 저장은 한 줄로 직렬화하고 착지 뒤 그사이 생긴 변경을 다시 저장하며, 편집기를 떠나는 모든 경로(탭 전환, 목록으로, 스냅샷 복구, 내보내기)는 플러시 결과를 검사해 실패하면 떠나지 않는다 (2026-09-03 저장 안전성 묶음: 저장 중 되돌리기 유실, 겹친 PUT 역순 착지, 이탈 시 플러시 실패 은폐를 해소) |
| 저장 충돌(다른 창이나 프로그램이 먼저 저장) | deck.json 바이트의 SHA-256 을 ETag 로 주고받는다. 화면은 GET 과 저장과 복원 응답의 ETag 를 기억해 다음 저장과 복원에 If-Match 로 보내고, 서버는 불일치를 412 로 거절한다(If-Match 가 없는 외부 도구 요청은 검사하지 않는다). 편집 화면은 자동으로 덮어쓰지 않고 '서버 내용으로 되돌리기' 를 제공하며, 다른 화면의 412 는 '서버 내용 다시 읽기' 배너로 회복한다 (2026-09-04 단계 5A A) |
| 실측 실패 | 실측 오류는 저장 결과와 분리해 유지하고 '다시 그리기' 로 재실측한다. 그동안 미리보기는 낡은 것으로 표시하고 편집을 열지 않는다 (2026-09-03) |
| 사용자의 deck.json 직접 수정 (손상, 잘못된 프리셋 값, 구조안에 없는 장) | 저장 시와 같은 검증을 읽기 경로(렌더 계획, 내보내기)에도 적용해 422 한국어 안내. 파싱 불가 프로젝트는 목록에서 제외하지 않고 제목 자리에 복구 필요 안내를 표시 (2026-08-28 단계 2 확정) |
| 렌더 검증 오염 | 검증은 항상 사본으로만 열고 종료를 코드로 보장 |

### 7.3 렌더 검증

Windows에서는 내보내기 후 PowerPoint 자동화로 사본을 열어 확인하는 검증을 옵션으로 제공한다. 환경이 없으면 건너뛴다. macOS에서는 단계 5A부터 코어 테스트, 화면 빌드, PPTX 생성과 재열기를 지원한다. PowerPoint for Mac의 실제 화면을 자동 캡처해 비교하는 기능은 별도 과제로 둔다. macOS 개발 지원과 macOS PowerPoint 자동 렌더 검증은 같은 요구가 아니다.

## 8. 테스트 전략

TDD로 진행한다. 실측된 실패 목록이 회귀 테스트가 된다.

- **골든 테스트**: 같은 덱 데이터로 내보낸 PPTX를 코드로 다시 열어 좌표, 폰트, ko-KR 속성을 기준값과 대조
- **회귀 항목**: 어절 줄바꿈 속성 존재, 본문 12pt 하한, 본문 영역 크기 단계 2개 이하(5.4의 정정 기준), 역할 태깅 존재, 내보내기 전후 deck.json 불변
- **분량 실측기**: 알려진 문장이 예상 줄수로 계산되는지
- **AI 파이프라인**: 모의 응답으로 형식 검증, 재시도, 수치 대조를 검사(실호출 없음)
- **운영체제 회귀**: GitHub Actions에서 Windows와 macOS 각각 백엔드 테스트, 프런트 테스트, 화면 빌드를 실행한다. 실제 Claude 로그인과 PowerPoint 화면 검증은 CI에 넣지 않는다
- **공개 저장소 경계**: Git이 추적하는 파일을 검사해 회사 원자료, 인증정보, 생성 PPTX, 로컬 프로젝트 데이터, 의존성, 임시 리뷰 기록을 거절한다. XLSX 자동 테스트에는 새로 만든 비기밀 픽스처만 허용한다
- **실기기 관통**: 단계 5A 완료 전 Mac Mini의 새 클론과 Windows에서 각각 샘플 업로드, AI 전송 확인, 저장, 내보내기, PPTX 재열기를 수행한다. CI 통과는 이 실기기 확인을 대신하지 않는다

## 9. MVP 범위와 로드맵

### 9.1 v0.1과 단계 5A: 1인 로컬 앱 완성

현재 제품은 1인 로컬 앱이다. 단계 5A에서는 상업 기능을 만들지 않고 다음 안전성과 검증 기반을 완성한다.

1. 자동 저장 요청 직렬화, 최신 편집 우선, 저장 실패 재시도, 화면 이탈 전 저장 확인
2. 프로젝트별 저장 잠금, 고유 임시 파일, 오래된 화면의 덮어쓰기 거절, 같은 프로세스 안의 내보내기 파일명 충돌 방지
3. 로컬 상태 변경 API의 동일 출처 요청 확인. 이 장치는 외부 공개 API용 인증을 대체하지 않는다
4. 실제 파일럿 원본인 XLSX 입력과 추출 결과의 시트명, 셀 위치, 수식, 링크 출처 보존
5. AI 전송 범위 고지와 로컬 세션별 첫 호출 확인
6. AI 호출 횟수, 모델, 토큰, 처리 시간, SDK가 제공한 비용값을 내용과 분리해 기록. 비용값이 없으면 추정하지 않는다 (2026-09-05 단계 5A C 구현 완료, 4.4절. SDK 실제 반환 형태는 D2 관통에서 실측)
7. Mac Mini에서 개발 가능한 실행 문서와 스크립트, Windows와 macOS 자동 테스트
8. 공개 GitHub에 올려도 되는 파일만 추적되는지 푸시 전에 자동 감사

### 9.2 단계 5B: 반복 가능한 로컬 파일럿

여러 실제 보고서를 끝까지 제작한다. 파일럿 전에 데이터 유실 0건, 작업 완주 여부, 수동 수정 시간, AI 재시도 횟수, PowerPoint 표시 결함, 다음 보고서 재사용 의사의 판정 기준을 적는다. 한 번의 내부 파일럿은 외부 고객 가치나 결제 의사를 증명하지 않는다.

### 9.3 단계 6: 외부 사용자 검증

초기 목표 고객 후보와 소수의 외부 사용자가 실제 업무 흐름에서 제품을 사용한다. 구매 주체, 현재 대체 방식, 자료 보안 요구, 선호 배포 방식, 반복 사용, 실제 결제 또는 유료 파일럿 의사를 확인한다.

### 9.4 상업화 의사결정 관문

다음 항목이 확인되기 전에는 결제, 다중 사용자 데이터베이스, 팀 관리, 앱 마켓 포장을 구현하지 않는다.

1. 실제로 비용을 지불할 고객과 구매 주체
2. 유료 로컬 데스크톱과 관리형 서비스 중 우선 배포 방식
3. AI 호출량과 원가, 실패와 재시도 비용
4. 저장, 전송, 보존, 삭제에 관한 고객 요구
5. 반복 사용과 지원 부담

### 9.5 단계 7과 8: 제품화와 유료 검증

관문 결과에 따라 유료 데스크톱 또는 관리형 서비스 한 가지를 우선 구현한다. 단계 7은 선택한 방식의 설치, 업데이트, 인증 또는 사용권, 데이터 수명주기를 구현한다. 단계 8은 유료 베타에서 실제 결제, 반복 사용, 지원 비용, 원가를 확인한다. 차트 템플릿, 양방향 재수입, PDF 내보내기, 프리셋 공유는 이 관문과 사용자 가치 검증에 따라 우선순위를 다시 정한다.

### 9.6 정책 워치 항목

Anthropic의 Agent SDK와 제3자 제품 인증, API 상업 약관, 데이터 처리 정책이 바뀌면 로컬 파일럿과 배포 프로바이더의 허용 범위를 다시 판정한다. 정책 변화만으로 기능을 자동 추가하지 않는다.

## 10. 배포 단계 유의점

- 앱은 독자 브랜드를 유지한다. AI 제공자 명칭과 표기는 배포 시점의 브랜드 지침을 다시 확인한다
- 본인 구독 프로바이더는 소유자 로컬 파일럿 전용이다. 유료 배포는 상업용 API 또는 당시 명시적으로 허용된 제품용 연동을 사용한다
- 공개 GitHub에는 소스, 테스트, 진본 기획서, 로드맵, 개발 환경 설정을 보관한다. 회사 원자료, 개인 인증정보, 생성 산출물, 로컬 프로젝트 데이터, 임시 리뷰 기록은 올리지 않는다
- 유료 배포 전에 코드 라이선스 전략, 외부 기여 처리, 제품명과 상표, 도메인, 앱 마켓 명칭 사용 가능성을 확인한다. 이미 공개된 Git 이력은 나중에 저장소를 비공개로 바꿔도 회수되지 않는다
- 외부 베타 전에 개인정보 처리, 데이터 삭제와 보존, 설치와 제거, 코드 서명, 업데이트와 되돌리기, 지원과 장애 대응을 출시 관문으로 확인한다
- 앱 마켓 포장은 목표 운영체제와 배포 방식이 정해진 뒤 해당 마켓의 당시 심사와 샌드박스 규칙을 검토한다
